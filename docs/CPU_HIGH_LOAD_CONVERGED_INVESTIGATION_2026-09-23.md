## 0. TL;DR

高 CPU 是**四个来源叠加**，量级差三个数量级，此前两份报告各自只看到其中一部分：

| # | 来源 | 实测量级 | 状态 |
|---|---|---|---|
| 1 | **trust 传感每 30s 突发**（lsof 采样 + 观察落库 + 相关器） | **平均 ~120% → 关闭后 2.8%** | ✅ A/B 实验证实，已由用户关闭（临时） |
| 2 | **`read_overview` 重聚合** | 无争用基线 2.2–2.5s；与 trust 争用时峰值 21–32s | ❌ 内因未定位 |
| 3 | **托盘节流窗失配** | 17/20 轻 tick 跑了 read_overview；挡住时 1.3s vs 刷新时 2.5–21.9s | ❌ 待修（一个常量） |
| 4 | **fsevents 线程 churn** | **0.3% 一核**（纯空闲实测） | ❌ 待修（零收益浪费，但量级极小） |

**轻路径（LIGHT-PATH spec 四阶段，`a8a26d3`）本身没有被打破**——路由、防饥饿、冷却、
定向同步全部按设计工作。问题在它的**周边**与**参数选择**上。

截图的 387%/613% 是多峰瞬时叠加；稳态在 0–3%（trust 关闭后）与每 30s 一次的
170–263% 突发（trust 开启时）之间跳。

## 1. 决定性实验：trust 传感 A/B

这是整个调查里最便宜、最有说服力的一步——**关掉嫌疑源，看曲线**。

| 指标 | trust 开启 | trust 关闭（90s 实测） |
|---|---|---|
| 平均 CPU | ~120%（8 分钟烧 10 分钟 CPU） | **2.8%**（90s 烧 2.5s） |
| 峰值形态 | 每 30s 一次 170–263% 突发 | 无突发；瞬时最高 60.4%（轻 tick 时刻） |
| 纯空闲窗口 | — | **0.3% 一核**（18s 零日志活动窗口） |

归因证据链（发现于全系统视角调查）：CPU 采样与 `TrustMonitorInvalidated` 时间戳
**逐条对齐**——

```
02:13:31.485 TrustMonitorInvalidated → 02:13:41 ps 243.0%
02:14:32.892 TrustMonitorInvalidated → 02:14:33 ps 262.7%
两次事件之间 CPU 回落 <30%
```

机制：trust 传感（opt-in，本机曾开启）每 30s spawn lsof → 解析 → 观察写入权威库
（写事务）→ `correlate_selected` 相关器 → 发事件。**这是按设计工作的安全功能，不是
bug**，但它是 trust 开启时稳态负载的绝对主导项。

**处置**：关闭是临时措施不是修复。要么优化（相关器增量输入、lsof 解析降频），要么
作为产品决策显式承认其资源代价（在 Findings/Trust 设置里写明「传感开启时的资源
预期」）。**不能就这么放着**——用户关掉它意味着一个安全功能事实上不可用。

## 2. `read_overview`：当前最大的未解项

### 2.1 分布

全日志 297 次调用：

```
n=297   min=1.50s   p50=2.16s   p90=8.27s   max=31.93s   mean=3.60s
累计 = 1070 秒（≈17.8 分钟）
```

同期其他步骤累计对比——量级完全不在一个档：

```
read_overview        1069.8s  (n=297)   ← 压倒性
budget_alerts         334.7s  (n=303)
drain_event_bus         2.2s  (n=310)
publish_invalidation    0.4s  (n=310)
refresh（托盘重建）      ms 级  (n=310)
```

### 2.2 组件全快、整体慢（关键否证）

真机 245MB 权威库上的逐组件隔离实测：

| 组件 | 隔离实测 |
|---|---|
| `claude_days` + `peaked_days` SQL（含 GROUP BY，186 分组） | **45ms**（命中索引 `usage_facts_harness_time`） |
| `claude_legacy_days`（legacy 聚合查询，核订增补） | **145ms**（当前 0 分组） |
| DB 打开序列（busy_timeout + journal_mode + user_version + repair） | **12–22ms** |
| 每次 open 的 DDL churn（DROP/CREATE VIEW 写事务） | 5–20ms |
| `load_pricing`（`include_str!` 常量解析） | 微秒级 |

**单组件全快、整体慢 40–400 倍** → 慢在**组合与争用**，不在任何单条 SQL。

**这条否证有直接的行动含义**：任何"优化 SQL / 加索引"的直觉都会扑空。

### 2.3 trust 关闭后的细化

trust 关闭窗口里，**21–32s 的峰值消失了，2.2–2.5s 的基线仍在**。

⇒ 争用解释**峰值**，不解释**基线**。基线的内因仍未定位，候选：
- 每次 open 的 DDL churn（写事务）
- WAL checkpoint 被读者吸收
- `overview_bundle` 内部某条查询的非线性劣化

### 2.4 下一步（观测先行，禁止投机优化）

把 Phase D 式的子计时伸进 `read_overview` 内部，分 5 段：
`open#1 / 主 SQL / open#2 / budget SQL / 组装`。~30 行，纯观测。
拿到段级分布再从 `open_readonly` / 进程内长连接 / checkpoint 主动调度 中择一。

**增量架构的设计结论（核订增补，供 P3 数据到位后择路）**：

1. **数据量不是当前成本来源**——四条 SQL 全部亚百毫秒（45/145/45/45ms），
   2.2s 基线是固定开销。若开销可治到 ~100ms，30s 全量刷新占空比仅 0.3%，
   「读侧增量」要解决的问题届时不存在。
2. 长期若要更快刷新，正确的增量位是**写时维护聚合**（sync 写事实的同一事务
   upsert `(harness, day, model) → 4 桶 SUM` 裸聚合表），配两层分离：裸聚合不含
   任何规则（订阅/归因/价目只在呈现折叠层生效，输入仅 ~186 组、微秒级）；
   失效边（PARSER_VERSION 重放 / 源删除 / 执行环境排除）走 wholesale 重算。
3. **不做读时差量**：订阅规则变更后已折算增量的回退边界极多，双计风险
   踩计费诚实红线（AGENTS.md）。

## 3. 托盘节流：抑制率随节奏涌现，实测 0–50%

### 3.1 现象与机制

spec §5.2 的意图是「轻 tick **跳过** `read_overview`，仅托盘节流到期时才跑」，
As-built 实现为 `TRAY_REFRESH_INTERVAL = 60s`。实测 20 次轻 tick：

```
含托盘刷新（跑 read_overview）：17 次 → 2.5s – 21.9s
不含（节流挡住）：              3 次 → 1.06s / 1.33s / 1.66s
```

**抑制率不是常数，取决于轻 tick 的触发节奏，而节奏本身是涌现的**：

| 阶段 | 轻 tick 间隔 | 抑制率 |
|---|---|---|
| trust 开启期 | 63–82s | **0%**（间隔恒 > 60s 窗口） |
| trust 关闭后 | ~31–67s | **~50%**（交替：刷新→挡住→刷新→挡住） |

间隔由三个分散在两个 crate、三份 spec 里的参数共同决定：
`WATCHER_SYNC_COOLDOWN`(30s) + self_monitor 拉长(→60s+) + **tick 自身耗时(1.3–21.9s)**。

### 3.2 正反馈

最后一项是关键——**它构成自我维持的坏稳态**：

```
跑 read_overview → tick 变慢(2.5–21.9s) → 下次间隔 >60s → 节流必过期 → 又跑 read_overview
```

反之一旦间隔落到 60s 以下，节流开始挡，tick 降到 1.3s，间隔进一步缩短，进入好稳态。
**系统是双稳态的**，而两份原始报告各自只观测到了一个稳态（见 §6）。

### 3.3 修复

`TRAY_REFRESH_INTERVAL` 60s → 5min（或直接「只有重 tick 刷托盘」）。

- 收益（已实测，非估算）：17/20 的轻 tick 从 2.5–21.9s 落到 ~1.3s 档；
- 代价：托盘三数字最多滞后一个重 tick 周期——**而重 tick 本就是 5 分钟口径**，
  所以这不是新增滞后，是回到既有口径；
- **同时应写死参数约束**：节流窗必须显著大于轻 tick 的最小可达间隔
  （`WATCHER_SYNC_COOLDOWN` + 典型 tick 耗时），否则机制恒失效。这条耦合此前
  没有任何地方记录（见 §5）。

**「那 30s 呢」的定量否决（核订增补）**：基线占空比 ~7% 尚可，但尾部长尾
21–32s **≥ 间隔本身**——最坏情况下刷新背靠背连转永远追不上，且 §3.2 的正反馈
在 30s 窗口下更容易锁死坏稳态。**30s 只有在 read_overview 固定开销被治到
~100ms 后才可行**（届时占空比 0.3%，问题消失）。

**决策门**：间隔的最终取值（5min / 只有重 tick / 治好开销后的 30s / 托盘标题
窄查询）应由 §2.4 的 P3 子计时数据 gate——常量关系断言（§5.2.1）先落地防回归，
间隔取值等数据。

## 4. fsevents 线程 churn：真实，但量级只有 0.3%

### 4.1 证据（两条独立路径互相印证）

全系统视角调查报告发现线程 ID 整体生灭；本次**独立复现成功**：

```
采样A：15013183 15013246 15013248 15013250 15013298 15013300 15013302 15013306
采样B（10s 后）：15013543 15013593 15013597 15013599 15013623 15013629
A∩B = 空集   ← 全部换新，不是稳定驻留
```

### 4.2 机制

worker 空闲分支每 `DEBOUNCE`(1.2s) 触发一次 `state.retry_pending()`，对 pending
根（实测 `pending_roots=4`，多为不存在的执行环境 skills 目录）逐个 `try_attach`。
macOS 上 notify 的 `watch()` 对不存在路径**每次尝试都启动 FSEventStream（含 runloop
线程）再以 PathNotFound 失败销毁**。⇒ 空闲时每 1.2s 制造一轮线程生灭。

### 4.3 量级修正（本次新增测量）

原报告列为 **P0**，量级描述为「持续本底 + 锁自旋」。实测修正：

- **纯空闲 18s 窗口（零日志活动）：0.06s CPU = 0.3% 一核**；
- 原报告引为证据的 `_pthread_mutex_firstfit_lock_wait × 350`，两次独立采样均为
  **0**，**未能复现**（可能仅在并发 tick 期间出现，或为瞬态）。

**定性完全正确**（目录不存在时以秒级节奏重试是零收益的纯浪费，合理节奏是分钟级），
**但量级不支持 P0**。修它的理由是"干净"，不是"省 CPU"。

**修复**：pending 重试指数退避（首次 30s，翻倍至 300s 封顶；挂载成功或拓扑替换时
重置）。~20 行。

## 5. 为什么这些能带着全绿门禁上线：测试覆盖的结构性缺口

`RUNTIME_TICK_LIGHT_PATH_TARGETED_SYNC_SPEC.md` §7 的测试矩阵声称 10 项，**实际
落地 3 项**：

| spec §7 声称 | 实际 |
|---|---|
| 唤醒槽并发压力 | ✅ 真有压测（10,000 次 wake 合并 + 8 线程×1,000 并发） |
| macOS FSEvents 真机写测试 | ✅ 有 |
| 依赖预算 / golden 双世界 | ✅ 有 |
| 升级规则（注入时钟穷举轻/重切换） | ❌ 无 |
| 路由 step-recorder | ❌ 全仓库零命中 |
| 执行环境过滤 `sync_facts(harnesses=…)` | ❌ 无断言 |
| **托盘节流「60s 内至多一次 read_overview」** | ❌ **无——正是本次漏掉的那条** |
| 备忘（同 revision 连续 IPC） | ❌ 无 |
| 回落（轻 tick 注入 Err 升级） | ❌ 无 |

落地的 3 项全是**基础设施类**（数据结构压力、依赖边界、字节回归）；**业务决策层
（路由/节流/升级/回落）7 项全空**。desktop crate 74 个测试，没有一个碰轻重路由。

### 5.1 更关键：就算那条节流测试写了，也未必抓得到

这个 bug **不是逻辑错误，是参数与涌现节奏的错配**。`tray_due = elapsed >= 60s`
这行逻辑完全正确。注入时钟的单元测试会喂它一个任选间隔（10s/30s），断言"60s 内至
多一次"——**通过，全绿**。

bug 只在真实间隔恒 >60s 时显形，而那个间隔由三个分散参数在**运行期涌现**。
没有任何常规单测会把它们放在一起看。

### 5.2 能抓到它的三类测试（都不在现有体系里）

1. **常量关系断言**（最便宜，3 行）：`TRAY_REFRESH_INTERVAL` 必须显著大于
   `WATCHER_SYNC_COOLDOWN` + 典型 tick 耗时。把隐含耦合变成会红的测试。
2. **循环级仿真**：注入时钟 + 注入 tick 耗时，驱动真实 `start_refresh_tick`，
   断言「N 分钟内 read_overview 调用次数 ≤ N/5」。这才是 spec 想要的 step-recorder。
3. **真机观测**——实际抓到它的方式，但最贵、最慢、最晚。

## 6. 方法论教训（本次最有价值的产出）

两份独立调查各自查到一半，且**各自都有一条结论被对方的数据证伪或细化**。复盘：

| 教训 | 来源 |
|---|---|
| `sample()` 的线程计数是**存在性**不是 CPU 消耗——线程阻塞在 `mach_msg` 时计数依然满格。判断"谁在烧 CPU"必须用 `ps -M`（每线程真实 CPU 时间）交叉验证 | 轻路径视角调查（据此撤回了"fsevents 泄漏"误判） |
| **但只看线程数量会漏掉 churn**——数量稳定不代表身份稳定。必须比对**跨采样的线程 ID 集合**，交集为空才是决定性证据 | 全系统视角调查（据此抓到 churn，前者漏了） |
| **事件时间戳 × CPU 采样的逐条对齐**是归因周期性突发的利器 | 全系统视角调查（前者看到了 30s 的 trust 事件却从未与 CPU 对齐，完全漏掉最大来源） |
| **组件隔离实测**：单组件全快而整体慢 → 结论是"慢在组合/争用"，直接否掉所有"优化 SQL"的直觉 | 全系统视角调查 |
| **小样本外推风险**：n=7 得出"节流从未生效(7/7)"，n=20 翻转为"17/20，抑制率随节奏变化" | 轻路径视角调查（本次自我订正） |
| **A/B 实验（关掉嫌疑源看曲线）是所有手段里最便宜、最决定性的**——90 秒得到 120%→2.8%，胜过任何采样分析 | 用户执行 |
| 调查期间的**并发编译**会污染耗时读数，必须显式声明混杂 | 轻路径视角调查 §7 |

**元教训**：两条独立调查路径的价值不在冗余，而在**互相证伪**。单独任何一份都会
导向错误的优先级——一份会去修 0.3% 的 churn（原 P0），另一份会漏掉 120% 的 trust。

## 8. 监控与防回归

- `self_monitor`（50% 阈值）本次**未触发**——符合"多个 <50% 来源叠加"的画像，
  说明单阈值看不住叠加型负载。考虑增加"累计 CPU 时间/墙钟"的滑窗比率指标；
- 给 `read_overview` 加超预算 WARN（>5s），与 Phase D 的 `refresh` 预算同款

  之后已是 2–14ms，5s 预算永远不会触发，测它没有信息量；
