# Agent Vitals App v1.0.0-beta.1 执行计划

日期：2026-09-13
依据：[v1.0.0-beta.1 功能范围与发布规格](./BETA_1_RELEASE_SPEC.md)
适用分支：`feat/v1.0.0-auto`
计划状态：待执行；本文不代表任何功能或门槛已通过。

## 1. 目标与完成定义

本计划的目标是把当前大量“已有实现、待接通或待验收”的能力，收敛为一个可由目标用户自行安装的 `v1.0.0-beta.1`。执行期间不扩展 Beta 范围，只关闭规格中的 B01–B12、T01–T13 和 G01–G09。

完成分两级：

| 里程碑 | 完成定义 |
|---|---|
| 内部候选版 RC | G01–G08通过；P0/P1为0；最终候选包完成T01–T13和自动化；若未签名，清楚标记“内部测试构建” |
| 对外 Beta | 在同一冻结候选上补齐G09；Developer ID签名、公证、干净用户安装、退出重开和升级通过；发布材料与包哈希一致 |

任何任务只有同时具备实现、适用测试和证据，才能记为完成。状态统一使用：`未盘点 / 已有实现待验收 / 缺口待修 / 阻塞 / 验收通过 / 延期`。

进度只报告三组数字：`B通过数/12`、`T通过数/13`、`G通过数/9`。不得用提交数、Loop数、代码行数或正式PRD的237项替代。

## 2. 执行原则与职责

### 2.1 范围纪律

- 允许进入当前计划：B/T/G直接阻断缺陷、必要测试夹具、发布脚本、说明和验收证据。
- 不进入当前计划：D01–D09，以及新执行环境、新MCP工具、高级workflow归因、额外报表和非阻断架构重构。
- 已经存在但延期的写入口从Beta导航和主操作中关闭；历史数据和兼容只读接口保留。
- 修复只覆盖阻断路径及必要相邻合同；不得因“顺手”扩大一个工作包。
- Vite/mock用于开发定位；B/T/G通过只接受冻结候选 `.app`、真实CLI/MCP或适用的集成测试证据。

### 2.2 角色

| 角色 | 职责 |
|---|---|
| 发布负责人 | 管理范围、优先级、候选身份、缺陷分级和Go/No-Go；不得单方面豁免门槛 |
| 实现负责人 | 盘点和修复代码；提交最小可审查变更；提供定向测试，不自行宣布最终UAT通过 |
| 验证负责人 | 管理夹具、执行自动化与真机T01–T13、保存原始结果；应与相应实现者分离 |
| 发布工程负责人 | 版本、构建、签名、公证、包校验、干净安装和升级验证 |
| 试用协调人 | 招募3名非实现者，按统一脚本观察任务，不做过程提示，记录误解和阻塞 |

一个人可以承担多个角色，但同一项的实现与最终验证不能由同一次自测同时关闭。最终Go/No-Go至少由发布负责人和验证负责人共同签字。

## 3. 总体路径与工期基线

```text
P0 基线与冻结
  ├─→ P1 首次价值与可信读取 ─┐
  ├─→ P2 计费声明与重算 ─────┼─→ P4 候选包全量验收 ─→ P5 独立试用 ─→ P6 签名发布
  └─→ P3 预算、事项与支持 ───┘
```

P1–P3可以在P0完成后按代码边界交错实施，但共享 Authority、查询合同、版本或前端状态的改动必须串行合入并立即对拍。P4开始后冻结功能；测试失败只进入针对性修复回路。

| 阶段 | 目标工作量 | 日历目标 | 退出条件 |
|---|---:|---:|---|
| P0 基线盘点与范围冻结 | 1–2人日 | 第1–2个工作日 | 当前改动可追溯；B01–B12逐项有状态与缺口；测试环境就绪 |
| P1 首次价值与数据可信 | 3–5人日 | 第2–6个工作日 | B01–B05、B10、B12具备候选实现；T01–T05/T07开发验收无P0/P1 |
| P2 计费、撤销与恢复 | 3–5人日 | 第4–8个工作日 | B06–B07具备候选实现；T06/T08/T10开发验收通过 |
| P3 预算、待处理与支持 | 3–5人日 | 第5–9个工作日 | B08–B09、B11具备候选实现；T09/T11–T13开发验收通过 |
| P4 冻结RC与全量门禁 | 2–3人日 | 第10–12个工作日 | G01–G06通过；同一RC包T01–T13全通过 |
| P5 三人独立试用与修复 | 2–4人日 | 第13–16个工作日 | G07–G08通过；P0/P1为0 |
| P6 签名、公证与发布 | 1–2人日 | 第17–18个工作日 | G09通过；最终分发包复验并发布 |

这是基于“大部分底层实现可复用”的目标工期，不是无条件承诺。若P0发现B01–B12中存在两项以上完整能力缺失，或签名凭据不可用，发布负责人必须在P0出口重排日期。签名凭据、干净测试用户和3名试用者从第1天并行准备，不能等到P5/P6才启动。

最快可交付路径：第12个工作日形成内部RC；对外Beta目标为第18个工作日。若G09外部条件未就绪，只交付内部测试构建，不降低或绕过macOS安全要求。

## 12. 缺陷处理与回归规则

| 等级 | 示例 | 处理 |
|---|---|---|
| P0 | 数据丢失/污染、错误计费、假0、敏感内容外发、破坏执行环境日志 | 立即停止相关验收；修复并重跑数据完整性、受影响T项和全量门禁 |
| P1 | B01–B12路径不可完成、启动/安装失败、金额跨面不一致、恢复失败、核心可访问性失败 | 阻断当前RC；建立触发步骤和回归后修复 |
| P2 | 不影响理解和操作的排版、非核心文案、已明确延期增强 | 记录到发布说明或后续；由Go/No-Go确认不升级为P1 |

同一根因连续两次修复失败时，停止继续堆补丁：补充最小复现和数据流定位，重新审查合同边界。不能通过删除断言、放宽MCP判定、刷新golden或更改夹具真值把失败改成通过。

## 13. 每日执行和报告格式

每日只更新一次主台账，避免在Loop日志、UAT文档和临时记录之间产生多个真相源。建议报告如下：

```text
日期 / RC：
B：x/12  T：y/13  G：z/9
今日关闭：E编号 + 证据
新增P0/P1/P2：数量 + issue
当前阻塞：阻塞对象、负责人、解除条件
下一步：最多3项，必须在关键路径
范围变化：无；如有则停止并回到Spec评审
```

每日优先级顺序：P0数据完整性 → P1用户主路径 → 当前阶段出口 → 自动化回归 → P2。非关键路径发现记录后移出当前RC，不现场扩展。
