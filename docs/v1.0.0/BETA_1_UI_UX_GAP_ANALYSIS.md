# Agent Vitals v1.0.0-beta.1 UI/UX 现状审查与调整方案

日期：2026-09-13
依据：[Beta 发布规格](./BETA_1_RELEASE_SPEC.md)、[Beta 执行计划](./BETA_1_EXECUTION_PLAN.md)、[v1.0.0 PRD](../AGENT_VITALS_APP_V1_0_0_PRD.md)、[v1 线框索引](../design/v1-wireframes/README.md)
状态：审查完成，尚未修改 UI 实现。

## 1. 审查对象与证据边界

本次通过 Computer Use 实际查看了 `/Applications/agent-vitals.app` 的总览、Token 日历、会话、Issues 和数据源页面，并读取了辅助功能树。实际运行包显示 App `0.11.0`，主二进制 SHA-256 为 `c26b619e…`；工作区最新构建仍显示 `0.11.0`，但主二进制 SHA-256 为 `d85e91e6…`，二者不是同一个包。

工作区最新 `.app` 因窗口读取超时未取得可靠的 Computer Use 截图。因此本文把证据分为：

- **当前实际界面**：来自 `/Applications` 已安装包的真实操作和截图。
- **最新源码现状**：来自 `workbench.html`、`workbench.css`、`workbench.js`；用于确认已加入但未在已安装包看到的字段和布局。
- **目标体验**：来自 v1.0.0 PRD 与五组线框，不代表实现已经完成。

凡需要确认最新构建实际交互的项，均标记为“最新候选待复测”，不以源码存在判通过。

## 2. 结论

当前 UI 的主要问题是信息架构仍接近研发控制台：功能和字段很多，但没有围绕三个用户问题组织——“用了多少”“费用应如何理解”“现在要做什么”。配置、诊断、账单、预算和结果同时堆在总览，导致首份价值被推到下方；技术状态直接暴露为英文 reason code；宽表在默认 760×560 窗口中挤压断裂。

与 v1.0.0 设想相比，底层数据展示能力大多已经有入口，差距集中在四件事：

1. **页面职责未分离**：总览承担了总览、设置、账单、诊断和数据源摘要五种职责。
2. **渐进披露没有落实**：低频配置与空值卡在首屏常驻；用户还没理解结果就面对大量表单。
3. **字段语言偏技术合同**：`provider`、`fair-market`、`missing`、reason code、金额“分”等直接面向普通用户。
4. **真实布局和等待体验未达门槛**：会话宽表明显破版；固定底部路径占空间并暴露绝对目录；Issues长时间加载只有一句文字，没有进度、部分结果或取消。

Beta 应先重组现有字段和入口，不需要先做新的视觉品牌。目标是把现有能力装进正确的页面和操作顺序。

## 3. 目标信息架构

主导航只保留四个用户任务，设置作为固定辅助入口：

```text
总览        用量        会话        待处理                         同步状态  [立即同步] [设置]
回答量级    看趋势      找具体工作  处理最值得行动的一件事
```

设置采用左侧分区：

```text
数据源
计费与套餐
预算与提醒
价格与显示
隐私与数据
关于与诊断
```

Beta 延期的账单录入、CSV导入、已确认支出预算创建和在线价格更新不显示可操作入口。已有数据保留只读兼容，不能因隐藏入口删除。

### 3.1 页面职责

| 页面 | 只回答的问题 | 主要动作 |
|---|---|---|
| 总览 | 本时间范围用了多少、费用是什么口径、哪里需要我确认 | 当前唯一最高价值动作，例如“确认计费方式”或“恢复数据源” |
| 用量 | 哪一天/小时变化最大，数据是否完整 | 选择日期并查看相关会话 |
| 会话 | 哪个具体工作消耗最多、费用状态为何 | 打开一个会话详情 |
| 待处理 | 哪件事最值得处理、影响什么、下一步是什么 | 对第一项执行确认/恢复/查看 |
| 设置 | 修改来源、计费、预算、显示、隐私和诊断 | 保存当前分区设置 |

## 4. 当前总览字段价值与处置

当前总览实际或最新源码中存在约五类面板、十余个指标和多组表单。以下处置直接用于 Beta UI 收口。

| 当前字段/区域 | 用户价值 | 必要性 | Beta 处置 |
|---|---|---|---|
| 时间范围、更新时间、来源状态 | 建立所有数字的口径和新鲜度 | 极高 | 放在总览第一行；增加今天/7天/本月/自定义切换；同步绿点改为带文字状态 |
| 本月名义成本 | 回答使用量对应的公开API价格量级 | 极高 | 作为第一主卡；紧邻“参考估算、非账单”和价格覆盖 |
| 已观测 tokens | 回答真实已读取用量 | 极高 | 第二主卡；显示会话数和已导入范围 |
| 价格覆盖 | 判断名义成本能解释多少用量 | 极高 | 第三主卡；显示未计价tokens并可下钻 |
| 计费方式待确认 | 让用户把估算分成订阅覆盖和额外按量 | 极高 | 主卡下唯一高价值提示；必须显示影响tokens、当前默认和确认收益 |
| 数据读取失败/缺价 | 告诉用户结果受何影响 | 高 | 与计费待确认分开；若更紧急则取代其成为本页唯一主动作 |
| 趋势和服务商分布 | 找变化和费用来源 | 高 | 主动作之后展示；服务商使用人类名称，详情再看原始ID |
| 今日 tokens / 今日名义成本 | 快速看今天 | 中 | 默认放菜单栏；总览选“今天”时间窗时复用三主卡，不再另建一排“今日卡” |
| 额外按量估算、订阅覆盖 | 套餐校准后的核心结果 | 高但条件性 | 只有具备相应证据时出现，不以空卡占位 |
| 已确认支出 | 有账单/付款证据时有价值 | 高但条件性 | 仅有数据时出现并标“已记录部分”；Beta无证据时不显示“无数据”卡 |
| 预算进度 | 已设置预算用户需要 | 高但条件性 | 仅配置后出现摘要卡；操作入口跳设置；未配置不显示0% |
| 单位成本 | 可做跨周期效率分析，但普通用户难以直接行动 | 低 | 从总览移除；后续放趋势详情或高级分析 |
| 缓存命中率 | 解释价格与技术效率 | 中低 | 从首屏移除；放会话/模型详情，必要时作为“费用为何变化”的解释 |
| 本月日均 tokens | 辅助趋势理解 | 中低 | 作为用量卡次级文案或趋势提示，不独立占卡 |
| “双轨账（本月）” | 能区分订阅和按量，但当前内容是技术投影 | 中高 | 改名“费用构成”，放在趋势之后；禁止展示 `fair-market`、`missing`、raw reason code |
| “现在该用谁” | 有可靠配额时可辅助决策 | 中且证据受限 | 移到二级分析或菜单栏；只有明确、带时间戳配额才显示，不用碰壁史推百分比 |
| 本月逐日 | 与Token日历重复 | 中 | 总览只留小趋势和“查看用量”；完整逐日移到用量页 |
| 数据源摘要 | 解释覆盖 | 中高 | 总览只显示“3个正常、1个需检查”；详细卡移到设置→数据源 |
| 导出当前月摘要 | 低频操作 | 中 | 移到设置→隐私与数据；总览金额详情可保留小型“导出此视图”次操作 |
| 保留期、统计时区 | 必要设置 | 高但低频 | 移到设置→隐私与数据、价格与显示；不占总览首屏 |
| 公共价格目录检查 | 价格治理 | Beta延期 | 隐藏可操作入口；设置中只读显示内置价目版本和“随测试版更新” |
| 帮助、诊断、版本、更新 | 支持与排障 | 高但低频 | 移到设置→关于与诊断 |
| 账单手工录入、CSV | 正式版支出完善 | Beta延期 | 从总览和Beta导航隐藏；尤其不能让用户输入“金额（分）”与内部字段 |
| 旧“跨执行环境按量实付预算”表单 | 兼容旧预算 | 低且易混淆 | 只读迁移说明；用户修改统一进入新版预算，不与两套预算表单同时出现 |
| 观察预算、已确认支出预算两个表单 | 预算管理 | 条件性 | Beta只开放观察预算；已确认支出预算创建按D01隐藏，已有值只读 |
| 全局固定绝对路径及fallback说明 | 研发诊断 | 低，且会泄露/遮挡 | 删除固定页脚；数据根简写放设置，高级展开才显示完整路径 |

### 4.1 Beta 总览推荐顺序

```text

名义成本                   已观测用量                价格覆盖
≈ ¥X（参考估算）           8.94B tokens              89% · 1.35B未计价
[查看价格依据]             [查看会话]                [查看未计价范围]

12.59B tokens 的付费方式待确认；当前仍按原厂API价格估算
[确认计费方式]  [稍后]

条件性区域：额外按量估算、订阅覆盖、已确认支出、预算进度
```

总览最多同时显示三项可完善事项，且只有一项使用主按钮。设置类入口不插入主卡之前。

## 5. 分页面差距与调整

### 5.1 顶部导航与窗口

当前：`总览 / Token 日历 / 会话 / Issues / 数据源`，右侧为无文字绿点、截图、刷新。Tauri默认窗口760×560、最小640×480；实际会话页已经发生左侧计数竖排、右侧执行环境chips挤出、费用列截断。

调整：

- `Token 日历`改为“用量”；`Issues`改为“待处理”；数据源移入设置。
- “截图”仅为开发/诊断功能，生产Beta移除；“刷新”区分“刷新界面”和“立即同步”，用户只看到后者。
- 同步状态用“已更新 15:47”“同步中 · 解析Codex”“1个来源失败”等文字，不只用颜色圆点。
- 默认窗口建议1120×780，最低1024×700，与PRD一致；200%字号时CSS视口仍会缩小，必须提供卡片/折行布局，不能只提高最小窗口掩盖问题。
- 顶部按钮命中区至少44×44；正文建议14–16px，辅助文字不低于12px；保留可见焦点和系统明暗模式。

### 5.2 用量日历

当前：月总量和“部分覆盖”有价值，但每日单元同时塞入tokens、多个执行环境金额缩写；截图中出现 `CC`、`CX` 等不解释缩写。小时区域位于日历下方，在560px窗口首屏不可见。

调整：

- 每个日期格只显示所选指标的一个主值；覆盖不足用文字/图标状态，不在格内堆多执行环境金额。
- 指标切换明确为“Tokens / 名义成本 / 按量估算”，不混入实际支出；每次只展示一种口径。
- 增加固定图例：有记录、真实0、无记录、未计价、导入未完成、未来日期；状态不能只靠颜色。
- 点击日期进入同页右侧或下方“日期详情”：总tokens、名义成本、会话数、覆盖、24小时图。没有小时证据时保留空白并解释，不能均摊。
- 日期详情提供“查看该日会话”，携带时间、执行环境、provider筛选；返回日历恢复月份和选中日。
- 执行环境/币种明细放日期详情列表，使用完整名称，不在格内使用 `CC/CX`。

### 5.3 会话列表与详情

当前：筛选功能丰富，字段包含标题、执行环境、模型、日期、tokens、估算成本、Findings；但默认窗口下工具栏和表格严重挤压，成本文案被截断，加载时空表会停留数秒。左侧“2026-09共205个会话·点击查看报告”被压成竖排，执行环境chips在右侧堆叠。

字段处置：

| 字段 | 价值 | 调整 |
|---|---|---|
| 标题/项目 | 极高 | 第一列；无标题用“执行环境会话 · 日期时间”，ID仅辅助 |
| 执行环境 + 模型 | 高 | 合成一列或副行，减少表宽 |
| 日期/时间 | 高 | 使用短格式；跨日可展开，不在列表塞完整范围 |
| Tokens | 极高 | 默认排序，右对齐，保留完整值辅助说明 |
| 费用状态/估算 | 高 | 显示短标签和金额；原因点开看，不把长句塞单元格 |
| Findings | 低且与待处理重复 | Beta列表移除；存在可行动事项时显示一个“需确认”短标签即可 |
| provider筛选 | 中高 | 名称改“服务商”；放“更多筛选”或宽屏第二行 |
| 模型筛选 | 高 | 保留；提供已知值选择/建议，避免要求完整内部ID |
| 计费状态筛选 | 高 | 保留人类标签：订阅覆盖、按量估算、待确认、未计价 |

宽屏使用五列：`标题/项目 | 工具·模型 | 日期 | Tokens | 费用状态`。小于900px改为两行卡片，不依赖横向滚动完成核心任务。筛选栏首行只放时间、搜索、排序和“更多筛选”；加载时保留骨架、阶段说明和取消/后台继续。详情顺序调整为摘要→异常/计费提示→token与费用组成→时间线→高级证据，raw/envelope/coverage默认折叠。

### 5.4 Issues → 待处理

当前：以总问题数、critical/warning/info、规则级汇总和原始明细为核心，字段为规则、严重度、类别、命中、会话、时间、对象、状态。它更像规则引擎控制台，并且“critical”容易被理解为已经发生严重损害。真实页面长时间停留在加载态，未展示可操作的下一步。

调整：

- 页面改名“待处理”，首屏展示“现在最值得处理”，按影响、证据充分度和可操作性排序。
- Beta只承诺四类：数据连接失败、计费待确认、价格缺失、预算阈值。行为规则保留时放“事件观察”二级区。
- 每张任务卡只显示：发生了什么、影响范围、当前处理、证据限制、主动作、状态。规则ID和哈希只在高级证据中显示。
- `critical/warning/info`不作为首屏四张统计卡；改为“需要你处理 / 系统正在恢复 / 仅供观察”等行动状态，并配文字或图标。
- “命中数”和“待办数”明确分开：例如“1项待办 · 汇总2617次相同事件”；支持分页与样本证据展开。
- 计费待确认跳确认面板；来源失败跳数据源并聚焦对应执行环境；缺价跳价格说明；预算阈值跳预算范围。
- 加载超过1秒显示骨架，超过10秒显示阶段、已有部分结果和后台继续/重试；失败不能显示空表或全0。

### 5.5 数据源 → 设置中的数据源分区

当前：页面先显示“其他本机位置”表单，之后才是现有来源。来源卡字段包含连接状态、会话数、facts数、扫描文件数、最近日志、路径，以及“立即同步/停止读取/删除已导入数据”三个并列按钮。WorkBuddy没有实验标签。

字段处置：

| 字段 | 价值 | 调整 |
|---|---|---|
| 来源名称、状态 | 极高 | 卡片标题；使用未发现/权限不足/导入中/部分失败/正常/暂停等完整状态 |
| 最近记录时间、最后成功同步 | 极高 | 分开显示，避免把“最近没用”误认为连接失败 |
| 导入范围、会话数 | 高 | 卡片摘要保留 |
| facts数、扫描文件数 | 低 | 放展开诊断，不占普通摘要 |
| 路径 | 中且敏感 | 默认简写，展开后显示完整；不放全局页脚 |
| 立即同步/重试 | 高 | 状态相关主动作；正常时不必持续突出 |
| 暂停/恢复 | 高 | 次动作；文案明确只影响后续读取 |
| 删除已导入数据 | 高风险低频 | 放“更多”或危险区，与“删除连接”分开，明确不删源日志并二次确认 |

页面顺序改为：全部来源状态→需要恢复的来源→添加其他位置→读取范围与隐私。WorkBuddy显示“实验支持”，缺少的字段写“此来源暂不提供”，不能用0。

### 5.6 设置

当前没有独立设置入口，多组表单直接堆在总览。最新源码甚至把导出、保留期、时区、在线价格、诊断、账单和两套预算都放在主卡之前，进一步偏离“先价值、后配置”。

调整：

- 建独立设置页或侧边栏，按目标信息架构分区，保存后留在当前分区并显示就地回执。
- 金额输入使用货币单位，例如“月预算 ¥500”，不让用户填写“50000分”；存储仍可使用minor unit。
- 时区优先系统值和可搜索选择器；IANA ID作为辅助，不要求普通用户手输。
- 表单按需展开；校验在离开字段或提交时就地显示，提交按钮有进行中、成功和失败状态并防重复点击。
- 高风险删除使用范围摘要、影响计数和明确确认；失败后焦点回到可修字段或错误摘要。

### 5.7 计费确认面板

当前已安装包的“确认套餐信息”曾无法展开；最新源码已调整按钮语义，但最新候选待真实 `.app` 复测。源码中的作用范围只有“该执行环境与服务商（按有效期）”，与Beta规定的“当前所选会话或明确日期范围”仍需核对。

调整：

- 使用右侧面板，保持总览上下文；一次只处理影响最大的一个组。
- 首部固定显示执行环境、服务商/模型、tokens、会话数、日期和当前估算依据。
- 单题选择：官方订阅、官方API、第三方、组织承担、仍不确定；选择后才展示必要字段。
- 作用范围仅开放“所选会话”和“明确日期范围”；默认最窄范围，不提供Beta延期的未来自动覆盖。
- 保存前预览“移出估算/保持估算/仍待确认”；最后按钮写“保存并重算”，过程中禁止重复点击。
- 成功回到原位置显示结果版本、影响会话数和“撤销”；失败显示“声明已保存，重算待重试”，旧结果仍可查看。
- “仍不确定”只显示影响说明和“保持当前估算并返回”，不创建声明或重算。

## 9. 验收方式

每个UI调整至少通过四层验证：

1. **结构检查**：生产DOM中总览不再含延期写入口；设置分区和主导航唯一；技术reason不会直接进入普通视图。
2. **浏览器开发验证**：快速核对布局、状态和事件，不作为最终通过。
3. **最终 `.app` 真机验证**：默认窗口、1024×700、200%字号、系统明暗、键盘和读屏；截图记录不能来自旧安装包。
4. **数据对拍**：总览、菜单、日历、会话与CLI/MCP在同一时间窗、币种、basis和结果版本一致；UI移动不能重写计算。

验收截图应包含版本/候选身份，使用脱敏夹具；不得展示真实用户名、绝对路径、会话标题或账户信息。最新候选真实 `.app` 未完成 Computer Use复核，首次实施任务应先固定候选并补一轮同页截图，作为本报告的“调整前”基线。

## 10. 决策建议

Beta UI 不需要推翻现有视觉语言。保留系统明暗、卡片、语义状态色和已有数据组件；先通过页面职责、渐进披露和响应式布局让用户完成任务。最值得立即执行的四项是：

1. 清空总览顶部的设置与账单表单，恢复三主卡和唯一事项。
2. 修复会话页默认窗口破版，并把长费用原因折叠到详情。
3. 把 Issues 改成四类可行动的“待处理”。
4. 用最终候选 `.app` 复测计费确认完整链，确认最新源码修复确实进入包体。

这四项完成后，界面会从“数据能力陈列”转为“用户任务入口”，也是当前最短的Beta体验收口路径。
