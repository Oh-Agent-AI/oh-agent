# 战斗单位标准化接入：L1–L9 验证方案

状态：设计草案，尚未接入生产规则。目标是用 L1–L9 验证同一套战斗单位接口，而非为每种怪兽新增一条宿主分支。L10 不在本阶段范围。

## 现状与约束

- `board.ts` 的权威物种和技能类型覆盖 L1–L8；状态分别散落在 `corrode`、`swarm`、`neural` 等字段。`rules.ts`、回放和展示中存在物种专门分支。
- `contracts/battleExtension.ts` 是未接线的泛型草案，不是已验证的标准；它强制随机状态，而现有规则未必使用随机。
- 本地回放 v1–v3 重建规则并对完整状态、日志和表现阶段计算摘要。直接给旧状态增加字段会改变摘要；旧版本必须走原有重建和摘要路径。
- 玩家计划的 `revision` 不覆盖敌方准备及结算过程，不能作为扩展原子提交的唯一版本。远程对局仍遵守现有协议与明确的能力门控。

## 统一边界

宿主拥有棋盘、单位、回合、随机源、对象 ID 和权威版本；单位实现只接收只读、版本化快照，不直接修改宿主、访问时钟、使用隐式随机数或执行 I/O。每个实现注册稳定的 `contentId`、`contentVersion`、状态和事件 schema 版本，以及明确的能力声明。

接口覆盖五个阶段：

1. **初始化**：由宿主提供确定的开局输入，返回可序列化的初始扩展状态。
2. **声明**：基于权威快照产生固定意图；意图包含目标、范围、顺序和失效条件。
3. **投影**：纯函数基于快照与声明计算玩家可见后果；不消耗随机、不修改状态。
4. **权威结算**：基于同一声明和当前版本产生候选状态、有序事件和随机源的新状态；宿主原子检查版本及身份后一次提交，失败不写任何部分。
5. **协调**：单位死亡、移除、地形变化或终局后，基于完整快照按固定顺序解除链接、过期效果和清理状态，产生可重演事件。

数据必须有界、纯数据、可验证，拒绝未知版本和畸形状态。ID 由宿主按固定规则分配，事件带稳定动作 ID 和单调序号。随机源只在规则实际使用时存在，记录算法版本和状态；表现动画不得消费规则随机序列。状态版本覆盖声明、结算和协调中所有相关事实变更，不能复用仅代表玩家计划的版本。

## 回放与兼容

新契约采用新的回放 schema 和规则版本，记录开局、内容版本、必要的初始随机状态与玩家指令，通过同一权威流程重建并校验状态及有序事件。导入先检查描述符、字段、数量与版本，再进行重演；摘要用于一致性校验，不是来源认证。旧 v1–v3 不迁移、不追加字段，保持原有重建与摘要算法，并通过固定旧档案回归。远程协议不会因本地接口而自动开放；须单独版本化、允许列表和兼容性测试。

## 验证矩阵

| 验证对象 | 要验证的接口能力 |
| --- | --- |
| L1 孢群体 | 单体行动、位置与伤害事件 |
| L2 流环体 | 有序直线、多目标投影与结算 |
| L3 孔洞行者 | 有界持续区域、到期与清理 |
| L4 晶簇体 | 条件状态与伤害拦截 |
| L5 群构体 | 稳定子体 ID、上限、出生、死亡和清理 |
| L6 相位体 | 多单位交换及落点冲突 |
| L7 引力核 | 有序强制位移、碰撞与失效原因 |
| L8 织网体 | 链接账本、断链和恢复 |
| L9 多核生命 | 阶段阈值、一次性迁移和原子提交 |

每个物种必须通过相同的契约测试：合法输入、非法/过期版本、预览无副作用、预览与实际结算一致、死亡和终局清理、确定性重复执行、保存/重演及篡改拒绝。还需验证不同物种按相同宿主 API 注册和执行，不在宿主新增物种专门分支。现有 L1–L8 的行为应有迁移前后等价测试；视觉事件必须对应已提交规则事件。

## 实施顺序

1. 从现有规则提取中立的宿主快照、单位注册、版本与有序事件边界；在不改变旧状态摘要的前提下，先为一个简单单位接入，证明实际回合而非仅类型可用。
2. 添加新回放版本与旧档案固定回归；以真实完成局验证保存、重演、篡改拒绝和版本降级。
3. 按 L1–L4、L5–L8、L9 的复杂度迁移；每批通过上表同一测试矩阵，逐步移除相应宿主特判。
4. 检查 City 展示、低动态、死亡、资源释放和目标设备性能；最后才开放已验证的演练入口。

完成标准：L1–L9 均实际通过统一接口执行权威回合并满足矩阵；旧档案回归通过；迁移没有扩大远程能力或改变既有战斗规则。当前尚未达到完成标准。
