## 0. 一句话结论

**轻路径按设计路由了，但它最大的那块收益没兑现**：`TRAY_REFRESH_INTERVAL`
（60s）比轻 tick 的真实触发间隔（63–82s）还短，托盘节流判定**恒为到期**，
于是每一次轻 tick 都照跑 `read_overview`——而 `read_overview` 占了轻 tick
耗时的 **93–96%**。用户看到的高 CPU 是真的，但它是**尖峰**（tick 执行的
十几秒）而非持续：调查期间多次实测进程稳态 0.0%。

## 2. F1：轻/重路由确实生效

按新版本启动时刻（第一次轻 tick，02:00:59）切分日志：

```
新版本运行期内：轻 tick 7 次 / 重 tick 3 次 / 轻→重升级 0 次
```

轻 tick 内部确实跳过了 spec §5.2 表里规定跳过的步骤——没有 `discover`、
没有 `sessions navigation` 子进程、没有 `budget_alerts`。定向同步部分也
按预期变快了：

```
轻 tick 的实际同步开销（稳定）：
  claude-sync   0.052–0.096s
  sync-facts    0.470–0.967s   ← 执行环境过滤 + walk 级裁剪生效
  drain_event_bus 0.006–0.012s
  合计 ≈ 0.53–1.08s
```

**这部分工作是好的，不需要改。**

## 3. F2：托盘节流窗选错了，导致 Phase B 的核心收益归零

### 3.1 现象

7 次轻 tick，**7 次全部**记录为「含托盘节流刷新」——`tray_due` 恒为真。

### 3.2 根因

```rust
// apps/desktop/src-tauri/src/lib.rs:1409
const TRAY_REFRESH_INTERVAL: Duration = Duration::from_secs(60);
// :1644
let tray_due = last_tray.elapsed() >= TRAY_REFRESH_INTERVAL;
```

代码逻辑本身没错，错在**参数值与系统的真实节奏不匹配**。轻 tick 的触发
间隔被三个因素顶高：

1. `WATCHER_SYNC_COOLDOWN` = 30s（watcher 唤醒的执行率下限）
2. `self_monitor` 在 CPU 高时把冷却拉长到 60s
3. tick 自身耗时 2–22s

实测间隔：

```
02:00:59 → 02:02:02 → 02:03:05 → 02:04:27 → 02:06:53 → 02:08:10 → 02:09:28
    (63s)     (63s)     (82s)     (146s)     (77s)      (78s)
```

**最小间隔 63s > 60s 的节流窗**——节流永远判定到期，等于不存在。

### 3.3 影响

Phase B 表里「轻 tick 跳过 `read_overview`」这一行**一次都没有发生过**。
轻 tick 的实测耗时因此是：

| 时刻 | 轻 tick 总耗时 | 其中 read_overview | 占比 |
|---|---|---|---|
| 02:04:27 | 21.89s | 21.03s | 96% |
| 02:06:53 | 20.75s | 19.91s | 96% |
| 02:08:10 | 16.89s | 15.78s | 93% |
| 02:09:28 | 17.49s | 16.62s | 95% |

去掉 `read_overview`，轻 tick 应该是 **0.53–1.08s**。

## 4. F3：`read_overview` 是当前真正的成本中心

全日志 297 次调用的分布：

```
n=297   min=1.50s   p50=2.16s   p90=8.27s   max=31.93s   mean=3.60s
累计 = 1070 秒（约 17.8 分钟）
```

同期其他步骤的累计对比：

```
read_overview        1069.8s  (n=297)   ← 压倒性
budget_alerts         334.7s  (n=303)
drain_event_bus         2.2s  (n=310)
publish_invalidation    0.4s  (n=310)
refresh（托盘重建）      ~0.01s 级 (n=310)
```

**Phase C 的 revision 备忘对这条路径天然无效**：轻 tick 刚写完新事实，
authority revision 必然前进，下一次读必定 miss。备忘只对「同 revision 内
的重复读」有效（IPC 侧连续刷新），对 tick 内的读一次都命中不了。

### 4.1 方差问题（未定位）

`read_overview` 的方差极大（p50 2.16s vs max 31.93s，15 倍）。新版本期内
的时间序列：

```
8.16s → 2.15s → 2.20s → 21.03s → 3.50s → 19.91s → 15.78s → 16.62s
```

**方差来源尚未定位**，有三条待验证假设：

- H1：与 `sync-facts` 写入的 SQLite 锁竞争（读在写后立刻发生）
- H2：`overview_bundle` 内部某条查询随数据量非线性劣化（权威库 234MB）
- H3：CPU 竞争（见 §7 混杂因素）

`read_overview` **内部目前没有任何子步骤计时**——Phase D 只拆了 `refresh`，
而 `refresh` 早在 `e0b9f07` 之后就只剩 2–14ms 的托盘重建了，拆它没有信息量。
**观测面加错了地方**。

## 5. F4/F5：CPU 特征与负载规模

### 5.1 系统时间主导

`ps -M` 每线程分解（取 CPU 时间最高的几条）：

```
STIME(系统)  UTIME(用户)
  1:02.08      0:28.59
  0:50.05      0:21.06
  0:47.26      0:18.75
  0:38.75      0:18.39
```

**系统时间约为用户时间的 2 倍**——这是 `stat`/`readdir` 系统调用密集的
签名，不是计算密集。

### 5.2 语料规模（负载的真实驱动）

```
~/.codex            29,593 文件 / 8.2 GB   ← 主导
~/.dsh                 650 文件 / 1.7 GB
~/.claude/projects     541 文件 / 828 MB
权威库 agent-vitals.sqlite3      234 MB
（另有 ~700MB 历史备份文件，不参与查询，仅占盘）
```

重 tick 的全量 walk 要 stat 近 3 万个文件——这是重 tick 成本的结构性来源，
也是 spec §1.3「乘性论证」的实证基础。

### 5.3 尖峰而非持续

调查期间多次采样：

```
02:05 ps → 291.3% （tick 执行中）
02:10 ps →   0.0% （tick 间隙）
02:12 ps →   0.0%
```

进程累计 CPU 9:32 / 运行 7:34 = 平均 126%，但瞬时在 0% 与 300%+ 之间跳。
用户截图的 387.6% 是**恰好落在 tick 执行窗口内**的瞬时值。

## 6. 撤回一个错误结论：fsevents 线程不是泄漏

调查中途我基于 `sample` 看到 **11 个 `notify-rs fsevents loop` 线程**，
判断为「拓扑替换时旧 watcher 未被 drop 的线程泄漏」，并已口头告知用户。
**这个判断是错的，现予撤回。**

纠正依据：

1. `WorkerState::apply()`（`watch.rs:623`）**确实**先 `self.watcher = None`
   （drop 旧后端）再建新实例——代码路径没有泄漏；
2. notify 6.x 的 macOS FSEvents 后端是**每个 `watch()` 调用起一个 run-loop
   线程**，不是每个 watcher 实例一个。11 个线程对应的是 11 个已挂载的根
   （实测 `facts_roots_attached=4` + `cache_roots_attached=7` = 11，完全吻合）；
3. 复测时线程数从 11 降到 5，随已挂载根数变化而非单调增长——排除泄漏；
4. 全部线程阻塞在 `mach_msg2_trap`（等待态，零 CPU 消耗）。

**教训**：`sample` 的线程计数是「该线程在采样窗口内存在的次数」，不是
CPU 消耗量。用它判断「谁在烧 CPU」会得出错误结论——本次若非用 `ps -M`
交叉验证，这条误判会进入修复清单并浪费一轮迭代。

## 7. 数据置信度与混杂因素

**必须声明的混杂**：调查期间本机同时在跑 `cargo build --release`（用户
截图里 `rustc` 96.1% 可见）。02:04 之后那几次 15–21s 的 `read_overview`
与编译窗口重叠，**这几个具体数值被 CPU 竞争放大了**，不能当纯净基线。

但两条结论不受此影响：

- F2（节流失效）是**逻辑判定**，与耗时无关——7/7 命中是确定的；
- F3（read_overview 主导）的统计基于 297 次调用（绝大多数不在编译窗口内），
  p50=2.16s / p90=8.27s / 累计 1070s，量级结论稳固。

**方差来源（§4.1）的定位必须在无编译干扰的窗口重做**。

## 8. 建议处置（按收益/风险排序）

| # | 处置 | 依据 | 预期收益 | 风险 |
|---|---|---|---|---|
| 1 | `TRAY_REFRESH_INTERVAL` 60s → 5min，或直接改为「只有重 tick 刷托盘」 | F2 | 轻 tick 从 2.6–21.9s 降到 0.53–1.08s | 低（托盘数字最多滞后一个重 tick 周期，本就是 5 分钟口径） |
| 2 | 给 `read_overview` / `overview_bundle` 加内部子步骤计时 | F3/§4.1 | 定位 15 倍方差的来源 | 无（纯观测） |
| 3 | 在无编译干扰窗口重测基线 | §7 | 剥离混杂，拿到可信基线 | 无 |
| 4 | 评估把 Phase D 的观测面从 `refresh` 移到 `read_overview` | §4.1 | `refresh` 已是 ms 级，拆它无信息量 | 需改 spec §5.4 |
| 5 | 清理 ~700MB 陈旧权威库备份 | §5.2 | 仅占盘，不影响性能 | 低 |

**建议先做 #1**：一个常量，改动面最小，收益按日志推算最直接——它是
Phase B 承诺收益能否兑现的开关。#2/#3 是把 §4.1 那个未解问题变成可回答
问题的前置。

## 9. 对 spec 的反馈

`RUNTIME_TICK_LIGHT_PATH_TARGETED_SYNC_SPEC.md` 需要两处修订：

1. **§5.3 As-built 的托盘节流方案需要标注实测失效**——60s 的窗口值与
   §5.2 的防饥饿参数（`WATCHER_SYNC_COOLDOWN` 30s + self_monitor 拉长）
   之间存在未被识别的耦合：**节流窗必须显著大于轻 tick 的最小触发间隔**，
   否则恒失效。这条耦合关系应该写进 spec 作为参数选择约束。
2. **§5.4 Phase D 的观测对象选错了**——`refresh` 在 `e0b9f07` 之后已经
   只剩托盘重建（2–14ms），软预算 5s 永远不会触发；真正需要归因的是
   `read_overview`（p90 8.27s，max 31.93s）。

---

**方法论备注**：本次调查的关键转折是用 `ps -M`（每线程真实 CPU 时间）
交叉验证 `sample`（线程存在性采样）——两者结论相反时以前者为准。§6 的
误判撤回即来自这次交叉验证。
