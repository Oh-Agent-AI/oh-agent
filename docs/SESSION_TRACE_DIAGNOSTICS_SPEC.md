## 0. 结论

1. **首发闭环**：发现高消耗 → 定位会话 → 看懂一条可信解释 → 采取一个行动 → 回来看变化。
   本规格覆盖「定位会话之后」的四步；「发现 → 定位会话」由总览穿透规格提供。
2. **aha moment**：「原来主要消耗集中在这一段；我知道发生了什么，也知道下一步该检查什么。」
   不是「轨迹图终于显示出来了」。
3. **三类诊断**，每条都回答四件事——测到了什么（事实）、影响多大、原因确定到什么程度、下一步做什么：
   - 高未命中输入（按证据分为：可能缓存过期 / 紧随模型切换 / 命中下降 / 原因未明）；
   - 单次输入规模增长；
   - 同一调用重复失败。
4. **口径先于诊断**（P0）：回合定义、token 口径、费用口径统一；错误的解释比没有解释更伤信任。
5. 数据源为权威库的标准化投影（`usage_facts` / `workflow_events` / `issue_instances`），前端只渲染。
6. **首发执行环境**：Claude Code 与 Codex。其余执行环境诚实降级，不阻塞主线。

## 1. 背景

### 1.1 现状

会话详情的「会话轨迹图」只画一条 `tool_call_count` 序列：没有基线、没有异常标注、不能下钻。用户
只看到消耗数字，不知道这些消耗发生在哪一段、为什么、该怎么办。

### 1.2 为什么不能把「命中率低」直接说成问题（2026-09-27，本机实测）

按「单次调用命中率 < 50% 且输入 ≥ 10,000 tokens、跳过会话前 2 次调用」筛出的低命中调用，按调用前的
证据归类：

| 会话 | 低命中调用 | 调用前空闲 > 5 分钟（缓存可能已过期） | 紧随模型切换 | 两者都不是 |
|---|---|---|---|---|
| claude-code `c95f7819…` | 18 | 5 | 2 | 13 |
| codex `01a0ba34…` | 127 | 26 | 18 | 91 |

两类解释有重叠（同一次调用可能既在长空闲之后、又紧随模型切换），所以各列不能相减。有预期内解释的
约占 28%（5/18、36/127）；剩下的也只是「原因未明」，不等于「本可避免」。所以诊断必须**把事实与
原因确定度分开表达**，不能一律称为「缓存断裂」。

## 2. 用户问题与本规格的回答范围

| 用户问题 | 本规格如何回答 | 不回答什么 |
|---|---|---|
| 会话中哪一段消耗高？ | 回合级消耗柱 + 区间定位 + 检查器 | — |
| 为什么消耗高？ | 三类诊断，事实与原因确定度分开，附可查看的证据 | 不把相关性当因果 |
| 这些消耗是不是浪费？ | 只给「相关消耗」与可能解释 | **不判定浪费、不给「可节省金额」** |
| 这个会话花了多少？ | 会话与回合级给名义成本（含输出、按调用模型计价、标明非账单，§8.5） | 诊断不给金额；无价卡时写「暂无可用计价依据」 |
| 我现在应该怎么做？ | 每条诊断附建议与代价（§7.5） | 不自动执行任何操作 |
| 优化后有没有改善？ | 标记会话、查看后续同类指标（P2，§9.3） | **不声称改善由某次操作导致** |

## 3. 设计原则

1. **结论先行，证据可查**：诊断卡在上，图与检查器是证据。
2. **事实与原因分开**：事实照实陈述；原因单列并标确定度（有证据 / 可能 / 原因未明），文案随之变化（§7）。
3. **影响不等于浪费**：只说「相关消耗」，不说「多付」「可节省」。
4. **建立在标准化投影上**：只读权威库三张表，不在查询时解析执行环境原始日志；诊断层没有执行环境分支。
5. **诚实降级**：缺数据显示为「未记录」并说明原因（§6.3），绝不画成 0。
6. **成本与安全分开**：安全类发现（SV6xx 危险操作等）单独成块醒目提示，不进入成本诊断清单、不挤占
   其排序。
7. **计算在执行环境侧，几何在前端且只有一份**；x 轴是回合序号；曲线可抽稀，诊断标记与失败标记不抽稀。
8. **出口红线不放宽**：见 §10。

## 4. 口径（P0：先统一，再诊断）

| 口径 | 定义 | 说明 |
|---|---|---|
| 回合 | 由 `workflow_events` 的 `task_started` 界定：一次用户请求到助手完成 | 区间 `[本次 task_started, 下一次 task_started)`，最后一个到会话末尾。只有 0–1 个回合起点、或过半调用早于首个回合起点时，退为「每次助手调用一步」；少量调用早于首回合时补一个前导步，不丢调用（实现：`session_insights::AxisPlan`，三处共用） |
| 助手调用 | `usage_facts` 一行（四个原生执行环境 `observation_kind = assistant-usage`） | 一个回合内可有多次调用 |
| 回合输入消耗 | 回合内所有调用的 `cache_read + cache_write + uncached_input` 之和 | **累计处理量**，不是上下文大小 |
| 单次输入规模 | 一次调用的 `cache_read + cache_write + uncached_input` | 日志口径下的输入规模；回合内取峰值 `input_peak` |
| 命中率 | `cache_read / 单次输入规模`（按调用算；区间命中率 = 区间 cache_read 之和 / 区间输入之和） | 冷启动与缓存过期都会合理地拉低它 |
| 相关消耗 | 诊断区间内的输入 tokens 及其占会话输入的比例 | 不换算金额；不叫「多付」「可节省」 |
| 名义成本 | 每次调用按其模型、路线的官方价计 `cache_read` / `cache_write` / `uncached_input` / `output` 四项之和；回合、会话为求和 | 即 CLAUDE.md 的 `nominal_cost`，不是账单、不扣套餐与折扣，与 `metered_*` 不相加；无价卡的调用不计 0，整体标「暂无可用计价依据」或部分覆盖 |

**G6（P0 前置）**：claude-code 当前每会话只有 1 个 `task_started`（293 个会话共 299 个；会话 `c95f7819…`
在调用树里有 71 轮）。根因：`harnesses/claude_code/sources/workflow.rs` 约 252 行只有第一条用户文本消息触发
`task_started`，`task_finished` 在会话末尾发一次（约 390 行，注释写明为保持既有 event_id 而冻结的历史
语义）。修复为每条用户文本请求开一个回合。event_id 以 offset 派生，新增回合事件不影响既有事件 id，
但既有 `task_finished` 的时点会变，须评估 `workflow_summary` 等消费者并同改；Python 镜像同步。
**不修则 Claude Code 整个会话只有一步，「定位消耗区间」无法成立。**

**已实现（r7）**：判据是 `harnesses::claude_code::sessions::turns::turn_signal`，evidence（SV612、调用树、
UserPrompts 覆盖）与 workflow 共用一份，Python 镜像 `claude_evidence.turn_signal`。首回合沿用历史判据
（event_id 不变）；其后排除 `isSidechain` / `isMeta` / `isCompactSummary`、执行环境回灌（`<task-notification>`、
`<local-command-*>`、`<bash-*>`）与只改设置的斜杠命令；贴图的请求（text + image）算新回合；
`[Request interrupted…` 产 `task_finished{cancelled}`（每回合至多一次）。本机重放：claude 回合
299 → 1,754，取消 86。源日志已被执行环境清理的旧会话无法重放，仍只有首回合，按调用铺开。

### 6.1 位置

`session_trace` 新增 output `insights`（`graph` / `timeline_series` 保留给调用树）。只读权威库。

（不是回合金额之和——逐组取整会累积误差），覆盖所有调用；价格快照最早只到 2026-09-09，更早的调用无
金额并给 `nominal_cost_reason`，不计 0。

本地证据（**不经 MCP**）：Tauri 命令 `session_trace_evidence(session_ref, from, to)` →
`query::session_insights::session_trace_evidence`，返回区间内逐次调用、每次失败的错误/参数摘录与分组键、
安全提醒命令摘要。

### 6.3 可用性与原因

| state | 条件 |
|---|---|
| `available` | 所需数据覆盖率 ≥ 95% |
| `partial` | 0% < 覆盖率 < 95%：未测部分显示「未记录」 |
| `unavailable` | 覆盖率 = 0%：显示「未记录」并附 `reason` |

`reason` 来自会话执行环境注册表的能力声明：`not_recorded_by_harness`（执行环境不记录）/ `not_ingested`（有数据未接入）
/ `no_data_in_session`（本会话恰好没有）。能不能画只看数据；为什么画不了由声明给出。

## 7. 诊断（首发三类）

规则是针对「回合序列 + 事件」的纯函数，放在 `agent-vitals-domain`；阈值集中定义、可配置，**首发阈值以
§11 的标注样本校准后定稿**。

每条诊断分开表达两件事（r6）：

- **事实**：测到了什么，例如「单次输入峰值增长 3.9 倍」「同一调用失败 4 次」。事实本身不带「可能」。
- **原因确定度**：为什么会这样，我们知道多少。取值 `evidence`（本机有可直接查看的证据，如错误摘录）/
  `possible`（有吻合的迹象但未证实）/ `unknown`（当前记录不足以解释）。

r5 的单一 `evidence_strength` 把两者混在一起：「输入增长」是测得的事实，却被标成「较可能」，用户分不清是
增长不确定还是低效不确定。r6 起不再使用该字段。

### 7.1 高未命中输入 `high_uncached_input`

- **事实**：区间内单次调用满足「命中率 < 50% 且单次输入规模 ≥ 10,000」。会话最初 2 次调用不判。
  相邻命中的调用合并成区间。
- **归类（逐次调用判定，区间取占比最高者，其余进 `context_notes`）**：

| `explanation` | 判据 | 原因确定度 | 进入诊断清单？ | 图上 / 检查器文案 |
|---|---|---|---|---|
| `possible_cache_expiry` | 本次调用前与上次调用间隔 > 缓存有效期（默认 5 分钟，按 provider 可配） | `possible` | 否，作为图上说明 | 「本回合前空闲 N 分钟，可能超过缓存有效期（按默认 5 分钟判断，实际取决于服务商）。」 |
| `after_model_change` | 本回合或上一回合有 `model_switched` | `possible` | 否，作为图上说明 | 「此处从 A 切换到 B，可能影响缓存复用。」 |
| `hit_rate_drop` | 同会话此前连续 ≥ 5 次调用命中率 ≥ 90%，随后跌破 50%，且不符合上两条 | `unknown` | 是 | 事实写「命中率从 X 降到 Y」；原因同 `unexplained` |
| `unexplained` | 以上都不符合 | `unknown` | 是 | 「该区间未观察到长时间中断或模型切换，当前记录不足以解释未命中原因。」 |

- **影响**：区间内 `cache_write + uncached_input` 之和（tokens）及其占会话输入的比例。**不换算金额。**
- **不做**：不称「缓存断裂」「多付」「可避免」；不写「间隔短所以不是缓存过期」这类排除式结论——
  间隔短不能单独排除缓存失效；不写「新模型没有可用缓存」这类未经日志证实的断言。

### 7.2 单次输入规模增长 `input_growth`

- **事实**：单次输入规模峰值在连续 ≥ 10 个回合内单调上升，且累计增幅 ≥ 3 倍。文案：「单次调用输入从 A 涨到
  B tokens，这段占本会话输入 P%。」
- **原因确定度**：`unknown`。文案：「尚不能确定是否包含不必要的上下文，也可能是任务本身需要。」
- **状态提示（非问题）**：已知模型上下文窗口时，峰值 ≥ 80% 窗口显示为状态标签「接近上限」，不单独进清单。
- **影响**：增长区间内的回合输入消耗占比。

### 7.3 同一调用重复失败 `repeated_failure`

- **事实**：同一会话内，相同 `invocation_fingerprint` 的 `tool_finished` 失败 ≥ 2 次；或 3 个回合内同一工具
  （`capability_id`）失败 ≥ 3 次。SV611（重复命令）作为佐证并入同一条。文案：「Bash 调用（参数相同）在 3 个
  回合里失败 4 次，错误摘要相同。」
- **原因确定度**：本机能读到错误摘录时为 `evidence`（错误摘要就是可直接查看的证据），否则 `unknown`。
  失败原因分类待 G8；首发不替用户归纳原因，只把错误摘要摆到眼前。
- **影响**：失败次数；这些失败所在回合的输入 tokens（文案「不代表都能省下来」）。

### 7.3a 实现中的调整与已知偏差（r7，待 §11.1 标注校准）

| 项 | 规格原文 | 实现 | 理由 |
|---|---|---|---|
| 调用指纹 | 「相同 `invocation_fingerprint`」 | 指纹改为「工具名 + 规范化参数」（PARSER_VERSION 6）；源日志已清理、无法重放的旧行仍是工具名级，识别后按「未知」处理并计入 `quality.legacy_fingerprints` | 旧指纹只编码工具名，「同一调用重复失败」退化成「同一工具失败过两次」（claude 119 组 → 27 组） |
| 同一调用重复失败 | 失败 ≥ 2 次 | 同指纹的失败相隔 > 5 个回合即切成不同串；回合范围重叠的多组合并为一条（`fact.groups`） | 真机有同一命令相隔 300 回合各失败一次；一个回合里 10 组并列诊断 |
| 同一工具反复失败 | 3 回合内 ≥ 3 次 | 贪心扫出每一段互不重叠的窗口 | 只报最大窗口会漏掉第二段 |
| 输入增长 | ≥ 10 回合、≥ 3 倍 | 另加峰值 ≥ 10 万 tokens；只在回合轴上判；区间起点取最后一个低点 | 上下文随对话累积是常态，按调用铺开时几乎全中；平台期不算增长 |
| 高未命中 | 未写下限 | 区间未命中输入 ≥ 会话输入 1% 才进清单 | 占比 0.09% 的条目对消耗无意义 |
| 模型切换说明 | 本回合或上一回合有 `model_switched` | 本次调用与上一次调用之间换了模型（或其间有 `model_switched`） | 更精确；按回合判会把整回合的未命中都归给切换 |
| SV611 佐证 | 并入重复失败 | 未并入 | SV611 在 Codex 上是 bash 子集判定，与指纹级分组口径不一，待统一 |
| `fact` 扩展字段 | — | `same_invocation`、`groups`（重复失败）、`hit_before` / `hit_after`（命中下降，后者只平均归为下降的调用） | 前端文案需要 |

真机 20 个标注候选（2026-09-28 本机重放）：健康会话 0 条诊断；Codex 上「同一工具 3 回合内失败 3 次」
仍偏多（单会话最多 45 条，界面只展示前 3 条），待标注后调阈值。

### 7.4 诊断条目形状

```jsonc
{
  "kind": "high_uncached_input",          // | "input_growth" | "repeated_failure"
  "steps": { "from": 18, "to": 21 },
  "fact": { "calls": 28, "uncached_tokens": 719000 },          // 按 kind 取字段，见下
  "impact": { "tokens": 719000, "share_of_session_input": 0.059 },
  "explanation": "unexplained",            // 见 §7.1 表；其余种类缺键
  "cause": "unknown",                      // "evidence" | "possible" | "unknown"
  "evidence": ["error_excerpt"],           // 本机可查看的证据种类；MCP 面只给种类，不给内容
  "context_notes": [{ "explanation": "possible_cache_expiry", "calls": 5 }],
  "remedy_id": "inspect-uncached-input"
}
```

`fact` 各种类字段：`high_uncached_input` → `calls` / `uncached_tokens`（`hit_rate_drop` 另有 `hit_before` /
`hit_after`）；`input_growth` → `peak_from` / `peak_to` / `ratio`；`repeated_failure` → `failures` / `steps_hit`
/ `capability_id`。**诊断条目不含金额字段**（r6 移除 r5 的 `estimated_amount`）。

### 7.5 下一步建议（remedy）

复用 `agent-vitals-data::issues::remedy_for` 的目录（Findings 页已在用），新增三项。原型用过的文案：

| `remedy_id` | 建议 | 代价 / 边界 |
|---|---|---|
| `inspect-repeated-failure` | 先弄清这个调用为什么失败，再让助手重试。 | 这几个回合共输入 N tokens，不代表都能省下来。 |
| `review-context-growth` | 看看会话里有没有与当前任务无关的内容；任务确实变了，可以拆成新会话。 | 新开会话会丢掉已有上下文，不建议一律这样做。 |
| `inspect-uncached-input` | 查看这段调用的模型和输入规模有没有变化。 | 不保证能降低消耗。 |

**排序（r6）**：先按原因确定度（`evidence` > `possible` > `unknown`），同级按 `impact.share_of_session_input`
降序；默认展示前 3 条。理由：用户能立刻动手处理的是有证据可看的那条。

## 8. 可视化

交互原型：<https://claude.ai/artifact/L5MvbuuxJLpZv5bwyeLx2G>（私有，示例数据；四个场景：有诊断 / 长会话
420 回合 / 未达提示条件 / WorkBuddy 降级）。本节以原型为准。

### 8.1 布局

**会话摘要 → 紧凑诊断列表 → 联动的轨迹与检查器**。默认选中排第一的诊断，检查器直接展示它的证据。

```
┌ 摘要：执行环境 · 开始 · 时长 · 回合 · 调用 · 输入/输出 · 命中率 · 名义成本（含口径小字）   安全提醒 [4 条 查看] ┐
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
┌ 值得关注 ─────────────────────────────────────────────────────────────── 3 条 · 有直接证据的排前面 ┐
│ ① 同一调用失败 4 次  回合 24–26  [有错误摘要]                                                  ▾ │
│    Bash 调用（参数相同）在 3 个回合里失败 4 次，错误摘要相同。                                     │
│    原因  错误摘要见证据。失败原因分类尚未接入。                                                   │
│    建议  先弄清这个调用为什么失败，再让助手重试。这几个回合的消耗不代表都能省下来。                   │
│ ② 单次输入峰值增长 3.9 倍  回合 6–30  [原因未明]   单次调用输入从 1.8 万涨到 7.1 万…            ▸ │
│ ③ 高未命中输入  回合 18–21  [原因未明]   4 个回合、28 次调用中，未命中缓存的输入 71.9 万…        ▸ │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
┌ 轨迹 ───────────────────────────────────────────────┐ ┌ 检查器（随选择切换，§8.4）────────┐
│ [全程缩略图，仅长会话]                                │ │ 同一调用失败 4 次 · 回合 24–26      │
│ 每回合输入消耗（累计）堆叠柱  ◷ 长空闲后 ◇ 模型切换     │ │ 4 次  相同调用失败                  │
│ 诊断区间底带 ① ② ③                                  │ │ 调用  Bash · npx vitest run …       │
│ 单次输入峰值 折线                                     │ │ 错误摘要（仅本机）                   │
│ 工具结果 竖条                                         │ │ [查看一次失败] [查看相关调用]        │
│ 回合 1 ─────────────── N                              │ │ 失败列表 · 建议                     │
└─────────────────────────────────────────────────────┘ └────────────────────────────────────┘
```

- 诊断列表每条默认一行标题 + 一行事实；**只展开当前选中的一条**（原因 + 建议）。不靠缩小字号塞信息。
- 安全提醒放在摘要栏右端（数量 + 查看），与成本诊断分开，不占诊断名额。
- 轨迹与检查器左右相邻；面板宽 ≤ 820px 时（按**容器**宽度判断，不按视口——会话详情在工作台里是
  约 460px 的侧栏）检查器紧随轨迹之下。r6 设想的底部悬浮抽屉不采用：面板本身在侧栏里，fixed 定位会
  盖住会话列表。
- 无诊断时：「在当前可分析的数据中，未发现达到提示条件的消耗异常。」下一行列检查范围（三类诊断）与
  「未达到提示条件」的记录（如失败回合、长空闲），这些仍标在轨迹上。不写「没有持续增长」这类强结论。

### 8.2 编码

| 元素 | 编码 | 说明 |
|---|---|---|
| 每回合输入消耗 | 堆叠柱（缓存读取 / 缓存写入 / 未缓存输入） | 标「累计」，**不标为「上下文」**；执行环境不报告的桶在图例标「执行环境不报告」，不画成 0 |
| 单次输入峰值 | 独立一行折线 | 跨长空闲断开 |
| 命中率 | 不画常驻折线；在检查器与诊断中给出 | 避免与消耗柱争夺注意力 |
| 诊断区间 | 柱下方底带，编号与诊断列表对应；`evidence` 实线，`possible` / `unknown` 虚线 | 颜色按种类：失败红、未命中橙、增长墨色 |
| 说明性标记 | ◷ 长空闲后、◇ 模型切换，灰色小图标标在对应回合柱顶 | 不进诊断清单 |
| 工具 | 每回合竖条：成功 / 取消 / 失败（红 + 斜纹，色弱可读） | 缺数据整行斜线底纹 +「未记录 · 原因」 |
| 回合结果 | 横轴上的点：失败实心红点、取消空心点 | — |
| 空闲 | 回合间隔 > 30 分钟折叠为缝隙并标「空闲 N 分」 | — |

### 8.3 长会话

回合数超过「每柱至少约 10px」可容纳的数量时：

- 最小柱宽 7px（r7；原 ~10px 在工作台约 460px 的详情侧栏里 40 个回合就要开窗口）。
- 主图只显示一个窗口；顶部加**全程缩略图**（按像素聚合，取窗口内最大值，未命中占比 > 50% 的列用警示色；
  诊断区间在缩略图底部标出），点击或拖动选择窗口。
- 提供「上一处 / 下一处诊断」；选中诊断或回合时窗口自动移到能看见它的位置。
- 窗口外的诊断区间在底带两侧显示方向标记（`‹ 3` / `2 ›`）。
- 诊断标记与失败标记不抽稀（沿用 §3 原则 7）；缩略图可以聚合。

### 8.4 检查器

主内容随选择变化，回答当前选择对应的问题，而不是每次都把命中率放最大：

| 当前选择 | 首要展示 | 其次 | 动作 |
|---|---|---|---|
| 重复失败 | 失败次数 | 调用与参数摘要、错误摘要（仅本机）、每次失败列表、建议 | 查看一次失败 · 查看相关调用 |
| 输入增长 | 增长倍数 | 起止峰值（带回合号）、区间调用数、占比、峰值小折线、原因、建议 | 查看峰值最大的回合 · 查看逐次调用 |
| 高未命中输入 | 未命中输入 tokens | 区间命中率 vs 会话其余部分、逐回合（空闲时长、模型、命中率）、原因、建议 | 查看逐次调用 |
| 普通回合 | — | 输入/输出、调用数、峰值、命中率、模型、结果、名义成本、四个桶、工具结果、该回合的失败（可点开） | 查看逐次调用 |
| 一次失败 | 工具与错误摘录 | 参数摘要、退出码、时间 | 查看该回合 · 查看调用树 |
| 逐次调用 | 调用表（模型、输入、命中、输出，低命中与失败行高亮） | — | — |
| 安全提醒 | 规则、命令摘要、所在回合 | — | 点击定位到回合 |

- 下钻有「返回」，形成一条可回退的路径；「查看调用树」进入既有 `TraceGraph` 视图。
- 错误摘录、参数摘要、命令摘要旁固定标注「仅在本机显示，不进入导出和 MCP」（§10）。

### 8.5 金额

- 摘要与普通回合检查器显示**名义成本**（`nominal_cost`）：按每次调用对应的模型、路线与官方价计算，**含输出**，
  小字写明「按调用模型的官方价估算，含输出，非账单」。
- 无可用价卡时写「暂无可用计价依据」，不按执行环境名推断计费方式（如不写「积分计费」）。
- 诊断条目与诊断检查器**不显示金额**；不出现「比全部命中多约 $X」「可节省」一类表述。

### 8.6 交互与可访问性

- 点击诊断行 → 展开该行、选中区间、窗口移到区间、检查器显示该诊断的证据。
- 点击 / 键盘选中任一回合 → 检查器；左右键逐回合移动；Esc 回到当前诊断。
- 每条泳道与诊断有文字摘要，屏幕阅读器可不看图获得同样结论。
- 不引用在线字体或其他外部资源（离线产品）；等宽数字用系统字体栈。

## 11. 验收

### 11.1 人工标注样本（阈值校准与误报检查）

- 从本机 Claude Code 与 Codex 会话中挑选约 20 个候选，附证据摘要（不含内容），由产品负责人逐个判定
  「正常 / 值得关注」及理由。
- 必须覆盖：冷启动、长空闲后继续（缓存过期）、主动取消、正常的大上下文任务、模型切换、重复失败、
  持续高命中的健康会话。
- 标注结果去标识后固化为 fixture；阈值（§7）按其校准：
  - 标为「正常」的会话，不得出现任何诊断条目（◷ ◇ 这类说明性标记不算）；
  - 标为「值得关注」的会话，前 3 条诊断须覆盖标注者给出的原因。

### 11.2 产品验收（可用性测试）

- 用户能否从总览独立找到值得关注的会话？
- 能否解释「输入多」「名义成本」和「实际账单」的区别？
- 能否分清一条诊断里哪部分是测到的事实、原因确定到什么程度？
- 选中「重复失败」后，能否在不翻找的情况下看到错误摘要？
- 能否根据建议选出一个合理的下一步？
- 冷启动、主动取消、正常的大上下文任务、长空闲后继续，是否被误报为问题？

### 11.3 技术验收

- domain 单测：回合区间落点（边界、同毫秒次序、早于首回合、无回合退化）；三类诊断的触发 / 不触发边界；
  解释归类（空闲、模型切换、基线下降）；原因确定度映射；排序（确定度优先，同级按占比）。
- data 查询走索引：`usage_facts_session_time`（带 `deleted_at_ms IS NULL`）、`workflow_events_session_time`；
  `EXPLAIN QUERY PLAN` 断言无全表扫描。
- 口径一致：同一会话的输入 tokens 与费用在总览、用量页、会话详情三处相等（测试钉住）。
- 出口：`insights` 序列化结果不含摘录、指纹、路径模式与原生会话 id。
- 前端契约：`unavailable` 按 `reason` 渲染；点击诊断选中正确区间并把窗口移过去；检查器按 §8.4 切换；
  诊断条目与诊断检查器不出现金额；消耗柱不标「上下文」；长会话（≥ 400 回合）缩略图与窗口可用；不发起任何
  外部资源请求；生产打包条件下几何可用（沿用 `572a078` 的检查方式）。
- 名义成本：模型切换的回合按每次调用各自的模型计价；含输出；与总览同一会话的名义成本相等。
- G6：claude-code fixture 含多条用户请求，产出同数量的 `task_started`；既有事件 id 不变；Python 镜像同步。
