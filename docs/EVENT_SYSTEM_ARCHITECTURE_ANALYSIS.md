# 事件系统架构全景分析

> 从标准事件系统架构维度审视 agent-vitals 的事件基础设施（2026-09-21）。
> 基座：已建成的事务性 outbox + 事件总线（`AGENT_VITALS_EVENT_BUS_ARCHITECTURE_SPEC.md` v1.5）+ SourceGraph 检查点。
> 视角：不是"还差什么"，而是**从标准架构看，这套系统的正确形状是什么、哪些缺口值得补、哪些缺口不值得**。

---

## 一、事件系统的五层标准架构

```
┌───────────────────────────────────────────────────────────────────┐
│ ⑤ 消费层（Reaction）                                              │
│    派生重算 · 缓存失效 · 通知 · 审计 · UI 推送                     │
├───────────────────────────────────────────────────────────────────┤
│ ④ 路由层（Routing）                                               │
│    类型路由 · 优先级 · 背压 · 死信 · 重试                          │
├───────────────────────────────────────────────────────────────────┤
│ ③ 投递层（Delivery）                                              │
│    at-least-once · 消费者幂等 · 顺序保证 · 追赶                   │
├───────────────────────────────────────────────────────────────────┤
│ ② 存储层（Persistence）                                           │
│    事务性 outbox · 事件日志 · 保留策略 · 模式演进                  │
├───────────────────────────────────────────────────────────────────┤
│ ① 事件分类（Taxonomy）                                            │
│    领域事件 · 集成事件 · 通知事件 · 基础设施事件                   │
└───────────────────────────────────────────────────────────────────┘
```

## 二、逐层评估：已实现 vs 标准

### ① 事件分类（Taxonomy）

| 维度 | 标准做法 | 现状 | 评价 |
|---|---|---|---|
| 领域事件 | 业务事实的过去时陈述 | ✓ FactsIngested、DeclarationSaved、PriceCardSaved | 正确 |
| 集成事件 | 跨系统边界的通知 | ✓ McpToolInvoked（审计旁路） | 正确 |
| 通知事件 | 触达用户的信号 | ✓ TrustMonitorEvent | 正确 |
| 基础设施事件 | 时间/健康/维护信号 | ○ HourTicked/DayRolled 保留位（分析裁决不发射） | 合理 |
| **事件分级** | 按业务关键性分级（critical/normal/audit） | ○ 所有事件同级——优先级丢弃有 audit < maintenance < derived < notification，但这是投递层的，不是分类层的 | **缺口小，影响低** |
| **事件溯源 vs 通知** | 事件是状态（sourcing）还是状态的通知（outbox） | ✓ 明确选择了 outbox（权威库是真相源，事件是通知） | 正确且重要 |

**结论**：分类层基本完整。缺的"事件分级"在当前规模（单用户桌面、消费量 <100/天）不值得引入。

### ② 存储层（Persistence）

| 维度 | 标准做法 | 现状 | 评价 |
|---|---|---|---|
| 事务性写入 | 事件与状态变更同事务 | ✓ `insert_outbox` 在调用方事务内，不开自己的事务 | 教科书正确 |
| 事件日志 | 事件可回放 | ✓ outbox 表 + ingested_run_id 关联，保留 7 天 | 正确 |
| 保留策略 | 按事件类型差异保留 | ○ 统一 7 天——关键事件（DeclarationSaved）保留太短，审计事件（McpToolInvoked）可能要更长 | **缺口中等** |
| 模式演进 | 字段只增不删、消费者容错 | ✓ schema_version + 前向兼容（词表外类型跳过+计数） | 正确 |
| **事件发现** | 消费者能查询"有哪些事件类型可用" | ○ 词表是代码常量，运行时不可查询 | **缺口小**——单进程桌面 app 无需动态发现 |

**结论**：存储层是本系统最扎实的部分。保留策略差异化和事件发现是未来扩展点，但当前不阻塞。

### ③ 投递层（Delivery）

| 维度 | 标准做法 | 现状 | 评价 |
|---|---|---|---|
| 语义 | at-least-once + 消费者幂等 | ✓ `(event_id, consumer_id)` 幂等键 | 正确 |
| 顺序 | 同类型有序，跨类型不保证 | ✓ 按 `occurred_at_ms` 排序 | 明确声明 |
| 崩溃恢复 | 未投递事件下次扫描 | ✓ 反连接 + tailer 补投 | 正确 |
| **消费者组** | 同一消费者的多个实例竞争消费 | ○ 单消费者——桌面 app 单进程，不需要 | **合理不补** |
| **事件携带状态** | 事件带足数据，消费者不需查库 | 部分——FactsIngested 带计数，消费者仍需查库做重算 | **风格选择，非缺口**——查库保证一致性 |
| **追赶机制** | 新消费者注册后从起点回放 | ○ 消费者注册时只处理新事件，不回放历史 | **架构上正确**——outbox 不是 event sourcing |

**结论**：投递层完整。消费者组和回放不适用于 outbox 模式。

### ④ 路由层（Routing）

| 维度 | 标准做法 | 现状 | 评价 |
|---|---|---|---|
| 类型路由 | 按事件类型分发给订阅者 | ✓ 闭集词表 + per-consumer 反连接 | 正确 |
| 优先级 | 高优先级事件不被低优先级阻塞 | ✓ bounded channel + 优先级丢弃（audit < maintenance < derived < notification） | 正确 |
| **背压** | 消费者慢时生产者减速或缓冲 | ○ 单进程同步调用，无异步管道——没有背压问题 | **合理不补** |
| **死信队列** | 处理失败的事件进入专门队列供人工干预 | ○ 失败记 last_error 但不重试——`failed_handler_records_error_and_does_not_retry` 钉住此语义 | **缺口中等**——消费者失败后自愈依赖"下一个同类事件"，如果事件稀少（月度声明），失败后可能长时间无自愈 |
| **重试策略** | 指数退避、最大重试次数 | ○ 不重试（设计决策：消费者幂等 + 下一个事件自愈） | 与死信是同一个缺口的两面 |

**结论**：死信/重试是标准架构里本系统**最大的真实缺口**。当前"失败不重试"在事件频繁（FactsIngested 每 tick 一条）时是安全的，但在事件稀少时（DeclarationSaved 可能一个月一次）会造成长时间无自愈。

### ⑤ 消费层（Reaction）

| 维度 | 标准做法 | 现状 | 评价 |
|---|---|---|---|
| 派生重算 | 事件驱动 materialized view 刷新 | ✓ price-reconcile、配额扫描、预算重估 | 正确 |
| 缓存失效 | 事件驱动缓存标记失效 | ✓ desktop-ui → app-event → webview 刷新 | 正确 |
| 通知 | 事件触发系统通知（带去重） | ✓ trust 报警（§7.2 门槛 + 24h 去重） | 正确 |
| 审计 | 事件本身作为审计日志 | ✓ McpToolInvoked 进 outbox（可查） | 正确 |
| **Saga / 流程管理** | 多步骤编排（事件 A → 动作 B → 事件 C） | ○ 无——多步骤通过 tick 顺序保证，不是事件链 | **合理不补**——tick 是 pipeline，不是 saga 场景 |
| **CQRS 读写分离** | 写模型产事件，读模型消费事件 | 部分——权威库是写模型，summary 是读模型，但读模型直接查库不是事件驱动投影 | **风格选择**——当前查询延迟可接受 |

## 三、标准架构的四个关键决策（本系统的回答）

### 决策 1：Event Sourcing vs Outbox

| | Event Sourcing | Transactional Outbox | 本系统 |
|---|---|---|---|
| 真相源 | 事件流 | 数据库 | **数据库** |
| 事件角色 | 状态本身 | 状态变更的通知 | **通知** |
| 回放 | 天然支持 | 需要额外设计 | 不回放（幂等重放替代） |
| 复杂度 | 高（需事件存储 + 投影） | 低（利用现有数据库） | **低** ✓ |

**回答：Outbox。** 权威库是唯一真相源（spec §1.1），事件是"权威库已前进"的通知。这是单用户桌面 app 的正确选择。

### 决策 2：推 vs 拉

| | 推（Push） | 拉（Pull） | 本系统 |
|---|---|---|---|
| 时延 | 低（事件即达） | 高（消费者轮询） | 混合 |
| 可靠性 | 丢推送需兜底 | 天然可靠 | 混合 |
| 复杂度 | 高（需管理连接） | 低 | **低** ✓ |

**回答：拉为主、推加速。** outbox 表是拉模型（drain 主动扫描），进程内通道是推模型（hook 叫醒）。崩溃恢复靠拉（重扫 outbox），低延迟靠推（mpsc 通道）。双通道并存是标准做法（apalis-sqlite 验证）。

### 决策 3：单一事件总线 vs 多通道

| | 单一总线 | 多通道 | 本系统 |
|---|---|---|---|
| 简单性 | 高 | 低 | — |
| 隔离性 | 低（一个消费者慢影响所有） | 高 | — |
| 适用 | 小规模 | 大规模 | — |

**回答：单一总线 + 类型路由。** 单用户桌面 app、消费者 <10 个、事件量 <100/天——单一总线的简单性远大于多通道的隔离需求。

### 决策 4：同步 vs 异步消费

| | 同步（dispatch 内联） | 异步（channel/thread） | 本系统 |
|---|---|---|---|
| 时延 | 低 | 高 | — |
| 错误传播 | 消费者失败影响生产者 | 隔离 | — |
| 顺序 | 强 | 弱 | — |

**回答：同步消费 + 事务外。** drain 在自动提交模式逐事件调 handler（同步），但 handler 自持连接（异步于 drain 的数据库连接）。这是"同步调用的异步语义"——简单且有崩溃恢复。

## 四、真实缺口排序（按补的价值）

| # | 缺口 | 标准 | 本系统实际影响 | 补的价值 | 建议优先级 |
|---|---|---|---|---|---|
| 1 | **死信/重试** | DLQ + 指数退避 | 稀疏事件失败后无自愈（DeclarationSaved 月一次） | 高——丢一次声明保存的重算可能延迟一个月 | **P1（应补）** |
| 2 | **保留策略差异化** | 按类型差异保留 | 审计事件 7 天太短（安全审计惯例 90 天+） | 中——合规需求驱动 | P2（应补） |
| 3 | 事件分级 | critical/normal/audit | 当前规模无实际影响 | 低 | P3（不急） |
| 4 | 事件发现 | 运行时可查词表 | 单进程不需要 | 极低 | 不补 |
| 5 | 消费者组 | 竞争消费 | 单进程不需要 | 极低 | 不补 |
| 6 | Saga/流程 | 多步骤编排 | tick 已是 pipeline | 极低 | 不补 |

**缺口的补法**：

### 缺口 1（死信/重试）的最小正确方案

```sql
-- 不建独立 DLQ 表——outbox 已有 last_error，缺的只是"该重试"的标记
ALTER TABLE event_deliveries ADD COLUMN retry_count INTEGER NOT NULL DEFAULT 0;
ALTER TABLE event_deliveries ADD COLUMN next_retry_at_ms INTEGER;
```

```rust
// drain 的反连接扩展：到期重试的失败行也算"未投递"
WHERE NOT EXISTS (... d.consumer_id = ?1 ...)
   OR (d.last_error IS NOT NULL AND d.retry_count < 3
       AND COALESCE(d.next_retry_at_ms, 0) <= ?now)
```

### 缺口 2（保留差异化）的最小正确方案

```rust
// retention_event_outbox 按事件类型差异保留
const RETENTION_BY_TYPE: &[(&str, i64)] = &[
    ("McpToolInvoked", 90 * DAY), // 审计面 90 天
    ("DeclarationSaved", 30 * DAY), // 计费关键 30 天
    ("FactsIngested", 7 * DAY),     // 高频 7 天
];
```

## 五、已建成系统的架构强项（不要在演进中丢失）

1. **事务性保证**——事件永远不脱离状态变更事务（outbox 的核心纪律，§1.2）；
2. **单一 UI 出口**——webview 只 listen 一个 `app-event`，类型在 payload 里判别（§1.3）；
3. **闭集词表**——写入与投递双侧校验，词表外类型跳过+计数（§1.6）；
4. **消费者幂等键**——`(event_id, consumer_id)` 双主键，重复投递 no-op（§1.7）；
5. **权威库是真相源**——事件是通知不是状态，回放不适用（outbox 正确性）；
6. **负面清单**——tick 编排、MCP RPC、billing golden、doctor 纯函数永不上总线（§7）。

这六条是系统的**架构脊柱**——任何演进（加消费者、加事件类型、加通道）都不应违背。

## 六、终极形态（如果所有缺口都补齐）

```
┌─ 事件分类 ────────────────────────────────────────────────────────┐
│  领域事件（FactsIngested, DeclarationSaved, PriceCardSaved）        │
│  集成事件（McpToolInvoked）                                        │
│  通知事件（TrustMonitorEvent）                                     │
│  保留位（HourTicked, DayRolled — 有消费者时激活）                   │
├─ 存储 ────────────────────────────────────────────────────────────┤
│  event_outbox（事务性，类型差异化保留：审计90d/关键30d/高频7d）      │
│  event_deliveries（幂等键 + retry_count + next_retry_at_ms）       │
├─ 投递 ────────────────────────────────────────────────────────────┤
│  双通道：mpsc（低延迟）+ outbox tailer（可靠性）                    │
│  at-least-once + 消费者幂等 + 失败重试（指数退避，最多 3 次）        │
├─ 路由 ────────────────────────────────────────────────────────────┤
│  闭集词表 + 优先级丢弃 + 死信（重试穷尽后 last_error 永久标记）      │
├─ 消费 ────────────────────────────────────────────────────────────┤
│  派生重算扇出 · 缓存统一失效 · 通知（去重窗口） · 审计日志           │
└───────────────────────────────────────────────────────────────────┘
```

这就是本系统事件架构的**完整正确形状**——不是 Kafka，不是 Event Store，而是一个**单用户桌面 app 的微型事件基础设施**：利用 SQLite 做可靠存储、利用进程内通道做低延迟投递、利用闭集词表做类型安全、利用消费者幂等做 at-least-once 语义。
