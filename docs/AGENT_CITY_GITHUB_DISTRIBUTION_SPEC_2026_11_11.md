# City 独立仓库与 GitHub 发行规格

状态：架构提案，2026-11-11；不表示在线市场或动态插件安装已经实现。关联 [City SDK 内容 MVP](AGENT_CITY_SDK_CONTENT_MVP_SPEC_2026_11_11.md)、[官方插件接入指南](OFFICIAL_PLUGIN_INTEGRATION_GUIDE.md) 和仓库 `AGENTS.md` 数据政策。

## 1. 目标与产品模型

让官方 Agent City 可以在独立 GitHub 仓库开发、测试和发布；开发者也可以在自己的仓库维护 City 世界、小游戏和资源。Oh Agent 提供发现、安装和运行所需的宿主能力。GitHub 托管源码、发布文件和索引，不自动提供商品审核、作者身份保证、支付、权益或应用沙箱。

区分两种交付：

| 对象 | 包含 | 执行方 | 发行要求 |
|---|---|---|---|
| City World / Mini-game 内容包 | 数据、声明式规则及允许的模型资源 | 已安装、可信 City runtime | schema、资源和摘要校验；来源信任和用户安装决定另行处理 |
| City App Plugin | WebView 应用代码及描述符，官方 City 本身属于此类 | Oh Agent 应用宿主 | 版本兼容、签名、安装、进程身份、隔离、权限及更新回滚；第三方安装尚未具备 |

内容作者可通过已注册生成器创建风格不同的 City，而自带新生成器或脚本运行时代码的 City 属于应用代码包，其发行不能继承内容包的信任。

## 2. 仓库与依赖方向

建议目标形态：

- `oh-agent`：桌面宿主、数据权威、权限 broker、安装注册表、官方索引信任根、App SDK 稳定契约及兼容测试。
- `agent-city`：官方 City WebView、世界生成器、玩法运行适配、官方资源及其发布流水线；依赖固定版本的公开 App SDK 和 City SDK。
- `city-sdk`：City 内容 schema、CLI、纯规则运行器、校验与测试向量。初期可留在主仓，待版本契约稳定后独立发行；即便独立也不得反向依赖官方 City 源码。
- `city-examples` 或开发者自己的仓库：仅依赖发布的 SDK，维护 world/game 源码和包。
- 官方目录仓库：经过审核的索引与版本记录。开发者仓库是发行源，加入官方目录由维护者审核；可查看未收录仓库的能力不等同官方背书。

实际名称和组织待定。分仓不要求 City 成为独立桌面程序，官方 City 仍作为 Oh Agent 内嵌 App Plugin 使用。仓库分离、独立构建、独立发布和客户端动态安装是四个不同里程碑；先做到前两项即可让代码独立维护。

## 3. 官方 City 解耦路径

1. 清点 `apps/agent-city` 对主仓源码、脚本、生成文件、fixture、构建路径和 Rust 私有 IPC 的依赖；逐一迁移到版本化 SDK、插件描述符或 City 自有代码。City 保持既有数据授权，不扩展数据集或远程传输。
2. 在当前仓库先建立可移植构建入口：依赖锁文件、固定 Node 版本、SDK tarball/registry 版本、构建产物清单与合成数据开发宿主；禁止通过相对路径 import 主仓私有模块。
3. 独立仓库 CI 从固定 SDK 版本构建 City 资源和 descriptor，运行 SDK 契约、生成器、驾驶、隐私边界测试；主仓 CI 以精确 commit 与 digest 获取已审核产物，验证兼容后将其编入官方桌面 bundle。当前内置插件注册与 WebView 生命周期保持现有模式。
4. 主仓使用版本锁文件记录 City 版本、来源 commit、产物 digest 和 SDK 兼容范围；构建不得跟随移动的分支或 `latest`。升级经 PR 更新锁文件，保留可回退的已验证版本。仓库拆分前后用相同输入比较布局、驾驶、数据投影和资源结果，记录必要差异。
5. 后续单独立项动态安装/更新 App Plugin；只有应用层身份、签名、sandbox、broker 和授权门槛通过后，才允许客户端从 GitHub 下载并运行新的 City 应用代码。仓库独立本身不提供这些能力。

迁移以先复制建立独立构建、主仓对照验收、再切换构建输入的顺序进行；删除旧目录前必须确认 CI、发布、许可证、资产归属、故障回滚和数据迁移，避免两处源码长期同时作为权威。当前分支尚未完成上述迁移。

## 4. GitHub 内容发布与市场

内容作者通过 SDK 创建 world/game 项目，CI 使用固定依赖版本执行校验、测试和打包，将不可变版本的内容产物及 manifest 发布到 GitHub Release；记录源码 commit、产物 digest、SDK/City runtime 兼容范围、许可证、预览和作者声明。tag 和 Release 可被仓库维护者修改，因此客户端必须验证由可信目录或明确的用户信任决定提供的预期 digest；仅从同一未认证仓库读取包和 digest 只能检查传输完整性，不能验证作者身份。

目标发现流程：开发者提交目录条目 → 审核内容和来源 → 官方目录发布带版本、包 digest、具体 commit/Release 地址、签名或可信元数据的条目 → 用户在 Shop 中查看 → 分别同意下载和安装 → 宿主验证并安装 → City 创建实例或绑定游戏。商品页展示来源、作者声明、权限/内容类型、兼容范围、版本和最后审核状态；下架或撤销后禁止新的安装/更新，并提示已安装用户，保留本地实例与恢复路径。目录审核并不等于对玩法或外部作者的绝对安全保证。

MVP 可先由创作者把 GitHub Release 文件自行下载到本地，再走原生文件选择器导入；此时 GitHub 是发布渠道，本机不具有在线市场。下一阶段再增加用户主动查看的官方目录及下载。单独用户添加任意 GitHub 仓库、社区自动收录、支付、评论与分成均需独立产品和信任决议。

## 5. 网络、信任和安装边界

现行 `AGENTS.md` 允许显式选择的官方应用索引及固定公开 HTTPS 来源的签名包下载，并要求安装满足签名、进程身份、沙箱和授权门槛；它不自动授权从任意第三方 GitHub 地址下载或允许通用内容包联网分发。在线内容市场上线前，必须先作明确产品与安全决议，按实际来源、内容类型和用户动作修订该政策并完成审查；在此之前仅支持用户自行下载后本地导入。GitHub 登录、公开仓库或 HTTPS 不能替代发布者认证。

在线方案须明确：可信目录根密钥、密钥轮换与撤销；目录版本单调性及防回滚；包签名如何绑定发布者、包 ID/version/digest 和类型；仓库转移、删除或作者密钥泄露时的处置；固定 HTTPS 来源、重定向限制、下载上限和内容校验；离线时沿用已验证目录或清晰降级。数据型包仍须执行资源预算和解析器约束；可执行应用还必须通过独立应用的签名、平台进程身份、沙箱及逐请求授权，不能因为目录通过审核而提升权限。

下载、安装、数据授权分别取得用户决定。远端请求不得携带本地日志、用户分析数据、机器标识、凭据或授权信息；不得添加追踪或后台同步。卸载、回滚、运行中版本固定、包依赖和缓存清理沿用内容 MVP 的引用保护与原子事务要求。GitHub 速率限制、目录不可用、包删除、摘要不匹配或签名撤销均要明确提示并保持已安装实例可恢复。

## 6. 验收里程碑

1. **独立源码构建**：官方 City 在干净 checkout 使用发布的 SDK 构建，无主仓私有路径；合成数据可运行，契约和关键行为测试通过。
2. **官方 bundle 消费**：主仓 CI 使用固定 City commit/digest 构建客户端；客户端完成 City、数据授权、活动、现有用户数据和回滚验收。
3. **GitHub 内容交付**：外部示例仓库生成 world/game v2 完整包并发布；用户自行下载后导入两个 City 实例，跨城市绑定并完成试玩。篡改、缺资源、版本不兼容均失败且不破坏既有安装。
4. **在线官方目录**：先完成政策修订与信任模型；目录签名/撤销、防回滚、下载与安装分别确认、断网和失效处理均通过，才上线 Shop 在线发现。
5. **独立 App Plugin 安装**：按单独的应用平台规格完成签名、系统进程身份、沙箱、权限 broker、升级/回滚和对抗验证，再验证官方 City 作为首个可独立安装的应用。不得用第 3 项内容包结果替代此验收。

## 7. 参考 DSH 的静态目录方案

参考 [DSH 官方插件索引](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/guide/plugin-market.md)：开发者维护独立源码和发布产物；目录维护者发布静态 JSON；发现界面展示版本与来源；安装交由宿主完成。参考 [DSH Marketplace 社区项目](https://github.com/ydhrdh/dsh-marketplace) 的逐条元数据、PR 审核、CI 校验和静态网站模式。两者为不同主体；DSH 官方自定义索引在其文档中属于实验功能，社区项目的审核标记由其维护者定义。

### 7.1 目录仓库与数据流

```text
开发者仓库 → SDK 校验及构建 → 固定版本 Release 内容包
                                      ↓
目录仓库的条目 PR → CI 校验 / 人工审核 → 静态 index.json
                                      ↓
                         Oh Agent Shop 浏览与选择
                                      ↓
             用户确认下载 → 宿主校验 → 用户确认安装 → 本地内容库
                                      ↓
                      City 选择世界 / 绑定游戏 / 试玩
```

建议目录仓库使用 `entries/<publisher>/<package-id>.json`、`schema/`、`scripts/` 和 `.github/workflows/`。CI 检查条目 schema、ID 唯一性、固定版本、来源、许可信息、兼容范围、产物摘要及链接可用性，生成确定性的 `index.json`。CI 检查不代表代码审计、真实安装或试玩；目录审核记录必须标明已做的检查及时间。市场 WebView 只展示目录和调用宿主允许的方法，不直接执行安装命令或运行从仓库获取的脚本。

### 7.2 索引契约草案

索引是展示与发现元数据，不是安装凭据的唯一信任根。以下字段为拟定概念，冻结 schema 前确定长度上限、国际化和兼容规则：

```json
{
  "formatVersion": 1,
  "catalogId": "official-city-catalog",
  "sequence": 1,
  "generatedAt": "2026-11-11T00:00:00Z",
  "entries": [{
    "kind": "city-world",
    "packageId": "example.desert-city",
    "publisherId": "example",
    "title": "Desert City",
    "repository": "https://github.com/example/desert-city",
    "versions": [{
      "version": "1.0.0",
      "sourceCommit": "<full-commit-id>",
      "artifactUrl": "https://github.com/example/desert-city/releases/download/v1.0.0/desert.ohcity",
      "artifactSha256": "sha256:<64-lowercase-hex>",
      "sdkContract": "<supported-range>",
      "cityRuntime": "<supported-range>"
    }]
  }]
}
```

这是字段示意，尖括号不是合法发布值。正式 schema 必须涵盖 `city-world`、`city-minigame` 和未来 `app-plugin` 的明确区分、来源与审核状态、文件大小、许可证、撤销信息及签名元数据；不能以 JSON 中自报的 publisherId 或仓库 URL 证明发布者身份。版本固定完整 commit 与产物 digest，不能把 branch、tag 或 `latest` 当作不可变内容。先建立官方单一目录；自定义目录和多目录冲突规则另行设计。

### 7.3 分阶段采用

- **先实现**：开发者独立仓库、SDK 构建可移植内容包、PR 审核静态目录，以及用户自行下载后通过本地文件选择器导入。目录网页可独立浏览，Shop 在线接入不作为此阶段完成条件。
- **再实现**：政策调整和信任根、签名/撤销、防回滚、下载范围与隐私审查完成后，官方 Shop 显示目录并通过宿主下载和安装。下载、安装和数据授权分别确认；索引损坏或下载失败时保留已安装内容。
- **单独实施**：官方 City 及第三方 App Plugin 的独立代码包安装，需要应用层进程身份、沙箱、签名、授权及更新链路；与声明式内容包分类、验证和权限分开。

验收除第 6 节外，增加：目录从固定输入可重复生成；重复 ID、无效 URL、移动引用、缺摘要、恶意路径和不兼容版本均拒绝；目录展示的版本/摘要与宿主实际安装结果一致；目录撤销、版本回滚、离线与 GitHub Release 被替换时符合第 5 节策略。可浏览和索引生成不等于安装成功或官方安全背书。
