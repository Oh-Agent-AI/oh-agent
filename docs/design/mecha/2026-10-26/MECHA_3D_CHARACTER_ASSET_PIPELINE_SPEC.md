# Oh Agent City 3D 角色资产创建方案

**状态：** 执行方案（先试制、通过验收后扩展到全阵容）
**版本：** 1.1（对齐现有程序模型代码：关节映射、清单驱动的动作时长、draw call/整场景预算、资产存储、16 米格尺度核对）
**日期：** 2026-10-26
**适用范围：** Agent City 机甲战棋角色模型、战斗动作和预览资产

## 1. 目标

建立一条从角色概念稿到游戏内可用角色资产的可重复管线。成品需要同时满足：

1. 保留五种角色的独特剪影和统一的工业机械语法。
2. 在 16 米战场格、当前镜头距离和昼夜光照下易于辨认。
3. 关键装甲、关节、武器和功能设备具有合理的机械连接关系。
4. 能播放待机、移动、攻击、受击、维修和倒地等动作，不穿插、不漂脚。
5. 文件大小、网格数、材质数和绘制调用符合桌面端实时渲染预算。
6. 动画表现只呈现已由战斗规则接受的行动，不改变命中、伤害或胜负判定。

本方案不把“AI 一键生成”作为交付标准。AI 生成的模型是建模初稿，必须经 DCC 整理、动作验证和游戏内验收后才能合入。

## 2. 角色阵容与视觉契约

五个角色共用以下设计约束：

- **三层机械结构：** 深色承重骨架、可见的中间关节和传动件、大块低多边形外装甲。
- **阵营与职业分离：** 职业保留自身主色；我方在固定部位使用青蓝标记 `#4FD8FF`，敌方使用珊瑚红 `#FF5C72`。靠轮廓、徽记和标记形状辅助识别，不只靠颜色。
- **材质层级：** 涂装装甲、裸露金属骨架、橡胶/复合材料关节、少量能源或传感器发光件。
- **细节原则：** 先保证轮廓、结构与动作可读，再添加编号、警示标、磨损。避免用噪点、密集刻线或发光边条替代结构设计。
- **比例和落点：** 保持项目单位约定、角色占格、朝向和脚底接地基准；导入模型不能私自改变战场规则坐标。
- **安全区：** 武器、天线、镰肢等超出躯干的部件应在完整动作范围内保持可读，避免遮住角色身份特征。

| 角色 | 战场占格 | 必须一眼识别的造型符号 | 主要活动部件 |
|---|---:|---|---|
| 突击 Assault | 1×1 | 巨盾、重拳、宽肩 | 盾臂、拳臂、肩甲、髋腿 |
| 射手 Gunner | 1×1 | 明显长轨道炮、瞄准传感器 | 炮身/后坐滑轨、支撑臂、头部传感器 |
| 支援 Support | 1×1 | 医疗标识、实体维修无人机/工具臂 | 维修臂、前臂工具、无人机 |
| 大怪 Boss | 2×2 | 前探三眼头、双镰、四足生物机械轮廓 | 头、镰肢、四足、分节躯干 |
| 袭扰者 Raider | 1×1 | 低伏楔形躯干、后掠四肢、窄爪 | 头、前后腿、背部传感器/推进件 |

## 3. 推荐技术路线

采用 **AI 多视图生成初稿 + Blender 机械分件与修模 + 刚体层级绑定 + GLB 导出 + Three.js 动作播放**。

### 3.1 AI 生成工具定位

首选以腾讯混元生 3D Pro 3.1 对设计稿进行多视图图生 3D 试制，尤其验证外轮廓和背面补全。它的专业版文档列出 3.0/3.1、多视图、白模、草图和网格/纹理相关选项，3.1 支持最多八视图；结果可以输出 GLB/FBX 等格式。使用前必须核对腾讯云控制台的当前入口、接口可用性、地区和服务条款。

关键限制：

- 3.1 与 LowPoly 参数不能同时使用。若优先用 3.1 多视图，需后续自行减面/重拓扑；不能把生成结果的面数默认视为可上线预算。
- 组件生成可以辅助识别模型部件，但不承诺部件语义、旋转轴、层级或绑定正确。输出必须人工检查。
- 自动绑骨接口针对人物或动物模型。标准人形要求 A/T Pose 且不应携带武器等额外部件；非人形模型需符合其动物模型输入假设。机甲外装甲、炮、盾、镰肢的刚体绑定应由 Blender 中的明确层级控制，不把自动蒙皮作为默认方案。
- 文生动作能力描述为人物动作输出。可以用于动作节奏参考，不假设生成动作可直接驱动机甲的刚性分件。
- **不在桌面应用内集成生成 API，不上传本地会话、路径、用户数据或运行日志。** 概念图送往外部生成服务属于单独的资产制作决策，需确认作品权利和供应商条款；只上传已批准的设计参考图。

### 3.2 Blender 和游戏运行时的分工

- **Blender：** 准确修正体块和关节位置；拆分刚体装甲/武器；设置对象原点和层级；建立命名、材质、LOD/减面版本；录制或调整动画；导出并回导验证 GLB。
- **Three.js：** 载入模型资源、建立动画状态映射、播放/混合动画、处理阵营材质状态和游戏镜头反馈。
- **战斗规则：** 继续由现有规则代码决定移动、命中、伤害、护甲、维修、倒地和胜负。动画只消费已接受的战斗事件，不回写规则。
- **现有程序模型：** 在资产逐个通过验收前作为可运行的占位和回退模型保留。网格资源可逐个替换，不做一次性全量迁移。

机甲优先采用“刚性零件跟随骨骼/对象节点”的绑定方式，而不是把整副装甲做成柔性蒙皮。躯干、四肢和尾部可有有限的局部变形，但盾、炮、肩甲、护甲板、镰肢应保持自身形状。

### 3.3 方案调整：Assault 改走「手工硬表面建模」主线（2026-10-27）

Assault 首版走了 §3.1 的 AI 生成路线（图生 3D → 减面 → 分件 → 烘焙），实测结果不适合直接上线：生成网格有双层薄片，焊接后仍有约 100 条绕向冲突边；UV 碎成约 1500 块、1K 图只用了 17%；盾与重拳把静止宽度撑到 21 米（§5.4.1 例外）。因此 **Assault 主线改为在 Blender 里按概念稿手工硬表面建模**，AI 生成只保留为概念探索与比例参考（把生成网格作为半透明参考对象载入 Blender 对照）。

做法（参考「Mechanical Spider」提示词的参考驱动流程：体块 → 比例修正 → 硬表面操作 → 装配 → 近景检查 → 材质）：

1. 通过 Blender MCP 在 Blender 里可视化建模；每一步用离屏渲染看正面/侧面/3/4 视图，不凭数字判断。
2. **利用左右对称**：躯干、头等中心件直接按 X=0 对称；成对的腿、肩甲、上臂只建右侧一套，再镜像出左侧（改网格数据并翻面，不用负缩放）；只有盾牌臂与重拳臂是不对称的，单独建。
3. 材质用「8×1 调色板贴图（最近邻采样）+ 独立青色自发光材质」：不需要 UV 展开与烘焙，阵营标记是独立材质，运行时改 `emissiveFactor` 即可换色。
4. 收尾脚本：烘进倒角 → 平直着色 → 顶点转世界坐标 → 按关节合并成 §5.2 的节点名 → 逐部件自检（体积符号、开口边、非流形）。

建模脚本和源工程放在仓库外（见 §7），本仓库只收通过阶段门 E 的 GLB。

## 4. 生产步骤与阶段门

### 阶段 A：冻结参考和资产合同

1. 为每个角色整理正面、背面、左/右侧面和 3/4 视图；每个角度单独成图，不把带文字的设计板直接作为视图输入。
2. 记录主色、阵营标记位置、武器安装侧、身高/宽深、脚底基准和朝向。
3. 参考图若缺少背面/顶面，不凭空将生成结果视为设计定稿；先补充视图参考或明确允许设计扩展的部分。
4. 确认图稿和输出模型可用于本项目、发行平台和后续修改，并登记生成模型/服务版本、生成日期和许可依据。

**阶段门 A：** 角色识别符号和多视图方向得到确认；单位尺度与占格合同写入资产清单。

### 阶段 B：两个代表角色试制

首批只做：

- **Gunner：** 测试人形、长武器、后坐滑轨与炮臂遮挡。
- **Raider：** 测试非人形低伏轮廓、四足结构和不同于 Boss 的独立语言。

建议每个角色先生成 2–3 个候选白模/低成本版本，选一个轮廓最准确的，再做材质与后处理；不要一开始就对所有角色做高质量贴图。对 Hunyuan 3D Pro 的 3.1 多视图结果，重点比较多视图一致性、背面补全、关节轮廓和零件连通性。

**阶段门 B：** 在游戏相机下角色可辨，模型尺寸正确，能被合理拆成刚体部件，且无明显结构缺失。未达标则修改参考图/提示和 Blender 体块，不继续堆细节。

### 阶段 C：Blender 清理与机械分件

1. 设定统一单位与朝向：项目坐标约定为角色面向局部 `-Z`、脚底 `Y=0`；导出前转换到 glTF 的 Y-Up 约定并在回导中验证。
2. 删除生成过程残留、内部碎片、重复面、非预期浮动网格和不可见噪片；检查法线、UV、材质和纹理引用。
3. 按运动功能拆分对象，并让每个活动部件的原点落在机械旋转轴/滑轨起点，而不是网格中心。
4. 节点命名和层级严格按 §5.2「关节映射表」：每个驱动节点对应现有 `MechaJoint`（`apps/agent-city/ui/src/game/mecha/animation.ts`），GLB 只能在其下增加可选子节点，不能改名或换父级。
5. 统一外装甲主色、阵营标识、受光边和发光材质。避免把阵营色烘焙进纹理，使敌我/选中状态能由运行时代码控制。
6. 创建高质量源文件与运行时版本；必要时在 Blender 中减面/重拓扑。原始高模和纹理不得直接作为默认运行时资源。

**阶段门 C：** 所有活动件原点、父子关系和初始姿态已人工检查；无错误穿插和断裂；模型在 Blender 中重新打开后仍可编辑。

### 阶段 D：绑定与动作制作

以现有游戏动作状态为合同：`idle`、`move`、`attack`、`repair`、`hit`、`defeat`。角色不支持的动作应映射到有意设计的替代动作，而不是静默套用错误动作。

- 待机：轻微能源/传感器节奏或呼吸式机械起伏，不持续强闪。
- 移动：脚步交替、膝/踝补偿和躯干惯性；四足角色使用对角步态或符合其设计的步序。
- 攻击：动作必须呈现武器发力路径；Gunner 加炮身后坐和回稳，Assault 展示盾/重拳，Boss 展示镰肢弧线，Raider 展示短促扑击。
- 维修：Support 使用工具臂/无人机靠近目标，避免和普通攻击共用挥拳动作。
- 受击：短促反应并回稳，不改变棋盘位置和生命结算。
- 倒地：重心下降并保持终态；不得让脚、头或武器穿透地面。

如果在 Blender 中制作关键帧，动作片段应以动作语义命名。GLB 导出后使用 Three.js `GLTFLoader` 读入 clips，并以 `AnimationMixer` 管理播放、停止和混合。若先采用程序驱动刚体节点，也要沿用同一状态合同，便于以后逐个替换为 GLB 动作。

片段时长不在 Blender 里各自决定：先在清单里写定（§5.3），再按清单时长制作关键帧。现有程序动作的时长和周期就是第一版清单的初始值，改动时长等同于改变战斗演出节奏，需要和 `MechaBattleAnimator` 的排队一起验证。

**阶段门 D：** 每个动作在正面、侧面和 3/4 视角完成检查；攻击朝向正确；脚底接地；角色根节点位置由战场系统拥有，动画不得拖动棋盘格位置。GLB 片段必须能用 `mixer.setTime()` 按指定时间确定性采样，`apps/agent-city/ui/scripts/verify-mecha-animation.ts` 的现有断言（板上位置不变、倒地不穿地、回到绑定姿态、武器刚性跟随）要对 GLB 模型同样运行并通过。只靠人眼看不算通过。

### 阶段 E：导出、接入和运行时验收

1. 每个角色使用独立 `.glb`，纹理嵌入，避免运行时依赖外部临时 URL。
2. 记录模型版本、动画清单、尺寸、面数、材质数、贴图尺寸和文件体积。
3. 在资产预览页检查角色全角度和动作；再进入实际 City 战斗棋盘检查尺度、颜色、网格遮挡、夜景对比和武器碰撞观感。
4. 对失败模型保留现有程序模型回退；加载错误不应导致 City 插件崩溃。
5. 清理 `AnimationMixer`、纹理、材质和几何体资源；检查切换角色和关闭 City 时没有重复实例或持续动画泄漏。

**阶段门 E：** 模型预览与战斗实景均通过；性能和文件体积在设定预算内；资源回退正常。

## 5. 运行时资产合同

本节以 `a7744f05` 的程序模型代码为准：`apps/agent-city/ui/src/game/mecha/models.ts`（尺度常量、零件挂载）和 `apps/agent-city/ui/src/game/mecha/animation.ts`（`MechaJoint`、`MechaAction`、动作时长、`MechaBattleAnimator`）。GLB 是同一合同的另一种实现，不另起一套。

### 5.1 坐标与尺寸

- 战场格：`MECHA_CELL_METERS = 16`，即 16×16 米；小型角色占一格，大怪占 2×2 格。
- 单位换算：`MECHA_METERS_PER_UNIT = 2`，场景 1 单位等于 2 米。Blender 源文件按**米**建模，导入后的缩放由运行时统一处理，GLB 内不再自带缩放。
- 角色 `root`：放置/朝向/棋盘逻辑归战场代码控制，**不在 GLB 里**。
- 角色 `visual`：GLB 的顶层节点必须命名为 `visual`，只负责模型局部姿势，不擅自更改战斗单位坐标。
- 朝向：静止时面向局部 `-Z`（与 `faceMechaTarget` 一致）；脚底静止基准为 `Y=0`。GLB 导入后检查 Y-Up、比例、面朝方向和原点。

### 5.2 关节映射表

运行时只认 `MechaJoint`。GLB 用下表左列的节点名，加载器负责把它们登记到对应的 `MechaJoint`。

GLB 节点用 snake_case，不直接用代码里的 `joint:arm-left` 形式：Three.js `GLTFLoader` 会对节点名做清洗（去掉 `:`、`.`、`/` 等字符，重名自动加后缀），带冒号的名字导入后会变形。因此**每个 GLB 内的节点名必须唯一**，且只能使用 `[a-z0-9_-]`。

| `MechaJoint` | GLB 驱动节点（人形） | GLB 驱动节点（四足：Raider/Boss） | 父节点 | 枢轴位置 |
|---|---|---|---|---|
| `body` | `body` | `body` | `visual` | 腰/躯干承重中心 |
| `head` | `head` | `head` | `body` | 颈关节；四足为前探颈根 |
| `arm-left` / `arm-right` | `upper_arm_l` / `upper_arm_r` | Boss：`scythe_l` / `scythe_r`；Raider：不使用 | `body` | 肩关节；镰肢根部 |
| `forearm-left` / `forearm-right` | `forearm_l` / `forearm_r` | 不使用 | `arm-*` | 肘关节 |
| `leg-left` / `leg-right` | `thigh_l` / `thigh_r` | `front_leg_l` / `front_leg_r` | `visual` | 髋关节；前腿根 |
| `shin-left` / `shin-right` | `shin_l` / `shin_r` | `front_shin_l` / `front_shin_r` | `leg-*` | 膝关节 |
| `rear-left` / `rear-right` | 不使用 | `rear_leg_l` / `rear_leg_r` | `visual` | 后腿根 |
| `cannon` | Gunner：`railgun` | 不使用 | `body` | 炮架回转轴 |
| `drone` | Support：`drone` | 不使用 | `body` | 无人机悬停基点 |

规则：

1. **表中节点是必需的**（对该角色适用的部分）。缺少任何一个，加载失败并回退到程序模型。程序动作和 GLB 片段驱动的是同一组节点，因此回退和逐个替换都不需要改调用方。
2. **父子关系不能改。** 例如 `leg-*` 的父节点是 `visual` 而不是 `body`，这是为了躯干起伏时腿不跟着抬起；GLB 里不能把腿挂到 `body` 下面。
3. **GLB 可以在驱动节点下增加子节点**，由片段驱动、程序动作不碰。允许的名字：`hand_l/r`、`foot_l/r`（人形）、`rear_shin_l/r`（四足）、`recoil_carriage`（Gunner，挂在 `railgun` 下，用于后坐滑轨）、`repair_tool`（Support，挂在 `forearm_r` 下）、`shield`（Assault，挂在 `forearm_l` 下）。不驱动的装甲件（`shoulder_l/r`、`hip_l/r` 护甲）作为普通网格挂在对应驱动节点下即可，不算关节。
4. **Support 的维修臂就是右臂**：现有程序动作的 `repair` 驱动 `arm-right` + `forearm-right` + `drone`，所以 GLB 里没有单独的 `repair_arm` 关节。
5. **保留标记节点**：所有角色在 `head` 下保留一个名为 `front` 的空节点或网格，标记面部朝向（`verify-mecha-models.ts` 用它检查朝向）；Assault 保留 `gauntlet-left` / `gauntlet-right`（`verify-mecha-animation.ts` 用来检查武器刚性跟随）。
6. 新增的驱动关节（需要程序动作也能驱动的）必须先改 `MechaJoint` 合同，再出 GLB，不能只在 GLB 里出现。

### 5.3 资产清单与动作时长

每个角色资源配一份元数据清单 `<id>.manifest.json`。**动作时长以清单为准**：现在写死在 `animation.ts` 里的 `durations` 改为按模型读取清单；程序模型带一份内置清单，取现有常量，作为回退和第一版初值。

```json
{
  "id": "gunner",
  "version": 1,
  "role": "Gunner",
  "footprint": [1, 1],
  "forward": "-Z",
  "heightMeters": 18.8,
  "clips": {
    "idle":   { "duration": 3.14, "loop": true },
    "move":   { "duration": 0.79, "loop": true },
    "attack": { "duration": 0.95, "loop": false },
    "hit":    { "duration": 0.48, "loop": false },
    "defeat": { "duration": 0.85, "loop": false, "holdLastFrame": true }
  },
  "actionMap": { "repair": "attack" },
  "materials": ["armor_blue", "frame_dark", "joint_rubber", "faction_accent"],
  "source": { "uri": "<资产存储中的位置>", "sha256": "<.blend 的哈希>", "blender": "4.x" }
}
```

- 初值来自现有代码：`attack 0.95`、`repair 1.2`、`hit 0.48`、`defeat 0.85` 秒；`idle` 周期 π 秒（`sin(t*2)`），`move` 周期人形约 0.79 秒、四足约 0.63 秒（`sin(t*8)` / `sin(t*10)`）。
- `actionMap` 写明角色不支持的动作映射到哪个片段（对应 §4 阶段 D「有意设计的替代动作」）。现有程序动作里非 Support 角色的 `repair` 走攻击分支，清单必须显式写出来，不能靠缺省。
- `MechaBattleAnimator` 用清单时长排「攻击 → 受击 → 倒地」的先后顺序。片段实际长度与清单不一致，受击就会切在攻击中间。
- **加载时校验**：GLB 内每个 `AnimationClip.duration` 必须与清单相差不超过 1/30 秒；循环片段首尾姿态一致；`defeat` 保持终态。任一不满足即视为加载失败，回退到程序模型并在 console 报出具体片段名。

动画事件从已提交的战斗结果产生。若战斗被拒绝或回滚，不播放成功攻击；播放结束不得自行改 HP、占格或行动顺序。死亡动作完成后单位仍按规则状态处理，镜头和碰撞也不得从动画骨架推导。倒地防穿地仍由运行时的 `rearExtent` 补偿负责，`defeat` 片段不能自带根位移，否则会和这层补偿叠加。

### 5.4 16 米格尺度核对

现有程序模型的实测尺寸（静止姿态、包围盒，单位米；用 `Box3.setFromObject` 乘 `MECHA_METERS_PER_UNIT` 测得）：

| 角色 | 占格 | 宽 X | 高 Y | 深 Z | GLB 允许高度 | 静止占地上限（X 与 Z 各自） |
|---|---:|---:|---:|---:|---:|---:|
| Assault | 1×1 | 14.0 | 19.6 | 6.3 | 17.5–21.5 | ≤15（程序模型；GLB 按 §5.4.1 声明外伸 20.5×9.8） |
| Gunner | 1×1 | 9.3 | 18.8 | 10.4 | 17.0–20.5 | ≤15 |
| Support | 1×1 | 12.0 | 18.4 | 8.0 | 16.5–20.0 | ≤15 |
| Boss | 2×2 | 22.8 | 23.5 | 29.2 | 21.0–26.0 | ≤31 |
| Raider | 1×1 | 10.0 | 7.2 | 11.7 | 6.5–8.0 | ≤15 |

规则：

- **占地**：静止姿态的 X、Z 包围盒都不能超过「占格数 × 16 米 − 1 米」，给相邻格单位留至少 0.5 米间隙。
- **高度**：在现有高度的约 ±10% 以内。超出算设计变更，需要单独确认：人形 18–20 米与周围中层楼（会话地块 14.4×16 米）同量级，高度一变，镜头遮挡和楼宇比例都会跟着变。
- **动作外伸**：攻击、后坐、镰肢挥动等动作姿态可以超出本格，但伸入相邻格不超过半格（8 米），并在验收记录里写明最大外伸量。
- **接地**：静止姿态 `minY = 0 ± 0.01 米`；任何动作、任何时刻 `minY ≥ −0.001 米`（与现有测试同一阈值）。
- **怎么测**：由 `verify-mecha-models.ts` 对程序模型和 GLB 跑同一套测量，不靠人工量。Blender 导出前再用 Blender 无界面模式加脚本做一次（本机 `/Applications/Blender.app` 可用），测量结果写进清单的 `heightMeters` 和验收记录。

#### 5.4.1 设计例外：Assault 的盾与重拳外伸出本格（2026-10-26 确认）

> **状态：恢复生效（2026-10-28）。** 2026-10-27 曾因手工建模 v2 压到 14.98 米而作废；但 v2 与概念稿的剪影相似度只有 0.598（宽高比 0.77 对概念稿 1.02），被评为「积木感」。用户已确认宽度按概念稿走（约 20–21 米），v2b 重做后例外重新登记：**静止宽 20.16 米、深 9.28 米、高 19.68 米（宽高比 1.02）**。清单用 `maxExtentMeters: [20.5, 9.8]` 声明范围，加载器只放行声明过的范围，且声明不得超过占格的 1.5 倍。未声明时仍按「占格 − 1 米」拒绝。动作外伸量仍需用新模型重测。

Assault A-01 首版 GLB 保留概念稿的宽站姿比例：左臂巨盾、右臂重拳都在躯干外侧。高度 19.6 米时，静止宽度 21.08 米，超过上面「静止占地 ≤15 米」的规则。

收窄方案试过：手臂连肩甲内收 2.75 米、两腿内收 0.9 米，再缩到 18.73 米高，可以压进 15 米。但轮廓明显变弱（重拳贴住大腿、盾贴住身体），评审后退回原比例。整体等比缩小到 15 米宽会只剩约 14 米高，成为三个人形里最矮的，也不采用。因此本条作为**设计例外**登记，不改规则本身。

实测外伸量（GLB v1，单位米，从本格中心量；本格边缘距中心 8 米。「前」指模型面朝的 −Z 方向）：

| 姿态 | 左右范围 | 超出本格边缘（左右） | 超出本格边缘（前后） |
|---|---|---:|---:|
| 静止 / `idle` | −10.54 … +10.54 | 每侧 2.54（左为盾，右为拳） | 0（深 10.87，在格内） |
| `move` | −10.54 … +10.54 | 每侧 2.54 | 后方 0.75 |
| `attack` | −10.54 … +11.80 | 右侧 **3.80（全部片段中最大）** | 前方 3.26 |
| `hit` | −11.22 … +11.24 | 左 3.22 / 右 3.24 | 0 |

- **豁免范围**：只豁免「静止占地 ≤15 米」一条。动作外伸最大 3.80 米，仍在「≤ 半格（8 米）」之内，那条规则照常适用。`defeat` 向后倒地会伸出身后很远，这对所有人形角色都一样，是程序模型就有的行为，不属于本例外。
- **会遮住相邻格**：盾和拳在视觉上会覆盖左右相邻格。静止时最多覆盖 2.54 米，攻击时最多 3.80 米，可能挡住或穿插相邻格的单位、格子高亮、地形与标记。按现有程序模型的半宽估算，左右紧邻时：
  - Support（半宽 6.0）静止时就会穿插约 0.5 米；
  - Gunner（半宽 4.65）与 Raider（半宽 5.0）静止时还有 0.8 / 0.5 米间隙，攻击时会穿插 0.5 / 0.8 米。
  这些角色换成 GLB 后要按实测宽度重算。
- **只影响表现，不影响规则**：占格、碰撞、射线选取、攻击目标仍由战场代码按 1×1 判定（§5.1）。外伸部分不算占格，不能被点选，也不阻挡别的单位。
- **验收要求**：在 City 战斗棋盘上，把 Assault 与每种相邻角色并排截图，检查左右邻接时的遮挡是否可接受；验收记录写上表中的外伸量。模型比例一旦改动就要重测本表，外伸超过 8 米或静止宽度再变大都需要重新确认。

### 5.5 运行时加载与回退（已实现，2026-10-27）

代码在 `apps/agent-city/ui/src/render/mecha/`：`glbModels.ts`（解析、校验、实例化，只依赖 three）、`glbRegistry.ts`（Vite 专用：资产 URL、fetch、缓存）、`animation.ts`（清单驱动的确定性采样）、`models.ts`（原地升级）。资产在 `src/assets/mecha/`，来源登记在同目录 `LICENSES.md`。

- **程序模型始终先出现，GLB 就绪后原地替换。** `createAssault()` 等仍同步返回程序模型；资产已缓存就在出生时直接是 GLB，否则加载完成后把根节点里的内容换掉。根节点的位置、缩放、朝向和动画器的键都不动，所以棋盘代码不用改。
- **任何失败都留在程序模型，不抛到页面上**：网络、解析、清单形状、合同校验（§5.2 节点与父子、静止旋转为单位阵、标记节点、朝向 −Z、片段时长与清单差 ≤1/30 秒、高度、占格）、实例化出错，都只 `console.warn` 一次。资产在加载回来之前模型就被销毁，也不会再升级。
- **时长以清单为准**：`mechaActionDuration`/`mechaActionSpan` 读清单，循环片段（待机、移动）没有终点；`repair` 走 `actionMap` 映射到 `attack`，不再是程序动作的 1.2 秒。攻击→受击→倒地的排队用清单时长。
- **确定性采样**：每个实例一个 `AnimationMixer`，所有片段常驻、只按权重切换，时间由我们自己折叠/夹取，所以能拖进度条、能写测试。三个坑（都有回归测试）：
  1. `LoopOnce` 片段播完会被置为 paused，之后 `setTime` 永远停在 0 秒——全部用 `LoopRepeat`，终点取 `duration − 1e-4`，否则会折回 0、倒地终态变成站姿；
  2. mixer 只在「轨道算出的值变了」才写回节点，**手工改动画驱动的节点会被它遗忘、残留到下一个片段**（倒地抬高曾因此在站起后留着 5.8 米）——倒地抬高只写在 mixer 不碰的外层 `mecha-lift` 节点上；
  3. 每个片段都带全部通道，切换片段才不会留下上一个片段的姿态。
- **释放**：实例的 `dispose` 只停 mixer、摘节点；几何、材质、贴图属于缓存、由所有实例共享（两个袭扰者之类共用一份），不随实例释放。
- **后续角色**：在 `glbRegistry.ts` 的 `SOURCES` 加一行，并在 `glbModels.ts` 的 `NODE_TREE`/`MARKERS` 补该角色的节点合同；不认识的角色加载器一律拒绝。

| 动作 | 6 个状态 | 5 个状态合同 + `actionMap` | 同左 | 可共享动作节奏，但不能牺牲角色差异 |

### 6.1 整场景预算

单台达标不等于整场达标。当前棋盘同时出场 6 台：Assault、Gunner、Support、Boss、Raider × 2。

| 指标 | 现状（6 台合计） | 上限 |
|---|---:|---:|
| draw call | 142 | ≤160 |
| 三角形 | 约 4.4k | ≤120k |
| GLB 合计体积（5 个角色） | — | ≤24 MB |

- 单台目标按上限取满（3 × 20k + 40k + 2 × 20k = 140k）会超出整场景预算，所以单台目标是**区间**，不是可以各自取满的额度。
- 两台 Raider 共用同一份几何体、材质和贴图（用 `clone()` 共享资源，只复制节点树），不各自加载一份。draw call 照算两台，但显存和加载只算一份。
- 测法：在实际 City 战斗棋盘上读取 `renderer.info.render.calls` / `.triangles`，记录替换前后的差值；只在模型预览页测出来的数字不算数。
- 角色模型叠加在 City 场景上，场景本身已经很重。如果整场帧率明显下降，即使上表都达标也要回头减面。

**Assault（手工建模 v2，含细节层）实测：** 13920 个三角形、13 个网格、18 个绘制调用（5 个带青色发光件的网格各多 1 个）、2 个材质、2 张 8×1 贴图（8 格调色板：护甲/饰边/深色/金属/橡胶/高亮黄/白色标记/视窗）、GLB **0.82 MB**、静止尺寸 14.98 × 19.61 × 12.05 米（含背包排气口的深度）；每个部件水密、体积为正；五个片段时长与清单一致，所有片段不陷地，循环无接缝（`glb_check.ts` 全部通过）。对照 AI 版：1.6 MB、1.2 万三角形、15 个网格、UV 碎成约 1500 块。细节是对照生成的参考模型逐项补的（六角螺母圆环关节、锯齿散热片、拳头上板小窗、领口与斜方肌甲板、切角六边形腹甲、台阶式盾面）。

如果纹理造成体积过大，先确认图案确实在当前镜头距离可见；不以无关紧要的高清纹理换取低帧率或大安装包。

## 7. 资产存储

**决定：运行时 GLB 进本仓库；源工程和生成中间产物不进本仓库。**

| 产物 | 存放位置 | 说明 |
|---|---|---|
| 运行时 `<id>.glb` + `<id>.manifest.json` | `apps/agent-city/ui/src/assets/mecha/` | 按 flora `.glb` 的先例，用 `?url` 导入（`src/assets/assets.d.ts`），随 Vite 打包进桌面应用 |
| 来源登记 | `apps/agent-city/ui/src/assets/LICENSES.md` | 沿用现有 flora 登记格式，补生成服务/版本、生成日期、许可依据、修改记录；不另起一份登记 |
| 概念设计稿 PNG | `docs/design/mecha/<日期>/` | 维持现状 |
| `.blend` 源工程、AI 原始输出、高模、源贴图、参考视图包 | 仓库外的资产存储（由资产负责人指定） | 清单 `source.uri` + `source.sha256` 指向它，保证每个 GLB 都能追溯到唯一的源文件 |

理由：

- 仓库没有启用 Git LFS，现有 `src/assets` 只有约 3 MB。二进制文件每提交一版都会永久留在历史里，`.blend` 通常是几十到几百 MB，放进来会让每个克隆和 CI 都背上。
- GLB 会直接进入安装包，所以 §6 把单个 GLB 体积从 8/15 MB 收紧到 4/8 MB，5 个角色合计不超过 24 MB。
- **只提交通过阶段门 E 的 GLB 版本**，试制候选和中间版本不进仓库。同一角色每多提交一次，历史体积就多一份。
- 如果以后需要在仓库内管理源工程，再单独评审是否引入 Git LFS：它会影响所有克隆、CI 和桌面发布流程，不在本方案里顺手启用。

## 8. 角色制作优先顺序

1. **Gunner：** 验证多视图比例、武器识别、刚体武器后坐和人形关节。
2. **Raider：** 验证四足模型的轮廓、步态和非人形约束。
3. **Assault：** 在共同人形骨架合同上加入巨盾、重拳和重心动作。
4. **Support：** 重点制作维修工具臂和可独立运动的实体无人机。
5. **Boss：** 最后进行高体量四足模型和双镰动作；此时可以复用 Raider 的四足技术验证，但不能复用其缩放模型或轮廓。

每完成一个角色，需将源工程、运行时 GLB、预览截图、动作清单和验收记录成套保存。不要五个模型一次性替换，以便出现问题时能定位来源并回退。

## 9. 验收清单

### 视觉

- [ ] 去色剪影下仍可区分五种兵种。
- [ ] 远景/战棋相机下，阵营标记和角色超级符号可见。
- [ ] 低亮度夜景下关节、腿和武器不融成黑色块。
- [ ] 不存在生成器常见的多余肢体、悬浮碎片、封闭孔洞和不合理背面。
- [ ] 发光、涂装、裸露骨架、关节材质能区分且不过度抢眼。

### 结构与动作

- [ ] 肩、肘、腕、髋、膝、踝的轴心和父子层级正确。
- [ ] 装甲板随对应身体部位运动，不变软、不穿插。
- [ ] 盾牌/轨道炮/维修臂/无人机/镰肢有正确安装点和动作范围。
- [ ] 移动脚步接地，移动结束回到静止姿态。
- [ ] 攻击方向与规则目标一致；受击和倒地不漂移棋盘坐标。
- [ ] 动作被中断、回滚、角色死亡或重生时能恢复正确姿态。
- [ ] 支持减少动态效果设置；关闭动画仍显示稳定静止模型。
- [ ] GLB 节点名、父子关系与 §5.2 关节映射表一致；`front` 等标记节点存在；节点名在文件内唯一。
- [ ] 每个片段时长与清单相差 ≤1/30 秒，`actionMap` 覆盖所有不支持的动作；`verify-mecha-animation.ts` 对 GLB 通过。
- [ ] 静止占地、高度、接地和最大动作外伸符合 §5.4，并写入验收记录。

### 工程与发布

- [ ] GLB 能在模型预览和 City 页面正常加载，console 无新增资源错误。
- [ ] GLB、纹理和动画预算有记录；模型切换后无明显性能回退。
- [ ] 单台 draw call 与整场景 draw call / 三角形在 §6、§6.1 上限内（在 City 战斗棋盘实测）。
- [ ] GLB 与清单放在 `src/assets/mecha/`，来源登记进 `LICENSES.md`；`.blend` 等源文件不在仓库内，清单 `source.sha256` 可追溯（§7）。
- [ ] 不依赖生成任务临时链接或运行时云端请求。
- [ ] 资产来源、工具版本、生成日期、修改记录和许可证依据已登记。
- [ ] 许可/商用条款经过项目负责人复核；不得将图像生成服务密钥打入客户端。
- [ ] 回退到程序模型正常，模型下载/解析失败不会导致整页或插件崩溃。

## 10. 风险和应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 多视图生成背面不一致 | 侧后视角、攻击动作时外形突变 | 补齐独立视图；在 Blender 中定稿背面，不把一张 3/4 图当完整模型合同 |
| 生成网格拓扑不适合刚体运动 | 肩肘扭曲、装甲穿插 | 切分刚体部件并设置真实 pivot；避免全身自动蒙皮 |
| 自动绑骨不适用于机械组件 | 机械腿、武器变成软组织式变形 | 以对象层级/骨骼驱动刚体为主；AI 绑骨只做隔离试验 |
| 高模和贴图让资源变大 | 安装包增加、显存/加载成本上升 | 先验证轮廓；压缩纹理、控制三角形和材质槽；按镜头距离制作运行时版本 |
| 阵营色被烘焙进贴图 | 难以支持换边、选中和夜景状态 | 阵营标识使用独立材质区域/网格，由运行时着色 |
| AI 资产授权或服务入口变化 | 发布和再分发风险 | 逐次核对现行服务条款、地区限制、输出使用范围和计费；保存审查记录 |
| 外部生成误接触用户数据 | 违反产品本地数据原则 | 仅传已批准的角色设计图；不传日志、会话、路径、用户数据；生成只用于资产制作 |

## 11. 首批交付物
