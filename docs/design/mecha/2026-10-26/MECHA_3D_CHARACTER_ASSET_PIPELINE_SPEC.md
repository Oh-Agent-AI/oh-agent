# Oh Agent City 3D 角色资产创建方案

**状态：** 执行方案（先试制、通过验收后扩展到全阵容）
**版本：** 1.0
**日期：** 2026-10-26
**适用范围：** Agent City 机甲战棋角色模型、战斗动作和预览资产

## 1. 目标

建立一条从角色概念稿到游戏内可用角色资产的可重复管线。成品需要同时满足：

1. 保留五种角色的独特剪影和统一的工业机械语法。
2. 在 16 米战场格、当前镜头距离和昼夜光照下易于辨认。
3. 关键装甲、关节、武器和功能设备具有合理的机械连接关系。
4. 能播放待机、移动、攻击、受击、维修和倒地等动作，不穿插、不漂脚。
5. 文件大小、网格数、材质数和绘制调用符合桌面端实时渲染预算。
6. 动画表现只呈现已由战斗规则接受的行动，不改变命中、伤害或胜负判定。

本方案不把“AI 一键生成”作为交付标准。AI 生成的模型是建模初稿，必须经 DCC 整理、动作验证和游戏内验收后才能合入。

## 2. 角色阵容与视觉契约

五个角色共用以下设计约束：

- **三层机械结构：** 深色承重骨架、可见的中间关节和传动件、大块低多边形外装甲。
- **阵营与职业分离：** 职业保留自身主色；我方在固定部位使用青蓝标记 `#4FD8FF`，敌方使用珊瑚红 `#FF5C72`。靠轮廓、徽记和标记形状辅助识别，不只靠颜色。
- **材质层级：** 涂装装甲、裸露金属骨架、橡胶/复合材料关节、少量能源或传感器发光件。
- **细节原则：** 先保证轮廓、结构与动作可读，再添加编号、警示标、磨损。避免用噪点、密集刻线或发光边条替代结构设计。
- **比例和落点：** 保持项目单位约定、角色占格、朝向和脚底接地基准；导入模型不能私自改变战场规则坐标。
- **安全区：** 武器、天线、镰肢等超出躯干的部件应在完整动作范围内保持可读，避免遮住角色身份特征。

| 角色 | 战场占格 | 必须一眼识别的造型符号 | 主要活动部件 |
|---|---:|---|---|
| 突击 Assault | 1×1 | 巨盾、重拳、宽肩 | 盾臂、拳臂、肩甲、髋腿 |
| 射手 Gunner | 1×1 | 明显长轨道炮、瞄准传感器 | 炮身/后坐滑轨、支撑臂、头部传感器 |
| 支援 Support | 1×1 | 医疗标识、实体维修无人机/工具臂 | 维修臂、前臂工具、无人机 |
| 大怪 Boss | 2×2 | 前探三眼头、双镰、四足生物机械轮廓 | 头、镰肢、四足、分节躯干 |
| 袭扰者 Raider | 1×1 | 低伏楔形躯干、后掠四肢、窄爪 | 头、前后腿、背部传感器/推进件 |

## 3. 推荐技术路线

采用 **AI 多视图生成初稿 + Blender 机械分件与修模 + 刚体层级绑定 + GLB 导出 + Three.js 动作播放**。

### 3.1 AI 生成工具定位

首选以腾讯混元生 3D Pro 3.1 对设计稿进行多视图图生 3D 试制，尤其验证外轮廓和背面补全。它的专业版文档列出 3.0/3.1、多视图、白模、草图和网格/纹理相关选项，3.1 支持最多八视图；结果可以输出 GLB/FBX 等格式。使用前必须核对腾讯云控制台的当前入口、接口可用性、地区和服务条款。

关键限制：

- 3.1 与 LowPoly 参数不能同时使用。若优先用 3.1 多视图，需后续自行减面/重拓扑；不能把生成结果的面数默认视为可上线预算。
- 组件生成可以辅助识别模型部件，但不承诺部件语义、旋转轴、层级或绑定正确。输出必须人工检查。
- 自动绑骨接口针对人物或动物模型。标准人形要求 A/T Pose 且不应携带武器等额外部件；非人形模型需符合其动物模型输入假设。机甲外装甲、炮、盾、镰肢的刚体绑定应由 Blender 中的明确层级控制，不把自动蒙皮作为默认方案。
- 文生动作能力描述为人物动作输出。可以用于动作节奏参考，不假设生成动作可直接驱动机甲的刚性分件。
- **不在桌面应用内集成生成 API，不上传本地会话、路径、用户数据或运行日志。** 概念图送往外部生成服务属于单独的资产制作决策，需确认作品权利和供应商条款；只上传已批准的设计参考图。

### 3.2 Blender 和游戏运行时的分工

- **Blender：** 准确修正体块和关节位置；拆分刚体装甲/武器；设置对象原点和层级；建立命名、材质、LOD/减面版本；录制或调整动画；导出并回导验证 GLB。
- **Three.js：** 载入模型资源、建立动画状态映射、播放/混合动画、处理阵营材质状态和游戏镜头反馈。
- **战斗规则：** 继续由现有规则代码决定移动、命中、伤害、护甲、维修、倒地和胜负。动画只消费已接受的战斗事件，不回写规则。
- **现有程序模型：** 在资产逐个通过验收前作为可运行的占位和回退模型保留。网格资源可逐个替换，不做一次性全量迁移。

机甲优先采用“刚性零件跟随骨骼/对象节点”的绑定方式，而不是把整副装甲做成柔性蒙皮。躯干、四肢和尾部可有有限的局部变形，但盾、炮、肩甲、护甲板、镰肢应保持自身形状。

## 4. 生产步骤与阶段门

### 阶段 A：冻结参考和资产合同

1. 为每个角色整理正面、背面、左/右侧面和 3/4 视图；每个角度单独成图，不把带文字的设计板直接作为视图输入。
2. 记录主色、阵营标记位置、武器安装侧、身高/宽深、脚底基准和朝向。
3. 参考图若缺少背面/顶面，不凭空将生成结果视为设计定稿；先补充视图参考或明确允许设计扩展的部分。
4. 确认图稿和输出模型可用于本项目、发行平台和后续修改，并登记生成模型/服务版本、生成日期和许可依据。

**阶段门 A：** 角色识别符号和多视图方向得到确认；单位尺度与占格合同写入资产清单。

### 阶段 B：两个代表角色试制

首批只做：

- **Gunner：** 测试人形、长武器、后坐滑轨与炮臂遮挡。
- **Raider：** 测试非人形低伏轮廓、四足结构和不同于 Boss 的独立语言。

建议每个角色先生成 2–3 个候选白模/低成本版本，选一个轮廓最准确的，再做材质与后处理；不要一开始就对所有角色做高质量贴图。对 Hunyuan 3D Pro 的 3.1 多视图结果，重点比较多视图一致性、背面补全、关节轮廓和零件连通性。

**阶段门 B：** 在游戏相机下角色可辨，模型尺寸正确，能被合理拆成刚体部件，且无明显结构缺失。未达标则修改参考图/提示和 Blender 体块，不继续堆细节。

### 阶段 C：Blender 清理与机械分件

1. 设定统一单位与朝向：项目坐标约定为角色面向局部 `-Z`、脚底 `Y=0`；导出前转换到 glTF 的 Y-Up 约定并在回导中验证。
2. 删除生成过程残留、内部碎片、重复面、非预期浮动网格和不可见噪片；检查法线、UV、材质和纹理引用。
3. 按运动功能拆分对象，并让每个活动部件的原点落在机械旋转轴/滑轨起点，而不是网格中心。
4. 使用稳定命名，至少覆盖：`root`、`body`、`head`、`shoulder_l/r`、`upper_arm_l/r`、`forearm_l/r`、`hand_l/r`、`hip_l/r`、`thigh_l/r`、`shin_l/r`、`foot_l/r`；按角色添加 `shield`、`railgun`、`recoil_carriage`、`repair_arm`、`drone`、`scythe_l/r`、`rear_leg_l/r` 等。
5. 统一外装甲主色、阵营标识、受光边和发光材质。避免把阵营色烘焙进纹理，使敌我/选中状态能由运行时代码控制。
6. 创建高质量源文件与运行时版本；必要时在 Blender 中减面/重拓扑。原始高模和纹理不得直接作为默认运行时资源。

**阶段门 C：** 所有活动件原点、父子关系和初始姿态已人工检查；无错误穿插和断裂；模型在 Blender 中重新打开后仍可编辑。

### 阶段 D：绑定与动作制作

以现有游戏动作状态为合同：`idle`、`move`、`attack`、`repair`、`hit`、`defeat`。角色不支持的动作应映射到有意设计的替代动作，而不是静默套用错误动作。

- 待机：轻微能源/传感器节奏或呼吸式机械起伏，不持续强闪。
- 移动：脚步交替、膝/踝补偿和躯干惯性；四足角色使用对角步态或符合其设计的步序。
- 攻击：动作必须呈现武器发力路径；Gunner 加炮身后坐和回稳，Assault 展示盾/重拳，Boss 展示镰肢弧线，Raider 展示短促扑击。
- 维修：Support 使用工具臂/无人机靠近目标，避免和普通攻击共用挥拳动作。
- 受击：短促反应并回稳，不改变棋盘位置和生命结算。
- 倒地：重心下降并保持终态；不得让脚、头或武器穿透地面。

如果在 Blender 中制作关键帧，动作片段应以动作语义命名。GLB 导出后使用 Three.js `GLTFLoader` 读入 clips，并以 `AnimationMixer` 管理播放、停止和混合。若先采用程序驱动刚体节点，也要沿用同一状态合同，便于以后逐个替换为 GLB 动作。

**阶段门 D：** 每个动作在正面、侧面和 3/4 视角完成检查；攻击朝向正确；脚底接地；角色根节点位置由战场系统拥有，动画不得拖动棋盘格位置。

### 阶段 E：导出、接入和运行时验收

1. 每个角色使用独立 `.glb`，纹理嵌入，避免运行时依赖外部临时 URL。
2. 记录模型版本、动画清单、尺寸、面数、材质数、贴图尺寸和文件体积。
3. 在资产预览页检查角色全角度和动作；再进入实际 City 战斗棋盘检查尺度、颜色、网格遮挡、夜景对比和武器碰撞观感。
4. 对失败模型保留现有程序模型回退；加载错误不应导致 City 插件崩溃。
5. 清理 `AnimationMixer`、纹理、材质和几何体资源；检查切换角色和关闭 City 时没有重复实例或持续动画泄漏。

**阶段门 E：** 模型预览与战斗实景均通过；性能和文件体积在设定预算内；资源回退正常。

## 5. 运行时资产合同

### 坐标与尺寸

- 战场格：16×16 米；小型人形角色占一格，大怪占两格。
- 角色 `root`：放置/朝向/棋盘逻辑归战场代码控制。
- 角色 `visual`：只负责模型局部姿势，不擅自更改战斗单位坐标。
- 脚底静止基准为地面高度；GLB 导入后检查 Y-Up、比例、面朝方向和原点。

### 动画状态数据

每个角色资源应有一个元数据清单，例如：

```json
{
  "id": "gunner",
  "version": 1,
  "role": "Gunner",
  "footprint": [1, 1],
  "forward": "-Z",
  "clips": ["idle", "move", "attack", "hit", "defeat"],
  "materials": ["armor_blue", "frame_dark", "joint_rubber", "faction_accent"]
}
```

动画事件从已提交的战斗结果产生。若战斗被拒绝或回滚，不播放成功攻击；播放结束不得自行改 HP、占格或行动顺序。死亡动作完成后单位仍按规则状态处理，镜头和碰撞也不得从动画骨架推导。

## 6. 初始质量预算

下表是**试制目标**，不是当前代码已验证的上限；首批 GLB 通过实际浏览器/桌面渲染后再校准。

| 指标 | 人形试制目标 | Boss 试制目标 | 超出时的处理 |
|---|---:|---:|---|
| 运行时三角形 | 8k–25k | 20k–50k | 先删不可见小件，再做减面/烘焙法线 |
| 材质槽 | ≤6 | ≤8 | 合并相近材质，阵营色保留可控参数 |
| 主贴图 | 1K 起步 | 1K–2K | 优先压缩/合图，避免高分辨率烘焙噪点 |
| GLB 体积 | ≤8 MB | ≤15 MB | 压纹理、减少重复资源、检查嵌入资产 |
| 骨骼/刚体节点 | 只保留可驱动部件 | 只保留必要腿、头、躯干、镰肢 | 删除纯展示用空节点，合并静态装甲 |
| 动作 | 5 个状态合同 | 5 个状态合同 | 可共享动作节奏，但不能牺牲角色差异 |

如果纹理造成体积过大，先确认图案确实在当前镜头距离可见；不以无关紧要的高清纹理换取低帧率或大安装包。

## 7. 角色制作优先顺序

1. **Gunner：** 验证多视图比例、武器识别、刚体武器后坐和人形关节。
2. **Raider：** 验证四足模型的轮廓、步态和非人形约束。
3. **Assault：** 在共同人形骨架合同上加入巨盾、重拳和重心动作。
4. **Support：** 重点制作维修工具臂和可独立运动的实体无人机。
5. **Boss：** 最后进行高体量四足模型和双镰动作；此时可以复用 Raider 的四足技术验证，但不能复用其缩放模型或轮廓。

每完成一个角色，需将源工程、运行时 GLB、预览截图、动作清单和验收记录成套保存。不要五个模型一次性替换，以便出现问题时能定位来源并回退。

## 8. 验收清单

### 视觉

- [ ] 去色剪影下仍可区分五种兵种。
- [ ] 远景/战棋相机下，阵营标记和角色超级符号可见。
- [ ] 低亮度夜景下关节、腿和武器不融成黑色块。
- [ ] 不存在生成器常见的多余肢体、悬浮碎片、封闭孔洞和不合理背面。
- [ ] 发光、涂装、裸露骨架、关节材质能区分且不过度抢眼。

### 结构与动作

- [ ] 肩、肘、腕、髋、膝、踝的轴心和父子层级正确。
- [ ] 装甲板随对应身体部位运动，不变软、不穿插。
- [ ] 盾牌/轨道炮/维修臂/无人机/镰肢有正确安装点和动作范围。
- [ ] 移动脚步接地，移动结束回到静止姿态。
- [ ] 攻击方向与规则目标一致；受击和倒地不漂移棋盘坐标。
- [ ] 动作被中断、回滚、角色死亡或重生时能恢复正确姿态。
- [ ] 支持减少动态效果设置；关闭动画仍显示稳定静止模型。

### 工程与发布

- [ ] GLB 能在模型预览和 City 页面正常加载，console 无新增资源错误。
- [ ] GLB、纹理和动画预算有记录；模型切换后无明显性能回退。
- [ ] 不依赖生成任务临时链接或运行时云端请求。
- [ ] 资产来源、工具版本、生成日期、修改记录和许可证依据已登记。
- [ ] 许可/商用条款经过项目负责人复核；不得将图像生成服务密钥打入客户端。
- [ ] 回退到程序模型正常，模型下载/解析失败不会导致整页或插件崩溃。

## 9. 风险和应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 多视图生成背面不一致 | 侧后视角、攻击动作时外形突变 | 补齐独立视图；在 Blender 中定稿背面，不把一张 3/4 图当完整模型合同 |
| 生成网格拓扑不适合刚体运动 | 肩肘扭曲、装甲穿插 | 切分刚体部件并设置真实 pivot；避免全身自动蒙皮 |
| 自动绑骨不适用于机械组件 | 机械腿、武器变成软组织式变形 | 以对象层级/骨骼驱动刚体为主；AI 绑骨只做隔离试验 |
| 高模和贴图让资源变大 | 安装包增加、显存/加载成本上升 | 先验证轮廓；压缩纹理、控制三角形和材质槽；按镜头距离制作运行时版本 |
| 阵营色被烘焙进贴图 | 难以支持换边、选中和夜景状态 | 阵营标识使用独立材质区域/网格，由运行时着色 |
| AI 资产授权或服务入口变化 | 发布和再分发风险 | 逐次核对现行服务条款、地区限制、输出使用范围和计费；保存审查记录 |
| 外部生成误接触用户数据 | 违反产品本地数据原则 | 仅传已批准的角色设计图；不传日志、会话、路径、用户数据；生成只用于资产制作 |

## 10. 首批交付物

Gunner 与 Raider 各自交付：

1. 参考视图包（正、背、侧、3/4，标注哪些为最终设计）。
2. Blender 源工程 `.blend`，包含命名零件、pivot、材质和动作。
3. 优化后的运行时 `.glb`，嵌入贴图和命名动画片段。
4. 元数据清单及面数、体积、材质数、动作时长记录。
5. 模型预览截图和实际战棋镜头截图。
6. 验收记录、已知问题和程序模型回退说明。

**扩展决策：** 两个试制角色全部通过运行时验收后，再按制作顺序扩展其余角色。若 AI 结果需要大量修面才能保留设计轮廓，就改为 Blender 手工/程序化建模作为主体，AI 仅辅助概念探索、贴图草案或局部装饰。
