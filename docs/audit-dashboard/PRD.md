## 1. 文档目的

本文定义 Agent Vitals「审计」Tab 的 V2 重构需求，将现有以数据陈列为主的页面改造成面向会话复核的审计 Dashboard。

页面必须帮助用户依次完成三个任务：

1. 判断本次会话发生了哪些异常信号，以及数据是否完整；
2. 定位异常发生的时间、步骤和上下文，理解原因；
3. 留下复核备注、复制证据，并在需要时导出留痕。

页面**不**假装能够干预 Agent 的执行——暂停、阻断危险工具、修改审批策略、限制 Token/费用、优化上下文或改变模型选择目前都不存在，也不应该在 UI 上表现得像存在。见 §3.3 产品分层边界。

本文是开发、设计与测试的唯一实施规格。既有 `AUDIT_TAB_DESIGN.md` 和 `AUDIT_TAB_UX_REVIEW.md` 保留为研究与决策记录；发生冲突时以本文为准。

## 2. 背景与问题

当前审计页面已具备行为 finding、Token 用量、费用估算、同类合并和人工标记能力，但存在以下关键问题：

- 顶部汇总、标题和可见列表使用不同计数口径；
- 页面没有直接回答“本次会话是否需要复核”；
- Token 与费用占据较多首屏面积，但不能直接推动下一步操作；
- 费用以精确金额呈现，容易被误认为账单；
- Finding 缺少规则解释、上下文和可靠定位能力；
- 每行常驻多个按钮，信息密度低，且缺少操作反馈；
- 标记默认跨会话复用，可能静默影响后续会话；
- 汇总不可筛选，已忽略项入口弱；
- 缺少响应式、键盘、屏幕阅读器和错误状态规范；
- **信息架构把「审计报告」（陈述事实）与「风险处置台」（暗示可以干预）混在一起**：确认安全/标记高危/忽略三个按钮常驻每一行，但都不改变 Agent 的后续行为，用户容易误以为点击后风险已被处理；
- 两张趋势图（时间线、上下文占用）共享 turn 横轴却分开摆放，未形成联动诊断价值；费用同一个数字在 KPI 卡和摘要行里出现两次。

## 3. 产品目标

### 3.1 核心目标

- 用户进入页面后 3 秒内可以判断本次会话发生了哪些异常信号；
- 用户可以从汇总或图表定位到具体 finding，理解异常发生的原因；
- 每个 finding 都能被解释、查看上下文，并留下复核备注；
- 引擎事实（严重度、发生次数、证据）与个人复核备注在展示上完全分离，备注不得改变、隐藏或重排引擎事实；
- 页面中的计数、成本和状态表达保持一致且可解释；
- 估算值、缺失数据和未知数据不得表现为精确事实或零值。

### 3.2 非目标

V2 不负责：

- 代替完整的 Trajectory 页面；
- 代替 dsh-context 的上下文构成分析；
- 提供财务账单或结算凭证；
- 根据单次会话自动建议删除技能或工具；
- 使用单次未触发记录判定技能为无用；
- 构建跨组织的审计治理后台；
- **暗示具备干预能力**：不得设计任何看起来会暂停 Agent、阻止工具、修改审批策略、限制 Token/费用或改变模型选择的控件，除非该能力已经真实存在；
- 把个人备注当作风险已解决的证明——它只是本地阅读记录，不改变历史发生的事实。

### 3.3 产品分层边界

审计 Tab 现在能提供的价值，和团队规划中的下一阶段价值，性质不同，必须在产品定位上明确拆开，避免 V2 为了显得"功能完整"而伪造干预能力：

| 层级 | 状态 | 职责 | 本次 V2 范围 |
|---|---|---|---|
| **Audit Report（审计报告）** | 当前 | 描述事实、解释异常、提供证据、允许添加个人复核备注 | 是——本文档的全部内容 |
| **Optimization（优化建议）** | V2 仅限诊断与文字建议；下一阶段才提供真实优化能力 | V2 可解释粗粒度上下文构成、识别规则可直接判定的结构性浪费，并给出不可执行的建议文字；逐技能/逐工具细分、相对浪费和真实优化能力按版本后移 | FR-04a、FR-04b 属于 V2；不提供任何会改变 Agent 行为的控制 |
| **Guardrails（护栏与干预）** | 后续 | 预算上限、危险操作前置审批、失败循环熔断、模型使用限制等真正能改变 Agent 行为的控制 | 否——在该能力真实存在前，V2 不得出现任何形似"审批/拦截/暂停"的控件 |

这条边界直接约束 FR-10（个人复核备注）、§8（图表分级）和验收标准：**任何控制按钮存在的前提是它背后有真实生效的能力，而不是“看起来该有”。**

## 4. 用户与使用场景

### 4.1 会话监督者

典型用户：开发者、Agent 使用者。

核心问题：

- Agent 刚才是否执行了危险操作？
- 哪个步骤需要我检查？
- 这是误报、正常审批还是实际风险？

成功标准：能在一个页面内完成判断、定位、查看证据和添加个人备注。

### 4.2 成本审视者

典型用户：团队 Owner、自付费用户。

核心问题：

- 本次会话费用大约是多少？
- 成本从哪一段开始增加？
- 模型切换、缓存或上下文是否存在异常？

成功标准：看到可解释的估算及其构成，不把估算误认为账单。

### 4.3 复盘与导出使用者

典型用户：开发者、事后复盘人员。

核心问题：

- 哪些 finding 有个人复核备注？
- 当时记录了什么判断依据？
- 能否导出本次会话的审计记录？

成功标准：导出内容包含原始 finding、个人备注、规则版本和估算假设。团队级操作者身份、不可变审计日志和合规证据不属于 V2。

## 5. 核心概念与口径

### 5.1 Finding 唯一标识

V2 必须使用稳定的 finding ID。推荐结构：

```text
findingId = sessionId + rule + normalizedEvidence + occurrenceGroup
```

`normalizedEvidence` 的规范化算法和 `occurrenceGroup` 的生成规则必须版本化；同一会话新增相同 occurrence 时不得改变已有 finding ID。不得仅以 `rule + evidence` 作为跨会话身份。

### 5.2 引擎事实与个人备注

每个 finding 包含两个不可由用户修改的引擎维度：

1. 引擎严重度：`critical | warning | info`；
2. 流程类型：`risk | approval | system | context | cost`。

V2 另提供可选的个人复核备注（`AuditReview`），只记录“我看过并留下了什么备注”。备注不是 finding 状态，不包含 safe/high-risk/ignored，不参与异常计数、排序或显隐。引擎严重度、发生次数和证据始终保持不可变并可见。

### 5.3 异常信号定义

V2 顶部“异常信号”使用固定口径：

```text
异常信号 = 去重后的 finding
         且 severity ∈ {critical, warning}
         且未被明确识别为已闭环的正常审批流程
```

异常信号数量完全由引擎事实计算，与个人备注无关。审批闭环的判断必须来自关联的 request/decision 事件，不得只根据规则名称推测。

### 5.4 计数口径

- 所有用户可见汇总均基于去重后的 finding；
- 总数 = 去重后的全部 finding 数量；
- 异常信号数 = §5.3 定义的集合大小；
- 有备注数单独统计，不与异常信号数相加减；
- 过滤后的列表数量必须与当前选中筛选器一致；
- 原始命中次数只在详情中以 `×N` 展示；
- V2 不提供隐藏 finding 的“忽略”状态；所有引擎事实始终可见。

## 6. 页面信息架构

页面从上到下分为四层（较 V1.0 少一层——费用不再单独占一整层，并入结论行与展开详情）：

1. 会话运行报告（结论 + 核心指标合并为一行）；
2. 会话健康时间线（时间线与资源趋势合并为一张图，共享 x 轴，可切换纵轴）；
3. 关键发现（异常摘要卡，指向证据而非处置按钮）；
4. Finding 历史队列（可筛选搜索，含行内详情与低权重个人备注入口）。

## 7. 功能需求

### FR-01 会话结论栏

页面顶部必须显示下列状态之一，**语言必须是陈述发现的事实，不是要求用户裁决**：

- `本次发现 N 个异常信号`（N = §5.3 定义的集合大小，N ≥ 1）；
- `未发现异常信号`（N = 0 且 finding 数据完整）；
- `数据不完整 · 已观测到 N 个异常信号`（数据不完整且 N ≥ 1）；
- `审计数据暂不完整`（数据不完整且尚未观测到异常；不得表达为“安全”）。

数据完整性与异常信号是两个可组合维度：数据不完整不能覆盖已经观测到的风险。只有 findings projection 本身不可用时才不显示异常数量；其他 projection 缺失时仍显示已观测到的异常，并在同一结论栏标注缺失范围。异常信号数量只由 §5.3 的引擎事实计算，与个人备注无关。

辅助信息包括：

- 有个人备注的 finding 数量；
- 数据更新时间或完整性提示。

不得把个人备注当作异常已解决的证明；个人备注不参与结论栏数字计算（§3.1、§5.2）。

### FR-02 结论行核心指标

结论栏下方以一行紧凑统计呈现（不是四张独立 KPI 卡片，避免与费用摘要、时间线重复占用首屏面积）：

1. 费用估算（收起状态下总费用的唯一出现位置，见 FR-06）；
2. 上下文峰值；
3. 可选的突出异常摘要——仅在存在规则直接支持的聚合信号时显示，例如“连续工具失败 5 次”；不得使用会话间语义会变化的兜底指标强行占位。不固定展示缓存命中率（无基线时它不构成头条信息，见 FR-05）。

每项必须包含分母、基线或解释性副文案，数据缺失时显示明确状态（"未上报""无法估算"），禁止只有百分比而没有分母或时间范围。

### FR-03 会话健康时间线（事件层）

FR-03 与 FR-04 渲染为**同一个组件**——「会话健康时间线」。底层 x 轴唯一采样单位是模型请求序号 `requestSeq`，turn 仅作为背景分组和标签；不得把一个包含多次请求的 turn 当成单一原始样本。通过 `[上下文] [Token] [费用]` 切换纵轴曲线，同一时刻只显示一条曲线，不叠加多轴；事件标记在任意纵轴下保持相同的 `requestSeq` 位置。

事件层展示：

- finding 严重度标记；
- 审批请求与审批结果；
- 模型切换；
- compaction（**已实现**：`compaction/start`·`summary`·`end`·`prune` 四类事件，见 §9.3a；`prune` 自身不带 turn，从 `turn/start`·`turn/end` 顺延——只喂 compaction 事件、不喂 turn 边界会让每条 prune 的 turn 落成缺失，实现时踩过这个坑）；
- 连续工具失败等关键行为。

交互要求：

- hover：预览事件摘要；
- 点击：固定选中，并定位、展开下方 finding；
- 再次点击：取消固定；
- 键盘方向键可在事件间移动；
- 图例可控制事件类型显隐；
- 选中状态不能只依赖颜色。

默认规则：

- 首次进入时，若 finding 跨越至少 3 个 turn 或存在明显事件聚集，则展开；
- 否则折叠为一行摘要；
- 用户选择需在本设备记忆；
- 不得仅以 finding 数量决定展开状态；
- 模型切换标记默认为低视觉权重的细刻度（不与风险事件同一视觉优先级）；只有当切换点与成本跳变、缓存命中率骤降或上下文占用异常同时出现时，才升级为突出标记——正常切换本身不是异常，不应制造图表噪声。

### FR-04 上下文/Token/费用曲线（纵轴层，与 FR-03 共享容器）

`[上下文]` 纵轴展示每次请求的：

- 当前上下文占用；
- 模型上下文上限；
- 会话峰值；
- compaction 前后变化。

`[Token]`、`[费用]` 纵轴分别展示截至该请求的累计曲线，事件标记跨纵轴保持一致位置。视觉上可以显示 turn 分组，但 tooltip 必须显示 `turn · request n/m · requestSeq`。

指标必须来自**单次请求**数据，不得使用会话累计输入 Token 推算当前上下文。若因像素密度按 turn 降采样：上下文取该 turn 内请求峰值；Token 和费用取该 turn 内增量并绘制累计值；tooltip 必须允许查看 turn 内全部请求，不得掩盖内部峰值。

`contextTokens = uncachedInputTokens + cacheReadTokens` **已交叉验证通过**（§16 第 2 项）：真实会话 687 个请求点，逐点核对无一超过当次 `contextWindow`——若这个推导是错的（比如 `inputTokens` 其实是累计值而非当次值），必然会出现超过分母的点，687 个点里 0 个超出，是这个推导成立的强证据，不是自我声明。字段不足（如缺 `cacheReadTokens`）时该点的 `contextTokens` 必须留空，不得用部分和顶替；隐藏 `[上下文]` 视图的条件改为”该会话可算占用的请求点比例过低”，不是”推导本身未验证”。

模型切换导致 context window 改变时，上限线必须同步变化，并标记模型名称；真实会话（session-e4b0be69，5 次模型切换）实测 `contextWindow` 全程恒为 1,000,000，pro/flash 两个模型窗口相同——**这只证明了”这次没变”，不能当成”永远不变”的证明**，上限线仍按最近一次 `request/context.contextWindow` 取值，不写死常量。

### FR-04a 上下文构成归因（回答"token 都去哪了"）

上下文峰值只回答"占了多少"，回答不了"占了什么"——这是用户四步追问链路（花了多少钱 → **token 去哪了** → 哪些浪费了 → 我该怎么办）里第二步的刚需，V1.2 把它划进 V2.1 是错的，本版拉回 V2。

**已实现**（core `context_composition()`，三处锁步）。真实会话实测：系统提示词 1,813 · 工具定义 7,646 · 技能目录 2,774（29 个技能）token，常驻合计 12,233（`est_tokens` 换算比例已切换为 DeepSeek 官方值，见 §16 第 12 项；本节数字是切换后的重新实测，不是旧比例的数字）。

要求：

- 按粗粒度类别拆分当前上下文（V2 实际只做 3 类**常驻前缀**，不是原规格设想的 5 类）：系统提示词（`request/header.data.header.system`）、工具定义（`header.tools` 序列化后文本）、技能目录；历史消息（user/assistant/tool-result）**不在这个函数的输出里**——它们不是"常驻"内容（每次请求都不同），要回答它们占多少，得用 FR-04 的 `contextTokens` 减去常驻合计，且这个减法必须带 §16 新增条款的那条警告；
- 技能目录识别依据 §16 第 10 项已确认的载体（`source.kind === "skill-catalog"`，挂在多种事件的 `entries` 字段上，取 `name + description` 拼接估算），不是专用事件类型；目录若中途重新发布，取**最后一次**发布的条目，不累加历次；
- V2 只做上述粗粒度拆分，**不做逐技能、逐工具的细粒度拆分**——那需要更细的归因规则和更多验证，留在 V2.1（§8）；
- 展示位置：不占首屏，作为上下文峰值指标或"关键发现"卡片的展开详情，符合 §3.1"低频信息放二级"的一贯要求；
- 诚实性要求与 FR-05/FR-06 一致：估算方法是 `est_tokens`（中文按 0.6 token/字符、其余按 0.3 token/字符——DeepSeek 官方换算比例，不是逐字符精确计），数值前必须有"约"或等价的估算标注，源事件（`request/header`、技能目录载体）从未出现时该类别显示"暂不可用"，不得用 0 顶替；
- **`est_tokens` 的换算比例已切换为 DeepSeek 官方值**（见 §16 第 12 项）：拿真实会话 550 段 assistant 输出（reasoning+text 合并）比对 provider 实际上报的 `outputTokens`，旧比例（CJK/1.5、其余/4）系统性低估 22.2%，官方比例（CJK×0.6、其余×0.3）低估 8.8%，明显更准，已经是 core/Python/wasm 现在的实现。这组误差率是用输出文本测的，FR-04a 估的是输入侧内容（系统提示词/工具定义），字符构成不同，误差率不能直接套用到这里的具体数字上——但换了比例之后 `est_tokens` 依然是估算，不是精确计数，"约"字样和"暂不可用"的降级规则不因为比例更准就可以省略。
- **常驻估算与 FR-04 的 `contextTokens`（provider 计数）不是同一个估算器，两者不能相减后当成精确的"未分类"数值**：真实会话首次请求的常驻估算是 12,233，provider 报的当次上下文是 13,959，差的 1,726 是首条用户消息与消息封套开销，不是常驻归因算漏了——这条差异必须在展开详情里用一句话说明，不能让用户以为两个数字应该对得上。

### FR-04b 结构性浪费识别与建议（回答"哪些浪费了""我该怎么办"）

**已实现**（core `waste.rs`/`waste.py`，规则码 `SV-COST-01`/`SV-COST-02`，不再是"待实现阶段确定"）。

"浪费"必须先分成两种，不能混着判断：

| 类型 | 判定方式 | 是否需要基线 | 归属 |
|---|---|---|---|
| **结构性浪费** | 规则可直接判定的事实，不依赖历史对比 | 不需要 | V2（本节） |
| **相对浪费** | 需要和历史/同类会话比较才能下结论（如缓存命中率偏低、上下文峰值偏高） | 需要 | 继续留在 V2.1，受 FR-05"无基线不告警"约束，不得提前 |

V2 覆盖两种结构性浪费模式：

- **`SV-COST-01` 重复工具结果**：同一个调用在 ≥2 个不同 turn 里得到完全相同的结果。判定键是 `(工具名, 参数, 结果内容)` **三元组同时匹配**，不是单看结果内容——只按内容分组会把"两次都读到空文件"这类巧合也算进来，语义上站不住；同一 turn 内的重复调用不算（更像同一工作单元里的正常校验，不是跨 turn 的重复劳动）。浪费量 = `est_tokens(内容) × (出现次数 − 1)`（第一次是必要工作，后续每次是纯浪费）。真实会话验证：796 个不同 (工具,内容) 组合，0 组重复——检测器在干净的正经开发会话上不报假阳性。
- **`SV-COST-02` 失败重试的上下文增量**：连续 ≥3 次工具失败之后，上下文实际增长了多少（用 FR-04 的 `contextTokens` 前后两次请求的差值衡量），**不是失败次数本身**——次数已经由 SV613 报过。这条**独立扫描**失败区间，不直接复用 SV613 finding 的证据：SV613 只锚定失败串的起点，不带终点，算不出区间内的 token 增量。找不到匹配的请求行、或区间前后上下文没有净增长（比如恰好发生了压缩）时不产出这条 finding，不倒扣负数、不拿其他 turn 的数字硬凑。真实会话验证：turn 70 一次 5 连失败，实测增量 1,964 token。

**明确排除**：`compaction/prune` 的 `shadowedTokenCount`（执行环境实测的被剪除 token 数，见 §9.3a）**不作为结构性浪费来源**。查过真实会话（session-e4b0be69）10 次 prune 具体剪了什么——全部是 turn 3 到 turn 60 里互不相同的一次性内容，不是重复读取，是上下文正常老化后被清理，不是浪费。这条本来是实现前的候选方案，验证过真实数据后主动排除：把正常的上下文管理标成"浪费"会让用户觉得系统在冤枉自己的正常行为。

每条结构性浪费必须包含：

- 影响量级估算（token 数，可选费用估算——费用估算由展示层用 `pricing.json` 折算，core 只给 token 数，不做定价）；
- 发生位置（turn/seq 区间）；
- 一句话建议级"怎么办"——面向用户如何调整 Prompt 或用法（例如"确认是否需要在每个 turn 重新调用「read」处理「config.yaml」"），具体到目标本身、可验证，不得使用"建议优化上下文"这类空泛表述；
- 建议是文字，**不是可点击执行的控制按钮**——V2 只到"告诉你怎么办"，不到"帮你做"，做到"帮你做"需要 §3.3 定义的 Optimization/Guardrails 层真实能力，属于 V3 范畴。

### FR-05 缓存命中率

基础公式：

```text
cacheHitRate = cacheReadTokens /
               (cacheReadTokens + uncachedInputTokens)
```

要求：

- 字段未上报时显示”未上报”，不得显示 0%；
- 没有历史或同类基线时，只显示中性结果；
- 只有存在可信基线时才能显示”偏低/偏高”；
- 点击后可查看 cached 与 uncached 构成、模型切换和时间变化；
- **不作为 FR-02 结论行或独立 KPI 卡片展示**——无基线时它是查证信息而非头条判断，只出现在费用摘要（FR-06）或上下文详情的展开区域。

### FR-06 费用估算

**收起状态下，总费用只在主信息层显示一次**：FR-02 结论行里的 `≈¥1,113.7`。点击/展开后允许展示逐模型、逐价格桶的构成金额，但不得再创建第二张总费用卡片或独立总费用摘要行。

默认摘要格式（作为结论行第一项，非独立区块）：

```text
≈ ¥1,113.7 估算 · 2 个模型 · 切换 5 次 · 查看构成
```

展开后展示：

- 逐模型费用；
- uncached input、cached input、output；
- 峰谷价格归属；
- 未知模型和未计价 Token；
- 价格表版本及更新时间；
- 计算假设；
- `估算值，不是账单` 声明。

字段缺失不得折叠为零。费用覆盖不足 100% 时显示覆盖率。

### FR-10 个人复核备注

审计 Tab 目前不具备暂停 Agent、阻止工具、修改审批策略、限制 Token/费用、优化上下文或改变模型选择的能力。V2 只提供当前设备上的个人复核备注，帮助用户记录理解和复盘线索；它不是风险处置，也不是团队级合规审计证据。

支持的操作：

- `[添加备注]`：记录个人判断依据，例如“该命令用于清理临时构建目录”；
- `[编辑备注]` / `[删除备注]`；
- `[复制证据]`：见 FR-11。

要求：

- 备注不得删除、修改、隐藏或重排原始 finding；
- 备注只属于当前 session 和当前浏览器资料，不跨会话继承；
- 新增、编辑和删除后显示即时反馈，删除支持撤销；
- V2 不声称记录操作者身份或提供不可变审计历史；团队级留痕需等待后端 registry、权限和审计日志能力。

## 8. 图表需求分级

### V2 必须

- 会话健康时间线（FR-03+FR-04 合并组件）：以 `requestSeq` 为底层采样轴、turn 为视觉分组，`[上下文][Token][费用]` 纵轴切换，事件标记常驻叠加。不再是两张并列图表。上下文来源未通过验证时按 FR-04 降级隐藏该视图；
- 上下文构成归因（FR-04a，粗粒度 3 类）：回答"token 去哪了"，V1.3 从 V2.1 拉回，展示位置为展开详情，不占首屏；
- 结构性浪费卡片（FR-04b）：不需要基线即可判定的浪费模式，附带建议级"怎么办"文字。

### V2 条件展示

- 无——费用曲线已作为会话健康时间线的一个纵轴选项，不再单独条件展示。

### 8.1 图表实现与框架引入门槛

V2 的会话健康时间线由 `SessionHealthTimeline` 组件以 **React + 原生 SVG** 渲染；不引入 Chart.js、Recharts、D3、uPlot 或其他专用图表框架。理由不是图表类型不足，而是 V2 只有一张请求级折线图，需要与 finding 队列精确双向联动、继承 DSH `--dsw-*` 设计变量，并提供可键盘操作的事件标记与文本替代；这些能力用原生 SVG 更直接、包体更小、可测试性更高。

组件输入必须与渲染实现解耦，至少包含 `metrics`、`events`、`mode`、`selectedEventId` 和 `onSelectEvent`。后续可替换绘制层，但不得改变指标口径、事件选择语义、列表联动或无障碍契约。

在单会话可见请求点不超过 1,000 时，使用 SVG；超过时先按显示像素宽度降采样曲线，保留全部 finding、模型切换和 compaction 事件。只有满足以下任一条件，才建立专项方案评估图表框架或 Canvas 渲染：

- 单会话需要在不损失交互精度的前提下展示超过 1,000 个请求点；
- 产品已确认需要缩放、框选、平移或多图联动；
- V2.1/V3 出现多个可复用的复杂图表，且原生 SVG 的性能或维护成本已有可复现证据。

无论采用何种绘制层，图表库不得自带独立主题、不可访问 tooltip 或与 DSH 冲突的全局样式；事件必须仍以形状、文本和列表记录辅助颜色表达。

### V2.1（Optimization 洞察层，§3.3）

- 上下文开销归因的**细粒度**拆分：逐技能、逐工具的常驻成本（FR-04a 只做粗粒度 3 类，逐项拆分需要更多验证，留在这里）；
- 缓存命中历史基线，以及依赖基线的**相对浪费**判定（FR-04b 已把不需要基线的结构性浪费留在 V2，本层只做需要基线才能下结论的部分）；
- 能力尚未上线前，只允许陈述式卡片"发现潜在优化机会"，不得附带看起来可执行的控制按钮（§3.3）。

### 明确不做

- Severity 饼图；
- Token 四桶环形图；
- 无分母的仪表盘；
- 与 finding 无联动的装饰性趋势图；
- 单独占据首屏的模型切换流程图；
- 两张共享横轴的图表并列摆放而不做纵轴合并（V1.0 的已知缺陷，§2）。

## 9. 数据需求与契约

### 9.1 Finding

```ts
interface AuditFinding {
  id: string
  sessionId: string
  rule: string
  ruleVersion: string
  severity: 'critical' | 'warning' | 'info'
  processType: 'risk' | 'approval' | 'system' | 'context' | 'cost'
  category: string
  toolName?: string
  evidence: string
  occurrenceCount: number
  seqs: number[]
  time?: number
  turn?: number
  step?: number
  callId?: string
  contextBefore?: AuditEvent[]
  contextAfter?: AuditEvent[]
  wasteTokens?: number
  suggestion?: string
}
```

**turn/step/callId 已实现**（core `Coords`，行为规则与轨迹检测器共用）：三者覆盖率天然不齐，不是缺陷——真实会话实测 `tool/call` 三者 100% 自带；`approval/asked` 只有 `callId`，`turn`/`step` 从最近的 `turn/start`·`step/start` 顺延；顺延值只在对应 turn/step 边界内有效，边界外（如首个 turn 之前的 `sandbox/mode`）三者均为 `null`，不臆造。

`wasteTokens` 与 `suggestion` 仅用于 FR-04b 的结构性浪费卡片；`suggestion` 是展示给用户看的建议文字，不是可执行指令。**规则命名空间已确定**：`SV-COST-01`（重复工具结果）、`SV-COST-02`（失败重试的上下文增量），与 `SV601`–`SV614` 分属不同前缀，避免和官方行为规则registry 混淆；`category` 统一为 `'cost'`。

原规格的 `wasteEstimate: { tokens: number; costEstimate?: number }` 嵌套对象**未采用**，改为扁平的 `wasteTokens: number`——费用估算是展示层用 `pricing.json` 折算的结果（与 FR-06 的定价路径一致），不该由数据引擎预先算好再传下来，避免两处定价逻辑分叉。

### 9.3 请求与上下文趋势

**已实现**（core `request_metrics()`）。真实会话验证：687 个请求点，逐请求四桶之和与按模型汇总的四桶之和逐字节相等（同源不变量，两侧各有测试钉死）。

```ts
interface RequestMetric {
  sessionId: string
  requestSeq: number
  seq: number
  time: number
  turn: number
  step?: number
  model: string
  contextTokens?: number
  contextWindow?: number
  uncachedInputTokens?: number
  cacheReadTokens?: number
  outputTokens?: number
  cacheWriteTokens?: number
}
```

原规格的 `compacted?: boolean` **已删除**：压缩是独立于单次请求的事件（同一 turn 内不一定对应哪个具体 request），硬塞成每行一个 true/false 既不准确、也等于给每一行都下了"查过了"的断言。压缩改为独立的 §9.3a `CompactionEvent` 契约。

字段命名口径：核心引擎（core/wasm）与执行环境投影发布的字段名都是 `snake_case`（`context_tokens`、`uncached_input_tokens` 等），不是本表这里为可读性用的 `camelCase`——投影层没有再套一层重命名，直接透传 wasm 输出，是为了避免命名映射本身成为又一处容易漂移的地方。客户端消费时按 `snake_case` 读取。

### 9.3a 压缩事件（`CompactionEvent`）

**新增**（V1.5）。回答"上下文什么时候被压缩、剪掉了多少"，`prune` 的丢弃量是**执行环境实测值**，provenance 与 §9.3/FR-04a 的 `est_tokens` 估算不同，展示层必须分开标注，不得混用。

```ts
interface CompactionRun {
  compactionId: string | null
  startSeq?: number
  startTime?: number
  turn?: number
  endSeq?: number
  hasSummary: boolean
}

interface CompactionPrune {
  seq?: number
  time?: number
  turn?: number
  shadowedTokenCount?: number  // 执行环境实测；缺则 null，不是 0
  shadowedSeqCount?: number
}

interface CompactionEvents {
  compactions: CompactionRun[]
  prunes: CompactionPrune[]
  prunedTokensTotal: number       // 只累加真正上报了 shadowedTokenCount 的那些
  prunesWithoutTokenCount: number // 缺口计数，单独暴露，不混进合计
}
```

`prune` 自身不带 `turn`，从 `turn/start`·`turn/end` 顺延；`compaction/start`·`summary`·`end` 三个事件按 `compactionId` 归并成一条 `CompactionRun`，不是三条。`prunedTokensTotal` **不进 FR-04b 的浪费判定**（见 FR-04b"明确排除"一节）。

## 12. 非功能需求

### 12.1 性能

- 首次可用内容在 projection 返回后 300ms 内完成渲染；
- 500 个去重 finding 下交互保持流畅；
- 大列表优先使用虚拟化或分页；
- V2 会话健康时间线使用 React + 原生 SVG，不引入专用图表框架；
- 可见请求点 ≤ 1,000 时 SVG 交互保持流畅；超过时曲线按显示像素宽度降采样，但 finding、模型切换和 compaction 事件不得丢失；
- 图表框架或 Canvas 渲染只可在满足 §8.1 的评估门槛后引入，且不得引入明显阻塞主线程的第三方依赖。

### 12.2 安全与隐私

- evidence 可能包含路径、命令和敏感上下文；导出前保持现有脱敏规则；
- 页面不得向外部服务发送审计数据；
- localStorage 中不得存储跨会话的全局豁免规则；个人备注必须以 sessionId 隔离；
- 导出文件应包含脱敏状态说明。

### 12.3 国际化

- **本条约束的范围是插件新增的面向用户文案，不含执行环境既有 UI**：DSH 执行环境
  自身的术语（如 `Session log`、`Workspace Write`）遵循执行环境自己的语言
  策略，插件不得为了满足这条而重新翻译或包裹执行环境已有文案——那样反而会
  制造插件与执行环境术语不一致的新问题（P2-03）；
- 插件新增文案（结论栏、KPI 卡、时间线、Finding 队列、导出等）中，中文和
  英文文案均来自 i18n 字典；
- 插件新增的用户界面不得出现无解释的中英文混排；
- `TOOL / APPROVAL` 应显示为本地化名称，内部枚举仅用于代码。

## 15. 验收标准

### AC-01 结论与计数

- 给定 8 条原始 finding，其中 2 组重复、2 条带个人备注；
- 顶部、过滤器、标题和列表必须使用同一套去重口径；
- 新增、编辑或删除个人备注不改变异常信号数量；
- 任意筛选下，显示数量等于实际列表数量。
- 当数据状态为 partial 且已观测到 3 个异常信号时，结论栏同时显示“数据不完整”和“已观测到 3 个异常信号”，不得隐藏任一信息。

### AC-02 个人备注隔离

- 在 session A 中为 finding 添加备注；
- session B 中相同 rule/evidence 不继承该备注；
- 回到 session A 时备注仍存在；
- 删除备注不影响 finding 本身及其计数。

### AC-03 费用诚实性

- 有费用时始终显示 `≈` 或“估算”；
- 展开后可查看计算假设；
- 未知模型不计价，并显示未计价 Token；
- 字段未上报时不显示为零；
- 没有可计价数据时不显示 ¥0。

### AC-04 图表联动

- 点击时间线 finding 后，对应列表行被定位并展开；
- 列表选择同步高亮时间线；
- 切换 `[上下文][Token][费用]` 纵轴时，事件标记位置保持不变，选中/固定状态不丢失；
- 模型切换和 compaction 具有独立图例，且模型切换默认为低权重刻度，仅在与成本/缓存/上下文异常同时出现时升级为突出标记；
- 键盘可以完成同样的选择流程。
- 上下文计算未通过验证或字段不足时，`[上下文]` 视图隐藏并显示不可用原因；不得用累计 Token 代替。
- V2 不引入专用图表框架；时间线通过 `SessionHealthTimeline` 的输入/回调契约与 finding 队列联动。超过 1,000 个可见请求点时，曲线可降采样，但所有事件标记及其键盘可达性必须保留。

### AC-05 个人复核备注

- 添加、编辑、删除备注和复制操作有成功或失败反馈；
- 备注不改变 FR-01 异常信号计数、finding 排序或可见性；
- 删除备注后用户可撤销；
- critical finding 添加备注后仍保持原严重度和原排序位置。

### AC-06 响应式

- 320px、768px、1280px 三个宽度无页面级横向溢出；
- 小屏不依赖 hover；
- 核心结论、过滤器和备注操作始终可访问。

### AC-07 可访问性

- 全流程无需鼠标即可完成；
- 图表具备文本替代；
- 展开、选中和动态反馈可被屏幕阅读器识别；
- 自动化检查无严重级问题。

### AC-08 上下文构成与结构性浪费诚实性

- 上下文构成归因（FR-04a）的每个类别数值前带估算标注（如"约"），说明可展开查看计算方法；某类别数据缺失时显示"暂不可用"，不得用 0 或省略该类别替代；
- 结构性浪费卡片（FR-04b）不得出现依赖基线的判断（如"缓存命中率偏低"）——混入即判定为缺陷；
- 每条结构性浪费卡片必须同时包含影响量级、发生位置（turn/seq）和建议文字三项，缺一不得展示；
- 建议文字旁不得出现可点击执行的按钮（如"一键优化""自动清理"），仅可提供"查看证据"这类指向性入口。

### AC-09 导出与复制（P2-01 新增）

- 点击"导出 JSON"必须产生可验证的完成或失败反馈——浏览器下载事件、成功提示（含文件名），或失败提示（含可诊断原因），三选一，不得五秒静默；
- 导出的 JSON 包含 FR-12 §7 定义的全部字段（`sessionId/exportedAt/ruleVersion/findings/reviews/usage/costEstimate/pricingVersion/assumptions/missingFields`），缺失字段进 `missingFields`，不得省略键；
- 导出内容遵循与页面展示一致的脱敏规则（见 §12.2）；导出文件包含脱敏状态说明；
- 自动化测试对导出结果做字段完整性断言，不能只靠人工点一次确认"看起来对"。

### AC-10 页面状态（P2-01 新增）

- §10 表格里的每一种状态（加载中/暂无数据/Clean/Partial/Error/超过 20 条/剪贴板失败/无价格/字段未上报）都必须有对应的 UI 呈现和自动化断言；
- Error 状态必须同时验证：失败原因文案、重试入口、已成功加载的部分数据仍然可见三者都在；
- Partial 状态必须同时验证："数据不完整"提示与已观测到的异常数量同时出现，不得互相覆盖（呼应 AC-01 最后一条）。

### AC-11 性能与规模（P2-01 新增）

- 500 条去重后 finding 时，过滤、搜索、展开操作保持可用（不要求量化到具体毫秒数，但不得出现界面卡死或事件丢失）；
- 1,000 个请求点以内，时间线以全量精度渲染；超过 1,000 个请求点时曲线降采样，但 finding、模型切换、compaction 事件标记必须一条不丢，且全部保留键盘可达性（§8.1、AC-04）；
- 至少一条自动化测试使用 >1,000 请求点的 fixture 验证上一条。

### AC-12 隐私与隔离（P2-01 新增）

- 个人复核备注按 `sessionId` 隔离，session A 的备注不得在 session B 中出现（AC-02 已覆盖，本条明确写入验收清单，避免遗漏）；
- 不存在任何跨会话生效的全局豁免规则（呼应 §12.2 "localStorage 中不得存储跨会话的全局豁免规则"）；
- 导出文件的脱敏状态与页面展示的脱敏状态一致，不得导出比页面展示更多的原始信息。

### 16.3 示例数据与验收 fixture 分离（P2-04）

本文档正文（尤其 FR-04a、§16.2）引用的具体数字（如系统提示词 1,813
token、687 个请求点）都来自**某一次真实会话在某一天的采样**，标注了
session 与采样日期的即为示例/验证记录，不是恒定不变的产品行为——同一
产品逻辑跑在不同会话上，得到合法但不同的数字（例如另一次采样可能是
19.6K 而不是 12,233）完全正常。**自动化验收必须使用独立、冻结的 fixture**
（`fixtures/`、`scripts/verify-*.mjs` 里手写的数据集），断言的是"这份
固定输入应该产出这个固定输出"，不是把文档里的示例数字焊死成页面的期望
值——文档示例更新（比如换一次采样、换一个 session）不应该触发任何自动化
测试失败。

## 17. 原型说明

原型用于表达信息层级和交互方向，不作为像素级最终视觉规范。开发时应：

- 使用 DSH 现有设计变量；
- 与 Chat、Trajectory 的边距、字体和滚动行为一致；
- 保持 findings 队列为视觉主体；
- 用实际可访问组件替代原型中的纯视觉元素；
- 以真实数据验证图表密度、极值、空状态和异常状态；
- 原型中出现的具体数值（如上下文上限 "128K"）均为占位，不是真实 `contextWindow`；开发时以 `request/context.contextWindow` 的实际上报值为准（§16 第 2 项——已确认，真实值是 1,000,000，不是 128K）。
- 关联的 V2 原型仍包含少量 V1.1 遗留内容（如未经验证的归因结论）；实现时必须以 V1.6 正文为准，后续视觉稿应移除这些内容。
- FR-04a 展开详情里的 token 数字（系统提示词/工具定义/技能目录）都经过 `est_tokens` 估算——比例已切换为 DeepSeek 官方值（§16 第 12 项），但仍是估算不是精确计数；原型上这些数字的"约"字样必须保留，不能因为界面好看就去掉。
