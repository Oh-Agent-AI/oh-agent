# 城市地图编辑器路线图（按优先级）

> 状态：P0 已完成（2026-10-12，见 §P0-1.5 / §P0-2.4 实施记录）；P1 起待排期。分支 `worktree-city-plan-repair`。
> 上游：`CITY_PLAN_MANUAL_REPAIR_SPEC.md`（编辑器现状，§13–§17）、`CITY_SITE_REGISTRY_SPEC.md`（对象注册表 B0–B4）。
> 两层架构不变：city-opt 是**默认地图生成器**，本分支是**用户地图编辑器**；编辑器只读生成器的导出，不改生成器文件
> （需要生成器改动的条目单列为「前置」，由 city-opt 线自决）。

## 0. 排序依据

1. **会不会让用户丢东西或用不了**——先修。main 已把默认时间窗从 30 天改为 366 天（`7f1938ec`），
   真实用户的城市会接近最大档（4000 栋），而编辑器只在 ≤ 380 栋上验证过交互。
2. **编辑能力缺口的频度**——用户已经点名的（改路型、过河、转角）优先于没提过的（景观、框选）。
3. **工程成本**——同档里先做小的。

## P0-1 大城市性能

### 1.1 实测（`scripts/bench-plan-editor.mjs`，2026-10-12，M 系列 Mac，node 22）

| --- | --- | --- | --- | --- |
| 生成器出图（参考，生成器的事） | 13 451 | 29 710 | 64 384 | 数据刷新/换种子 |
| `layoutCity`（命中规划缓存） | 78 | 466 | **1 322** | **每次编辑提交**（见 1.2） |
| `applyPlanPatch`（一条画路） | 2.5 | 3.9 | 6.8 | 每次提交 |
| `validateRoadAdd` | 1.0 | 0.7 | 1.6 | 画路悬停 |
| `validateEdgeDrop` | 18 | 150 | **727** | **橡皮擦悬停** |
| `validateNodeMove` | 0.4 | 1.7 | 2.3 | 拖路口悬停 |
| `bulldozeForRoads`（试算一笔穿楼的路） | 229 | 309 | **8 858** | **画路/拖路口悬停**（有推平/安置时） |
| 选中会话楼的 40 个候选地块 | 26 | 86 | **331** | 选中 |
| `auditLayout` | 66 | 664 | **3 602** | 点「体检」 |
| `snapPoint` / `nearestEdgeAt` / `pickSite` | ≤ 0.6 | ≤ 0.6 | ≤ 0.6 | 悬停 |

规模：4000 楼时 2402 路段、1533 路口、8815 地块、332 处设施。

### 1.2 问题

- **悬停卡死**：4000 楼时画一条穿楼的路，悬停试算要 8.9 秒（推土机安置 4 栋会话楼）；橡皮擦每移一下 0.7 秒。
  §16.2 把预览改成推土机试算是对的（预览与结果一致），但没在大城市上测过。
- **每次提交都全量重排**：`CityEngine.setPlanPatch` → `applyModel` → `layoutCity`。道路/设施编辑根本不需要重排
  （`layoutCity` 只为移楼的 pins 存在），却每次付 1.3 秒，再加场景重建（未测，见 1.4 第 1 步）。
- **体检 3.6 秒**：按需触发、可接受但不舒服；提交后面板开着时会自动重跑，等于每次编辑多 3.6 秒。

### 1.3 设计

预算（4000 楼）：**悬停 ≤ 16 ms**（一帧）、**选中 ≤ 50 ms**、**提交 ≤ 300 ms**（不含场景重建）、**体检 ≤ 300 ms**。

1. **提交分级**（CityEngine）：补丁变化只涉及 `roadOps/highwayOps/siteOps/suppressedContext` 时，直接在缓存的
   `baseLayout` 上重套补丁（7 ms），不调 `layoutCity`；只有 `buildingMoves` 增删才走 `layoutCity`（pins 必须在落位阶段生效）。
   需要确认的不变量：没有 buildingMoves 变化时，`layoutCity(model, previous)` 与缓存的 `baseLayout` 相同——守卫断言之。
2. **空间索引**：规则层现在逐条扫全城路段/地块/障碍。加一个随布局对象缓存的网格索引（WeakMap，按布局回收，同 `obstacles()` 的做法），
   给 `rectClearOfEdges`、`reservedParcelIds` 的命中查询、`validateBuildingMove`、`edgeAt`、`hitsBy` 用。
   `planner/` 里已有 `SegmentIndex`，优先复用（只读导入，不改它）。
3. **推土机**：安置循环里每安置一栋就全量 `applyPlanPatch` + 从近到远对每块地完整校验。改为：一次算出占用集合，
   候选先用 O(1) 的「地块被占？」筛掉，再做完整校验；安置后增量更新占用集合，不重套补丁；最后只套一次补丁验证。
4. **悬停降级**：试算超过 16 ms 的，悬停时先给 `roadImpact` 的估计（已有，琥珀色 + 「约」字），鼠标停住 150 ms 后再跑精确试算并替换；
   提交永远跑精确的。预览与结果「一致」的承诺改为「停住后一致」，并在面板上区分「估计」与「确切」。
5. **橡皮擦**：`validateEdgeDrop` 的「楼会不会失去道路/断网」是全城连通性检查。改为只检查被擦路段两端各 N 跳内的局部连通性
   （删一条边只可能把与它相邻的部分切开），全城检查留到提交时。
6. **体检**：同样走空间索引；面板开着时提交后**不自动全量重跑**，只标「可能已过期，点刷新」。

### 1.4 步骤与验收

1. 先补测场景重建：在浏览器里测 4000 楼一次编辑的「提交 → 可交互」总时长（`performance.mark`），拆成 补丁/重排/场景 三段。
2. 1.3-1（提交分级）→ 1.3-2（索引）→ 1.3-3（推土机）→ 1.3-5 → 1.3-4 → 1.3-6，每步跑 `bench-plan-editor.mjs` 记一行数。
3. 验收：4000 楼下上表加粗各项达到 1.3 的预算；`verify-plan-*` 全绿；索引前后所有校验结果逐字相同（守卫：在真实城市上对 200 个随机操作比对新旧实现）。

### 1.5 实施记录（2026-10-12）

| 4000 楼 | 实施前 | 实施后 | 预算 |
| --- | --- | --- | --- |
| 推土机试算 | 8 858 ms | 28 ms（悬停移动中给估计，停住 150 ms 再跑） | 悬停 ≤ 16 ms ✅ |
| 擦路校验（首次 / 之后） | 727 ms | 11 ms / 3 ms | ✅ |
| 选中会话楼的 40 个候选 | 331 ms | 17 ms | ≤ 50 ms ✅ |

- **提交分级**：`CityEngine.setPlanPatch` 比较前后补丁的移楼钉子（`pinsKey`；无移楼 = 无钉子 = 与无补丁同键——首版把档位拼进键，空补丁与无补丁不同键，
  浏览器实测仍每次全量重排，已修）；钉子不变沿用缓存的 `baseLayout`。移楼仍走 `layoutCity`（~0.9 s，钉子必须在落位阶段生效）。

- **缓存与索引**（`planGeometry`）：按布局缓存地块索引、占用集合、落位表、地面路网格；按模型缓存楼索引。缓存命中核对来源数组引用**与元素数**

- **结果逐字不变**：`rectClearOfEdges` 包围盒粗筛、`rectClearOfRoads` 只查网格邻域、擦路只重算「最近路恰被擦」的楼、推土机先用占用集合筛——

## P0-2 扩档不丢修改

### 2.1 问题

`scaleTierFor = ceil(会话数 / 400)`。会话数跨过 400 的倍数，城市升档：岛按原形状放大、地块与路口全部重排。补丁记着自己写在哪一档，
档位不符就**整份作废**（`tier-changed`，§16.5 只做了横幅提示和一键清除）。366 天窗口下，活跃用户每隔几周就会跨档一次——
用户的感受是「我改好的地图过几天全没了」。

生成器对会话楼已经做了跨档迁移（`cityLayout.ts`：按 `新岛半径 / 旧岛半径` 把每栋楼映射到放大后原位置附近的空地块），编辑器的补丁应同样处理。

### 2.2 设计：补丁 v2，每条操作带锚点坐标

重定位需要知道每条操作「当时在哪里」。现状：
- 道路 add/move、高架、自由级设施搬家的目标本身就是坐标——可直接缩放；
- 路段 drop、路口 move 引用的 id 由坐标派生（`x:z`、`from/to`）——可解析出坐标；
- 设施操作带 `at`；街区/地块目标 id 里有面多边形坐标——能解析但脆弱；
- `buildingMoves` 只存目标地块 id。

**v2**：`PlanPatchV2` 给每条引用型操作加 `anchor: Vec2`（写入时记下被引用对象的中心），`buildingMoves` 改为
`{ parcel: string; anchor: Vec2 }`。读 v1 存档时一次性迁移：能从 id 解析出坐标的补 anchor，解析不了的保留原样（只能同档使用）。

**重定位**（`remapPlanPatch(patch, fromTier, toTier, ratio, layout)`，纯函数）：

| 操作 | 规则 |
| --- | --- |
| 画路 / 高架 / 自由级搬家目标 | 坐标 × ratio，照常重放 |
| 删路段 / 拖路口 / 切高架 | anchor × ratio 后找最近的同类对象，容差 `6 × ratio`；找不到 → 单条 `remap-failed` |
| 设施拆除 / 搬家 | `at` × ratio 后找最近的同类设施（同 kind），容差同上；街区/地块目标按 anchor × ratio 找最近的合法目标 |
| 移楼 | anchor × ratio 找最近的空地块（与生成器迁移同一规则）；找不到 → 单条失效，楼按常规落位 |

- 重定位结果**作为新的一版补丁提交**（可撤销），原补丁归档到存档的 `history[tier]`（每档留一份），用户可以在面板上「恢复旧档修改」比较。
- 面板：横幅改为「城市扩大了一档，已为你的 N 处修改重新定位，M 处没找到对应位置（查看）」。失效条目在体检里逐条列出并能定位。
- 不承诺跨档后一模一样：新档的路网是生成器重新长出来的，用户画的路会接到新路网上，结果可能与原意略有出入——这是如实的代价。

### 2.3 验收

- 守卫：真实城市 380 → 420 楼（1 → 2 档）、1600 → 2000（4 → 5 档）各造 30 条混合操作的补丁，跨档后重定位成功率 ≥ 80%，
  失败条目都有 `remap-failed` 记录，补丁重放无其他失效；同档读写 v2 存档与 v1 行为一致；v1 → v2 迁移幂等。
- 降档（会话数减少）同样处理（ratio < 1）。

### 2.4 实施记录（2026-10-12）

- **不升补丁版本号**：锚点做成可缺省字段（`roadOps.drop/move.anchor`、`siteOps.move.toAnchor`、`siteOps.cls`、`moveAnchors`、`islandRadius`），
  v1 存档照读；没锚点的旧条目按 §2.2 的回退规则处理（路段/路口 id 自带坐标；移楼与街区/地块目标没有 → 单条失败）。
- **设施按类别匹配**（`siteOps.cls`，如 `civic/school`）：公共设施 id 是序号，跨档后同号可能是另一种设施——首版按 id 前缀 + 近距离匹配，
  真实城市里设施搬家 4/4 失败。现在搬家在同类里取最近的（不限距离：意图是「这种设施放到那儿」），拆除限 80 内；目标街区/地块取缩放位置附近**合法**的
  （`siteMoveProblem`），不是最近的。
- **重定位不进撤销栈**：撤销回旧档补丁在新地图上画不出来，下一次同步又会自动重定位，等于空转；旧档撤销历史一并清空。原补丁存入
  `archive[种子][旧档]`。
- **触发**：界面胶水的 `syncInfo`（数据刷新、进入修复模式、每次编辑后都会调）发现档位不符即调 `remapForTier()`，不等用户进修复模式。
- **验收**（`verify-plan-remap.mjs`，登记 planning 组，计数锁 74）：合成城市 1 → 2 档每类操作精确落到放大后的对应对象、降档可逆；
  真实城市 380 → 420 楼 **93%**（26/28）、1600 → 2000 楼 **86%**（24/28），重放无失效，耗时 61 / 162 ms；失败的多是新档里那附近没有空街区可放设施、
  路网重长后附近没有对应的路。浏览器：1 → 10 档（×2.24）2/2 重定位，横幅如实显示，原补丁已存档。

## P1-3 设施落位走生成器判定（注册表 B3）

city-opt 已导出 `checkSitePlacement`（`d500ffc7`）。按 `CITY_SITE_REGISTRY_SPEC.md` §5/§10 B3 实施：`planSites.siteMoveProblem`
的街区级/地块级判定改调生成器谓词，删掉编辑器自造的「整块空街区」近似与 `PICK_HEIGHT` 表；修 D1（城区地标搬到装不下包络的地方）、
D2（不规则街区里设施出界）。既有补丁里原本「合法」的少数搬家会被判失效，如实上报（注册表 SPEC §12-3）。小，建议紧跟 P0 做。

**实施记录（2026-10-12）**：`planSites.blockPlacement` / `placementVerdict` 调 `checkSitePlacement`——
街区级（face-lot）设施保持自身尺寸，按确定顺序试落点（街区中心 → 地块重心 → 各地块中心，地块朝向 → 转 90°），取谓词接受的第一个；
包络用 `civicEnvelopeSize`（花园用自身矩形）；城区地标（face-reserve）按「地址 ⊕ 17 m 裙房」检查；占用不含正在搬的那座。
谓词拒因映射成编辑器码（越面/压洞 → `does-not-fit`，压路 → `site-over-road`，高架 → `highway-clearance`，压设施 → `target-occupied`）。
候选绿框画设施真实会落的位置与尺寸。`verify-plan-sites` (b2)：L 形街区装不下学校（D2）、12 × 12 街区装不下地标裙房（D1）、搬家不被拉成街区外接矩形。
真实城市：搬到首个候选 118 次干净 / 17 座无候选（与前相同）；扩档重定位 380 → 420 由 26/28 变 25/28——多出的那条是旧近似放行、谓词判装不下的搬家，如实失效。
未做（注册表 B3 的其余部分）：`listSites` 改遍历注册表、删 `PICK_HEIGHT`——要等注册表的 `instance()` / `pickHeight()`（`pendingCapabilities`）落地。

### 3.1 已先做：自由级设施的真实占地（2026-10-12，用户截图「为什么占地是圆形，建筑无法衔接路网」）

致敬地标与市政用地在布局里是「中心 + radius」，radius 是生成器的**名义预留圆**，不是模型形状。编辑器曾直接拿圆做自由落位：
路必须离中心 ≥ 0.75r（矩形车站永远贴不上路）；接入路从圆的外接方形外起笔（r·√2 外，离真实边缘大半个半径）；搬家不转向，正门朝着原来的方向。

- `engine/planFootprint.ts`：按模型给真实占地（局部凸多边形并集，+z 为正面）——地面登记表里的（庄园）用声明；渲染层导出了几何的
  （市政厅 `civicGroundFootprint`、车站站台 + 站房、体育场看台外廓）用真实形状；其余（塔、摩天轮、公园、港口…）仍是预留圆，`exact: false`。
- 落位校验（`freeMoveProblem`）对真实形状查：占地可建、离路肩 ≥ 1、不与会话楼/其他设施相交；占用预留（`reservedParcelIds`）同口径。
- **贴路**（`autoPlaceFree`）：点在路旁，设施转到正门朝路、平移到前沿离路肩 `ROAD_SETBACK`（3，同 `MODEL_ENVELOPE_CONFIG.defaultRoadSetback`）；
  离路远只转向不平移；`[` / `]` 在自动朝向上再转 90°。目标格式 `@x,z,yaw`（旧 `@x,z` 保持原朝向）。
- **接入路从正门起笔**（`accessRoadFor`），不穿过建筑本体；正门已挨着路就不补。一端在正门、另一端朝门外的路**不算压到**该设施——
  首版推土机会把接入路服务的那座设施自己推平（测试 (j) 抓到），画路接到门口同理。
- 浏览器：中央车站（r 46，真实占地 69 × 57）贴到滨海路旁，正门离路肩 3，无失效。

**3.1b 两层投影 + 件表投影**（同日，用户：「摩天轮、港口不该是圆」「建筑空间从上到下投影到地面、叠加基座」「电视塔的底还是巨大的圆」）：

- 形状来源按优先级（`FootprintSpec.source`）：物理声明（凯旋门、歌剧院陆侧、摩天轮）> 地面登记表（庄园）> 渲染层导出（市政厅、车站、体育场）
  > **件表俯视投影**（`engine/planProjection.ts`：电视塔、宝塔、灯塔——声明式模型但物理声明待补；按编译器的变换顺序把每个件投到地面取凸包，
  外切采样只大不小）> 名义圆（双子塔、扭转塔、观景塔、港口、公园——手写造型，没有件表）。海上歌剧院按圆（声明只覆盖陆侧）。
- 两层：`parts` = 落地实体（地形可建、正门）；`overhead` = parts ∪ 悬挑 ∪ 运动包络俯视投影——路与楼、楼与楼的碰撞都按它，
  与生成器 `modelEnvelope.conservativeProjection` 同口径：没有高度契约就不放路从悬挑/转盘下穿过（凯旋门两墩之间按设计是路面，待模型层给净空声明）。
- 实测：电视塔名义圆 Ø44 → 裙房 Ø17.3；宝塔 Ø36 → 19.4；灯塔 Ø28 → 15 × 10；摩天轮 Ø52 → 平台 20.5 × 8 + 转盘窄条 57.4 × 5.2。
- 选中/试算/推平标记按多边形画：地面占地实填，俯视投影超出部分淡填 + 虚线框。路障判定先包围盒粗筛、再按多边形细判。

## P1-4 改已有道路的路型

现在只能擦掉重画。新操作 `roadOps: { t: "restyle"; edge: string; width?: 5|8|12; purpose?: "waterfront" | null }`：
- 橡皮擦旁加「改路」工具（或画路工具里点一条已有路）：悬停高亮整条路（`roadPaintPlan` 的 run，不是单个路段），点选后面板给路型按钮。
- 变宽会压到两侧的楼：走推土机（推平/安置），与画路同一套提示。
- 滨海景观带随 `purpose` 自动派生（§17.1 的 `deriveCoastRoads` 已支持）。
- 不能改：桥面（`edgeLocked`）。

**实施记录（2026-10-13）**：
- 操作定为 `{ t: "restyle"; edge; width; purpose?: "waterfront"; anchor? }`——记**目标状态**（宽度必填，purpose 缺省 = 普通路），重放幂等；
  已是目标路型是无操作；桥面 / 缺失路段如实 stale（`road-restyle`）。kind 随宽度（≥ 8 为 arterial），id 不变。
- 「整条路」用 `planRoadRules.roadRun`：沿**度 2 路口**走、同宽同用途、遇岔路/换路型/桥面停——不用 `roadPaintPlan` 的 run
  （那是画线的视觉分组，跨路口）。编辑器一次把一整段写成多条 restyle、同一步撤销。
- 工具「改路」（T）：先选路型（无高架），悬停按目标宽度画整段；变宽时停住后跑推土机试算（`freshRoadGeometry` 把同 id 变宽的路段当新几何）。
  提示：`drops-waterfront`（景观带随之撤掉）、`narrows-arterial`、`far-from-coast`；滨海景观带随 purpose 自动增撤。
- 扩档：与 drop 同法按锚点找新档对应路段，路型原样带过去。
- 测试：`verify-plan-patch` (t)、`verify-plan-bulldozer` (l)、`verify-plan-repair-controller` (y)、`verify-plan-remap` (a2)。

## P1-5 地面桥

地面路过河仍是 `road-in-water`；高架能过河但不通车。设计：画路时线段穿过水面，若两岸都是陆地、水面段长度 ≤ 160，
自动把水面段生成为桥（`bridge: true, structure: "deck"`）、两端各一段引道（`structure: "ground-approach"`），与生成器的桥同构。
- **前置确认**：渲染层画桥面读的是 `roadEdges` 里 `bridge` 的路段（`roadSystem.ts:33`），桁架装饰读 `layout.bridges`。
  需确认补丁新增的 bridge 路段能被画出来、车流能走——若车流路径（`carPaths`）只来自生成器，需要 city-opt 导出车流派生函数。
- 规则：桥不能有路口（交叉自动生成路口时跳过桥段，已是现状）；桥长 > 160 拒绝；桥下净空（高架、航道）提示。

**实施记录（2026-10-13）**：
- 前置确认：渲染层 `buildInfrastructure` 对任何 `bridge: true` 的路段画桥面（桥面高 = 两端地面较高者、护栏、标线、每 32 一个桥墩），
  桁架装饰读 `layout.bridges`——补丁生成的桥两样都能画出来，不需要 city-opt 改渲染。车流（`carPaths`）只来自生成器，
  补丁新路（含桥）上没有车——与其它画出的路一致，记为已知限制。
- 判定 `planGeometry.wetSpan`（校验与重放共用）：一笔直路每 1 单位采样可建性；恰好一段不可建、两端在陆地、
  水面段两端各伸 3（桥台）后 ≤ 160 → 桥；端点在水里 / 连跨两段水 → `road-in-water`；太宽 → `bridge-too-long`（提示改用高架）。
- 重放：`add` 铺每一段时若跨水，拆成 引道（`ground-approach`）+ 桥面（`bridge: true, structure: "deck"`，锁定）+ 引道，
  新桥面登记进 `layout.bridges`。倒圆弧段不判水（拐角在路尽头的陆地上）。
- 校验：桥上不能有路口（交点落在桥面段内 → `junction-on-bridge`）；桥上方有高架 → 提示 `bridge-under-viaduct`；
  提示 `bridge:N`（桥长）。航道提示未做：生成器的 `boatLanes` 恒为空，环岛航线是 `boatLoops`，口径待与 city-opt 对齐。
- 测试：`verify-plan-patch` (u)（合成河：桥形、锁定、登记、端点在水、两条河、海峡太宽、桥上路口）；
  `verify-plan-bulldozer` 真实城市一笔过河 → 48 长的桥，干净重放。原「地面路过不去、高架能过」的前提随之改为「高架能跨河」。
- 扩档重定位：1600 → 2000 由 24/28 变 23/28——随机生成的编辑里有一笔现在成了合法的桥，放大后那一笔不再恰好跨一段水，如实失效。

## P1-6 弧线路（2026-10-13，用户：「城市规划游戏怎么处理拐角」）

调研（城市天际线 1/2、模拟城市 2013、Transport Fever 等）的共同做法：拐角由游戏生成、半径随路的等级走；曲线工具点起点/弯/终点。
本期做编辑器侧能独立完成的一项——**弧线工具**；路口路缘圆角与大路小路的层级（大路贯通、小路停止线）属渲染层，已另立 city-opt 任务。

- 补丁：`add` 多一个可选 `via`（弧线经过点）。几何 `planGeometry.curvePoints`：二次贝塞尔、控制点 2·via − (a+b)/2，
  曲线在 t=0.5 正好过 via（用户点的是「路要经过的地方」）；约 6 一段采样、**段数取偶数**（奇数时中点落在两采样之间，路不过用户点的位置——测试抓到）。
  校验、预览、重放共用这一条折线。
- 最小转弯半径按路型（`minCurveRadius` = 3 × 路宽，夹 12–36，与拐角倒圆同口径）：小路 15、次干道 24、主干道 36，太急 → `curve-too-tight`。
- 弧线不过水（`curve-over-water`），过河切回直线自动架桥；穿过现有路自动开路口并在交点断开。
  **采样点正好压在路上**（经过点点在路上时必然）时交点检测（排除离端点 1 以内）两侧都看不见——曾弧线压路而过不开路口；重放与校验都补「路上的点」判定（容差 1，与排除半径一致）。
- 交互：画路工具里「直线 / 弧线」切换（C 键）；弧线 = 起点 → 经过点（不吸附，引导线不校验）→ 终点；Esc 先撤经过点、再撤起点；落笔后终点成新起点可连续画。高架不提供弧线。
- 扩档：via 随坐标缩放。测试：`verify-plan-patch` (v)、`verify-plan-repair-controller` (z)；浏览器真实城市从路尽头画一段弧线，15 点折线与预览一致、无失效、撤销干净。

## P2-6 高架匝道接地面路

高架现在两端落地即止，不接路网，车流不上高架（生成器的高架也是）。若要「能走的高架」：高架端点吸附地面路口时生成一段匝道路段，
车流派生把高架纳入。**需要生成器的车流派生配合**，先与 city-opt 线对齐再排期。

## P2-7 框选与批量操作

框选（按住 Shift 拖矩形）选中区域内的设施/路段：批量拆除、批量擦路、「清场」（推平区域内所有非会话建筑，会话楼走安置）。
批量操作是一条复合补丁操作、一步撤销。依赖 P0-1：批量推平是性能最差的路径。

## P2-8 景观工具

种树（点/刷）、放公园、挖景观湖。新的补丁层 `landscapeOps`；树走现有 `parkTrees` 渲染，公园/湖作为新的自由级设施。
依赖注册表 B1（名称统一）与 P1-3（落位判定）。

## P3-9 撤销历史持久化

撤销栈只在内存里，刷新就没了。按种子存最近 50 步到存档（补丁本身已持久化，只多存历史）。

## P3-10 导入/导出

导出 JSON（补丁 + 种子 + 档位 + 版本）；导入时跨档走 P0-2 重定位，失效逐条报告。

## P3-11 端到端交互回归测试

现有测试覆盖到控制器（纯状态机）与规则层；画布上的拾取问题（拾取盒挡住空地、移动工具选不中细塔）都是手测发现的。
`scripts/verify-plan-repair-e2e.mjs`：用引擎级模拟点击（`pointer.set` + `handleClick`，本分支浏览器验证一直这么做）录
「选中 → 搬家 → 画路 → 拖路口 → 高架 → 撤销」，断言补丁与场景。需要无头 WebGL（playwright + chromium 或 node 的 headless-gl），
先评估 CI 可行性；不可行就作为本地脚本。
