# P2：Mecha 回合 AI 搜索性能基准（2026-11-03）

## 结论

**本次测量不足以证明必须引入回合 AI Worker，因此不改生产架构。**在以下隔离 Chrome 场景中，真实同步搜索使已经排队的合成定时器等待约 16–49 ms；起伏地形两种策略的搜索 p95 为 48.70 / 46.40 ms，接近 50 ms 长任务阈值，值得进一步调查。搜索持续时主线程不能处理其他任务，但定时器延迟既不是物理输入延迟，也不是画面卡顿或真实用户体验的测量。Node 出现较大的尾部离群值，不能将其当作 Chrome/Tauri 的阻塞时间。

现有 `fightWorker.ts` / `fightSearchRunner.ts` 处理的是**战场选址** `searchPrepared`，有 Worker 与分片回退；它不是本次的回合 AI。后者 `controller.ts` 的 `planFor` 缓存未命中时同步调用 `planForDoctrine`，例如非任务开局建议；缓存命中不会再次搜索。基准刻意直接调用规划器，测的是未命中的真实搜索，而非每次 UI 操作都会支付此成本。

## 固定局面及方法

- 四个合成但规则合法的起始局面：standard-normal / standard-hard 使用 `createMatch` 的 `covers_sparse_mid`、`siege` 默认棋盘；city-flat-hard 与 city-hilly-hard 使用规则测试的三个固定城市楼锚点（west 40,40；mid 52,40；north 40,52，半宽 3、地面 4、高 8），经 `siteMechaWindow` → `matchFromSite`；前者高度恒为 4，后者高度是 `4 + 1.5*sin(x/10) + 1.5*cos(z/13)`。两者均为 hard / siege，地表格均为 land，但后者高度 1.14–6.79，触发地形路径成本分支。均调用 `bossPrepare`，检查出生点位和 `player_plan`。
- 每个局面各跑 tunnel、peel，候选计数按 Assault/Gunner/Support 排序。规划器对候选组合执行真实规则模拟及评分，并额外考虑一次 hold；组合数是乘积，不假装所有组合均合法。每个场景/策略先预热 4 次，然后轮转采样 20 次；Node 和浏览器各 160 次计时。
- 计时只包围 `planForDoctrine`；不含城市生成、候选计数、合法性验证、UI/渲染、Worker 启动/消息复制或结果显示。Node 每次验证结果一致及状态不变，并通过 `playTurn` 验证每个首选方案合法；浏览器每次与 Node 方案比对并验证状态不变。固定输入与确定性不意味着覆盖所有局面或代码版本。
- 浏览器为本地 Vite 提供的空页面，不加载 City UI；在调用同步搜索之前排一个 0 ms 定时器，记录它到回调的时间（包含搜索与之后的校验/调度），作为**合成事件循环排队实验**。没有合成点击、真实输入、输入到绘制/提交的端到端测量。单独空闲定时器基线 p50 4.50 ms、p95 4.60 ms；浏览器的计时器钳制和调度使其不能简单相减获得纯输入延迟。
- Chrome 支持 Long Tasks API；在采样窗口记录 0 条 ≥50 ms 长任务。该观察是此隔离运行的结果，不证明其他局面、设备、真实页面或冷启动没有长任务；本测量亦未验证任何 Worker 方案的端到端收益、数据复制成本和正确性。
- 统计单位 ms；p50 为中位数，p95 为 nearest-rank（20 个样本中第 19 小），min/max 含离群点；仅一次运行、样本少、未控制后台负载/热状态或多机差异。采样轮转降低固定顺序偏差，但不构成置信区间或产品验收门槛。
