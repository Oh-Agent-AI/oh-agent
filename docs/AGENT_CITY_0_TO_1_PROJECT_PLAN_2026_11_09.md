# Oh Agent City 0→1 项目计划

状态：建议排期，待实施。以现有可玩的官方 Agent City 为 SDK 参考实现。首轮以 macOS 桌面和合成数据开发预览为验收目标。原阶段一的 5–7 周估算覆盖 City 创作闭环，加入 SDK 抽取与外部开发样例后，按第一周技术切片重新估算。Shop 在阶段一通过后单独排期。

依据：[City 产品方案](AGENT_CITY_CREATOR_STORE_PRODUCT_2026_11_09.md) · [Creator Studio 软件架构](AGENT_CITY_CREATOR_STUDIO_ARCH_2026_11_09.md)

## 目标

以 SDK 为创作入口，在现有 City 上验证换肤、玩法挂载和本地安装，再推出官方 Shop，销售 **City 皮肤和内嵌小游戏**。用两种皮肤、两个固定合成布局、竞速和寻宝两个小游戏验证组合。复用现有 City 移动控制、相机、场景和游戏会话。Studio、CLI 和 Agent 共用内容契约与校验规则。

## SDK 与参考实现

接口签名、CLI 命令和 MCP 工具见 [SDK API v0.1](AGENT_CITY_SDK_API_2026_11_10.md)。

现有 `@agent-vitals/app-sdk` 已提供插件 RPC 和类型化数据客户端，当前为仓库内的私有包。沿用它作为宿主接入层。把可复用的 City 布局、皮肤、场地查询和玩法规则放在独立的 City 创作层。官方 Agent City 作为这层的第一个真实使用者，并提供合成数据样例。活动生命周期与资源租约由 City 内部活动宿主管理。独立插件只在需要城市世界时依赖 City 创作层。

| 创作目标 | SDK 起步模板 | 首轮交付 |
|---|---|---|
| 独立 Plugin App Game | 插件清单、入口、宿主桥接 | 一个从空目录创建的最小游戏，可在合成数据开发宿主中预览。桌面正式分发仍走官方注册链路。 |
| Agent City 世界 | 布局、皮肤、地标与锚点 | 从官方 City 模板派生一张绿洲布局，交给现有 City 运行时预览。 |
| City 内嵌小游戏 | 场地槽位、规则、挂载 | 创建一个玩法包，绑定到两张地图，在同一运行器上试玩。 |

人和第三方 Agent 都可按同一个流程操作：生成项目 → 编辑清单和内容 → 校验 → 用合成数据预览或试玩 → 打包。先交付可脚本化的 CLI 和结构化错误。内置 Studio 与 MCP 再接项目服务，提供带修订号的预览、提交与回滚。创作和打包使用同一套版本契约，但打包产物的类型与分发路径按模板区分。

SDK 首轮开放开发创作能力。第三方可执行插件的桌面安装单独验收签名、进程身份、沙箱和授权。官方 City 的本地数据仍通过 Rust 的类型化接口授权，由可信 TypeScript 适配器处理。第三方开发样例和内嵌小游戏首轮使用合成数据，Shop 首发范围继续为官方皮肤和小游戏。

## 从现有 City 开始迁移

文件映射、兼容策略和首个可合并切片见 [现有 City 与玩法的 SDK 迁移方案](AGENT_CITY_SDK_MIGRATION_2026_11_10.md)。

1. **统一场景入口判断。** 先收敛场景点击、机甲入口、道路审计和梦境预览共用的空闲场景条件。继续核对工具栏与实际执行入口，逐步统一它们的准入和拒绝结果。驾驶和飞行已使用内部 `GameScenePort`，机甲仍经 `acquireModeLease` 获取镜头能力。保留各玩法的运行逻辑，先让活动宿主统一掌管进入、退出和资源归还。核对正常退出、取消准备、失败和快速切换。
2. **让现有玩法使用场地挂点。** 以驾驶或飞行验证一个现有入口可由场地描述驱动，再用不同规则的第二个活动验证契约。挂载只记录入口、位置和配置。新入口应复用统一准入流程，存档和成绩按挂载隔离。
3. **从现有 City 风格抽取皮肤契约。** 先把默认外观纳入皮肤注册表，再接入一个新皮肤。以相同布局下的道路、碰撞和挂点为对照，验证换肤、失败回退和重启恢复。
4. **让 Studio、Agent 和 Shop 复用接口。** Studio 编辑规则与挂载，MCP 调用同一项目服务。Shop 在本地组合验收通过后接目录、安装和权益。

活动宿主是 City 内部的运行边界。Studio 和 City 间的试玩交接属于 Oh Agent 插件宿主，两条迁移分别验收。现有的 [City 活动平台方案](CITY_ACTIVITY_PLATFORM_ARCH_2026_11_07.md) 提供入口与租约设计，具体接入顺序以上述现状为准。

## 交付顺序

| 时间 | 工作包 | 交付与通过条件 |
|---|---|---|
| 第 1 周 | 驾驶与 SDK 技术切片 | 用现有驾驶会话和租约建立回归基线，统一驾驶准入并覆盖与现有活动的互斥。接入三点竞速包，走通锚点、规则、HUD 和合成数据试玩。另行验证 Studio 与 City 的最小快照交接，据此重估后续排期。 |
| 第 2–3 周 | 规则运行与场地绑定 | 建立布局、皮肤、小游戏、挂载模型。接通本地官方内容的验证与安装。竞速绑定两座城，同一城市能进竞速与寻宝两个入口。挂点缺失或不兼容时阻止启动并给出可修正的提示。验证启动、退出和局内状态隔离。 |
| 第 3–4 周 | 项目服务与 MCP | Agent 能查询场景对象，摆放模型、移动检查点和编辑规则。通过预览与提交修改草稿。无头检查返回失败节点、对象和事件位置。处理版本冲突、重复提交、撤销、权限撤回和重启恢复。 |
| 第 4–5 周 | Studio 与玩家试玩 | 玩家从 City 打开内置 Studio，查看场景差异、挂载和规则。用诊断定位对象或节点，修正后重跑。玩家亲自试玩固定版本，再返回原草稿。走打包桌面端的正常输入、HUD 和插件切换路径。 |
| 第 6–7 周（缓冲与试点） | 打包验收与创作试点 | 让创作者描述自定义玩法，并在没有工程人员帮助时完成一次创作、一次换城或换挂点、一次规则修改。记录规则表达、场地匹配和试玩反馈中的实际阻力。 |

如果两种玩法需要两份专用运行代码，先调整规则原语或缩小玩法差异，保留“规则定义能决定流程”的验收。如果现有场景没有统一挂点能力，先用两个官方场地清单验证契约。若跨插件交接暂未稳定，先在 Studio 内验证同一规则运行器与场地绑定，正式 City 试玩和回跳仍作为待验收项。

## 阶段一通过条件

1. 同一布局可在两种皮肤之间往返切换，两种皮肤均能启动竞速和寻宝。换肤前后道路、碰撞、挂点、入口和成绩一致。重启可恢复皮肤及挂载。坏皮肤回退到默认外观。
2. Agent 能依据自然语言新增或改变一条规则，例如「三处宝箱任选顺序，收集两处后码头才亮起撤离区，超时失败」。用实际试玩证明目标或胜负行为发生了变化。
3. 同一个竞速定义可以挂到两座 City，分别使用本地挂点。任一兼容城市也可同时提供竞速和寻宝入口。切换、重启、删除一个挂载时，其他配置与成绩保持各自独立。
4. Agent 能按稳定 ID 查询、摆放和移动对象及检查点。不可达检查点返回受影响的对象、槽位和原因，创作者可调整位置或重新绑定。修复后能原子保存、撤销，并亲自试玩固定版本。
5. Agent 通过本地 MCP 操作获授权项目。无头规则检查和玩家可视试玩分别验收。试玩结果与分析数据、城市布局和草稿写入分离。
6. 第三方 Agent 或开发者从空目录按 SDK 文档创建模板项目，通过公开入口校验和预览，且项目无须导入官方 City 的内部模块。至少实做独立小游戏预览、第二张 City 布局和一个跨地图内嵌玩法样例。

## 阶段二：官方 Shop

阶段一通过后，沿用宿主的本地内容安装和应用入口接 Shop。首发上架两种皮肤和两种官方小游戏样例，实际收费范围根据测试和发行渠道决定。

| 工作包 | 交付与通过条件 |
|---|---|
| 目录与商品详情 | Shop 有独立入口。皮肤显示预览和渲染兼容性，小游戏显示所需场地能力及可用挂载位置。 |
| 购买与权益 | 接通经确认的支付渠道，用测试交易验证确认购买、失败重试、重复回调、恢复购买、退款和离线权益。生产收费以前述验收为门槛。 |
| 安装与使用 | 已购买的皮肤可安装、预览、应用和切回。已购买的小游戏可安装、选择场地、挂载和试玩。重启能恢复状态，包损坏或不兼容时提示原因。 |

发布验收各走一笔皮肤和小游戏的测试购买。一个用户能把新皮肤应用到已有 City，并在换肤前后玩同一个小游戏；再购买另一个小游戏，在同一座城添加第二个入口。创作者上架、社区交易与通用插件平台另行评估。
