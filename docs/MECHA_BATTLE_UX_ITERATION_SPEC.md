# Agent City 机甲战斗体验迭代 SPEC

日期：2026-10-31  
状态：提案，待产品与技术评审；文中“必须”为目标要求，不代表已经实现  
适用分支：`feature/mecha`；规则基线：`mecha-v1.4`  
范围：本机 City 机甲战斗的规划、预览、提交和结算反馈

## 1. 背景与问题

本方案参考《陷阵之志（Into the Breach）》UX 设计调研（2026-10-29，第 3–6 页及第 7–13 页战斗截帧）。借鉴目标是**让玩家理解敌人意图和行动后果**，不是复制其电网、像素美术或战斗规则。用户提供的截图包含：战斗 HUD 与敌意、选中和可走格、伤害与推挤预览、弹道、攻击次序、电网及局外海图。

2026-10-31 在浏览器中使用合成 City 数据、30 个会话、seed `4196523069`、1100×700 视口观察到：首回合三个机甲草稿均为 Hold，面板显示三机预计受击 0；直接提交后，防守建筑总 HP 从 80/80 降至 68/80。首回合画面和展开攻击顺序时，左上面板占用战场空间。该样本不能证明所有地图、视口或原生窗口都有同样问题；上次实测也未成功走完目标选择与攻击，不把攻击表现当作已实测结论。

**核心问题**：现有预览可表达推动后的敌方预告和机甲受击，但提交前的建筑损失、威胁来源、次序与局部行动后果不够直观。城市氛围增强了沉浸感，也提高了场景与战术标记之间的竞争。

## 2. 目标与非目标

### 2.1 目标

1. 提交前说明当前方案对防守建筑和机甲的预计后果，预测不可用时诚实降级。
2. 让玩家从敌人追踪到攻击范围、对象与顺序；移动范围、目标和危险信息可同时辨认。
3. 在整包语义下，提供目标伤害、推动/碰撞和后续行动落空的可解释预览。
4. 保留 3D 城市，同时建立可读、可操作的战术视图。
5. 明确自动草稿、未规划、待机、撤销和重置的语义；中文、英文、鼠标、键盘及触屏有对应操作路径。

### 2.2 非目标

- 不引入独立电网、环境攻击、刷怪点、四岛地图或战役成长；不声称建筑 HP 等于原作电网。
- 不改变生命、伤害、地形、回合数、胜负、部署、敌方 AI 或自动草稿算法；如需改规则，另行评审并按规则版本处理。
- 不将三机整包改为原作逐台即时执行，不把玩家规划顺序改为结算顺序。
- 不做联网、遥测、数据上传、局外商店、全面美术重做或移动端原生应用。
- 本文是 UX 增量方案，不覆盖既有架构及权限政策。`MECHA_CITY_FIGHT_REMEDIATION_SPEC.md` 中规则/控制器约束仍有效；历史文档中与现行代码不一致的旧规则、旧方格回退描述不作为本次基线。

## 5. 统一预览数据与一致性契约（A，B 扩展）

### 5.1 数据来源和时点

`playTurn` 是正式结算权威；`previewPlan` 必须复用与 `playTurn` 相同的 `runTurn`/规则路径、同一份输入 `MatchState` 和草稿计划，不能复制伤害公式到表现层。预测只在克隆上运行，不改变真实 state、草稿、冷却、日志、随机状态或演出队列。

记录四个逻辑时点（实际内部数据结构可复用现有 snapshot/event，但不得靠屏幕推算）：

1. `start`：玩家回合起始、尚未规划移动/行动的已提交状态；包含建筑 stake 与 HP。
2. `afterMovement`：所有机甲移动完成。
3. `afterPlayer`：固定顺序的玩家行动完成、敌人尚未行动；提前出现终局则停止在真实结算的阶段。
4. `end`：敌方结算及本回合必要的胜负/下回合准备完成；若提前终局则为真实停止点。

敌人意图展示必须区分 `afterPlayer` 的本回合预告和下一回合准备后的意图，不能把后者误标成本回合。若提前胜利或失败使敌人不行动，显示“本回合敌方不再行动”，而不是伪造一次攻击。

### 5.2 建议类型语义

下列是契约示意，命名可按代码调整；不要求把完整 MatchState 暴露给渲染层：

```ts
type PreviewStatus =
  | { status: "ready"; revision: number; draftVersion: number;
      assumedMechs: MechId[]; outcome: Outcome | null;
      buildings: Array<{
        id: string; cells: Cell[]; staked: boolean;
        startHp: number; afterPlayerHp: number; endHp: number; maxHp: number;
      }>;
      enemyOrder: Array<{ actor: string; skill: BossSkill; cells: Cell[] }>;
      mechHitsAfterPlayer: Record<MechId, number> }
  | { status: "invalid"; revision: number; draftVersion: number; fault: PlanFault }
  | { status: "unavailable"; revision: number; draftVersion: number; reason: string };
```

- 防守建筑汇总 `start`、`end` 分别是本局 stake 建筑 HP 求和；净变化为 `end − start`。展示 `预计损失 N` 仅用于净变化为负；若未来规则允许回血，净增长不能错误显示为负伤害。
- 对象级记录保留每栋建筑标识、占格、HP 和是否 stake，避免把非防守建筑计入败北条。建筑在玩家行动阶段或敌人阶段受损都必须计入回合整体净变化；细分阶段可用于说明原因，不以机甲受击替代。
- `mechHitsAfterPlayer` 仅表示玩家行动结束后到敌方阶段结束的 HP 减少，沿用现有指标含义；不把它说成包含玩家碰撞友伤的“本回合全部损失”。如展示整回合净变化，必须另起字段并明确时点。
- `outcome` 是试算的实际回合结果，而不是简单由血量自行推断；`null` 表示试算没有终局，不表示保证胜利。无 stake 建筑时显示“无防守建筑”，而不是 `0/0` 或虚构败北。
- 没有显式行动的存活机甲，在预览中保留已规划的移动并假设行动为待机；没有规划移动时才是“原地 + 待机”。`assumedMechs` 必须列出所有被假设待机的机甲，包括已规划移动但未选行动者。现有 `previewPlan.assumed` 仅列出完全未传入的机甲，因此控制器须结合草稿的 `explicit` 补齐标签，不得改变现有移动语义；正式提交仍要求所有存活机甲显式规划。草稿非法或试算不可用时不得复用旧数字或显示 0。
- 预览请求及结果绑定 `match.revision` 与单调递增 `draftVersion`；任何移动、行动、重置、doctrine、重新开始、结算等改变相关输入的操作都使旧结果失效。若未来异步计算，再增加请求 ID；返回时逐项检查 revision、draftVersion 和对局实例，过期结果直接丢弃。
- 任何 hover 候选方案使用单独的临时输入标识，不覆盖正式草稿预览；离开目标、取消、选择其他机甲、重置、切换对局或提交后立即清除。暂停/演出/终局不得允许提交或编辑。

### 5.3 预览失败

`invalid` 展示可解释的非法原因与机甲；`unavailable` 展示“预览暂不可用”，都清除依赖该次计算的损失、顺序、目标结果及结局数字。可保留当前已知的原始敌意，但必须标记“当前局面，非草稿预测”；不可把 fallback 当完整预测。能否正式提交仍按现有规则/校验决定，不把未知显示为安全；正式提交仍须权威重验并原子拒绝非法计划。

## 6. A / P0：提交前后果与敌意归属

### 6.1 建筑和风险摘要

在固定 HUD 中展示“防守建筑 当前/最大”，旁边展示本方案试算后的净变化和最终值。例如：`防守建筑 80/80 → 预计 68/80（-12）`。当 `assumedMechs` 非空时同时显示“假设：射手、支援待机”；有终局时用明确文字表达 `预计胜利`、`预计建筑全毁 / 全机毁灭 / 超时`，不只使用红色。

点击/聚焦风险摘要可展开逐栋列表及关联地块；字段包括当前 HP、预计 HP、是否毁灭及 stake 标识。点击条目聚焦或高亮对应棋盘位置；无法安全聚焦镜头时至少突出显示并提供文字定位。建筑均未受损时明确显示 `预计建筑损失 0`，不得把“机甲受击 0”放成全局安全结论。

若计划全部显式待机且预计防守建筑有损失或出现失败，提交时展示一次非阻塞的确认：列明损失/失败与“继续提交”“返回修改”。不因为有风险禁止玩家牺牲建筑；无风险的待机不弹该确认。确认后再次检查 revision 与 draftVersion，变化则要求重新确认。其余高风险非全员待机方案不新增强制弹窗，保持提交低摩擦。

### 6.2 攻击来源与叠层

- 默认显示每个敌人的本回合预计落点；保留敌人、技能和落点的关联。支持鼠标悬停、点击/触屏点选、键盘选择敌人或列表项；所选敌人、落点和类型同时高亮，其他威胁仍可辨认。
- 方向/路径只在规则可明确提供时绘制；对范围攻击使用范围边界、方向标记或图例，不凭落点虚构直线弹道。路径被建筑遮挡时至少保留目标侧标记和列表回退。
- 棋盘状态使用可组合层：移动范围底色、威胁条纹/轮廓、合法目标边框、选中标记彼此独立；同格不能只因 `target > telegraph > reach` 而丢掉危险。颜色之外必须有形状/纹理/文字，不能仅靠红绿区分。
- 一格被多个敌人威胁时保留全部来源；选中每个敌人均能查到该格。图形不下得时提供可聚焦的文本列表；预计敌人已被消灭或提前终局时，不绘制其不会执行的攻击。
- 按规则试算后的敌意展示，并明确标记“按当前方案预测”；无效/不可用时遵守 5.3 的降级。默认总览不因鼠标离开而永久停留在某个敌人。

## 7. B / P1：行动预览与次序

### 7.1 目标指向和草稿

状态路径：`选中机甲 → 编辑移动 → 选择可用行动 → 指向合法目标（临时预览）→ 选择目标写入草稿 → 修改或统一提交`。取消目标只退出瞄准，不提交、不消耗 Reset。

- 鼠标悬停合法目标时，仅临时替换当前机甲行动，以完整草稿跑同一试算；展示目标预计 HP 变化、推挤方向/最终位置、碰撞涉及对象及其 HP 变化。确认点击才写入草稿。
- 触屏首次点目标进入预览，面板提供“确认选择”和“取消”；键盘选择目标并确认采用相同语义。两者都不可因第一次触碰就静默提交整包。触屏/键盘必须能通过列表选择，即使 3D 单位被遮挡。
- 规则未发生推挤、无碰撞或目标不合法时如实显示；无法确定结果显示“不可预览/原因”，不猜一个方向。支持多格 Boss、多个碰撞对象、伤害为 0、敌人提前死亡。
- 固定显示我方实际结算顺序。对于前一台行动导致后续行动落空，显示哪一台、原因及“不消耗冷却”；依据真实试算事件，不能根据表面位置自行猜测。
- 同时提供“该行动造成的变化”和“整包结束后结果”的明确标签；实际链式碰撞按规则事件/快照呈现，不把其他机甲的伤害归给当前技能。选中之后草稿变化重新计算完整预览。

### 7.2 攻击顺序叠层

按需开关显示敌人序号并保留文本列表；数字来自本回合预计实际发生的敌方事件顺序，不包括已死亡或未执行的敌人。序号和对应攻击落点/列表项双向联动。无敌方行动展示空态。可通过按钮及键盘访问；仅在验证平台和浏览器快捷键冲突后再决定是否绑定 Alt。不得与玩家机甲固定行动顺序使用同一种无说明编号。

## 8. C / P1：战术视图、HUD 和新手路径

### 8.1 布局与视觉

- 将建筑资源、回合/胜负目标、敌方意图、机甲与提交区建立清晰层级。攻击顺序列表默认折叠，打开后不遮挡当前聚焦单位及其主要威胁；空间不足时使用可滚动侧栏/可折叠面板，而不是扩大覆盖整个棋盘。
- `战术视角` 仍保留城市上下文，强化 10×10 边界、当前棋盘和选中单位，降低棋盘外背景干扰；旋转后标记与棋盘保持对应。模型被建筑遮挡时提供轮廓/标记或列表定位，不因装饰挡住唯一操作路径。
- 选中机甲的卡片、场景标记和名称相互对应；突出可走区域与危险叠加。不同状态必须有非颜色提示，并在图例或帮助中解释。
- 适配 1100×700 和 1440×900 桌面、390×844 触屏视口；内容可折叠/滚动，不互相覆盖阻止提交、取消或查看资源。设备像素比和系统缩放不能改变落点与点击位置对应关系。

### 8.2 草稿与撤销说明

- 当开场草稿由系统生成，标记“系统建议，可修改”；明确显示各机甲是待机还是其他行动，不能假定自动计划永远都是待机。
- 后续回合显示 `已规划 n/存活机甲数`，列出待规划机甲；说明预览对未规划机甲的待机假设与“正式提交需要显式规划”是两回事。
- 展示已选行动、目标和必要的不可用原因：例如射程、冷却或移动后可用。若某行动当前不合法，不将其描绘成可直接执行。
- Undo 的说明是“恢复最近一次移动前的草稿，可能一并恢复其他机甲规划”；Reset 说明“每场一次，恢复本回合开始时草稿，不撤销已结算回合”。草稿变更引起其他机甲计划失效时须可见说明。
- 动作按钮提供中文/英文、焦点可达与文本 tooltip；未来动画 tooltip 是 P2，不以动画代替文本。

## 9. 可访问性、性能与数据边界

- 不只依赖颜色、声音、悬停或精细点选；敌人/目标/操作的等价文本列表可用 Tab 和 Enter/Space 操作；画布上的视觉状态有屏幕阅读器可读摘要。避免将大量逐格变化不断放入 `aria-live`；只播报选择、错误和关键结果变化。
- 焦点可见；面板展开/关闭后焦点有可预测的去向。输入框/下拉框获得焦点时不劫持其原生键盘操作；本期保留当前 Escape 关闭语义。
- 悬停试算使用缓存或合并同一帧的重复请求；不得为了渲染每个格子分别运行完整回合。销毁场景时清理监听器、Three 对象和未完成计算。性能验证见第 11 节，不以牺牲正确性伪造零损失或跳过验证。
- 本方案为本机计算，不增加网络、遥测、日志上传或读取额外用户数据。开发/测试使用合成 City 和固定战棋 fixture；不得把真实用户 City/会话数据放入截图或测试仓库。

## 11. 验收与验证计划

### 11.1 A：预测准确性和敌意

- 固定 fixture 重现：机甲敌方阶段受击 0，但防守建筑 80 → 68；提交前显示建筑预计损失 12、结果 68，提交后实际一致。不能只断言三机受击。
- 分别覆盖：不受损、多个建筑同时受损、部分毁灭但未败、全部 stake 毁灭、非 stake 建筑受损、无 stake、玩家行动中推敌撞楼按现有规则不伤楼、敌方阶段伤楼、提前胜利/败北、全机毁灭和超时。
- 构造部分草稿：既覆盖完全未规划，也覆盖已移动但未选行动；两者均列为假设待机，后者的预览必须保留已规划移动，预测可见但提交仍禁用；计划补齐后移除假设提示。无效计划、旧 revision、重置、换 doctrine、重开及预览失败时不出现过期数值。
- 多个敌人威胁同一格，且该格同时可达/可选目标：来源和危险纹理仍可分别查询；悬停、点选和键盘选敌结果一致。
- 全员显式待机且预计损楼：确认显示正确损失，可取消或继续；回到编辑后修改草稿不得沿用旧确认。无损待机不弹。
- 定向和多个确定性生成局面中，对所有**合法完整**计划比较 `previewPlan` 与 `playTurn` 的各阶段/最终建筑 HP、机甲 HP、敌方实际次序与 outcome；检查两者调用前后输入无变化。对部分计划先按约定补全后比较，并保持“仅预览不可提交”。

### 11.2 B：行动结果与次序

- 覆盖直接伤害、0 伤害、击杀、多格 Boss、成功推挤、撞墙/友军/障碍、多目标碰撞、无推挤、修理和目标非法；显示值与真实试算事件一致。
- 前一台击杀目标或推离距离使后续机甲落空：显示对应原因，落空与冷却消耗同最终结算一致。
- 临时 hover 不改变草稿；鼠标移开、点击取消、触屏取消、切换机甲、重置及提交后不残留旧预览。触屏首次点击只预览，确认后才写草稿。
- 敌人次序叠层与文本列表一致；提前终局或敌人死亡时不出现虚假编号；无法显示图形时列表仍可访问。

### 11.3 C：可用性、视觉与性能

- 以可复现合成数据和固定 fixture 运行 1100×700、1440×900、390×844；分别检查普通态、敌人焦点、移动与危险重叠、选目标、展开顺序、预览错误及结算后。保存中英文截图并记录种子、视口、缩放及浏览器/原生环境。检查棋盘和关键操作可见、没有被面板阻断；浏览器验证不替代 Tauri 实机验证。
- 鼠标、键盘、触屏分别走通选择机甲、查看威胁、选目标、取消、修改草稿与提交；不能只用截图或无头测试代替操作验证。验证暂停、演出、终局下不允许编辑，重开和退出后监听器及对象得到清理。
- 用固定高威胁 fixture 在目标桌面硬件上测量 20 次连续目标切换：记录浏览器、硬件、p50/p95 预览响应和最慢帧；目标 p95 ≤ 200ms、无超过 100ms 主线程长任务。未达标则标记切片未通过性能验收并分析，不隐藏慢结果或返回虚假预测。
- 至少 5 名未参与设计的目标用户使用合成 fixture 做两项任务：指出哪栋建筑受威胁、说明当前草稿的预计建筑损失和下一步可执行操作。记录成功率、耗时和误解点；目标每项至少 4/5 人无需提示完成。未达目标先改设计或明确接受风险，不把测试结果视为普遍人群统计。
