## 0. 结论先行

第一轮的目标是「把噪声压下去、把信号提上来」，**已经达成**：SV605 误报归零、
findings 按严重度分组着色、token 从裸数字变成 `226.4M` + 分段条、成本按模型分桶计价。

第二轮暴露的是**新一类问题**：不再是「数据难看」，而是**「数据自相矛盾」和「操作没有闭环」**。
一屏之内出现三套互不相等的计数，用户会先怀疑数字，再怀疑规则引擎——
这比第一轮的 14 条误报更伤，因为误报可以解释，矛盾数字无法解释。

| 类别 | 数量 | 代表问题 |
|---|---|---|
| 🔴 P0 一致性缺陷（可验证的 bug） | 3 | 汇总数 ≠ 列表数；标记跨会话泄漏；成本估算被当成账单 |
| 🟡 P1 操作闭环缺失 | 4 | 复制无反馈、汇总不可过滤、标记无撤销总入口、seq 是死文本 |
| 🟢 P2 信息密度与可读性 | 4 | 右侧按钮墙、缺时间维度、规则码不可查、无导出 |

## 1. 场景与用户分层（先定这个，优先级才有意义）

审计 tab 现在把三个不同任务塞进了一屏。它们的成功指标完全不同：

| 用户 | 场景 | 核心问题 | 现在最挡路的 |
|---|---|---|---|
| **A. 会话监督者**（开发者本人，跑完一轮回看） | 「这个 agent 刚才有没有干出格的事」 | 高危事件在哪、是不是误报 | 汇总数与列表数不一致；无法一键只看 critical |
| **B. 成本审视者**（团队 owner / 自付费用户） | 「这一轮烧了多少，为什么这么贵」 | 钱花在哪个模型/哪个桶 | ¥1113.7 看起来像账单，实际是含假设的估算 |
| **C. 合规留痕者**（企业 / 事后复盘） | 「把这次会话的行为记录留档」 | 导出、跨会话对比 | 无导出；标记只在浏览器 localStorage，换台机器就没了 |

**判断**：当前实现服务 A 最好、B 次之、C 几乎为零。
优先级应按 **A → B → C** 排，即先把「看得准」做实，再把「算得清」标注清楚，
最后才补「留得下」。下面的 P0/P1/P2 就是按这个顺序排的。

## 2. P0：一致性缺陷（必须修，都是代码级可验证的）

### P0-1 一屏三套计数，互相矛盾 🔴

**现象**（截图直接可复现）：顶部 chips 显示 `✕ 3 严重 · ⚠ 3 警告 · · 2 提示`，
小标题写「行为审计 · 8 条」，但下方**只渲染出 `警告 · 2` 和 `提示 · 2` 两组共 4 行**，
且 **critical 组完全不存在**，底部另有「已忽略 2 条」。

**根因**（`AuditView.tsx`）：

| 位置 | 数的是什么 | 结果 |
|---|---|---|
| L414 `SummaryChips({ findings })` | **原始** findings，未去重、未剔除已忽略 | 8 条 → chips 3/3/2 |
| L460 `t('findingsHeading', { n: findings.length })` | 同上，原始条数 | 「8 条」 |
| L442–447 `activeGroups` | **去重后**（F4 ×N 合并）**且剔除 `ignored`** | 实际 4 行 |
| L465 `IgnoredSection` | 被剔除的那些 | 「已忽略 2 条」 |

于是「3 严重」在列表里蒸发——它们全被标记成了 ignored，chips 却仍然计入。
用户看到红色的「3 严重」，滚动一屏找不到任何一条 critical，**只会得出一个结论：这个面板在骗我**。

**修法**（三选一，推荐 B）：

- **A. 全部改成一致口径**：chips 与标题都用「去重后 + 剔除已忽略」的数。
  最简单，但丢失「原始命中量」这个真实信号。
- **B.（推荐）显式区分两个口径**：chips 与标题用 `活跃 N（另有 M 已忽略）`，
  即 `⚠ 3 警告` 变成 `⚠ 2 警告`，标题变成 `行为审计 · 4 条 · 已忽略 2`。
  已忽略的数字单独成一个灰色 chip，可点击直接展开底部区块。
  口径唯一、信息不丢、且给了「已忽略」一个入口（顺带解掉 P1-3）。
- **C. 保留双数字**：`⚠ 3（显示 2）`。信息全，但一行里放两个数认知成本高，不建议。

**验证**：`verify-render.mjs` 加一条断言——构造「N 条 critical 全部预先标记为 ignored」的
fixture，断言 chips 中不出现 `严重` 或出现的是 `0`，且标题数与实际渲染行数一致。

### P0-2 标记（F3）跨会话泄漏 🔴

**现象**：`MARKS_STORAGE_KEY = 'agent-vitals-audit:marks:v1'`（L84），
键是 `JSON.stringify([rule, evidence])`（L86）——**不带 session id**。

**后果**：在会话 A 里把 `SV601 / rm -rf /tmp/build` 标成「安全」，
到了会话 B，只要出现**逐字相同**的 evidence，这条 finding 会被自动淡化并沉底；
标成「忽略」的更是直接从主列表消失，落进底部折叠区。
**用户在另一个上下文里做的一次判断，永久地、静默地压制了未来所有会话的同一告警。**

这与本仓库最硬的那条纪律直接冲突（CLAUDE.md：「安全启发式只排序，绝不豁免」）——
`is_cited()` 都不允许压制 finding，用户的一次误点却可以。

**修法**（分两步）：

1. **立刻**：给存储键加 session 维度，`marks:v1:<sessionId>`；或键内加 sessionId。
   默认**不跨会话继承**。（`ConvViewProps` 里是否直接暴露 session id 需核实；
   若没有，退而用 `cwd + 首个事件时间戳` 作为会话指纹。）
2. **其次**：`ignored` 的语义从「移出列表」降级为「折叠但计数可见」——
   配合 P0-1 的方案 B，已忽略数量永远显示在顶部，不存在「静默消失」。
3. **未来**：接 AGENT_BEHAVIOR_AUDIT §7 的治理 registry 时，
   跨会话继承应该是**显式选项**（「对所有会话应用此判断」勾选框），而不是默认行为。

---

### P0-3 ¥1113.7 看起来像账单，实际是含假设的估算 🔴

**现象**：费用区块只有一行 `¥1113.7　其中高峰时段 ¥252.5`。字号 16、加粗、tabular-nums——
所有视觉语言都在说「这是一个精确的、权威的数字」。

**实际上它至少含三个假设**（设计稿 §5 S6 已写明，但**一个都没出现在 UI 上**）：

| 假设 | 现状 | 误差方向 |
|---|---|---|
| 缓存写入按 ¥0 计（价格表无此行） | 本次 cache-write = 0，恰好无影响 | 未来会低估 |
| 空闲/高峰时段按事件时刻归属 | 高峰价 = 空闲价 ×2，归属错则差一倍 | 双向 |
| 未知模型桶不计价 | 有 `unpricedNote` 但只在 `unpriced > 0` 时出现 | 低估 |

设计稿原话是「**宁给两个数，不给一个假数**」，实现却给了一个数。

**修法**：
- 金额旁加「估算」角标（`≈ ¥1113.7`），hover 展开假设清单；
- 或在 `费用估算` 小标题右侧常驻一行灰字：`按 DeepSeek 官方公开价估算 · 缓存写入按 0 计`；
- 成本区块加 `data-audit-cost-disclaimer` 锚点，便于测试断言它存在。

**这条的产品风险高于它的技术难度**：一旦用户拿这个数去对账、发现对不上，
整个 tab 的可信度会一起崩——包括算得完全正确的 findings。

## 3. P1：操作闭环缺失

### P1-1 复制（F2）无任何反馈 🟡

`copySeq()`（L191）写完剪贴板就结束，按钮不变、不吐 toast。
`navigator.clipboard` 不可用或权限被拒时（L198 的 `catch`）**静默失败**——
用户以为复制了，粘贴出来是空的。

**修法**：按钮点击后文案切换为「已复制」持续 1.5s（一个 `useState` + `setTimeout`）；
`catch` 分支切换为「复制失败」并把 seq 直接选中展示，让用户手动复制。

### P1-2 汇总 chips 不可点击过滤 🟡

设计稿 §5 S2 就写了「后续可点成过滤器」，至今未做。
现在 3 个 chips 纯装饰，而这是**用户看到的第一个元素**——
第一眼看到的东西不可交互，会拉低整个页面的可操作预期。

**修法**：chips 变成 toggle filter（多选，默认全选）。
与 P0-1 的方案 B 合并做：`✕ 2 严重`／`⚠ 2 警告`／`· 2 提示`／`⊘ 2 已忽略`，
点「已忽略」直接展开底部区块。**一次改动同时解掉 P0-1、P1-2、P1-3。**

### P1-3 「已忽略」缺少总入口与批量撤销 🟡

底部一行灰色小字 `▸ 已忽略 2 条`，紧贴输入框，极易漏看。
且**没有「全部取消标记」的入口**——用户一旦误标一批，只能一条条点回来，
而已忽略的那批还藏在折叠区里。

**修法**：折叠区展开后，标题行右侧加「全部恢复」；
或在 tab 右上角加一个「重置本会话标记」（配合 P0-2 的 session 作用域，语义才干净）。

### P1-4 `#440338` 是死文本 🟡

seq 号占了一段视觉权重，等宽字体、右对齐，看起来像可点的锚点，实际不可点。
（`ConvViewProps` 确实没有 jump-to-seq，设计稿 §6.2 已核实——这是**契约限制不是实现偷懒**。）

**修法（不依赖执行环境契约）**：
- 把 `#440338` 本身做成复制触发器，去掉旁边那个独立的「复制」按钮——
  **少一个按钮，且消除了「看起来能点」的误导**（顺带缓解 P2-1 的按钮墙）；
- hover 时提示「点击复制 seq，可在轨迹 tab 搜索」。

## 4. P2：信息密度与可读性

### P2-1 右侧按钮墙 🟢

每行固定渲染 `复制 · 安全 · 高危 · 忽略` 四个按钮（L289–297）。
4 行 = 16 个按钮，**按钮数量超过了 findings 数量的 4 倍**，
视觉权重压过了 evidence 本身——而 evidence 才是用户真正要读的内容。

**修法（择一）**：
- **hover 显形**：默认只显示 seq，鼠标进入行时才淡入操作组（桌面端最优）；
- **收敛为单按钮**：一个 `⋯` 展开三态菜单（触屏友好）；
- **已标记才常驻**：未标记行只显示 `⋯`，已标记行常驻显示当前状态（一个 chip，可点击改）。

推荐第三种：它让「已做出的判断」保持可见（治理留痕的核心诉求），
同时把未处理行的噪声降到最低。

### P2-2 缺时间维度 🟢

「行为审计 · 8 条」没说是哪段时间。findings 有 `time` 字段但 UI 完全没用。

**修法**：标题后加时间跨度 `（14:02–15:37）`；行内 evidence 右侧或 hover 显示相对时间。

### P2-3 规则码不可查 🟢

`SV613` 有中文名「进度停滞」，但用户想知道「触发条件是什么、为什么算问题」时无处可去。
仓库里 `AGENT_BEHAVIOR_AUDIT.md` 有完整定义，客户端拿不到。

**修法**：i18n 字典每条规则补一个 `rule_SV613_desc`（一句话触发条件），
规则码 hover 显示 `title`。**零新增依赖、纯字典扩充**，性价比最高的一条。

### P2-4 无导出 🟢

场景 C（合规留痕）完全落空。CLI 侧 `behavior --json` 已经有完整输出，
tab 侧却拿不到——数据就在浏览器内存里，只差一个按钮。

**修法**：右上角「导出 JSON」，导出 `{ findings, usage, cost, marks, sessionId, exportedAt }`。
注意：**导出必须包含 marks 和估算假设**，否则导出的成本数会脱离上下文被当成账单（P0-3 的下游风险）。

## 6. 衡量指标

改完之后怎么知道有效？三个可埋点的信号：

| 指标 | 定义 | 目标 | 对应问题 |
|---|---|---|---|
| **首屏一致性** | chips 数字 == 可见行数（自动化断言，非埋点） | 100%（测试红线） | P0-1 |
| **标记转化率** | 有 findings 的会话中，至少标记过 1 条的比例 | > 30%（说明用户真的在用治理能力，而不是当只读报表看） | P1-3 / P2-1 |
| **成本区块 hover 率** | 费用数字被 hover / 展开假设的比例 | > 15%（说明「这是估算」传达到了） | P0-3 |

前两个能用现有渲染测试与 localStorage 统计近似，第三个需要 DSH 侧的埋点通道——
**没有埋点通道就不要假装有数据**，那就退回到定性验证：找 3 个真实用户跑一轮，
问一句「这个 ¥1113.7 你觉得是什么」，答案里出现「账单」就是没做到。

## 7. 与第一轮设计稿的关系

第一轮（AUDIT_TAB_DESIGN.md）的 F1–F4 / S1–S6 **全部完成且有效**，本文不推翻任何一条。
本文补的是第一轮没覆盖的三个维度：

1. **跨组件一致性**——第一轮逐个组件优化，没人检查它们加起来是否自洽（→ P0-1）；
2. **状态的作用域**——F3 只定义了「三态」，没定义「这个态属于谁、活多久」（→ P0-2）；
3. **估算的表达**——S6 把计算做对了，但没规定 UI 必须暴露它的假设（→ P0-3）。

这三条是同一类问题的三个面：**功能做完了，语义没定义完**。
下次加功能时，验收清单应固定包含一问：「这个数字/状态，和屏幕上其他数字/状态是什么关系？」

# 第三轮：Dashboard 化与视觉语言复用

> 触发：能否复用 Trajectory tab 的 TOOL / ASSISTANT / USER / CONTEXT 要素、行点击、二级详情？
> 参照：[dsh-context](https://www.dsh.plus/en/plugins/dsh-context/) —— 同生态的兄弟插件，
> 已经把「单 tab 内做成 dashboard」这条路走通了（本仓库 `verify-render.mjs` 的注释即引用其
> `tests/repro-real-react.mjs` 作为先例）。

## 8. 能复用什么：先划清边界（已核实，非推测）

结论先行：**组件不能复用，契约和视觉语汇必须复用。**

### 8.1 组件层：不可复用（硬事实）

| 核实项 | 结论 |
|---|---|
| `@deepseek-ai/dsh-client-ui-conversation` 的 `./client` 入口导出 | 只有 `apply` / `inject` / `ConversationService` + **一批纯 type**（`lib/types/client/index.d.ts`） |
| `ChatView` / `DetailsPanel` / `ContextMeter` / `MessageItem` / `StatsLine` | `.d.ts` 存在于 `lib/types/client/{chat,skeleton}/`，**未在入口 re-export** → 无法 import |
| Trajectory tab 本体 | 来自**另一个包** `ui-trajectory`（`conversation.view` 的注释原文：「trajectory/waterfall from ui-trajectory」），不在依赖里 |

→ **TOOL / ASSISTANT / USER 徽章只能按同一套视觉规格重画，不能引用。**
这不是妥协，是插件边界的正常形态：审计是 out-of-tree 插件，跨包复用组件会把它绑死在
一个 rc 版本的内部实现上。**复刻视觉、对齐词汇、各自实现**是正确的耦合度。

### 8.2 契约层：这里有比组件更值钱的东西

核实 `contract/views.d.ts` 与 `contract/slots.d.ts` 时挖到三条关键契约：

**(a) 官方的「事件坐标系」是四元组，不是 seq**

```ts
interface SelectionTarget { turnSeq: number; stepSeq?: number; callId?: CallId; toolName?: string }
```

审计的 finding 现在只带 `seq`。**应该对齐到这个四元组**——不只是为了跳转，
更因为 `turn / step` 是画任何时间轴的 x 轴，没有它就没有 dashboard（见 §10）。

**(b) 跨 view 跳转的通道存在，但对审计 tab 是单向的**

```ts
interface ConvViewOwnerProps {
  inspect?: { callId: CallId } | null   // 收：别的 view 让我聚焦某个调用
  onInspectDone?: () => void            // 收完确认
}
```

审计 tab 能**接收** inspect 请求（它可以成为跳转的**目标**），
但**没有任何发出通道**——`ConvViewProps = PropsRuntime<'conversation.view'>`，
**不含 `PropsStore<ChatStore>`**（对比：`ChatViewSlotProps` 和 `DetailsSlotProps` 都含）。
`store.inspect` / `store.view` 只有持有 store 的视图能写。

→ 这从**契约层**证实了第一轮 §6.2 「F2 只能降级为复制」的判断是对的，
并且第一次给出了**唯一的上游修复路径**：`conversation.view` 的 owner 需要向下传一个
`onInspect(callId)` 回调（内部写 `store.inspect` + `store.view = 'trajectory'`）。
这是一条可以向 DSH 提的、具体到函数签名的需求，不是含糊的「希望支持跳转」。

→ **且跳转的键是 `callId` 而非 `seq`**。`tool/call.data` 里有 `callId`
（`behavior.rs` / `behavior.py` 的文件头注释已写明），但 finding 的 wire schema
把它丢了。**现在就该把 `callId` 加回 finding**——一个字段，为将来铺路（见 §10）。

**(c) 二级详情面板（`conversation.details.tool`）是 `single` slot，已被认领**

`DetailsSlotProps` 含 store，审计 tab 不含 → **无法驱动官方详情面板**。
二级详情只能**在审计 tab 内部自建**。这反而是好事：审计要看的详情（规则说明、
证据全文、前后事件上下文）和「工具调用输出」根本不是一回事。

### 8.3 该复用的：词汇表

徽章要打，但**命名对齐官方 `ChatNodeKind`**（`conversation-nodes/` 目录即枚举：
`assistant` / `command` / `compaction` / `fallback` / `message` / `retry` / `tool` /
`turn-error` / `turn-tail`）。审计关心的事件源只有三类，建议：

| 审计徽章 | 事件源 | 对齐关系 |
|---|---|---|
| `TOOL` | `tool/call`、`tool/result` | 直接沿用官方 `tool` kind 的配色与字重 |
| `APPROVAL` | `approval/asked`、`approval/decided` | 官方无对应 kind，新增；沿用同一套 badge 规格 |
| `SANDBOX` | `sandbox/mode` | 同上 |

**纪律**：沿用官方**规格**（字号、圆角、大写、字距），不发明第二套；
但**不硬套**官方枚举里审计用不到的 kind——审计的维度是「finding 来自什么事件」，
不是「聊天流里这是什么节点」。**看起来是一家，读起来是自己的语义。**

## 9. Dashboard 化：借 dsh-context 的成熟范式

### 9.1 dsh-context 做对了什么

它把一个 tab 做成了「**五合一 dashboard**」（stats / composition / history / events / messages），
其中四条模式可以直接搬到审计：

| dsh-context 的做法 | 为什么有效 | 审计的对应物 |
|---|---|---|
| 堆叠条**按模型完整上下文窗口**缩放，灰色轨道表示剩余 headroom | **分母有意义**，条形长度承载信息 | 我们的 `TokenBar` 分母是自身总和 → 见 §9.2 |
| 「每个模型请求一根条，Turn/Step 粒度，横向滚动」 | 把聚合终值还原成**过程** | findings / 成本时间轴（§9.3） |
| hover 出 tooltip，**点击 pin 住**完整拆解 | 浏览与深读分离，pin 住的详情不随鼠标乱跳 | 行点击 → 二级详情（§9.4） |
| 时间轴上打 **✂ 标记**（compaction / pruning 发生处） | 事件标记让曲线可解释 | **模型切换标记**（pro→flash→pro） |
| 事件流按 **Inject / Compact / Prune / Switch 过滤** | chip 即过滤器 | 严重度 chips 即过滤器（P1-2 已提） |
| 「**Honest coverage**」：compaction 之前的步骤显式标注为近似 | 不确定性写在脸上 | **正是 P0-3 需要的先例**——同生态已经确立了这条纪律 |

**最重要的一条**：dsh-context 用「Honest coverage」标注近似值，
和本仓库「harness 能力缺失时不伪造」是同一条纪律的两个实例。
**P0-3（¥1113.7 看起来像账单）在兄弟插件里已经有现成答案**，照做即可，不需要重新设计。

### 9.2 先砍掉一个假图表：现在的 TokenBar 不承载信息

`TokenBar`（`AuditView.tsx:227`）把四个 token 桶按**它们自己的总和**归一化。
本次会话输入占 99.7% → 那根条 99.7% 是一个颜色。**它每次都长这样。**
截图里就是一条几乎纯色的蓝条 + 右端一小截浅色——占了一整行视觉预算，信息量约等于零。

dsh-context 的做法点破了症结：**堆叠条的价值全在分母**。
它的分母是「模型完整上下文窗口」，所以条形长度直接回答「还剩多少余量」。

**改法（二选一）**：
- **A（推荐）**：换分母——按**单次请求的上下文占用 / 模型窗口上限**画，保留灰色 headroom 轨道。
  这需要 per-request 明细（§10-2），但它把一根装饰条变成了真正的仪表。
- **B（过渡）**：保留现有分母，但**加一条数值副标题**（「输入占 99.7% · 缓存命中率 18%」），
  让百分比以文字承载，条形降级为纯装饰并缩小高度。

在 A 的数据到位前先做 B——**不要让一个不承载信息的图形占据首屏一行**。

### 12.2 三个可直接搬用的实现事实（推翻了我的两处推测）

**(a) 它完全不用 SVG，也不用任何图表库** —— 全 bundle `svg` 出现 0 次。

`trendChart.tsx` 整个历史图表 **178 行**，堆叠条就是嵌套 div：

```js
const CHART_H = 112, BAR_W = 14, BAR_GAP = 2
<div className="lc-bar" style={{width: BAR_W}}>
  <div className="lc-bar-stack">
    {CATS.map(c => <div style={{ height: Math.max(1, Math.round(v / maxTotal * CHART_H)) + 'px',
                                 background: c.color }} />)}
  </div>
</div>
```

Y 轴只有三个标签（`max` / `max/2` / `0`）+ 两条网格线。
→ **§10 说的「手写内联 SVG，200 行以内」可以下修：div + 高度百分比，更简单，且天然继承 DSH 主题。**

**(b) 它用 CSS class + 注入 `<style>`，我们用内联 style 对象** —— 这不是风格差异，是**能力差异**。

`styles.ts` 324 行集中定义 `lc-*` 类；`AuditView.tsx` 则把 style 对象散在每个 `h()` 调用里。
后果很硬：**内联 style 写不出 `:hover`**。
所以 §9.4 提的「hover 显形操作栏」「hover 预览 tooltip」「整行 hover 高亮」——
**在当前的内联 style 架构下一条都做不了**。

→ **这是 ④ 结构批次的真正前置条件**：先把 `styles/index.ts` 从「导出 style 对象」
改成「导出 CSS 文本 + 类名常量」（`index.cts` 里已经有注入 `<style>` 的 `ctx.effect`，
`STYLES` 常量也已存在，**管道是通的，只是没用起来**）。这条改动不新增任何依赖。

**(c) 组件用 `makeXxx(kit)` 工厂闭包拿 `t`/`fmt`，不 prop-drill**

```js
function makeTrendChart(kit) { const { t, fmt, fmtTime, catLabel } = kit; return function TrendChart(props) { … } }
```

我们现在把 `lang` 一层层往下传（`FindingGroup` → `FindingRow` → `MarkControls` 全带 `lang`）。
改成 `viewkit` 工厂后 `lang` 从组件签名里彻底消失。**纯重构，零行为变化，顺手做。**

### 12.3 两个数据源发现（直接改写 §10 的 D1/D2）

**(a) `request/context` 事件带 `contextWindow`** —— 我们没消费这个事件类型。

```js
case 'request/context':
  if (typeof data.contextWindow === 'number') s.contextWindow = data.contextWindow
```

这就是 §9.2 里「按模型完整上下文窗口缩放、灰色轨道 = 剩余 headroom」的分母来源。
→ **D2 补一条：`RELEVANT_TYPES` 加入 `request/context`，取 `contextWindow`。**
一个事件类型换来一个有意义的分母，性价比极高。

**(b) 模型切换有显式信号，不需要我们去推断**

```js
case 'request/header':
  if (data?.reason === 'change' && s.model !== s.lastModel)
    s.events.push({ seq, time, kind: 'model', from: s.lastModel, to: s.model })
```

我们现在的 `tokenByModel.sequence` 是**对活跃模型做相邻去重**推出来的序列——
只有模型名，**没有 seq、没有 time、没有 from/to**，所以那五个 chip 只能一字排开，
画不到时间轴上（这正是 §9.3 图 1 缺的东西）。
DSH 直接给了 `reason === 'change'`，比我们的推断更准且自带坐标。
→ **D2 修正：不要给 `sequence` 补坐标，改为新增一条 `modelSwitches: [{seq, time, from, to}]`**，
这是 marker 的正确形状。（core/python/wasm 三方锁步。）

**(c) 标记（marker）挂到哪根条上——现成算法**

```js
// 事件挂到第一根 seq >= ev.seq 的柱子上
for (let r = 0; r < requests.length; r++) if (requests[r].seq >= ev.seq) { markers[r] ??= ev; break }
```

`✂` 就是柱子上方一个带 `title` 的 `<span>`，**没有任何定位数学**。我们的模型切换标记照此实现即可。

### 12.4 交互状态机：三个状态，全部受控

`TrendChart` 是**受控组件**，三个状态都在父级：

| 状态 | 语义 | 我们的对应 |
|---|---|---|
| `hoveredSeq` | 瞬时预览；**同时驱动旁边的 Context browser 实时刷新** | 悬停泳道上的点 → 下方 findings 表预览该条 |
| `selectedSeq` | 点击 pin 住；再点同一根 = 取消 | 点击 → 行内展开二级详情 |
| `activeTurn` | 悬停下方 turn 条带 → 非本轮柱子整体变暗 | 按 turn 圈选一段会话，findings 表随之过滤 |

**「hover 图表驱动旁边面板」（linked views / brushing）是它最值钱的交互**，
README 原话：「Hovering a bar also drives the Context browser beside it」。
→ 我们的对应形态：**悬停 findings 泳道上的某个点，下方表格滚动并高亮该条**；
移开鼠标回到用户自己 pin 住的选择。这比「点击跳转」轻，且不需要任何执行环境契约支持。

它还额外做了两件小事，都值得抄：
- **横向滚动的边缘渐变**：`edges` 状态跟踪 `scrollLeft`，两侧渐变提示「还有内容」；
- **自动贴右**：挂载时 `scrollLeft = scrollWidth`（最新数据在右端），
  且用户已在右端附近时保持贴右，否则不打断用户的滚动位置。
  **时间轴默认展示最新，这是审计场景同样需要的默认。**

### 12.5 它怎么处理「估算 vs 真实」—— P0-3 的现成答案

```js
const anchorOf = (req) => req.prompt > 0 && req.total > 0 ? req.prompt / req.total : 1
// 各分类的估算值统一乘以 anchorOf(req)
```

**保留估算的「比例」，把「量级」锚定到 provider 上报的真实值**；
tooltip 里两个数并排显示（`estimated` 与 `actual`）；
覆盖不到的区间（compaction 之前的步骤）**卡片上明写「只是近似」**。

README 里那句话应该刻进我们的验收标准：

> **never a token sum without its items** —— 绝不给出一个没有构成明细的总数。

我们的 `≈ ¥1113.7` 现在正是「一个没有明细的总数」。
→ **P0-3 的修法定稿**：金额旁标 `≈`，点开展开逐模型 × 逐桶的构成表，
并显式标注「缓存写入按 0 计」「空闲/高峰按事件时刻归属」两条假设。
不需要重新设计，照 dsh-context 的形做。

### 12.6 顺带确认的一件事：UI primitives 包是存在的，但几乎不该用

`dsh-context` 声明了 `@deepseek-ai/dsh-client-ui-primitives` 作为
**optional** peerDependency（`peerDependenciesMeta.optional: true`），
整个 1961 行 bundle 里只用了**一个符号**：`MarkdownText`。
其余全部手写。

→ 回答第三轮最初的问题：**「复用 DSH 的 UI 组件」在实践中约等于不存在。**
生态里做得最好的插件也是自己画，只在渲染 Markdown 这种真正复杂的地方才借力。
我们连 Markdown 都不需要渲染 → **primitives 包不必引入**，
坚持 §8.1 的结论：复刻视觉、对齐词汇、各自实现。

## 13. 一句话总结第三轮

> Trajectory 的**组件**复用不了，但它的**坐标系**（turn/step/callId）必须对齐；
> dsh-context 的**图表**不必重造，但它的**范式**（有意义的分母、过程而非终值、
> 诚实标注近似）应当照搬。
> 审计 tab 缺的从来不是图，是**把三个静态终值还原成一条会话时间线**——
> 图只是它的表现形式。

拆包之后要补第三句：

> 挡在时间轴前面的不是图表技术（178 行 div 就够，连 SVG 都不用），
> 而是两件不起眼的事——**内联 style 写不出 `:hover`**，以及
> **模型切换序列没带 seq/time**。
> 前者卡死了所有悬停交互，后者让曲线没有 x 轴。
> **③ 铺路批次才是真正的关键路径**，⑤ 图表反而是最轻的一批。

# 第四轮：设计原则（信息分层纲领）

> 前三轮都在回答「哪里错了」，但没回答「凭什么这么排」。
> 没有原则，每次改版都是重新拍脑袋，而且**下一个人接手时会把它改回去**。
> 本节是审计 tab 的信息架构纲领，优先级高于前三轮的任何单条建议——
> 前面的 P0/P1/P2 与它冲突时，以本节为准。

## 14. 先量一遍：首屏的像素预算被谁吃掉了

原则要从证据来。按截图实测（内容区 y≈100→855，可视 **755px**，再往下被输入框遮挡）：

| 区块 | 高度 | 占比 | 谁在看 | 看完有下一步动作吗 |
|---|---:|---:|---|---|
| 严重度 chips | 32px | 4% | 所有人 | ❌ 不可点，无动作 |
| TOKEN 用量（4 个数 + 一根条） | 75px | 10% | 场景 B | ❌ 看到 226.4M，然后呢 |
| 费用估算（含 5 个模型 chip） | 175px | **23%** | 场景 B | ❌ 知道切换过了，然后呢 |
| 行为审计列表 | 295px | 39% | **场景 A（约 70% 的访问）** | ✅ 唯一能驱动动作的区块 |
| 分隔线 + 区块间距 | ~178px | **24%** | — | — |

三个数字很刺眼：

1. **留白和分隔线吃掉 24%** —— 比 TOKEN + chips 加起来还多。
2. **费用（23%）逼近 findings（39%）**，但 70% 的访问是为 findings 来的。
3. **首屏 37% 的面积（chips + token + 费用）没有任何一处可以点击**。

**用户第一眼看到的，是一片不能操作、也不指向下一步的数字。**

## 15. 六条设计原则

### 原则 1｜首屏回答问题，不是陈列数据

**用户什么时候点开审计 tab？** 三个真实触发时机，频率差一个量级：

| 触发时机 | 频率 | 用户带来的问题 |
|---|---:|---|
| 一轮长任务跑完 | ~70% | **「刚才这一轮，安全吗？」**（是非题） |
| 看到额度/账单告警 | ~25% | 「钱花在哪一段」 |
| 要交付 / 留档 | ~5% | 「导出一份」 |

七成的访问带着一个**是非题**来。而首屏给的是三个计数 chip，
**要用户自己把「3 严重」翻译成「有问题」**——翻译这一步，就是产品没做完的活。

更糟的是这个翻译**会翻错**：SV610「审批决定 allowed-once」是 warning，
但那是用户自己批准的，风险为零；SV609「审批请求」是 info，同样不是风险。
**规则严重度 ≠ 风险结论。** 直接把严重度当结论展示，等于把误判外包给用户。

**改**：首屏第一行是一句**结论**，不是一排计数：

```
⚠ 本次会话有 1 项需要复核        · 3 项已确认安全 · 2 项已忽略 · 2 项为正常审批流
```

`需要复核` 的定义要写死在代码里、并可解释：**未被标记、且严重度 ≥ warning、且不属于
审批/沙箱正常流程的 finding 数**。没有这条的时候，结论行显示 `✓ 未发现需复核项`。

**验收测试**：把首屏截图给一个没用过的人看 3 秒，问「这次会话有问题吗」。
答不上来，或答错，就是原则 1 没做到。

---

### 原则 2｜像素预算按访问频率分配，不按功能重要性

费用计算是这个项目里技术含量最高的部分（四方锁步、逐字节对账），
但**技术投入不能兑换成屏幕面积**——那是给团队的奖励，不是给用户的价值。

**分配依据是「有多少次访问是为它来的」**：

| 区块 | 现状 | 建议 | 依据 |
|---|---:|---:|---|
| 结论行 | 0 | ~40px | 100% 的访问都要看 |
| findings | 39% | **≥ 55%** | 70% 的访问为它而来 |
| 费用 | 23% | **≤ 8%（压成一行，可展开）** | 25% 的访问，且看完不需要立即动作 |
| TOKEN 用量 | 10% | **0（并入费用展开层）** | 见原则 3 |
| 留白/分隔 | 24% | **≤ 12%** | 三个区块用两条分隔线 + `space.lg` 是过度分隔 |

费用压成一行的具体形态：

```
≈ ¥1113.7  ⓘ 估算   ·  deepseek-v4-pro ¥1089.5  ·  flash ¥24.1  ·  切换 5 次 ▾
```

一行承载：总额、估算标记、逐模型明细、切换次数、展开入口。
**原来 175px 表达的东西，40px 表达完，且信息量更大**（多了「切换 5 次」这个数）。

---

### 原则 3｜信息密度 = 单位像素承载的维度数，不是塞进去的字符数

「有限空间承载信息量」最容易走偏的地方：把密度理解成「字更小、行更挤」。
真正的密度是**同一块像素同时回答几个问题**。

dsh-context 的柱子是范本：**14px 宽的一根柱子**同时承载 6 个维度——
总量（高度）、六类构成（分段）、turn 归属（下方色带）、是否发生 compaction（✂）、
hover 态、selected 态。

反例就在我们自己的实现里：

| 元素 | 占用 | 承载的维度 | 密度 |
|---|---|---|---|
| `TokenBar` 分段条 | 整行 × 6px 高 | **1 个**（四桶比例），而且输入恒占 99%+ → **实质 0 个** | 极低 |
| 每行右侧 4 个按钮（复制/安全/高危/忽略） | 行宽的 ~30% | **1 个**（标记状态），且是低频操作 | 极低 |
| findings 行的 severity glyph | ~12px | **2 个**（严重度 + 是否被标记高危 ▲） | 高 |

→ **`TokenBar` 应当删除**（不是优化）。它每次都长一个样，占一行像素承载零维度。
它想表达的「输入占 99.7%」用**一句文字**表达即可，占 0 行（并进费用行）。

→ **4 个按钮应收进 hover / 展开层**，行上只留一个 `⋯`；
已标记的行用**一个彩色 chip** 常驻（同时承载「标记状态」和「标记类型」两个维度）。

**验收测试**：对首屏每个元素问一句——**「它在不同会话之间会变得不一样吗？」**
答案是「基本都长一样」的元素，就是零密度元素，应当删除或降级。

---

### 原则 4｜折叠可以隐藏细节，不能隐藏风险

这是对「低频信息是否放二级」的直接回答：**可以，但入口标签必须携带结论。**

现状是这条原则的完美反例：底部一行灰字 `▸ 已忽略 2 条`。
折叠低频信息，方向对；但**入口不承载结论**——用户不知道被折叠的里面有 3 项 critical。
一个永远不被展开的折叠区，把最高风险藏住了。

**规则**：任何折叠入口的标签必须携带**被折叠内容的最高严重度**：

```
▸ 已忽略 2 条（含 ✕ 3 项严重）      ← 对
▸ 已忽略 2 条                       ← 错
```

**「折叠态测试」**（建议写进验收清单）：
> 假设这个折叠区**永远不会被展开**，用户会不会因此做出错误判断？
> 会 → 入口标签的信息不足。

同一条测试适用于所有降级：截断的长路径（hover 才见全文）、
`showAll` 折叠掉的第 21 条之后的 findings、以及未来的图表折叠态。

---

### 原则 5｜默认态即最优态

用户不做任何操作时看到的那一屏，必须是对**最高频场景**最优的那一屏。
每一个需要用户先点一下才变好用的设计，都是把成本转嫁给了每一位用户。

对照检查（当前实现）：

| 默认态 | 现状 | 是否最优 | 依据 |
|---|---|---|---|
| findings 排序 | critical → warning → info，组内 seq 降序 | ✅ | 最高危 + 最新在前，正确 |
| 严重度过滤 | 全选（无过滤） | ✅ | 首次访问不该预设过滤 |
| 分组折叠阈值 | `COLLAPSE_AT = 20` | ⚠️ | 20 条撑满整屏；高频场景是「快速扫一眼」，建议降到 **8**，配合原则 4 的入口标签 |
| 已忽略区 | 默认收起 | ✅（补齐标签后） | 低频，收起正确 |
| 时间轴图表（未来） | — | 建议**默认展开图 1、图 2 收起** | 成本曲线服务 25% 场景 B，泳道服务 70% 场景 A——但泳道在 findings 少于 ~10 条时没有形态可言，**按数据量自适应**：findings ≥ 10 才默认展开 |

**最后一条是原则 5 的精髓**：默认态可以**由数据决定**，而不是写死。
8 条 findings 画泳道是浪费，80 条画泳道是救命。

---

### 原则 6｜任何一个汇总数，都必须能点开看见它的构成

直接借 dsh-context 的纪律：**never a token sum without its items**。

这条同时管三个地方：
- `≈ ¥1113.7` → 点开是逐模型 × 逐桶的构成表 + 两条计价假设；
- 结论行的 `1 项需要复核` → 点击即过滤出这 1 项；
- 每个严重度 chip → 点击即过滤（P1-2）。

**反过来也成立**：如果一个数字**点不开**，说明我们没有它的构成——
那就不该用「精确到小数点后一位」的形态展示它。
`¥1113.7` 与 `≈ ¥1.1k` 传达的确定性完全不同，而后者才是诚实的。

## 16. 应用原则后的信息分层表

把审计 tab 的全部信息按 **L0–L3** 归位。

> ⚠️ **本节的判据已被 §19 修订**。这里原写「判断依据只有一条：用户需要它的频率，
> 不是它有多重要」——**过度简化了**。频率与重要性是两条独立的轴，
> 压成一轴会把「高频但不重要」误当成重要（费用区块占 23% 首屏即由此而来）。
> 下面的 L0–L3 分层结论仍然成立（它们恰好与四象限一致），但**判据以 §19 为准**。

| 层 | 触达成本 | 内容 | 高度预算 |
|---|---|---|---|
| **L0 结论** | 0 操作 | 一句话结论（原则 1）；可点的严重度/已忽略 chips | ~70px |
| **L1 扫描** | 眼睛扫 + 悬停 | findings 分组列表（kind 徽章 + 规则 + 证据）；费用一行；时间轴图（数据量够时） | ~420px |
| **L2 详情** | 1 次点击 | 单条 finding 展开：证据全文、规则说明、turn/step/callId、前后事件、标记与复制；费用构成表；TOKEN 四桶明细 | 按需 |
| **L3 溯源** | 2 次点击 / 跳出 | 导出 JSON；原始事件；跨会话对比（未来） | 按需 |

**被明确降级的**（原来在 L0/L1，应下沉或删除）：

| 信息 | 从 | 到 | 理由 |
|---|---|---|---|
| TOKEN 四桶数字 | L0 | **L2** | 看完无动作；总量信息并进费用行 |
| `TokenBar` 分段条 | L0 | **删除** | 零维度（原则 3） |
| 5 个模型切换 chip | L0 | **L1 一行内的「切换 5 次 ▾」** | 保留「切换过」这个信号，明细下沉 |
| 每行 4 个操作按钮 | L1 常驻 | **L2 / hover** | 低频操作占高频信息的像素（原则 3） |
| `#440338` seq | L1 常驻 | **L2** | 无跳转能力时它只是噪声（§8.2b） |

**被明确升级的**：

| 信息 | 从 | 到 | 理由 |
|---|---|---|---|
| 「需要复核」结论 | 不存在 | **L0 第一行** | 70% 访问的核心问题（原则 1） |
| 已忽略中的最高严重度 | 藏在 L2 | **L0 入口标签** | 折叠态测试（原则 4） |
| 估算假设 | 不存在 | **L0 一个 `ⓘ`，L2 展开全文** | 原则 6 + P0-3 |
| 规则触发条件说明 | 不存在 | **L2** | 二级详情的核心内容（D3） |

## 17. 把原则变成可执行的验收清单

原则不写成测试就会被下一次改版磨掉。四条测试建议直接进 `verify-render.mjs`
或人工评审清单：

| # | 测试 | 类型 | 对应原则 | 状态 |
|---|---|---|---|---|
| T1 | **3 秒测试**：首屏截图给未使用者看 3 秒，问「这次会话有问题吗」，答对率 | 人工，每次改版 | 原则 1 | 待原则 1 落地后执行 |
| T2 | **恒定元素扫描**：三份差异极大的会话渲染首屏，逐区块比对——逐字节相同 = 零密度 | 自动化 | 原则 3 | ✅ 已落地 |
| T3 | **折叠态测试**：折叠入口标签必须携带被折叠内容的最高严重度 | 自动化 | 原则 4 | ✅ 已落地（含反向用例 T3b） |
| T4 | **可展开性**：首屏每个数值型元素都必须有 onClick 或展开入口 | 自动化（遍历渲染树断言） | 原则 6 | ⏳ 待原则 6 落地后加 |

### 17.1 T2 / T3 的实现与边界（`scripts/verify-render.mjs`）

**新增的可测性支撑**：首屏区块补了 `data-audit-summary` / `data-audit-tokenbar` /
`data-audit-ignored` 三个锚点；`verify-render.mjs` 加了 `localStorage` stub
（Node 没有，此前 F3 标记的所有代码路径在测试里根本不可达），
并手写了一个平衡标签扫描器 `extractRegion()` —— 本包不依赖 jsdom，不为一个测试引入它。

**T2 的实现**：三份 fixture（`big-session` / `small-session` / `huge-critical-session`），
token 量级差 700 倍、模型组合与 findings 完全不同。对五个锚点区块断言两件事：
每份 fixture 都必须渲染出该区块；且三份的输出**不得逐字节相同**。
同时打印 Dice 相似度供人评审。当前实测：

```
summary 0.58 · tokens 0.88 · tokenbar 0.84 · cost 0.41 · findings 0.43
```

**T2 的诚实边界（必须写明，否则会被误读为「TokenBar 通过了体检」）**：
本测只抓**逐字节相同**。`TokenBar` 属于「三次都几乎一样、但不完全一样」的
**近恒定元素**——0.84 的相似度里，差异几乎全部来自 `title` 里的数字，
条形本身的视觉形态三次无法区分。要自动裁决它就必须引入任意阈值，
而**调阈值等于调 fixture 调到自己想要的结论**。
→ 因此 `TokenBar` 的存废仍是**原则 3 的人工判断**（结论未变：应删除），
T2 只负责挡住「新增一个恒定元素」这类回归。

**T3 的实现**：预置两条 critical 为 `ignored`，在**折叠态**（行未展开，正是
「永远不展开」的假设场景）下断言入口标签含 `✕` 与条数；
配一条反向用例 T3b：被忽略项全是 info 时，入口**不得**谎报出更高严重度。

**两条测试都做过 red-then-green 验证**（一个从没红过的测试不是护栏）：

| 测试 | 注入的缺陷 | 结果 |
|---|---|---|
| T3 | 把折叠标签改回 `已忽略 {n} 条` | ✅ 红，报「折叠隐藏了风险」并打印实际 region |
| T2 | 把 `TOKEN_SEGMENTS.pick` 全改成常量 | ✅ 红，报 `data-audit-tokenbar` 零信息密度 |

# 第五轮：承接优先级与目标布局

## 19. 四象限承接优先级（修订 §16 的单轴判据）

§16 写的是「**判断依据只有一条：用户需要它的频率，不是它有多重要**」——
这条**过度简化了**。频率和重要性是**两条独立的轴**，压成一轴会犯一个具体的错：
把「高频但不重要」误当成「重要」，然后给它首屏面积。
费用区块占 23% 首屏，正是这个错误的产物。

正确的承接优先级是**两轴四象限，每个象限配不同的体验策略**：

```
        重要 ↑
             │
   P1 低频重要          P0 高频重要
   「条件常驻」          「直接给答案」
   平时是入口，触发时升格   常驻首屏，且必须是结论态
             │
   ──────────┼──────────→ 高频
             │
   P3 低频不重要         P2 高频不重要
   「移出主界面」         「压缩到极致」
   二级页/导出/CLI/不做    一行、一个角标，绝不占块
             │
```

| 象限 | 体验策略 | 失败模式（做错时长什么样） |
|---|---|---|
| **P0 高频重要** | **直接给答案**——常驻首屏，且**必须是结论态**，不能让用户自己翻译数据 | 给了计数让用户自己判断（现状：「3 严重」） |
| **P1 低频重要** | **条件常驻**——平时收成一个入口/角标；**触发条件满足时升格**，且入口标签必须携带结论 | **静默**（现状：3 项 critical 被折叠进「已忽略 2 条」） |
| **P2 高频不重要** | **压缩到极致**——用户每次都会瞥一眼，所以不能删；但看完不驱动动作，所以**绝不允许占一个区块**。一行、一个数、一个角标，配可展开 | **被误当成重要**而获得区块面积（现状：费用 23% + TOKEN 10%） |
| **P3 低频不重要** | **移出主界面**——二级页、导出、CLI，或者**直接不做** | 为了「功能完整」留在首屏（现状：`TokenBar`） |

### 19.1 审计 tab 的全量信息盘点

| 信息 | 频次 | 重要性 | 象限 | 策略落点 |
|---|---|---|---|---|
| 「有没有需要复核的」结论 | 高 | 高 | **P0** | 首屏第一行，一句话 |
| findings 分组列表 + 证据 | 高 | 高 | **P0** | 首屏主体，≥55% 面积 |
| 严重度/已忽略 chips | 高 | 高 | **P0** | 首屏，且可点即过滤 |

| 估算假设（缓存写按 0 计…） | 低 | 高（影响信任与对账） | **P1** | 平时 `ⓘ`；**`unpriced>0` 时升格为黄字一行** |
| 已忽略项里的最高严重度 | 低 | 高 | **P1** | **入口标签必须带**（✅ 已落地，T3 守） |
| 三态标记操作 | 低 | 中 | **P1** | hover / 展开层显形；**已标记的常驻一个 chip** |
| 总费用金额 | 高 | 低 | **P2** | 压进一行 |
| TOKEN 总量与占比 | 高 | 低 | **P2** | 并进同一行，只留「输入占 99.7%」 |
| 「模型切换过」这个事实 | 高 | 低 | **P2** | 同行末尾「切换 5 次 ▾」 |
| 逐模型费用明细 | 低 | 低 | **P3** | 收进 `▾` 展开层 |
| TOKEN 四桶明细 | 低 | 低 | **P3** | 同上 |
| `TokenBar` 分段条 | 高 | **无** | **P3** | **删除**（原则 3） |
| `#440338` seq | 高 | 低（无跳转能力时） | **P2→P3** | 换成 `T31·s2` 坐标，移进展开层 |
| 导出 JSON | 低 | 高（仅对场景 C） | **P1** | 右上角一个图标按钮 |
| 跨会话对比 | 低 | 低（当前无用户） | **P3** | **不做** |

### 19.2 三条从象限推出的硬结论

1. **P2 是最危险的象限**。「用户每次都看」极易被误读成「重要」，于是拿到区块面积。
   审计 tab 现在 33% 的首屏（费用 23% + TOKEN 10%）全是 P2——
   **压缩后应 ≤ 8%**，腾出的 25% 全部给 P0。

2. **P1 的验收标准是「触发时会不会被看见」，不是「做没做」**。
   估算假设做了但只是静态灰字 → 未知模型出现时用户仍不会注意 → P1 失败。
   所以 P1 必须写**升格条件**：
   `unpriced > 0` → 黄字；`ignored` 里含 critical → 入口带 ✕（✅）；
   finding 含 SV601/SV602/SV603 → 结论行标红而非标黄。

3. **P3 要敢删**。`TokenBar` 是「为了功能完整而留」的典型——
   删掉它，首屏没有任何损失，反而多出一行给 findings。

# 第六轮：Token 区块的归类修正（并驳回饼图）

> 触发：「Token 用量删除了？是不是可以做成饼图或环形图？这些其实比价格更管用。」
> 结论：**「比价格更管用」成立且我归类错了**；**饼图不成立**，理由与 TokenBar 完全相同。

## 21. 我在 §19.1 犯的归类错误

§19.1 把「TOKEN 总量与占比」整块判成 **P2（高频不重要）**。这个判断把两样不同的东西
当成了一样：

| 信息 | 看完有下一步动作吗 | 正确象限 |
|---|---|---|
| **原始数字**「输入 226.4M · 输出 685.8K」 | ❌ 没有 | **P2**（原判正确） |
| **派生洞察**「缓存命中 18.1%」 | ✅ 有——命中率低意味着上下文在被反复重发，该 compact / 该查请求结构是否打断了前缀匹配 | **P0**（原判**错误**） |

**「原始 token 数字」和「从 token 派生的洞察」不是同一类信息，不该同进同退。**
我把它们一起降级了，这是错的。

而「token 比价格更管用」这个判断有三条硬理由，应当写进象限判据：

1. **token 是 provider 上报的 ground truth；价格是 tokens × 一张有假设的价格表**
   （缓存写按 0 计、空闲/高峰按时刻归属）——多一层推导就多一层不确定。
2. **价格是业务数据**，会随官方调价变动，本仓库明确规定它「变了不需要 golden `--update`」；
   token 是测量结果，性质完全不同。
3. **决定性的一条：token 能驱动动作，价格不能。** 看到 ¥1113.7 用户不会做任何事；
   看到「缓存命中 18%」用户会去查上下文结构。

→ **修订**：§20 目标布局里 token 与价格的次序应当**对调**——
token 派生洞察在上（P0），价格在下（P2）。原稿把两者一起压进一行、且价格在前，是错的。

## 22. 为什么不做饼图 / 环形图

用真实数据算一遍就清楚了（总计 277.2M）：

| 桶 | 值 | 占比 | 环形图上的弧长 |
|---|---:|---:|---|
| 输入（未命中） | 226.4M | 81.7% | 294° |
| 缓存读 | 50.1M | 18.1% | 65° |
| 输出 | 685.8K | **0.25%** | **0.9°** —— 画不出来 |
| 缓存写 | 0 | 0% | 0° |

**两条否决理由**：

1. **量级差 330 倍，饼图的前提不成立**。饼图适用于 3–6 个**量级可比**的切片；
   `输出` 那片是 0.9 度弧，在任何尺寸下都是一条看不见的线。
   （审计 tab 里没有任何一组数据满足饼图条件：费用 pro : flash = 98 : 2 同样不行；
   findings 2/2/2 倒是可比，但三个数不需要图。）

2. **更根本的一条：环形图就是把条形图卷成一个圆——同一个分母、同一份信息量。**
   §9.2 从 dsh-context 拆包里得出的结论是「**堆叠条的价值全在分母**」：
   它按**模型完整上下文窗口**缩放、留灰色 headroom 轨道，所以条形长度直接回答
   「还剩多少余量」。我们的 TokenBar 用**四桶自身之和**做分母，所以每次都长一样。
   **换成圆形，分母没变，信息量一分没多。**

> 问题从来不在形状，在分母。把一个零维度的条卷成一个零维度的环，不是可视化。

## 24. 顺带挖出的真缺陷：「缓存写 0」是一个伪造的列 🔴

追这个问题时核到 `scripts/agent_vitals/agent/usage.py:77`：

```python
"cache_write_tokens": _int_or_none(usage.get("cacheWriteTokens")) or 0,
```

**字段缺失被折叠成了 `0`。** 而项目记录明确写着：DSH 的 adapter 在真实会话里
**只上报 `input` / `output` / `cacheRead`，`cacheWriteTokens` 字段整个不存在**
（会话 94997694 实测）。

于是 UI 上那个「缓存写 0」读起来是「我们测到了零次缓存写入」，
**真相却是「这个执行环境根本不报缓存写入」**。

这正是 CLAUDE.md 里最硬那条纪律的反例：

> Never substitute install time or mtime for a missing trigger count —
> a report missing a column is useful; a report with a fabricated one is not.

`classify()` / SV605 都严格遵守了「拿不到就降级、不臆造」，而成本折叠这里
**用 `or 0` 把「未上报」和「零」合并了**——同一个仓库里的两套标准。

**修法**（三方锁步：`usage.py` ↔ `usage.rs` ↔ wasm）：

1. 区分 `None`（未上报）与 `0`（上报了零）。折叠时 `None` 不参与求和，也不写成 0。
2. UI：`formatTokens` 已经用 `!== undefined` 判断、会自动省略该项——
   所以**只要引擎不再把缺失填成 0，UI 端零改动**即可恢复诚实。
   若希望显式告知，显示 `缓存写 未上报` 而不是省略。
3. 成本侧：`缓存写按 ¥0 计` 这条假设的措辞要改——
   现在是「价格表没有这一行所以按 0」，实际还叠加了「量本身就没上报」，
   **两个不确定性叠在一起，`≈` 角标的展开层必须两条都写。**
4. 加一条 regression：构造一份**缺 `cacheWriteTokens` 字段**的 usage 事件，
   断言折叠结果里该桶是「未知」而非 `0`。

**优先级：P0**。它不是显示问题，是**测量诚实性**问题——
与 P0-3（估算被当账单）同类，且比它更硬，因为 P0-3 至少标了「估算」，这个连标都没标。

### 25.1 M3 修正了我对 TokenBar 的论断

我在 §22 写的是「环形图＝条形图卷成圆，问题在分母」。截图让这条更精确：

dsh-context 的堆叠条里，`User Messages 0%` 和 `System Prompt 2%` 在条上**几乎看不见**——
按我原来的逻辑这条也该判死。但它是有效的，因为**条与图例是一个整体**：
条给形态，图例给数值。`System Prompt ≈1.7k 2%` 这一行本身就承载了三个维度。

→ **修正后的判据**：
一根堆叠条是否有价值，取决于两件事——**分母是否有意义**，以及**图例是否携带数值**。
我们的 `TokenBar` **两条都不满足**（分母是四桶自身之和；数值只在 hover 的 `title` 里）。
所以删除的结论不变，但理由要写全：不是「条形图不行」，是「**没有分母、也没有图例的条不行**」。

## 26. 产品判断：构成分布不在审计 tab 重做

用户想要的「多少是 system、多少是 tool schema、多少是 user」——
**dsh-context 已经做到了我们不可能超过的程度**：六类构成 + Top-5 大户 +
逐条目展开 + 逐 step 历史 + 估算/实测对账。它有**一整个 tab** 在做这件事。

在审计 tab 里做一个更差的复制品，是 §9.3 已经写过的错误：

> 若 dsh-context 已安装，这张图应该直接让位。**不与兄弟插件重复**，
> 比功能完整更重要。

**但同一份数据可以问一个不同的问题。这才是审计该做的：**

| | dsh-context | 审计 tab |
|---|---|---|
| 问题 | **上下文由什么构成？** | **这些构成里，哪些是你没打算付的？** |
| 性质 | 描述性 | **判断性** |
| `Tool Results 43.2k 56%` | 陈述事实 | 其中**失败调用**占多少？失败的结果仍占上下文、仍每轮重发、仍计费 |
| `Tool Schemas 7.1k 9% · 25 个` | 陈述事实 | 25 个里**几个本次一次都没被调用**？它们的 schema 每轮都在重发 |

这正是本仓库的核心命题在会话内的投影——
**agent-vitals 的本业就是「哪些 skill 常驻上下文却从不触发」**，
`Tool Schemas` 的分布就是这个问题在单次会话里的形态。
而「`scan.py` 测量，`SKILL.md` 判断」这条分工，恰好对应
「dsh-context 测量构成，审计判断浪费」。

### 26.1 审计版本长什么样

```
上下文浪费   ≈12.3k / 77.6k        16%
  ⚠ 失败工具结果      ≈8.1k    连续 5 次失败仍占用上下文并每轮重发（关联 SV613）
  ⚠ 未触发工具定义    ≈4.2k    25 个工具中 12 个本次一次未调用 · 常驻成本/轮
  完整构成分布 →  Context tab
```

三行，外加一个明确的**交接链接**。不抢 dsh-context 的活，也不放弃审计的判断职责。

### 26.2 数据可行性（已核实，非推测）

两条都能用**我们已经消费的事件**算出来：

| 指标 | 数据来源 | 现状 |
|---|---|---|
| 失败工具结果的 token 量 | `tool/result`（已在 `RELEVANT_TYPES`）+ core 的 `est_tokens` | ✅ 数据齐 |
| 未触发工具定义的 token 量 | `request/header.tools`（schema 全文，dsh-context 正是从这里估的）− `tool/call` 的 name 集合 | ✅ 数据齐 |

`est_tokens` 已是 core 的纯函数且被 `test_characterization` 钉住精确值，
Python/Rust/wasm 三方现成。**不需要新的事件类型，不需要 D2。**

### 26.3 一条必须守住的分寸：报成本，不报判决

「本次会话未调用」**不等于**「这个工具该删」——
一个工具在这次会话没用上，完全可能在下一次是关键。

这与仓库已有的纪律完全同构：**僵尸技能需要 `zombie_min_age_days`（默认 14 天）年龄门**，
单次未触发从来不足以定罪。

→ 所以措辞必须是**「常驻成本 ≈4.2k/轮」**（一个测量值），
**不能**是「建议移除这 12 个工具」（一个判决）。
判决留给用户，或留给跨会话聚合之后——这正是 §7 那句
「安全启发式只排序，绝不豁免」的另一面：**审计给证据，不替用户做决定。**
