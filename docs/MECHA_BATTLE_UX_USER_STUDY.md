> 对应 `MECHA_BATTLE_UX_ITERATION_SPEC.md` §11.3。此文件是执行准备，**不是已完成的用户测试或通过证明**。真实结果与验收状态见 `MECHA_BATTLE_UX_ACCEPTANCE.md`。

## 1. 目的和边界

确认未参与设计的目标用户，能否在合成战斗局面中：

1. 指出本回合按当前草稿预测受威胁的防守建筑。
2. 说明当前草稿的预计防守建筑损失，以及现在可执行的一项下一步操作。

至少招募 **5 名未参与该设计的目标用户**。先说明这是产品界面测试而非能力考试，征得参与同意；用户可随时停止。不要使用真实会话、账号、日志或任务内容。默认只记录参与者代号，不记录姓名、联系方式、屏幕录像、声音或其他个人信息；若另需录制，应事先单独征得同意并遵守团队的数据处理规定。不要上传测试数据。

## 3. 主持人口播和步骤

先说：

> “我们想了解这个界面是否清楚。请按照自己的理解操作并尽量说出你的想法；如果找不到也没关系。除非你要求结束，我不会提示具体按钮。”

1. 将预设草稿和界面交给参与者；不要预先展开答案、指向按钮或演示操作。开始计时。
2. **任务 1**（念原文）：“按照当前计划，这一回合哪些防守建筑受到敌方攻击威胁？请指出它们。” 记录回答、对应位置和完成时间。允许参与者自行查看界面与操作，但不要提示。如果其操作改变了草稿，先记录，再由主持人恢复同一局面；恢复过程不计为完成且不向参与者解释答案。
3. **任务 2**（念原文）：“按这个计划，防守建筑预计会损失多少？现在你可以做什么下一步操作？” 记录其损失数值、对操作的描述及完成时间。不要引导其提交或真的损毁建筑；说明一个当前可执行的操作即可。若需要恢复原草稿，任务 2 重新计时。
4. 两项无提示阶段结束后，才可询问：“哪里让你犹豫或误解？” 若之后给予提示或演示，另行记录；不要把提示后的成功计成无提示成功。

主持人应记录参与者主动使用的鼠标、键盘或触屏操作、明显犹豫和原话中的非个人信息。不得暗示建筑名称、损失值或要点击的控件。对帮助、意外改变草稿、退出或中断如实记录。不要用开发者或自动化操作冒充参与者。

## 4. 判定规则

- **任务 1 成功**：无提示指出答案卡中所有预计受威胁的防守建筑，且未将其他建筑误判为受威胁。可通过名称、坐标或准确指认位置作答；对局内没有受到攻击但可能被其他行动撞击的对象，不自动混为敌方威胁。
- **任务 2 成功**：无提示给出答案卡中正确的本回合防守建筑净损失，并正确指出此状态下一项真实可执行操作（例如可提交时说明提交，或可编辑时说明修改计划）。只说“安全”“等一等”而没有有效操作不算成功；不能把机甲受击当作建筑损失。
- 测试前由主持人与产品负责人确认答案卡、任意时间上限和中断处理。SPEC 没有规定耗时上限；即使设定研究用上限，也必须单列为研究约定，不能冒充 SPEC 门槛。记录每项实际耗时，含超时与失败。
- 每项至少 **4/5（80%）的有效参与者无提示成功**是 SPEC 目标；若超过 5 人，成功人数至少为有效人数的 80%（向上取整），并记录实际分子和分母，不能把 `4/5` 擅自换成固定的四人即可。任何缺失答案、提示后成功、环境中断或不确定判定不得当作成功。环境失败应单列，修复并重测后才作为有效参与者计入分母。
- 少于 5 名有效参与者、任一任务低于目标或局面无法核验时，验收尚未通过；记录改进或经评审接受的风险。样本量小，不对更广泛人群作统计推断。
