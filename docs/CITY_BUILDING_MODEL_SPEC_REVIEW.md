# 评审：CITY_BUILDING_MODEL_SPEC（BuildingModel 统一范式）

评审日期：2026-10-08。评审对象：`docs/CITY_BUILDING_MODEL_SPEC.md`（2026-10-08，状态「设计定稿待评审」）。
依据：本分支（merge-test-landmarks，8dab98cb）与 main 工作区的真实代码，数字均为实测，不是转述。

## 0. 结论

**有条件通过。** 方向对（声明层统一、运行时两条编译路径），但 SPEC 目前把「要统一什么」和「统一到多深」混在一起，
且有三处前提与代码对不上。建议**砍成两段交付**：

1. **先做「公共用地 + 配套 + 地标」的单体通道**（批 0、2、1），收益大、风险低、可独立停。
2. **会话楼附件通道（批 4）和批量编译器不做，另立项**。它是风险最大、收益最小的一段，SPEC 自己也承认主体不迁。

另外两条硬性前置：**先合并本分支再动 cityParts**（见 §3）；**验收从「截图逐像素等价」改成「场景图哈希等价」**（见 §4.2）。

## 1. SPEC 做对了的

| 点 | 为什么对 |
| --- | --- |
| 统一声明层、不统一运行时表示（§0 设计立场） | 4000 栋会话楼靠实例化，地标靠异构组合，两者强行同构必丢其一。这条判断是整份 SPEC 最重要的一句。 |
| 规划选址与造型分层（§3「model 不知道城市的存在」） | 与现有分层一致：`cityPlan` 选址、`cityParts` 造型。守住这条线才可能复用。 |
| 夜景豁免是声明语义，不是校验器猜的（§6.5 末段） | 与我们夜景 SPEC 的结论一致：只有光源发光；`night` 缺省 = 不发光。 |
| 四层验证「写错就过不了」优先于「写错了守卫抓」（§6.5） | 正确的优先级。判别联合让非法件在 tsc 就不可表示。 |
| 吸收旧守卫要做等价证明、禁止顺手加强（§6.6） | 防止守卫迁移时悄悄放松或收紧，这条纪律我们这轮也踩过坑。 |
| 价值与批次可独立停（§8） | 每批视觉零变化、可停。 |

## 3. 必须先解决的冲突：与本分支改动的重叠

本分支在 SPEC 之外**已经做了**其中一部分，并且改动面与 SPEC 完全重叠：

- 地标造型已拆成独立文件，registry 已存在（`engine/models/registry.ts`，kind → 造型函数 + 中文名）。这等于批 1 的「物理拆分」。
- 夜景：`cityLightBudget.ts`、立面 shader、`neonMesh` 门控、`setNightGlow` 全部改过。SPEC §6/§10 说「night 声明统一走 nightLighting 分发后，N1/N2 的门控改动一处生效」，但 `render/nightLighting.ts` 不存在。
- `cityParts.ts` 在本分支比 main 少 245 行（拆出去了），**行号和结构都已分叉**。

**建议顺序：先合并本分支，再启动 SPEC 批 0。** 否则批 0 在 main 结构上写、批 1 又要重新对齐本分支的文件，必然两头冲突。

## 4. 设计层面的问题

### 4.1 Part 字母表不够覆盖现用几何

SPEC §4 说「覆盖 buildLandmarks/buildPublicSites/buildCivics 现用全部几何」。实测对本分支的地标造型文件：

| 现用特性 | 出现处 | Part 能否表达 |
| --- | --- | --- |
| 部分球（phi/theta 范围，半球壳） | 帆顶歌剧院壳、穹顶 | 否：`sphere` 只有 size |
| 带弧长参数的圆环（半环拱圈） | 凯旋门拱圈 | 否：`torus` 无 arc |
| 开口圆柱 + 双面材质 | 机场壳形航站楼、歌剧院壳 | 否：无 `open`/`side` |
| 几何烘焙非均匀缩放（`scale(0.75,1.6,0.9)`） | 歌剧院壳 | 部分：size 可近似，但烘焙的是几何而非实例 |
| 实例的 x/z 轴旋转（`rotation.x/z`） | 摩天轮辐条、塔基支撑腿、宝塔 | 否：只有 `yaw` 与 `pitchZ`（且仅装饰件） |
| renderCanvas 生成的亮窗贴图 + 日夜贴图切换 | 双子塔、扭转塔 | 部分：`panel`/`windows:canvas` 只声明了名字，没定义 day/lit 两张贴图如何生成 |
| 旋转件与夜灯批次（`landmarkSpinners`、`nightLights.heads/neon`） | 摩天轮、灯塔、悬索桥 | 部分：`spin` 有，但夜灯是引擎共享材质（`MeshBasic` 批次），Part 的 `emissive` 倍率无法对应 |

**要补**：`rot: [rx, ry, rz]`（替换 yaw/pitchZ）、`sphere` 的 `phi/theta`、`torus` 的 `arc`、`open: boolean`、`side: "double"`、
灯泡件改成引用共享夜灯批次而不是自带 emissive 倍率。否则批 1 会有一半楼落进「未范式化白名单」，范式就名存实亡。

### 4.2 验收标准「截图逐像素等价」不可执行

- 仓库没有像素对比基础设施；渲染截图依赖真 GPU（Chrome + Metal），CI 里软件渲染慢且各机器不一致。
- 夜景、阴影、反射带时间/天气变量，逐像素必然有噪声。

**建议改为「场景图哈希等价」**：对同一 (kind, seed)，旧路径与新路径各自构建 `THREE.Group`，遍历所有网格，
对 `(几何顶点缓冲, 世界矩阵, 材质 color/emissive/side)` 取哈希并排序后比较。这是确定性、可进 CI、
比截图更严的等价证明，完全不需要 GPU。像素截图只留作人工抽查。

### 4.3 编译器的真实收益在材质缓存，不在 DSL

现状 `material(color, emissive)` 每次调用都 `new MeshLambertMaterial`，一座地标几十个材质对象。
编译器按 `(role, color, emissive)` 缓存材质，draw call 与内存都会下降。**这个收益不需要 Part DSL 就能拿到**，
可以作为批 0 的独立小步先做。

### 4.4 两条编译器路径的边界不清

§5 把「会话楼 = 批量、地标 = 单体、同一 model 可混用」写成规则，但没有定义**混用时的所有权**：
批量通道的 `claim/seal` 要求构建期一次性领槽；会话楼是随数据重建的。SPEC 也说「form 主体声明化另立项评估」。
**既然主体不迁，批量编译器就不该在本范式里实现**——只保留单体通道，批量通道留给拆分 SPEC 的 `BatchRegistry`。

### 4.5 四层验证偏重

L1 判别联合 + L3 CI 守卫已经足够；L2「dev 构建注册期逐 model 跑 geometry」与 L4「编译器夹取并计数」增加了运行时路径，
而 L4 的输入（budget）目前根本不存在（地标只有 `radius`）。**建议先实现 L1 + L3，L2/L4 等出现真实缺陷再加。**

### 4.6 与夜景预算的衔接缺失

SPEC 的 `emissive: number` 是「夜门控自发光倍率」，但本分支夜景已改成**统一预算**（`cityLightBudget.ts`：
`window/street/neon/landmark` 四类、每类固定强度与色温范围）。Part 的 `emissive` 应取预算的**类别**
（如 `"neon" | "landmark-window" | "street"`），而不是自由数值，否则会重新长出手填倍率。

## 5. 风险与代价

| 项 | 评估 |
| --- | --- |
| 技术风险 | 中。批 0–2 低（件列表已是 box/cylinder/glow 数组，`buildPublicSites`/`buildCivics` 几乎是直译）；批 1 中（上面 §4.1 的缺口）；批 4 高。 |
| 回归风险 | 靠场景图哈希等价（§4.2）可把「视觉零变化」变成可机器验证。 |
| 范围蔓延 | 高。SPEC 同时承诺 DSL、双编译器、四层验证、守卫吸收、内容包格式；其中内容包「皮肤」没有任何当前需求。 |
| 收益 | 新增建筑 = 一个文件 + 注册行：**这一点本分支的 registry 已经拿到了**；DSL 额外带来的是可序列化与守卫自动化。 |

**收益判断**：DSL 的边际价值主要是「内容包」。如果近期没有皮肤/自定义城市需求，批 1 之后的投入回报递减。

## 7. 对 SPEC 的修改建议

1. §0 用实测数字重写现状表（31 条、4670/4425 行、21 守卫、拆分后的目录结构）。
2. §4 补全 Part 字母（`rot`、`phi/theta`、`arc`、`open`、`side`、共享夜灯批次引用）。
3. §5 删除批量编译器；单体通道对接拆分 SPEC 的 `BatchRegistry` 只作为「将来」接口。
4. §6.5 验证层缩为 L1 + L3；验收改场景图哈希等价（§4.2）。
5. `emissive` 取夜景预算类别（§4.6）。
6. §7 明确悬索桥归属；样例 A 重写成可编译代码。
7. §8 批 4 标注「不做，另立项」；批 0 增加「材质缓存」子步。
8. 前置条件写明：**先合并本分支**。

## 8. 立即可做、风险为零的小步

不依赖 SPEC 定稿，可以现在就做：
- 材质缓存（`(color, emissive)` → 同一材质实例），预期明显减少地标材质对象数量（具体倍数待实测，这里不下数字）。
- 场景图哈希守卫：给现有 10 个地标造型建立「基线哈希」，之后任何重构都用它证明等价。
