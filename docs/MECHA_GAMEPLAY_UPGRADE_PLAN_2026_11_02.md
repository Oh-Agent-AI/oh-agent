## 1. 设计目标

Mecha 的目标体验不是“更多单位、更长技能列表”，而是让每个回合都能形成一个可推理的战术谜题：

```text
看到威胁 → 判断目标 → 选择站位 → 决定行动 → 承担代价 → 复盘结果
```

理想状态下，玩家在提交计划前应该能回答五个问题：

1. 本局赢的条件是什么？
2. 敌人下一步要打哪里？
3. 我能救什么、挡什么、杀什么？
4. 这个计划的代价是什么？
5. 如果失败，失败发生在哪一步？

---

## 2. 可玩性五支柱

### 支柱 1：公开谜题，不是赌博

敌方意图、伤害、范围和结算顺序必须提前可读。玩家可以犯错，但不能因为“看不到规则”而犯错。

### 支柱 2：位置本身就是武器

伤害很重要，但击退、阻挡、堵门、改变敌人目标、保护建筑同样重要。站位改变战场，而不是只为了让攻击进入射程。

### 支柱 3：目标之间必须有张力

杀 Boss、保建筑、阻止增援、保护机甲不应总是同向。好的回合应该是“不能全要”，而不是“全选最优”。

### 支柱 4：每个技能都有清晰身份

每个技能都应该有独特限制和最佳场景。低伤害但强位移的技能可以和高伤害技能一样重要。

### 支柱 5：失败能被复盘

失败后玩家应该知道关键原因：漏看击退、目标落空、建筑被击中、错失修理或站位暴露。可解释的失败比轻松胜利更有长期吸引力。

## 3. 当前可玩性判断

当前 Mecha 已经具备几个很好的基础：

- 三机甲、小棋盘、整包计划，决策规模适合策略思考。
- Boss / raiders / buildings 已经形成基本目标压力。
- `tunnel` 与 `peel` doctrine 已经提供两种战术取向。
- 高度、障碍、掩体、建筑 stake 已经有地形潜力。
- 本地和远程都走计划提交，不需要靠实时操作优势取胜。

主要可玩性短板：

| 问题 | 玩法影响 |
| --- | --- |
| 敌人意图和结算结果还不够“一眼可读” | 玩家难以建立稳定推理模型。 |
| 位移更多像控制，而不是战术工具 | 低伤害技能难以获得足够价值。 |
| 胜负目标偏固定 | 杀敌和守楼之外缺少可选压力。 |
| doctrine 是内部策略，不完全是玩家可理解的战术姿态 | 玩家不知道自己选择了什么风格。 |
| 修理和冷却的价值缺乏足够压力 | 支援位有时容易变成固定答案。 |
| 失败缺少复盘层 | 玩家较难从错误中学习。 |

## 4. 核心循环升级

### 4.1 单回合循环

目标循环：

```text
1. 读目标：本回合必须保护什么？
2. 读威胁：敌人准备打哪里，伤害多少？
3. 选姿态：推进 / 守楼 / 控位 / 拆增援。
4. 编辑计划：移动、攻击、修理、击退。
5. 预览后果：伤害、落点、落空、建筑风险。
6. 提交：规则权威结算。
7. 复盘：看事件链和下一回合威胁。
```

UI 应该让前五步在一张棋盘上完成，而不是强迫玩家在大量面板和文字之间来回切换。

### 4.2 局内成长循环

每场比赛中，玩家应该逐渐掌握：

- Boss cadence。
- raider 偏好。
- 击退可以打断什么。
- 哪些格是必守点。
- 什么时候修理比输出更重要。
- 什么时候主动暴露机甲更划算。

这不是数值成长，而是规则理解成长。

### 4.3 局外成长循环

局外通过地图、目标、机甲组合和难度保持新鲜感：

- 不同地图强调不同地形。
- 不同目标改变 doctrine 价值。
- 不同敌人组合惩罚固定套路。
- 更高难度增加压力，但不增加隐藏规则。

## 5. P0 升级：可读性与决策质量

这是第一优先级。可玩性提升的基础是让玩家理解战场。

### 5.1 敌意意图分层

敌人意图分三层展示：

| 层级 | 内容 | 默认展示 |
| --- | --- | --- |
| 必读层 | 攻击者、目标格、大致伤害 | 始终显示 |
| 条件层 | 击退、碰撞、连带目标 | 选中相关单位/目标时显示 |
| 细节层 | 完整结算顺序、原因说明 | 按需展开 |

默认画面必须能回答“谁要打哪里”，但不应把所有预测细节塞满屏幕。

### 5.2 攻击后果预览

每次选择目标时显示：

- 预期伤害。
- 预期死亡。
- 是否落空。
- 是否触发建筑损伤。
- 是否击退。
- 是否打断敌人行动。

对辅助技能，还要显示：

- 修理量。
- 被修理对象。
- 修理后是否能承受关键攻击。
- 是否浪费了本回合输出机会。

### 5.3 击退落点预览

击退不能只画一个方向箭头。玩家需要知道：

- 被击退者最终停在哪格。
- 是否撞墙、撞楼、撞单位。
- 是否被推入危险地形。
- 是否脱离攻击范围。
- 是否打断敌人意图。
- 被撞对象各受多少伤害。

这是 Mecha 后续最有价值的一条可读性升级。

### 5.4 禁用原因可视化

一个行动不可用时，UI 不应只是灰掉。长按、悬停或详情面板应说明：

- 超出射程。
- 无直线。
- 目标已死。
- 高度不可达。
- 冷却未完成。
- 目标被规则保护。
- 与整队移动冲突。

这能减少“为什么不能选”的挫败感。

### 5.5 结算顺序提示

当前整包计划适合策略思考，但玩家需要理解顺序。建议用简短阶段条表达：

```text
移动 → 行动 → 事件结算 → 敌人 → 回合结束
```

不需要展示每个内部判断，但需要说明：

- 行动顺序固定。
- 目标可能因位移而落空。
- 落空不会消耗冷却。
- 建筑和单位死亡在事件层可见。

### 5.6 P0 补充：开局部署阶段

这是一个明确缺口。原版 Into the Breach 在战斗开始前有部署/落位阶段；当前 Mecha 则基本直接进入规则生成的首回合。

当前代码锚点：

- PvE：[`rules.ts`](../apps/agent-city/ui/src/game/mecha/rules.ts) 的 `standardDeploy()` 固定把三台机甲放在下边线。
- PvP：[`rules/pvp.ts`](../apps/agent-city/ui/src/game/mecha/rules/pvp.ts) 的 `createPvpMatch()` 自动按列生成双方出生点。
- 控制器和 UI 没有“部署计划确认”流程。
- `createMatch()` 虽然允许传入自定义 `mechs`，但没有面向玩家的合法性校验、撤销、确认和远端同步。

这不是单纯缺一个 UI 环节，而是缺一个可验证的比赛阶段。

#### 5.6.1 目标

增加一个开局部署阶段：

```text
进入战斗 → 显示部署区 → 选择机甲 → 选择合法格 → 确认部署 → 生成首回合敌意 → 进入 player_plan
```

部署阶段的价值：

- 给玩家开局的主动权。
- 让不同地图产生不同的开局选择。
- 强化“地形即策略”的体验。
- 为守楼、堵路、阻止 spawn 等后续玩法打基础。
- 让玩家在看到首个 telegraph 前，先理解自己的进场位置和目标。

#### 5.6.2 首版范围

建议先做 PvE 本地部署，不做 PvP 同时隐藏部署。

最小闭环：

1. 战场初始化后进入 `deployment` 状态。
2. UI 显示三台机甲和可部署格。
3. 玩家逐台放置或交换位置。
4. 提交完整部署方案。
5. 权威规则校验所有位置。
6. 合法后写入 `MatchState.mechs`，再调用 `bossPrepare()` 生成首回合意图。
7. 状态进入 `player_plan`，开始正常回合。

首版不需要：

- 隐藏部署。
- 同时远程部署。
- 复杂阵型卡牌。
- 机甲换装。
- 部署阶段倒计时。
- PvP 部署。

#### 5.6.3 合法部署规则

部署格必须满足：

- 在棋盘内。
- 在本次地图定义的部署区内。
- 不是水、山、不可通行或规则禁止地形。
- 不与障碍、建筑、Boss、raider 或其他机甲重叠。
- 不使用将来会被敌人首回合立即占用的 spawn 格。
- 三台机甲全部放置且位置唯一。

建议首版使用保守部署区，例如下边线附近的一行或两行开放地，而不是全图任意落位。  
部署区可以由战场数据显式声明，也可以先由地图指纹推导；若远端参与，必须使用同一个权威计算结果。

#### 5.6.4 状态与规则接口

建议新增明确阶段，而不是只让 UI 在进入战斗前改数据：

```ts
export type Phase =
  | "deployment"
  | "enemy_prepare"
  | "player_plan"
  | "resolving_boss"
  | "finished";

export type DeployPlacement = {
  mechId: MechId;
  pos: Cell;
};

export type DeployPlan = {
  revision: number;
  placements: DeployPlacement[];
};

export type DeployTurn =
  | { ok: true; state: MatchState; log: TurnEvent[] }
  | { ok: false; fault: DeployFault };
```

规则权威需要提供类似：

```ts
validateDeployPlan(state, plan)
applyDeployPlan(state, plan)
```

要求：

- 输入状态不可变。
- 部署计划原子成功或原子拒绝。
- 成功后 revision 递增。
- 成功后才调用 `bossPrepare()`。
- 失败时保留部署草稿和失败原因。
- `MatchRuleAdapter` 后续暴露可选 `deploy()`。

#### 5.6.5 UI 行为

部署界面至少要有：

- 可部署格高亮。
- 当前选择机甲高亮。
- 未放置机甲提示。
- 已放置位置提示。
- 重置部署。
- 撤销上一步。
- 确认按钮，且只有在三台全部合法放置后可用。
- 非法落点显示原因：超出部署区、被占用、地形不可用等。
- 退出或返回入口。

部署阶段不显示敌人意图，因为首回合意图应在部署确认后生成。  
但可以显示地形信息、建筑 stake、任务目标和机甲基础能力。

#### 5.6.6 本地 PvE 与远程 PvE 的差异

本地 PvE 可以先把部署做成前置 UI：

```text
选站点 → 部署 → createMatch(custom mechs) → playTurn
```

这能最快验证可玩性。

远程 PvE 则必须把部署当作比赛状态的一部分：

- 快照必须包含 `deployment` 阶段。
- 客户端提交 `DeployPlan`，不能只提交本地改好的初始状态。
- 权威端复验部署。
- 成功后才广播新的完整快照。
- 断线重连必须能恢复部署阶段。

因此本地验证可以先行，但 UI 和 controller 不应把部署逻辑写成无法迁移到远程的纯前端副作用。

#### 5.6.7 PvP 部署策略

PvP 部署是更大的设计问题，不建议首版直接做。

可选方案：

| 方案 | 优点 | 风险 |
| --- | --- | --- |
| 保持自动出生点 | 简单、公平、易测试 | 缺少开局策略。 |
| 交替落位 | 可远端同步，策略明显 | 先后手体验需要调平。 |
| 同时隐藏部署 | 更接近真实博弈 | 需要隐藏信息、阶段同步和反作弊边界。 |

PvP 部署应等 PvE 部署、PvP 核心规则和远端阶段同步稳定后再评审。

## 6. P0 升级：Doctrine 从“内部策略”变成“玩家战术姿态”

`tunnel` 和 `peel` 已经存在，但玩家应该能理解自己选择的是什么。

### 6.1 Doctrine 命名与表达

建议 UI 使用更直观的名称：

| 内部 doctrine | 玩家可读名称 | 一句话目标 |
| --- | --- | --- |
| `tunnel` | 强攻核心 | 优先压 Boss，可接受一定建筑/单位风险。 |
| `peel` | 守卫街区 | 优先保护建筑和清理近身威胁。 |
| 未来 `contain` | 锁位压制 | 优先用位移和站位限制敌人。 |
| 未来 `deny` | 封锁增援 | 优先阻止 spawn。 |

首版不需要新增四种，只需要把现有两种做成明确选择。

### 6.2 Doctrine 信息

选择 doctrine 时显示：

- 优先目标。
- 会牺牲什么。
- 建议保护哪台机甲。
- 对当前威胁的简要说明。

例如：

- 强攻核心：“优先削减 Boss，可能放任远端建筑受损。”
- 守卫街区：“优先保护建筑，Boss 击杀速度可能更慢。”

### 6.3 Doctrine 不应变成自动最优

Doctrine 是玩家表达意图，不是隐藏最优解按钮。  
AI 可以帮助填充计划，但 UI 应保留：

- 手动覆盖。
- 撤销草稿。
- 查看为什么推荐该目标。
- 提交前确认。

### 6.4 当前 AI 求解器算法与升级边界

当前 AI 不是 minimax、A*、MCTS 或多回合最优求解器，而是：

```text
doctrine 焦点 → 每机甲候选裁剪 → 候选组合 → 整包规则模拟 → 全局评分 → 确定性选择
```

具体流程：

1. 根据 `tunnel` 或 `peel` 选择战术焦点。
2. 为每台机甲计算可达格，并按接近焦点的启发式排序。
3. 保留少量候选位置，通常是原位加前几名。
4. 在候选位置上生成 `legalActions()`，再用局部分数裁剪。
5. 将三台机甲候选做笛卡尔组合，形成完整 `ArenaPlan`。
6. 对每个计划调用规则模拟，再按 doctrine 权重评分。
7. 选最高分计划；同分使用确定性 tie-break。

当前规模大约是每台机甲 5–6 个候选，三机甲组合约 200 个左右。对 TypeScript 来说通常足够快，因此 AI 升级的第一优先级不是换语言，而是把算法边界和评分因子显式化。

#### 6.4.1 可玩性要求

AI 是“推荐器”，不是“答案机”：

- 推荐计划必须来自规则权威可接受的行动。
- 相同 `MatchState` 和 doctrine 必须产生相同推荐。
- UI 可以展示推荐理由，但不应该宣称它是唯一正确解。
- 玩家必须能覆盖 AI 推荐、撤销草稿并提交前确认。
- 自动求解不能变成替代思考的主玩法。

推荐理由应映射到显式评分因子，而不是只显示“AI 建议”：

| 因子 | 玩家可读解释 |
| --- | --- |
| boss damage | 对核心威胁造成伤害。 |
| raider damage | 清理近身或威胁建筑的敌人。 |
| building protection | 减少建筑损伤。 |
| mech survival | 降低机甲阵亡风险。 |
| position value | 抢占关键格、保护目标或改善下一回合站位。 |
| cooldown value | 保留或使用关键技能。 |
| repair value | 修复关键单位，换取下一回合承伤能力。 |

#### 6.4.2 性能与二进制策略

性能路线应分级：

1. **保持 TypeScript**：当前搜索规模小，先建立 golden tests。
2. **抽评分契约**：新增 `CandidateSource`、`PlanSimulator`、`PlanScorer`、`PlanEvaluation`。
3. **优化重复计算**：缓存寻路、可达格和合法动作，避免无边界 `structuredClone` 扩散。
4. **Worker 化**：只有当搜索影响输入帧率时，把 AI 放入 worker，并带 revision 和取消机制。
5. **Rust / WebAssembly**：仅当计划评估数达到数千、引入多回合前瞻，或 worker 化后仍有性能瓶颈时考虑。

不建议现在直接编译成平台原生二进制。UI 主要运行在 WebView / 浏览器语境中，原生二进制会带来构建、平台适配和调试成本；当前更大的收益来自评分契约、缓存和 Worker 边界。若未来需要二进制，优先选择 **Rust core → WebAssembly → Worker**，并让 TypeScript 继续负责 UI、协议和会话编排。

## 7. P1 升级：位置操控与地形价值

这一层让战斗从“选伤害”变成“改写战场”。

### 7.1 位移技能的价值模型

位移技能应满足至少一种用途：

1. 打断敌人攻击。
2. 把敌人推进危险格。
3. 把敌人撞入其他单位。
4. 保护建筑。
5. 阻止 spawn。
6. 改变 Boss 位置或朝向。
7. 让下一回合形成更好的夹击。

如果一个击退只能“稍微改变位置”，它的可玩性价值就不足。

### 7.2 地形交互

建议优先强化以下地形：

| 地形 | 玩法用途 |
| --- | --- |
| 火/危险区 | 持续伤害或削弱，鼓励把敌人推进去。 |
| 阻挡格 | 阻断路径和射线，制造保护点。 |
| 高度 | 提升视野/射程或限制攀爬，服务已有 heights。 |
| 掩体 | 减伤但可被特定武器绕过。 |
| spawn 点 | 站位阻止增援，形成 deny play。 |
| 建筑格 | 保护目标，也是压力来源。 |

不要一次加太多地形；先让 2–3 种地形形成稳定组合。

### 7.3 位置技能原型

后续技能可以按以下原型设计：

- **击退者**：把目标推离关键格。
- **牵引者**：把敌人拉近，方便近战或集中火。
- **拦截者**：把自己变成挡路单位。
- **开拓者**：改变可通行性或创造临时通路。
- **压制者**：让敌人无法移动或行动，但伤害不高。

每个原型都应有清晰反制方式，避免形成无敌解。

---

## 8. P1 升级：目标与任务类型

### 8.1 首批任务目标

建议先做 4 种目标，不要一次铺开：

#### A. 守卫核心建筑

- 胜利：撑过指定回合或击败 Boss。
- 失败：关键建筑损毁。
- 核心压力：站位和保护优先。

#### B. 讨伐 Boss

- 胜利：击败 Boss。
- 失败：机甲全灭或建筑全毁。
- 核心压力：输出节奏与冷却管理。

#### C. 阻止增援

- 胜利：阻止指定数量 spawn 或坚持回合。
- 失败：过多敌人出现。
- 核心压力：占位、击退、区域控制。

#### D. 紧急回收

- 胜利：回收一个或多个目标物。
- 失败：目标物被摧毁或回合超时。
- 核心压力：路径规划、护送和取舍。

### 8.2 可选目标

每个任务可挂 1–2 个可选目标：

- 无机甲阵亡。
- 建筑损伤低于阈值。
- 在 N 回合内完成。
- 回收额外资源点。
- 不使用修理。
- 用击退造成指定碰撞伤害。

可选目标不应决定基础胜负，但可以用于难度评价和复盘。

### 8.3 目标提示

每回合应显示：

```text
胜利：击败 Boss
危险：建筑 HP 6/8
可选：无建筑损伤
威胁：Boss 下回合准备扫击
```

目标信息不能只在开局出现。

---

## 9. P1 升级：敌人行为可读且可学习

### 9.1 敌人不作弊

远程和本地都应遵守同一规则：

- 敌人意图在玩家计划前可见。
- 玩家提交后敌人不替换目标。
- 敌人不可使用玩家不可见的能力。
- 结算逻辑与 UI 预览一致。

### 9.2 敌人行为模型

每种敌人应有清晰偏好：

| 敌人 | 建议偏好 |
| --- | --- |
| raider | 攻击最近/高价值目标，必要时砸建筑。 |
| 大怪 | 高伤害但 cadence 明显，存在强 telegraph。 |
| 支援型敌人 | 强化或治疗，逼玩家调整优先级。 |
| 远程敌人 | 站位刁钻，但暴露时容易被打断。 |
| 爆炸型敌人 | 逼迫玩家用位移，而不是硬拼。 |

不要求首版全做；关键是每个敌人都有一种玩家必须回应的威胁。

### 9.3 敌人组合

好组合应制造多个小决策：

- 远程 + 近战：是否先处理后排。
- 高伤 Boss + 快速 raider：是否分兵。
- 护盾单位 + 输出单位：是否用位移拆开。
- 增援 + Boss：是否封锁 spawn 或抢血量。

避免只是数量加倍的难度提升。

---

## 10. P1 升级：行动资源与代价

### 10.1 冷却要有战术意义

冷却不只是等待。它应制造取舍：

- 用完强力技能后，下一回合是否必须保守？
- 保留冷却是否可以打断 Boss 关键动作？
- 提前用掉是否会导致无法处理下一波？

UI 可以显示“本技能在 N 回合后可用于关键威胁”。

### 10.2 修理不是免费安全

修理应有明确代价：

- 占用行动。
- 可能错过击杀。
- 可能错过关键站位。
- 只能修到上限。

好的修理决策通常有两种：

1. 本回合保命。
2. 为下一回合承受一次攻击做准备。

如果修理永远优于攻击，说明输出或威胁压力不足。

### 10.3 移动代价

当前移动/半步模型已经有地形意义。建议让玩家理解：

- 这台机甲还能不能先手到达关键格。
- 站上高地是否值得暴露。
- 绕开掩体是否耽误输出。
- 挡在建筑前是否能承受攻击。

---

## 11. P1 升级：PvP 可玩性

PvP 不应只是把 PvE Boss 换成另一组机甲。

### 11.1 PvP 核心乐趣

PvP 强调：

- 读对方站位。
- 抢关键格。
- 目标选择博弈。
- 击退反制。
- 先手/后手节奏。
- 保护与斩杀的取舍。

### 11.2 首版 PvP 原则

- 双方使用同一规则集。
- 回合权限明确。
- 整包计划提交。
- 结算顺序固定。
- 目标绑定规则公开。
- 无隐藏随机惩罚。
- 掉线不应立刻由客户端决定胜负。

### 11.3 PvP 可读性

需要额外显示：

- 哪些单位属于自己。
- 哪些格属于敌方或中立。
- 哪些行动只能对己方使用。
- 哪些目标会暴露给对方下一回合。
- 当前回合属于谁。

### 11.4 避免“先手必胜”

可以通过以下手段缓解，但必须单独评审：

- 对称出生点。
- 交替首动或统一移动结算。
- 回合内行动上限。
- 防守型技能。
- 地形不对称但收益平衡。
- 双方目标不完全相同。

不要在未验证前通过随机暴击或隐藏优势来平衡。

---

## 12. P2 升级：教学、复盘与长期留客

### 12.1 轻教学

不需要完整教程关卡。可在前几回合嵌入提示：

- 第一回合：选择移动。
- 第一次出现敌意：解释目标格。
- 第一次选择击退：解释落点。
- 第一次冷却：解释机会成本。
- 第一次建筑受伤：解释危险阈值。

提示应可关闭。

### 12.2 战术图例

提供常驻图例：

- Boss footprint。
- 敌意格。
- 移动范围。
- 攻击范围。
- 击退方向。
- 阻挡/掩体。
- spawn 点。
- 目标物。

所有图标应有一致形状和颜色。

### 12.3 回合复盘

每回合结束提供简短摘要：

```text
击杀：2
建筑损伤：2
机甲损伤：3
落空行动：1
关键击退：Gunner 将 raider 推离建筑
下一威胁：Boss 扫击 A1/B2
```

不要求完整日志默认展开。

### 12.4 失败复盘

失败面板应回答：

- 致命事件发生在哪一回合。
- 哪个单位或建筑先失守。
- 哪些行动落空。
- 哪个敌人造成最大伤害。
- 玩家是否曾有机会避免。

这不是惩罚，而是教学。

---

## 13. 难度设计

难度应通过压力来源组合，而不是单纯加数值。

### 13.1 难度递进

| 难度 | 目标 |
| --- | --- |
| 入门 | 敌人意图简单，容错高，教学提示明显。 |
| 标准 | 两种目标压力并存，需要取舍。 |
| 困难 | 敌人组合更复杂，错误代价明显。 |
| 挑战 | 固定 seed、可选目标严格、AI 优化更激进。 |

### 13.2 难度原则

- 不隐藏规则。
- 不靠随机暴击制造挫败。
- 不让 UI 变得更复杂来换取难度。
- 高难度优先增加目标冲突和敌人组合，而非血量翻倍。

---

## 14. UI 原则

### 14.1 图形优先，文字其次

优先级：

1. 棋盘状态。
2. 敌意格。
3. 选中单位可用行动。
4. 预期后果。
5. 目标状态。
6. 详细解释。

### 14.2 三种信息层

- **常驻层**：生命、敌意、目标、当前选中。
- **选中层**：范围、目标、预计伤害、落点。
- **按需层**：规则说明、结算顺序、完整日志。

### 14.3 反馈必须闭环

每个操作后应有可见反馈：

- 选择成功：目标高亮。
- 选择失败：原因显示。
- 计划提交：进入结算状态。
- 行动落空：明确标记。
- 建筑受击：目标面板与棋盘同时反馈。
- 机甲死亡：不能只从血量判断。

---

## 15. 与架构升级的对应关系

可玩性升级不要求重写架构，但依赖几个架构能力：

| 玩法能力 | 架构依赖 |
| --- | --- |
| 敌意预览 | 只读棋盘查询和目标校验。 |
| 击退落点预览 | 纯规则模拟或隔离投影。 |
| 落空与事件解释 | `TurnEvent` 结构完整。 |
| Doctrine 推荐解释 | `PlanEvaluation` / `ScoreFactor`。 |
| 远程一致表现 | 完整快照 + `PresentationStages`。 |
| 任务目标扩展 | 规则策略和胜负条件版本化。 |
| 复盘 | 快照、事件、回合序号。 |
| AI 推荐解释 | `CandidateSource`、`PlanSimulator`、`PlanScorer`、`PlanEvaluation`。 |
| AI 异步化 | Worker 请求绑定 revision、requestId 和取消机制；原生二进制暂不需要。 |
| 开局部署 | `deployment` 阶段、部署区查询、`DeployPlan` 原子校验、`MatchRuleAdapter.deploy()`。 |

因此建议可玩性 P0 与架构文档中的 Phase 0 / Phase 1 同步推进。

## 16. 实施路线

### P0：让玩家理解战场

目标：不改大规则，显著提升决策质量。

1. 敌意格、目标、伤害稳定显示。
2. 攻击/修理后果预览。
3. 击退落点与碰撞预览。
4. 禁用原因说明。
5. 结算顺序简图。
6. `tunnel` / `peel` 改成玩家可读的战术姿态。
7. PvE 本地开局部署：部署区、选择机甲、放置、撤销、重置、确认。
8. 部署规则校验与默认部署区 golden tests。
9. AI 推荐 golden tests：固定局面、固定 doctrine 输出固定计划。
8. `PlanEvaluation` 输出主要评分因子，供调试和后续 UI 解释。

验收：

- 新玩家能在无说明情况下回答“谁会打哪里”。
- 玩家能在提交前看到主要后果。
- 落空和建筑风险不再像隐性失败。
- 固定局面下推荐计划可复现。
- 玩家能在开局选择三台机甲的合法部署位置，并理解非法原因。
- 部署确认后生成的首回合敌意与未部署时的规则流程一致。

### P1：增加战术深度

目标：让位置和目标成为核心玩法。

1. 强化 2–3 种地形组合。
2. 增加或强化位移技能价值。
3. 引入 deny spawn / rescue / defend 等目标类型。
4. 冷却和修理形成更明确取舍。
5. 敌人组合开始惩罚单一套路。
6. PvP 使用清晰身份、目标绑定和对称公平规则。
7. 不同任务目标使用不同 doctrine 权重和推荐解释。

验收：

- 低伤害位移技能有明确使用场景。
- 不同目标下最强 doctrine 不同。
- 玩家能说出每台机甲的独特价值。
- PvP 不因界面或规则不可读产生争议。

### P2：建立长期吸引

目标：从“能玩”进入“愿意反复玩”。

1. 轻教学。
2. 回合复盘。
3. 失败复盘。
4. 挑战 seed。
5. 目标评级。
6. 更多地图与敌人组合。
7. AI Worker 化和搜索预算仅在性能需要时启用；WASM 仍按基准结果决定。

验收：

- 玩家失败后能说出改进点。
- 同一地图在不同目标下产生不同打法。
- 更高难度不依赖隐藏规则。
- 社区可讨论固定局面和最佳解。

---

## 17. 验收指标

不引入用户遥测；验收以本地可观察行为和人工测试为主。

### 可读性

- 新玩家 30 秒内识别当前威胁。
- 玩家能在提交前说出主要风险。
- 落空行动有明确标记。
- 建筑受击有清晰反馈。

### 决策深度

- 同一地图在不同目标下产生不同最佳计划。
- 至少存在“伤害收益”与“位置收益”都合理的回合。
- 修理、输出、保位三种选择都可能在特定局面成为最优。

### 学习曲线

- 前三回合不需要长文档。
- 玩家能通过复盘理解第一次失败。
- 敌人行为可预测，不出现“看不懂的惩罚”。

### PvP

- 双方能分清自己的单位与回合。
- 相同计划的重复结算结果一致。
- 断线、迟到消息、非法计划不会破坏比赛状态。

### AI 推荐

- 固定局面、固定 doctrine、固定权重版本输出固定计划。
- 推荐理由可追溯到主要评分因子。
- AI 不越过规则权威；计划仍由 `MatchRuleAdapter` 校验。
- 搜索不阻塞关键输入，必要时降级为禁用推荐而非冻结 UI。

---

## 18. 不建议做的事

为保持玩法聚焦，以下事项暂缓：

- 不要一次性加入大量新机甲。
- 不要先做复杂随机装备。
- 不要把 PvE 改成实时操作。
- 不要让自动求解变成主玩法。
- 不要用隐藏随机惩罚制造难度。
- 不要为了视觉酷炫牺牲敌意清晰度。
- 不要把完整调试信息暴露为默认 UI。
- 不要在可玩性验证前扩展远程数据通道。
- 不要在评分契约和性能基准建立前引入 WASM 或原生二进制求解器。
- 不要把 AI 推荐呈现成唯一正确解。

---

## 19. 一页摘要

当前 Mecha 已经有正确的战术骨架。  
下一步不是堆内容，而是强化三个体验：

1. **看得懂**：敌意、后果、击退落点、禁用原因全部可读。
2. **有取舍**：目标、冷却、修理、站位之间形成冲突。
3. **学得会**：回合复盘和失败解释帮助玩家成长。

首版重点建议：

- 把 `tunnel` / `peel` 变成玩家理解的战术姿态。
- 做好敌意格和击退落点预览。
- 用 2–3 个新任务目标制造不同 doctrine 的价值。
- 保持规则确定性，让失败可以复盘。
- AI 只做可解释推荐；当前保持 TypeScript，先补评分契约和 golden tests，暂不引入二进制。
- 增加开局部署阶段，先做 PvE 本地闭环；远程和 PvP 部署另行评审。
