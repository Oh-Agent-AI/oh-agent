## 二、先排除的三个方向（都有实测证据）

1. **时区**。会话文件时间戳 104,809 条**全部**以 `Z`（纯 UTC）结尾，无一条带
   数字偏移。计价脚本 `Z → UTC → astimezone(+8)` 后按北京日/小时判峰谷。用三种
   时区假设把去重后请求流逐小时对官方**北京**逐小时请求数（export
   `start_time_iso` 自带 `+08:00`）：

   | 假设 | 逐小时 Σ|Δ| | 对齐 |
   |---|---|---:|---|
   | UTC→+8（实现口径） | **430** | 小时 19/20 完全相等；其余多数 ±15% 内 |
   | `Z` 当北京时间（不换算） | 2770 | 零小时对齐，错位 8h 的典型锯齿 |

   时区处理正确。若把 `Z` 当北京时间，就是差 6.4 倍的灾难性错位。

2. **计价卡与峰谷窗口**。export 逐小时逐模型行 × 官方单价：峰段（工作日北京
   9-12/14-18，`usage.rs::is_peak_slot` 同窗口）恰为谷价 2×——23/23 行零例外。
   pricing.json providers.deepseek-official 卡（flash 0.05/1.5/4.5、pro 0.15/4.5/13.5
   谷价，峰价 2×）与官方应用单价逐项相等。**价卡与峰谷判定不是差价来源**。

   **二修加做了两级更强的核对**，把这条从「不是来源」升级成「可用来精确复现账单」：

   - **对官方文档逐项**（<https://api-docs.deepseek.com/zh-cn/quick_start/pricing/>，
     用户 2026-09-02 提供）：flash 0.05/0.10、1.5/3.0、4.5/9.0，pro 0.15/0.30、
     4.5/9.0、13.5/27.0，峰段定义「周一至周五 9:00–12:00、14:00–18:00 北京时间，
     其余五折」——与 `pricing.json` 的 `_doc` 及 `usage.rs::is_peak_slot`
     （105-119 行，含周末全天谷价那条被真实账单纠正过的规则）**逐项相同**。
   - **对导出逐行**：第二份导出 72 条计价行，逐行用「本行小时 → 峰/谷 → 我们的
     价卡」取价，与导出自带的 `price` 列**不符 0 行**；用导出自带单价反算总额得
     ¥74.3797，与 `cost` 表完全相同（说明官方 `price` 列本身已含峰谷）。
   - **精确复现**：`我们的价卡 × 官方 token 量 × 每行真实小时 = ¥74.3797`，
     与账单 **完全相等**。

   这条复现是二修的关键证据：**我们的价卡对、峰谷窗口对、token 也基本在手上，
   横在「现有数据」与「分毫不差的账」之间的只剩小时轴**（§6）。

3. **会话里没有账**（该方向在 §4 修正前曾部分成立——见浅扫描假象一节）。会话
   文件确实承载今天 ~95% 的请求量；「大部分流量在文件里看不见」的早期结论是扫描
   深度不足的假象。

### 3.1 二修：ledger 层的闭合分解（这才是能分因子的那条链）

上面这条链**分不出主次**——「缺 ~¥12」里基线错记与全谷价混在一起，因为它的

做反事实**，把两个因子隔离开，得到一条三段闭合的链（22:22 同刻）：

| 层 | 金额 | 到下一层的差额来源 |
|---|---:|---|

## 五、token 层缺陷：cost-state 基线折到会话 `startTime` 日

> **二修定性**：本节的机制描述与实测数字全部成立且未变，但它**不是钱上的主因**
> ——在今天的数据上净额只值 ¥3.30（§3.1），因为被 §7 的 pro 虚高抵消掉了。
> 抵消是会话形态的巧合，不是修复：换一天没有子代理 pro 流量，这 37% 的 flash
> 缺口就会赤裸暴露。**照修，但排在小时轴之后**（§9）。

实现 `claude_cost.py::_apply_record`（196-227 行）遇 `cost-state` 时：

```python
sess["baseline"] = baseline      # cost-state modelUsage 累计，整段
sess["tail_days"] = {}           # ← 清空此前所有行
sess["baseline_day"] = day_from_ms(startTime)   # 归会话起始日；缺 startTime 才退 ts 日
```

`_rebuild_days` 随后把 baseline 整段放进 `baseline_day`，尾差（`tail_days`）按行
自己的 ts 日。设计前提（§9.3「逐行 message.usage 求和必然漏——压缩掉的 cache
read 在行里零可见」）假定压缩会删历史行。**真机否定了这个前提**：压缩在这里是
追加 `cost-state` 检查点、**保留**历史行——753e 的 live 文件 12,797 行，末条
cost-state 在第 10,110 行，此前 1,175 条 09-02 去重请求仍带时间戳在盘上。于是
「有日界可用的行」被整段甩进无日界可用的 startTime 基线，跨午夜会话的当日消费
错记到起始日。

三个今日活跃的跨午夜会话，逐会话实测（09-02 北京日，`message.id` 去重，flash
cr）：

| 会话 | 09-02 实际 | 记到 09-02 | **错记到起始日** |
|---|---:|---:|---:|
| 2279b7b0（当前会话） | 38.7M | 5.7M | **33.0M → 09-01** |
| 753e080a | 137.1M | 44.9M | **92.2M → 09-01** |
| b695a35f | 88.3M | 16.0M | **72.3M → 08-31** |
| **合计** | **264M** | 66.6M | **197.5M** |

后果直接可见于 ledger 日桶：09-01 flash cr = 363M（被跨日基线灌爆），09-02 只
剩 192M（只有基线后的行尾增量）。**今天 ~197.5M flash cache-read 记到了昨天**。

## 六、主因：日桶 × 全谷价（无小时轴）——占差额 89%

> **本节是二修改写的**。初版把它定为「次因」「口径保守而非错账」，据 §3.1 的
> 闭合分解这两个定性都不成立：它是差额的 89%（¥25.68/¥28.98），且其立论前提
> 在真机上是假的。

ledger 是 flat 直图日桶（只有 4 型 token，无 hour 轴），`claude_day_cost` →
`price_claude_map` → `price_claude_model` → **`flat_rate`（`cost.rs:710-718`）对
`{off_peak, peak}` 对象一律取 `off_peak`**。对 cr 占绝对主体的 flash 日桶，谷价
0.05 vs 峰价 0.1 意味着高峰时段真实花费被砍半；今天 69% 的消费落在峰窗，于是
砍掉 ¥25.68。

**为什么「保守」这个说法站不住**：`flat_rate` 的注释写的理由是
「Claude 会话文件没有时段证据，全按空闲档折，是最保守的官方价」——**前半句在
真机上是假的**。§2.1 已实测：会话文件 104,809 条时间戳**全部**带 `Z`，每一条
assistant 行都知道自己是几点。时段证据一直在盘上，是 `_rebuild_days` 归日时把
小时**丢掉了**，不是文件里没有。在有证据的情况下取下界，不是「保守」，是把一份
可精确计算的账降级成系统性低估——而且低估幅度随当天峰段占比浮动（今天 69%
→ 低估 35%），既不稳定也无法标注。

**另有一处必须一并改的陈述性缺陷**：`cost.rs:709` 的注释写
「deepseek 官方高峰 00:30–08:30 北京时间」——**这个窗口是错的**，与同 core crate 的
`usage.rs::is_peak_slot`（周一至五 9-12/14-18）、`pricing.json` 的 `_doc`、以及
官方文档三方都矛盾（00:30–08:30 是 V3/R1 时代的**优惠**时段，方向也反了）。
Python 镜像 `cost.py::_flat_rate` 的同段注释没有这句错误窗口，但共用了同一个
「没有时段证据」的假前提。谁来实现小时轴都会先读这两段注释，**必须同改**，
否则错误窗口会被照着实现进去。

## 七、pro 一栏的「正确」是巧合

托盘 pro ≈¥20.81 恰好 ≈ 官方 pro ¥20.93，**不代表归日对**：ledger 09-02 pro
40.6M cr 是基线后行的**原始求和**（无去重），而全树去重 pro 只有 14.5M cr——
原始膨胀 ~2.8× 与缺量大致抵消，撞出个对的钱。pro 一栏与 flash 一栏在同一套
baseline 归日下，随时可能随会话形态翻转而一起偏。对账看 token 不看钱：pro
ledger 40.6M(raw) 既 ≠ 去重真值 14.5M 也 ≠ 官方 19.2M。

**二修：这个巧合的作用域比初版认为的大得多——它掩盖的是 §5 本身。**
逐 token 类对照（22:22 同刻，ledger 09-02 vs 官方 09-02）：

| | ledger 09-02 | 官方 09-02 | 比值 |
|---|---:|---:|---:|
| flash `cache_read_input_tokens` | 183,550,976 | 292,248,448 | **0.63** |
| flash `input_tokens`（对官方 cache_miss） | 4,371,481 | 5,871,819 | 0.74 |
| flash `output_tokens` | 1,968,771 | 2,949,237 | 0.67 |
| pro `cache_read_input_tokens` | 40,639,488 | 19,209,216 | **2.12** |
| pro `input_tokens` | 2,899,223 | 1,580,286 | 1.83 |
| pro `output_tokens` | 123,579 | 149,583 | 0.83 |

flash 因 §5 的基线错记**少 37%**（对照 ledger 09-01 flash cr = 370,159,104，
被跨午夜会话灌爆），pro 因本节的未去重**多 2.1×**。一个少 ¥13 量级、一个多 ¥10
量级，**净剩 ¥3.30**（§3.1 第一段差额）。初版按「托盘 ¥46 vs 官方 ¥73」的总额
推断归日是主因，正是被这个净额骗了：token 层两个 37%/112% 的大洞，在钱上只剩
11%。**任何只看总额的对账都会重犯这个判断**——claude 账的对账必须逐模型逐
token 类看量，钱只能用来排序优先级。

## 八、剩余不可恢复量（修 fold 后仍在的洞）

官方 ¥73.09 − 全树去重真值 ¥58.79 = **¥14.3**：以 pro 高峰时段（北京 13/17 点）
**uncached input** 为主的流量 + ~5% flash。它们既无 live 行（压缩保留窗外真删、
或会话轮换移除）也无当日 cost-state 时点——只有累计值、无小时戳，任何按行重算
都补不回。这是 fold 改用「行归日 + 基线残差」后应**如实报为残差哨兵**的量
（`unaccounted`/partial，VITALS_CORE v0.7 §2 事实行的 `unaccounted_usage` 同族），
不是要抹平的目标。

## 九、修订方向（对 §9.3 文档化近似的证伪）

`_apply_record` 不该在 cost-state 到来时 `tail_days={}` 清空既有行——真机上那些
行还在、带真实日界。改为：

1. **行按自身时间戳归日为主**（现状已如此，但不该被 cost-state 打断）；
2. **cost-state 只当对账锚**：记录 `baseline`（含 startTime/累计 modelUsage）但**不
   进日桶、不清 tail_days**；
3. 重建时逐会话算 `Σ行 vs 基线`：行和 ≥ 基线 → 无缺漏，baseline 弃用（行已覆盖，
   replace 逻辑处理的双同值/中间行问题随之消失）；行和 < 基线 → 差值 = 真压缩掉
   的无日界残差 → 归 startTime 日但**标 partial/unaccounted**，绝不静默。
4. 文件日后真被截断（size 回缩）→ checkpoint 整份重折，行少了基线在 → 残差哨兵
   兜住。两态都稳：**行全在 → 日界精确；行被删 → 残差诚实**。

这同时满足 `CLAUDE_CODE_INTEGRATION.md` §9.3 与计划的 D6（「可检出有 cost-state
但行和 < 账单 → 残差哨兵如实报」）——现实现是反的：基线为主、行只补尾差，把
「有日界的行」降级成了「无日界的基线」的附庸。

### 9.1 二修：先做小时轴，再做归日

初版本节只写了归日一件事。按 §3.1 的分解，落地顺序应是：

1. **小时轴（先做，占差额 89%）**。ledger 日桶下再分 hour 桶；`claude_day_cost`
   按 hour 查 `is_peak_slot` 取价，而不是 `flat_rate` 硬取 `off_peak`。数据源
   是现成的——行本身带 ts（§2.1 的 104,809 条），`_rebuild_days` 现在把小时丢了
   而已；`is_peak_slot` 也是现成的且已被真实账单验证过（含周末那条）。同时
   订正 `cost.rs:709` 的错误窗口注释与两侧「没有时段证据」的假前提（§6 末）。
   验收标准是硬的：**用本仓价卡 + 真实小时重算今日 = 官方账单**（§2.2 已证明
   这条等式在数据层成立，¥74.3797 = ¥74.3797），实现后应能端到端复现。
2. **归日 + pro 去重（后做，必须同批）**。§9 的 1-4 条照做，但 `message.id`
   去重要和它一起上：只修归日会让 flash 补回来、pro 的 2.1× 虚高单边暴露，
   总额从偏低翻成偏高（§7）。两者是同一批改动的两半。
3. **残差哨兵**（§8 的 ~¥14 不可恢复量）随 2 一并落，如实报 partial /
   `unaccounted`，不抹平。

三步都做完，托盘该列的语义才从「已知方向的低估」变成「精确 + 显式残差」。
