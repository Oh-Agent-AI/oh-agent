# 机甲战棋 PvE / PvP 代码复用架构与迭代计划

> 状态：设计提案，基于当前 `codex/mecha-battle-ux-integration` 工作区的代码（包含未提交改动），不是已实现清单。配图：[PvE / PvP 共享架构图](design/mecha/mecha-pve-pvp-shared-architecture.svg)。本方案不变更 Assault 陡坡规则；该限制及其契约差异另行评审。

## 1. 结论

值得复用的主体是**棋盘查询、计划处理、行动结算流程、事件模型、规划交互和战术展示**；但复用代码不意味着 PvE、PvP 的伤害、击退、敌人行为或胜负条件必须相同。用共享的机制和流程承载明确的模式策略，避免复制两套规则循环；本地与远程可共享表示和交互逻辑，远程始终由桌面权威会话复验并提交。

这不是把 `pvpProjection` 喂给 PvE 结算函数：对手机甲目前被投影成类似 Raider 的对象，只能支持已有的部分查询，不能视为完整统一模型。迁移应先建立行为基线，再逐块抽取；未决定的差异继续保留。

## 3. 目标分层和职责

建议在现有 `game/mecha/` 范围内渐进拆分，以下名称为设计候选，**不是现有 API 或承诺的目录**。保持现有公共入口，逐步替换内部实现；不新增 Rust 战斗规则副本。

| 层 | 候选职责 | 使用方 | 原则 |
| --- | --- | --- | --- |
| 共享视图和草稿 | 棋盘坐标、选中/悬停、草稿编辑、确认/取消、试算结果视图模型、回看模型 | 本地和远程 UI | 不持有权威状态；相同视觉信息来自同一次匹配当前 revision 的试算。渲染与输入适配可各自保留。 |
| 通用战斗领域核心 | 棋盘/实体只读视图、路径和占位查询、批量移动校验、行动合法性及目标绑定、按序结算、落空、事件构造 | PvE/PvP 各自规则适配器 | 面向中立实体 ID/阵营/能力查询，不将敌方单位假扮为 Raider；以模式策略决定语义，不能静默统一玩法。 |
| 模式策略 | 目标过滤、防御/伤害、位移碰撞、能力与冷却、终局及阶段推进 | 共享核心编排 | PvE/PvP 的差异显式注入和版本化；避免核心出现散落的 `if (pvp)`。 |
| 预检边界 | 复制快照并运行指定阶段，返回 `ok / rejected / unknown` 与可证明的效果 | 草稿和可选可视化 | 目标为无可观察副作用：不修改输入、权威状态、共享事件接收器；失败或不确定不画成保证发生。 |
| 会话/执行 | 本地 controller；远程 `MatchSession` 与模式适配器 | 本地/桌面远程宿主 | 将通用核心作为同一份 TypeScript 库各自在对应运行时调用；复用代码不等于共享同一内存状态。 |
| 传输 | 现有 Rust 网关、`app-remote:v1` 和 relay | 远程会话 | relay 认证与转发，不结算；只允许已批准的机甲比赛数据，不扩展插件数据出口。 |

### 建议的流程接口（示意，待契约评审）

```ts
// 仅表示边界，不代表现存类型，也不要求一次性替换整个状态。
type ModePolicy<S> = {
  readBoard(state: S): BattleBoardView;        // 稳定实体 ID、阵营、位置、地形等只读查询
  validateAction(view: BattleBoardView, action: PlannedAction): BoundAction | PlanFault;
  resolveAction(state: S, action: BoundAction): Resolution; // 伤害/位移语义由模式定义
  advancePhase(state: S): PhaseResult;          // PvE 敌方阶段 / PvP 阵营交替与胜负
};
// 校验 → 移动落位 → 绑定目标 → 按序执行（执行时重查）→ 模式阶段。
// 预检与正式结算可以选择不同阶段，但要说明语义并共用对应的阶段实现。
```

接口应先用现有两种模式的最小测试证明足够，避免建立一次性覆盖所有未来玩法的复杂框架。单体行动可合法、整包仍可能因目标占用或其他行动冲突失败；UI 必须区分单项预检和整包结算。若只预检部分阶段，不能承诺后续行动/敌方阶段的最终结果。

### 明确保留的玩法差异

| 维度 | PvE 当前 | PvP 当前 | 迁移决定 |
| --- | --- | --- | --- |
| 参与者和对象 | 玩家机甲、Boss、Raider、建筑等 | A/B 双方机甲 | 抽象实体身份、阵营和能力，不把 Raider 当作 PvP 机甲的正式数据模型。 |
| 伤害与击退 | 敌人有各自防御；近战命中存活 Boss 可触发 Boss 位移 | 伤害计算使用对手机甲防御；当前攻击不做相同击退 | 保持现状，PvP 是否增加击退须先产品决策、单独评审规则版本。 |
| 回合与胜负 | 敌人预告、敌方行动，含建筑等目标与终局条件 | A/B 轮流；全歼、认输；上限 30 个双方回合后按剩余总 HP 裁定 | 模式阶段和终局各自实现；同用流程不吞掉模式特性。 |
| 契约 | `mecha-v1.4` | `mecha-pvp:v1` | 纯重构保留各自可观察行为；有意变化须显式评审规则与协议版本，并协调远程兼容。 |

错误码/cause、事件顺序、目标绑定、落空和冷却也可能存在模式差异，先记录实际基线；不要为了“统一”悄悄改变现有行为或更新快照掩盖回归。

## 4. 运行时与权威

1. **本地 PvE**：本地 UI → controller/草稿 → 本地 PvE 规则正式提交 → 更新本地状态和演出。不经过远程 relay 或现有 `MatchSession`。
2. **远程 PvE/PvP**：浏览器按快照本地编辑并预检 → 发送正式计划 → relay 转发 → 桌面隐藏 WebView 中的 `MatchSession` 做身份、轮次、revision、命令去重检查并由相应规则适配器复验/结算 → 返回权威快照与事件 → 客户端播放。预检只是提示，最终以宿主复验为准，状态变化或权限变化时可能被拒绝。
3. 未来两条路径引用**同一代码库中的共享纯核心**，但客户端和宿主分别运行，不能共享可变事件 sink 或把客户端结果当权威。相同规则版本、相同完整输入和相同预检阶段，结果应一致；不完整数据或异常返回 unknown。
4. 网络仅在用户主动启动或批准的机甲比赛范围内传递 `RemoteArenaV1`、比赛指令、快照和事件；不得扩充为城市/用户数据同步。TLS 不代表端到端加密。远程白名单、宿主提交后消息被拒导致不同步等问题应独立跟踪，不能靠抽取共享核心宣称解决。

## 5. 迭代顺序与验收

| 优先级 | 工作 | 完成条件 |
| --- | --- | --- |
| P0 差异基线 | 分别固定现有 PvE/PvP 的合法/非法计划、位移、伤害、错误及完整事件序列；梳理远程宿主输入和预检隔离 | 两模式各自的回归测试通过；记录已知差异，不把规则变更混在重构中。 |
| P1 查询与计划 | 建立中立只读战场/实体视图；分步抽取寻路、批量移动冲突、行动合法性与目标绑定，替代部分假 Raider 查询 | 新旧实现对相同输入的计划通过/拒绝、原因、移动后状态及绑定目标一致；既有本地和远程 UI 可用。 |
| P2 行动与事件 | 提取按序执行、重查、落空、事件骨架和可共用的冷却/修理机制；通过模式策略保留伤害、击退等差异 | 新旧状态、事件及顺序、落空 cause、冷却、终局逐项等价；PvE 敌方阶段和 PvP 阵营切换保持原样。 |
| P3 预检与体验 | 将预检改为显式隔离的阶段化 API；统一规划视图模型和共用 HUD/棋盘交互，适配两种渲染容器 | 同 revision、同完整输入、同阶段下，预检与权威对应阶段一致；独立渲染和小窗口/中英文/键盘可达回归通过，失败和 unknown 不误导。 |
| P4 远程实机验收 | 在现有协议和数据出口内验证完整链路 | 真实 Tauri、两设备、公网中继、断线重连、重复命令、过期 revision、宿主不可用/发送失败均有可观察结果，不声称模拟测试等同实机。 |

### 核心回归矩阵

- **计划**：缺项/重复机甲、非法行动、越界和障碍、移动终点冲突、移动后合法性、隐式唯一目标与显式目标、版本过期。
- **执行**：前序行动击杀目标、目标移位、执行者失效、落空不误扣冷却；修理与技能冷却、伤害、事件顺序、阶段快照及终局按各模式基线对照。
- **隔离**：成功、拒绝和异常的预检均不改变输入、权威状态或事件接收器，不污染下一次预检/正式结果；交错调用不串事件。过时或缺失信息给出 unknown / 拒绝，而不是虚构效果。
- **远程**：玩家授权、轮次、revision、命令幂等、快照与事件传播；相同完整输入和阶段下，客户端预检与宿主结果一致，同时覆盖提交前状态已变化的拒绝路径。验证网络投影与数据出口约束。
- **展示**：试算结果与棋盘、说明、动画共享语义；不同模式的本地/远程视图、10×10 格拾取、640×480 / 800×600 / 1100×700、中文/长英文、键盘与屏幕阅读器均回归。

## 6. 需要产品决策

- PvP 是否允许击退及碰撞伤害？迁移前不新增；若要新增，另做平衡和规则版本评审。
- 哪些预检结果可作为保证，哪些只能标为可能或未知？预检范围要与可见信息一致。
- PvP 是否长期公开双方完整状态？若未来引入隐藏信息，先调整投影和预检契约，不能让客户端共享核心泄露权威私有数据。

## 7. 房主组局：目标与范围

**设计目标：一个房间、一个桌面权威宿主、同一套 PvP 规则和状态，两种席位配置。** 房主是管理者，A/B 是玩家席位，观战是只读能力；这三者互相独立，一个人可以同时拥有管理者和玩家能力，但观战不能隐含操作能力。

| 场景 | 房主 | 玩家 A | 玩家 B | 当前状态 / 目标 |
| --- | --- | --- | --- | --- |
| 本地 PvE | 本地玩家 | — | — | 已有本地代码路径；不创建远程房间。 |
| 房主参赛 | 房间管理者 + 玩家 A | 房主 | 一位受邀好友 | 已有远程 1v1 路径；远程启动后桌面 City 本地回合锁定，房主使用自己的远程链接参赛，City 画面不跟随远程局。 |
| 房主组局观战 | 房间管理者 + 本机观众，不占玩家席位 | 受邀好友 1 | 受邀好友 2 | **待开发**：两个独立受邀席位、房间生命周期及桌面实时只读观战。 |
| 远程自己玩 PvE | 房间管理者 + 远程玩家 | 房主 | — | 保持现有独立 PvE 远程路径，本次不改其玩法、协议或生命周期。 |

首版观众限定为**创建房间的桌面房主**，不做第三方观众链接或公开旁观。目标是在同一桌面战场视图中，房主参赛时以 A 席身份操作远程权威对局，房主观战时仅只读；房主也可继续使用自己的远程链接参赛。桌面参赛是**待开发**，不能复用本地 PvE controller 直接更改远程权威状态。房主手机链接是拥有玩家 A 权限的凭证，不得转交给好友充当 A；好友必须使用自己席位的邀请。一个人通过多个设备连接时，授权绑定到主体和席位，不因设备数量获得额外席位或权限。

本方案不改变 PvE/PvP 数值、AI、击退、Assault 陡坡限制与现有 `mecha-pvp:v1` 玩法。房主电脑仍负责权威结算；中继只认证和转发，不是云端战斗服务器。桌面退出、休眠或失联时不可继续结算，首版不承诺迁移宿主、云端恢复、公开房间、自动判负或回合计时。

### 7.1 现状与差距（不是已完成功能）

- `contracts/match.ts` 的 `MatchPlayer` 仅有 `host | guest`；`MatchSession` 构造时要求 `host` 是 A，提交和快照都按玩家身份检查。`RemoteSessionHost.ts` 在唯一 `guest` 获批时把已有 PvE 会话替换为新的 PvP；不能直接再接一个 guest。
- 中继 `relay/worker.ts` 固定 `host / owner / guest` 和单一获批 guest，WebSocket 替换逻辑按角色处理；两个好友若共用 `guest` 身份会互相替换、权限混淆，不能通过复用同一邀请链接解决。
- Rust `remote_gateway.rs` 创建时固定 `owner / A / host`；`remote_gateway_projection.rs` 与相关请求、响应投影限制只允许既有 owner/guest 身份。不能只改前端或放宽全部白名单，需要端到端版本化升级和受限投影。
- 远程启用后桌面 City 显示原本本地局面而非远程状态，且本地规划锁定。房主观战需要新的、经授权的本机只读状态通道和展示，不是直接解除锁定。
- 上述代码状态来自当前工作区，含未提交改动；最终以目标分支合入内容为准。远程实机 / 公网验收仍未完成。

## 8. 目标架构与授权模型

```text
房主电脑（创建房间 / 批准邀请 / 管理房间）
 ├─ 本机战场视图 ◄── 受限快照 + 结算事件（参赛可操作 / 观战只读）
 └─ 权威宿主 MatchSession ── 同一 PvP 规则适配器与对局状态
            ▲  ▲                     ▲
       玩家 A  玩家 B             房间管理命令
            └── 已授权设备 ── relay / Rust 网关 ──┘
```

本地图中的箭头表示逻辑关系，不要求桌面观战流经过公网；优先使用可信宿主到活动 City 视图的本机受控通道，不为本机战场视图额外开放公网数据面。房主在桌面参赛时，本机可信通道必须将玩家 A 指令送往同一个权威会话，按身份、回合、revision、命令 ID 和规则复验；不修改被锁定的本地 PvE 状态，也不通过自行伪造 host 角色来绕过授权。网络玩家的请求经 relay 与 Rust 网关再进入宿主；`MatchSession` 是桌面隐藏 WebView 内的权威会话，不是 relay/云端权威。客户端预检只提供提示，权威宿主按当前状态再次检查并结算。

### 8.1 主体、席位、凭证分离

以下为目标领域模型示意，命名和 wire schema 以实现前协议评审为准，不代表当前类型已存在：

```ts
type RoomConfiguration = "owner_plays" | "owner_observes";
type Seat = "A" | "B";
type SeatState = "empty" | "invited" | "pending_approval" | "occupied";
// 管理者是权限而非阵营；observer 是只读能力而非玩家。
type RoomView = { roomId: string; roomRevision: number; phase: RoomPhase;
  config: RoomConfiguration; seats: Record<Seat, { state: SeatState; participantId?: string }> };
```

- **宿主进程**：持有权威状态并执行规则；不自动是 A、B 的玩家，不接受由普通客户端自报的 host 角色。
- **房间管理者**：经本机宿主信任链验证，创建、批准/拒绝邀请、开局和关闭房间。管理权不通过好友邀请传递；管理者是否拥有 A 席必须单独校验。
- **玩家主体**：唯一的会话内 opaque `participantId` 与已批准席位绑定；一个席位至多一个主体，一个主体至多一个玩家席位。每个好友有各自邀请、设备秘密、批准记录和重连凭证；身份不使用真实姓名或机器标识。
- **本机观战**：经受信宿主绑定到当前有效的本地 City 视图实例，只能接收声明的比赛投影，不获得玩家命令或管理命令的网络凭证。若活动实例已失效，停止投递并显式显示不可用。
- **设备连接**：凭证和连接标识不能等同于席位或角色；多个已授权连接是否允许并行是实现决策，首版至少保障按**具体设备/主体**替换与重连，不能按泛化的 `guest` 替换导致另一个玩家下线。撤销必须同时使对应重连凭证、票据和活动连接失效。

### 8.2 权限矩阵（由宿主在每次请求重新验证）

| 操作 | 房间管理者 | 当前有效席位玩家 | 本机只读观众 | 未获批 / 被撤销设备 |
| --- | --- | --- | --- | --- |
| 创建/关闭房间，邀请、批准/拒绝 | 是，仅受信本机管理通道 | 否，除非同一主体另外拥有管理权限 | 否，仅因观战不获得管理能力 | 否 |
| 查询房间状态 / 订阅比赛投影 | 是 | 是，仅自己获授权的房间 | 是，仅该桌面实例及声明字段 | 否；待批准仅展示等待状态 |
| 提交计划 / 认输 | 仅当其主体占有相应玩家席位 | 是：本人席位；计划还须当前回合、revision、局面合法 | 否 | 否 |
| 修改他人席位 / 伪造 side、playerId | 否；只能使用经验证的房间管理操作 | 否 | 否 | 否 |

relay 注入可信连接身份；Rust 网关与权威宿主根据经过验证的身份、房间和当前绑定交叉核对，**不得信任客户端 payload 自报角色、playerId 或 side**。每条命令在副作用发生前校验，响应/事件交付前再次检查连接仍有效；过期、撤销、过回合、旧 revision、重复命令必须明确拒绝或按幂等规则返回已确定结果。房间管理权限与观战能力互不推导。

## 9. 房间流程与状态机（目标）

`roomRevision` 跟踪席位/批准/房间状态，`match.revision` 跟踪回合状态，二者不能混用；具体字段和协议以契约评审为准。

1. **创建大厅 `lobby`**：房主明确选择“自己参赛”或“邀请两位好友”；初始化席位。参赛时 A 绑定房主、B 待邀请；观战时 A/B 均待邀请。此时不启动 PvP 回合，也不擅自改变正在玩的本地 PvE。界面展示远程模式对本地规划的锁定以及停止/恢复行为。
2. **邀请与批准**：每个空席位分别生成短时、一次登记的独立邀请；受邀设备登记后进入待批准，房主可批准或拒绝。邀请必须携带目标席位并在服务端绑定，但不凭链接自报身份直接授权；互换链接、并发批准、重试和撤销都不得造成双重占座或越权。过期/拒绝回到空席位，可重新邀请。时长复用现有十分钟方案作为建议，最终与协议安全评审一致。
3. **准备并开始 `starting → active`**：仅当两个席位均已批准、连接/授权状态符合开局要求时，房主显式点击开始。按最新房间 revision 原子校验并冻结席位、创建全新的对称 PvP 局；重复开局返回同一结果或明确失败，不能产生两局。开局失败留在可恢复状态并展示原因，不静默开始部分席位的比赛。新流程与当前“批准好友即替换 PvE”的旧流程分开兼容，不能无版本地改变旧客户端语义。
4. **对局 `active`**：仅当前阵营经授权的玩家可提交；正式结算后向两名授权玩家及本机观众发送同 revision 的受限权威状态和事件。客户端可以跳过动画，但最终状态必须收敛；观众无行动、确认、取消提交和认输入口，也必须通过服务端拒绝直接构造的命令。
5. **断线 / 撤销**：普通网络断线不立刻清空席位或自动判负；客户端以设备凭证重连，重取权威快照并继续。首版不自动替补或换人；对局中拒绝直接更换席位，房主可明确结束房间。房主电脑不可用时客户端显示宿主离线、暂停等待或不可用，不能本地擅自结算或承诺云端恢复。重连恢复后不重放为新命令。
6. **终局 / 关闭 `finished → closed`**：按现有 PvP 规则产生终局；房主可结束房间，停止后撤销相关授权和连接并停止向本机观战发送。离开房间、停止远程和本地战局恢复的既有行为需清楚提示；新版本是否继续采用“停止远程重开本地局”的行为，须在实现前与现有 UX 契约核对并明确，不得静默覆盖本地进度。

**原子性及恢复要求**：批准与占座、开局和重复命令需在权威边界串行化或采用等价的 revision/CAS 机制。结算成功但响应或事件丢失时，不重复执行；客户端用同一命令 ID 重试或重取快照核实。若本机网关的出站投影拒绝结果，不能把结果伪装成客户端已收到：显式记录/显示同步失败，通过可验证的重取或恢复路径收敛；若无法证明状态，显示不可用。不得借重试扩大数据投影范围。

## 10. 观战体验与数据边界

- 桌面参赛与观战共用战场坐标、3D 场景、战术图层、事件回放、历史日志和显示模型；参赛时按 A 席权限和当前回合开放规划，观战时以只读能力配置禁用动作输入，不能复制一套规则或结算。桌面与房主远程设备同时连接时，均以宿主 revision 和命令幂等为准，旧草稿不得覆盖新状态。观战者可自由移动镜头和查看公开单位信息；观战视图无草稿、目标确认、认输或提交入口，界面始终标识“观战中”、双方席位、当前回合及连接状态。
- 本机先取得权限内的最新快照，再订阅后续事件；订阅和快照之间不得漏事件，使用 revision 对齐、去重、缺口检测与重取。暂停播放或跳过演出不影响权威结算；掉线/宿主关闭时保留的旧画面要标记过时，不能伪装为实时。
- 当前 PvP 玩家可见完整比赛快照；观战投影首版限于已授权、必要的比赛战场、公开机甲、阶段、结果及战斗事件，**不传玩家未提交草稿、连接秘密、认证票据、设备/本地标识或本地 City 用户数据**。若未来加入隐藏信息，应先重新设计逐角色投影和消息广播，再开放该玩法。
- 用户明确启动远程比赛并分别批准好友；按现有政策只传递 `RemoteArenaV1`、比赛命令、快照和事件的版本化允许字段。relay 只保存短期授权等元数据，比赛正文内存转发，不得持久化。TLS 不代表端到端加密；不得新增遥测、任意 IPC/SQL、日志或其他用户数据上传。

## 11. 契约、兼容与实施拆分

不将已有 `mecha-net:v1` / `app-remote:v1`、Rust 投影或规则版本视为可静默改变的内部细节。实现前先确定房间命令、身份、字段和错误码的新旧兼容策略；对现有固定身份/事件语义不能兼容的变化使用**明确的新协议版本或新能力标识**，具体命名需评审。新旧端协商不兼容时显示升级/不可用，不降级为放宽权限或混用身份；旧 1v1、远程 PvE 和本地 PvE 行为应保留回归。若将“创建房间”和“启动对局”拆开，新协议应明确创建/开始/失败的幂等及事件顺序，不复用旧 `match.join` 的隐式替换语义。

| 顺序 | 改造范围 | 具体交付与门禁 |
| --- | --- | --- |
| R0 方案和安全契约 | 房间配置、角色/席位、受限字段、状态机和协议协商 | 审核同意边界；固定现有 owner vs guest 的基线和真实验收缺口；不改变规则。 |
| R1 会话领域 | 房间管理层 + `MatchSession` / `RemoteSessionHost` | 宿主与 A/B 解耦；两个独立席位、批准和幂等开局；两种配置调用同一 `pvpRules`；现有模式回归。 |
| R2 通信和权限 | relay、Rust 网关、请求/响应投影、凭证和撤销 | 独立席位认证和逐请求授权；按身份路由；严格输入、出站及本机观战白名单；版本拒绝和撤销/竞态测试。 |
| R3 桌面观战及房间 UI | `RemoteMechaControls`、桌面 City 视图、只读展示模型 | 选择房主参赛/观战、两个席位邀请与批准、开局；房主桌面参赛操作与实时只读观战复用同一战场，展示断线状态；不开放观众操作。 |
| R4 全链路验收 | 测试、隐私与真机验收 | 模拟测试通过后，以真实 Tauri、两台独立好友设备及公网中继验证；覆盖断线/重连、关闭及投影拒绝故障。部署和验收结论单独记录。 |

R0–R4 描述房间能力的交付顺序，与第 5 节的 PvE/PvP 共享核心 P0–P4 是**两条可并行的工作流**：房间可继续调用现有 PvP 适配器，不必等待规则核心重构；共享核心重构须保持两种房间配置结果一致，不能先合并成一个大改动后才验证。上线须同时满足安全和完整链路验收门禁。

## 12. 场景化验收清单

1. **房主参赛**：房主创建房间、批准一位好友，房主通过桌面战场作为 A 操作并与好友完整完成一场 1v1；另测房主使用远程链接参赛。玩家 A/B 仅能控制各自阵营，双方最终状态与日志一致；本地 PvE 和旧版远程流程未回归。
2. **房主观战**：房主不占 A/B；两位不同好友使用各自邀请、分别获批并进入各自席位；房主显式开始后两人完成一场 1v1，桌面实时看到相同 revision 的结果和回看，且没有可执行动作入口。
3. **身份与权限**：未获批、撤销、过期凭证不能读取对局或操作；伪造另一人/阵营/观战身份、尝试让观众提交或认输均被拒；A/B 各自断线重连不踢掉对方；管理权限不随好友链接或观战权限下发。
4. **竞态与恢复**：同席位两个并发申请只能批准一人；不同席位并发批准不会交换席位；重复开局、重复计划、响应丢失、事件漏达、stale revision、单人掉线、房主离线、对局中试图换席、关闭期间投递均有明确可验证结果，无重复结算或数据泄露。
5. **等价和投影**：两种房间配置在相同地图、相同初始 PvP 状态与同一行动序列下，权威状态、胜负、事件和顺序一致。客户端预检不能代替宿主结果；玩家/本机观众看到各自权限内的一致状态。验证网关拒绝非法嵌套字段、未提交草稿及秘密不出现在任何观众数据中。
6. **实际验收范围**：桌面真实 Tauri + 两名不同设备好友 + 配置好的公网中继；在支持的窗口尺寸、中文和英文下验证观战、键盘/屏幕阅读器可达性和日志。模拟浏览器、relay 单测、dry-run 或截图不替代真机公网验收。

以上为目标与验收标准，不代表两好友组局、桌面观战、规则复用抽取或公网部署已经完成。

### 远程同步与演出边界（实现补充）

- 本地控制器与远程 `MatchSession` 使用同一个 PvE 规则适配器入口；共享的是结算规则，不代表本地控制器已改造成远程会话。PvP 保留独立规则适配器。
- 远程客户端在首个快照、重连或发现不连续结果时暂停操作并缓冲事件；快照完成后按版本处理，丢弃重复/过期结果。PvE 的 revision 是状态版本而不是回合数，不能以 `+1` 判断连续性。无法确认连续时只接受权威快照；缺失的历史无法由快照补回，界面需明确提示。
- 界面权威状态和场景播放分离：连续演出排队；播放、连接中断和同步期间禁止棋盘决策，直到场景追上权威状态。替换快照可以中止过期演出；同 revision 但局面或地图不一致时仍以快照校正，纯元数据更新不打断演出。页面隐藏时暂停演出计时。
- v1 的结算事件不含前置 revision，当前连续性检查依赖现行 PvE/PvP 规则的版本增量及可用的演出前状态，**不是通用事件序列证明**。如需完整回放、精确断点续传或未来规则版本支持，需另行设计并全链路升级带前置版本/序号和历史恢复的协议；不得在现有严格投影上擅自加字段。
