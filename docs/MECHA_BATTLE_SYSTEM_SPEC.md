## 1. 会话结论

我们从《陷阵之志》调研与截图出发，反复对照 Agent City 战斗场景和 SVG 原型，形成以下共识：

1. **游戏是 3D 城市机甲战棋**：保留 Agent City 城市与中央 10×10 棋盘，不把战场替换成原作的 2D 像素棋盘。城市是场景，棋盘、单位和战术信息是战斗时的视觉主体。
2. **借鉴清晰决策，不复制规则**：让玩家看懂敌方预告、自己可选动作和行动后果；参考原作的优先级与表达方法，不照搬电网、像素美术、即时行动或其他具体玩法。
3. **真实胜利目标第一，预测第二**：例如消灭敌人、保护建筑等，必须根据本局实际规则显示。敌意和草稿预测为玩家服务，风险细节不应取代战斗目标或长期占据主画面。不能为“像原作”而隐藏关键风险或伪造预测。
4. **少文字但信息完整**：默认显示决策所需的信息，详情、顺序、日志按需展开；图形配短标签，禁用原因和异常必须能找到。精简不等于单纯缩小字体或裁切文字。
5. **结束回合是常用主操作**；手动规划本身是回合制，不需要常驻“暂停游戏”。演出有暂停/继续和跳过的独立需求。保留重置战术视角，旋转属于相机操作，不应作为主战斗操作抢空间。
6. **先 P0 可读与交互，再 P1 操作流程，最后 P2 视觉统一**；当前不优先模型重做、扫描线或辉光。
7. **本地与远程应复用可复用部分**，但 PvE / PvP 的规则适配、权威边界和权限差异必须明确；房主参赛或仅组局观战应共用同一套 PvP 领域逻辑，不复制一套游戏。
8. **远程组局属于目标，不等于已经完成**：首版远程已有基础；“房主不参赛、两个好友对弈、房主观战”及桌面直接操控远程权威局仍须开发和真机验收。
9. **雾化不等于性能优化**：背景渐隐可以提升视觉层级；减少 GPU 或内存开销需要真实剔除、LOD、资源管理和测量。
10. Assault 特殊陡坡限制暂不作为本轮 UX 规则需求。未评审、未同步的规则变更不得悄悄成为 `mecha-v1.4` 行为；在目标分支并行修改中存在的契约风险要另行核对，不能宣称已经消除。

## 3. 产品目标与范围

### 3.1 目标体验

玩家无需阅读长段说明，即可回答：**本局怎样赢、什么不能失守、敌人准备做什么、我的机甲能做什么、当前方案会导致什么、是否可以结束回合**。行动失败、风险未知或状态不同步时，界面不应给出错误的确定性。

### 3.2 首要场景

| 场景 | 玩家任务 | 本 SPEC 要求 |
| --- | --- | --- |
| 本地 PvE | 从城市进入战棋，完成三机整包规划，查看敌意、确认并结算 | 本次 UI 迭代主路径 |
| 远程自己玩 | 使用授权设备规划桌面宿主权威的 PvE 对局 | 共用核心语义、不同终端可使用适配布局；不以本地预览代替宿主 |
| 房主与好友 PvP | 房主组局，自己占 A、好友占 B | 使用同一 PvP 规则与受控权限；桌面直接参赛是目标能力 |
| 房主组局观战 | 房主不占席，两个获批好友占 A/B，房主在本机只读观战 | 目标能力，需独立席位与只读投影；不得复用参赛凭证冒充观众 |

首版不要求第三方观众链接、公开匹配、云端托管权威、持久战报或房主离线后继续比赛。

### 3.3 非目标与变更门禁

- 不重做 3D 模型，不引入为炫目服务的特效；不把原作 8×8、逐机即时开火、独立电网或限回合防守照搬成本项目规则。
- 本地 UI 批次不修改移动、碰撞、伤害、敌人 AI、胜负或规则版本；需要修改必须单独评审并同步本地、远程契约与测试。
- 不因为复用而强迫 PvE/PvP 拥有完全相同伤害、胜负或阶段；不将展示预测当作权威计算。
- 不将本文当作远程部署或安全审计的完成证明。后台联网、额外数据出口或用户数据上传不在授权范围。

## 5. 用户流程与状态模型

### 5.1 本地 PvE 时序

```text
城市入口 → 生成/加载站点 → 敌方准备并宣告 → 玩家规划
  → 选择机甲 → 规划移动 → 选择动作及目标 / 明确待机
  → 查看当前计划预测 → 结束回合 → 权威校验
  → [拒绝：保留可恢复草稿并说明原因] 或 [成功：权威状态已提交并生成事件]
  → 基于事件演出 / 暂停演出 / 跳过演出 → 场景追上权威状态并可回看
  → 下一回合敌方宣告，或胜负终局
```

- 以上是产品流程，不强制把所有界面步骤变成新的规则 phase。规则已有 `enemy_prepare`、`player_plan`、`resolving_boss`、`finished`；目标选择、草稿、演出和同步状态属于独立的 UI / 演出状态。
- 在正式结算之前，选择、移动及目标操作编辑草稿，不应改变权威比赛；取消目标不等于取消整包。撤销和每局一次重置遵循现有具体语义，不宣传为无限撤销已结算行动。
- 预测可对未规划存活机甲按待机进行假设，但这**不代表允许提交不完整计划**：现有本地规则需对每台存活机甲明确规划或待机。开场系统建议与玩家主动选择必须区分。
- 成功结果由同一次权威结算产出状态和事件。演出只是消费事件的表现，暂停/跳过不能再结算一次或导致最终 HP 与权威状态不一致；重开/退出时清理旧演出与试算。

### 5.2 UI 状态与可操作性

| 状态 | 棋盘和主要操作 | 用户必须看到 |
| --- | --- | --- |
| 规划 | 选机甲、移动、选择动作；合法时可结束回合 | 目标、当前机甲、可走/危险、计划状态、下一步 |
| 选择目标 | 点合法目标并确认或取消；不直接提交回合 | 合法目标、所选效果或未知、明确取消与确认 |
| 计算中 / 结果无效 | 不展示旧结果为新结果；提交资格按真实规则决定 | “计算中”“计划无效”或“预测不可用/风险未知”及原因 |
| 提交/结算中 | 禁止重复提交及冲突编辑 | 处理状态，拒绝时显示原因；不要提前显示未来事件 |
| 演出中 | 不接受战术编辑；支持暂停/继续和跳过 | 演出状态，结束后可发现上一回合结果 |
| 终局 | 停止规划与再次结算 | 真实胜负原因，回看与退出入口 |
| 远程不同步/断线 | 不可提交基于不可信状态的计划 | 同步中、断线或不可用；可恢复时重取权威状态 |
| 观战（目标） | 只读观察与回看，任何提交/认输均无权限 | 观战身份、同步状态及比赛结果 |

状态进入、退出、重连及异步完成须校验 match/session identity、状态 revision、草稿版本和请求代次；过期结果不得覆盖新选择。可视化不存在的信息时使用“未知”，不以 0 或成功代替。

## 6. 信息架构与 UI 规范

### 6.1 信息优先级

| 层级 | 内容 | 呈现要求 |
| --- | --- | --- |
| 始终可发现 | 本局胜利目标、真实失败条件/守护资源、回合、三机身份与状态、当前步骤、结束回合及不可用原因 | 简短、主次清楚；守楼条仅汇总本局需要守护的建筑，不把非目标建筑当失败资源 |
| 依当前步骤 | 可达格、敌方宣告、草稿预测、动作、目标、确认/取消、必要的已知关键风险或未知警告 | 图文来自同一份有效视图模型；移动/选目标切换时清理失效状态 |
| 按需展开 | 威胁来源/顺序、分建筑细节、碰撞与落空原因、完整战报、设置和远程连接详情 | 有明确名称，不以“+”“顺序”单独表达；不改变棋盘点击模式，不隐藏必要的错误 |

### 6.2 战场标记语义

以下色彩只是视觉建议；必须同时用**形状、边框、纹理、图例/文字**区分，具体实现由视觉与可访问性测试确认。

| 语义 | 建议表达 | 数据与行为约束 |
| --- | --- | --- |
| 可移动范围 | 低遮挡填充 + 边界，例如绿色系 | 根据当前机甲、真实规则与有效草稿计算；不能表示被挡格可达 |
| 移动目的格 | 清晰轮廓/标记与单位卡同步 | 明确是草稿目的地，不暗示已实际移动 |
| 当前敌方宣告 | 红色斜纹/敌意符号、来源关联 | 来自当前局面敌意，不声称是草稿造成的最终结果 |
| 草稿预测威胁 | 与当前宣告不同的轮廓或图案，并标“预测” | 仅在当前草稿试算有效时显示；未知时移除旧预测、保留有标签的宣告 |
| 可选/已选攻击目标 | 可选边框与已选准星层级区分 | 按真实合法目标与占格绘制，不把单一锚点假充多格目标 |
| 伤害/位移/碰撞 | 目标数字与有证据的方向或位置 | 仅展示试算事件可证明的结果；阻挡、无位移、落空、失败或未知不画成功箭头 |
| 已选机甲 | 地面环/轮廓 + 头顶选择箭头；名称在侧栏/左下卡片同步 | 不依赖 HP、颜色或模型大小识别；单位移动草稿和演出时不能错指 |

- 图层重叠时仍能识别所有相关语义，优先保留单位、目标及威胁轮廓；多敌人同格能追溯来源。提供常驻精简图例及可访问文字，不能把长坐标列表常驻在画布上。
- **棋盘单位头顶只显示小血槽和必要的选中箭头，不显示头像、姓名/HP 文字组成的身份标签，不用引线将标签挪到远处。** 血槽基于当前 HP / 规则最大 HP，不能把受伤后当前 HP 作为最大值；数据未知时明确退化，不伪造满血。
- 单位模型、头顶血槽、侧栏头像与左下大头像应对应同一实体 ID；身份名称与数值 HP 放在侧栏/详情，避免重复覆盖棋盘。键盘、触屏和屏幕阅读器的识别仍须单独验收。
- 高楼与 HUD 覆盖不可用视觉弱化代替可操作性；保留可发现的地图聚焦/查看路径，旋转、缩放及不同 DPR 后拾取坐标一致。

### 6.3 面板与控制

- **目标面板**：以真实本局胜利目标为标题，次列守护资源和关键进度；预测与风险作为辅助内容，不把“本回合威胁”冒充胜利目标。不同模式/场景缺少字段时不得猜测。
- **左侧机甲列表**：紧凑的设定稿缩略图、名称、血量、当前选中、计划状态。默认显示计划来源及非零受击风险/未知警告；按需展开完整移动目的地 + 动作 + 目标及预测受击数值，不丢失“未规划 / 系统建议 / 明确待机 / 主动规划”区别。无目标动作不填虚构目标。
- **左下当前机甲区**：当前机甲名称与 HP，下方为原角色设定稿的大头像和并排动作卡，不把大头像搬到棋盘单位头顶。使用本项目机甲/怪兽设定图；没有驾驶员系统，不照搬参考中的驾驶员头像或虚构机制。
- **目标预测区**：在 640×480 及更大布局中使用独立的右下区域，确认/取消立即可见，长结果可滚动；不能把左下设定稿头像/动作卡卷出视野，或盖住可见单位头顶血槽。选目标时可暂时收起上一回合与设置详情，不删除其数据。
- **动作卡**：显示实际能力名/图标、可用状态；不可用原因例如冷却、距离、遮挡、没有目标，以及可行下一步，原因以规则返回或可验证查询为准。状态变化立即更新；不可推断原因时显示通用不可用。
- **结束回合**：常用且可见，标明可提交或具体阻止原因；风险提示突出已知关键后果和未知，不能把 `3/3` 当完整计划。全员待机有损楼或终局的确认保留现有行为，不增加无意义的每回合弹窗。
- **回看**：演出结束或跳过后提供易发现的上一回合摘要和完整日志；预测与实际结果明确区分。缺失明细或远程历史不完整要明示。
- **相机**：保留重置到可操作棋盘的战术视角；移除“旋转 90°”按钮（包括次级区域），不移除已有拖动旋转能力；键盘相机可达性若依赖该按钮，须以不抢占主界面的替代操作满足。镜头重置不能改变规则、草稿或选中对象。
- **暂停**：玩家静态规划不需要常驻“暂停游戏”；仅在演出/自动流程确有暂停含义时提供清晰命名的暂停、继续或跳过，远程不能由展示暂停冻结宿主权威。
- **顺序/查看模式**：查看敌人来源与顺序使用明确的列表/按钮，并显示焦点；展开详情不能悄悄把棋盘移动点击变成另一种行为。若未来引入模式切换，必须显著显示模式、退出方式及点击含义。

### 6.4 自适应与无障碍

优先重组信息与渐进披露，合理响应式字号有下限和可读性，不以缩小字号、隐藏风险或截半行替代适配。中文及较长英文在 640×480、800×600、1100×700 下完成规划、确认、取消、结束回合和查看回看；详情可滚动且有可发现路径，当前确认/取消始终可见或明确可达。保留可访问名称、选中/禁用语义、可见焦点、合理焦点顺序和焦点恢复；不单靠颜色。Esc 等快捷键先解决现有关闭战棋冲突，不擅自改变。

## 7. 敌方预告与预测的实现原则

### 7.1 预告从哪里来

敌方准备阶段由规则/敌人脚本生成可公开的意图和目标格；当前宣告的来源、技能、目标范围、顺序或伤害**只有规则实际提供时才能显示**。不是读取对手玩家的私有未提交计划，也不是用模型朝向或视觉射线自行猜测。如果模式不允许提前公开或数据缺失，显示对应不可用状态。

### 7.2 草稿预测如何工作

```text
权威 match snapshot + 当前草稿 / 候选目标
  → 将未规划单位以待机作为明确假设，克隆状态
  → 通过对应 PvE/PvP 规则适配器执行合法性校验与试算
  → 返回成功 / 非法 / 不可用，及有证据的事件、终局、敌意和 HP 变化
  → 同一 revision + draftVersion + request identity 的 UI 视图模型
  → 同步驱动棋盘、动作卡、目标和风险摘要
```

试算不得修改权威状态、草稿或共享事件接收器。对仍有效的相同快照与完整计划，预测事件/结果应与权威结算相符；权威版本变化、模式规则不同或命令被拒时不作这种保证。预测中的直接行动伤害与整个包结束 HP 区分；不能从整包结果倒推并冒充单次攻击伤害。前序行动使后续落空时，明确显示落空原因，不播命中。

预测失败、校验拒绝、异步过期和模式不支持是不同状态；清除过期目标、位移和草稿威胁，但仍可展示独立标识的当前宣告。提交时再次由权威校验，不能因为本地试算成功就绕过。

## 8. PvE / PvP / 远程目标架构

现状：本地控制器与远程会话已复用部分规则和草稿函数，但还不是同一 UI 和同一会话。以下为渐进式**目标架构**，接口名称非实现承诺：

```text
       本地桌面 PvE UI     远程玩家 UI      本机观战 UI
               \             |             /
          共享展示模型 / 草稿交互 / 棋盘语义（观战只读）
                          |
          MatchClient 边界：local adapter / remote adapter
                          |
     ┌────────────────────┴──────────────────────┐
     │ 通用棋盘查询、移动与动作机制、事件及预检   │
     │            PvE 策略     |     PvP 策略    │
     └────────────────────┬──────────────────────┘
           本地权威 controller  或  桌面权威 MatchSession
                                           |
                  Rust 网关（鉴权/投影）↔ relay ↔ 已授权设备
```

- 共享草稿编辑、计划描述、坐标、合法性接口、试算结果、事件视图模型和可组合 HUD；WebGL/城市场景与不同终端布局作为适配层。逐块抽取，不一次重写。
- 共享棋盘查询与战斗机制，模式策略注入各自目标、伤害、碰撞、结束条件及阶段规则；同库代码可在不同运行时执行，但**不共享同一份内存或权威状态**。不把 PvP 对手伪装成 PvE 敌人作为长期统一实体模型。
- 本地由本地规则入口权威结算；远程由桌面 `MatchSession` 按规则、权限和 revision 权威校验，relay 不结算。客户端只提交计划而非计算结果，响应与事件由权威产生。
- 保持现有行为和规则版本，通过回归对照验证；房间能力和共享核心可并行推进，房间先复用现有 PvP 适配器，不等待一次性重构。

### 8.1 房间与权限（目标）

房间管理者、玩家 A/B 席位、只读观战身份和设备凭证分离。房主可同时是管理者与 A，也可仅为管理者 + 本机观众；每位好友使用独立邀请/授权，不分享房主玩家凭证。

| 操作 | 管理者 | 持本人有效席位的玩家 | 只读观众 | 未授权 |
| --- | --- | --- | --- | --- |
| 邀请、审批、开始/关闭 | 本机受信管理通道 | 不因参赛自动获得 | 否 | 否 |
| 获取获准的对局投影 | 是，限授权范围 | 是，限本人授权房间 | 是，限本机观战投影 | 否，待批准只看等待状态 |
| 当前回合提交 / 认输 | 只有同时占有效席位才可 | 仅本人席位，且回合、revision、规则合法 | 否 | 否 |

目标房间流程：`lobby → starting → active → finished → closed`；邀请、获批、撤销、断线和重连是席位/连接状态，不等同于比赛 phase。A/B 都获批后房主显式开始；开局和占位须原子、可幂等重试。断线不自动替补/判负；宿主离线明确不可用，不承诺云端继续。对局中换席、停止远程后本地局恢复策略需产品评审；不得静默覆盖已有进度。旧流程和新流程的兼容及版本需明确设计。

### 8.2 同步与安全门禁

- 权威状态、演出播放进度、客户端草稿、房间/席位状态分离；不要把回合数、state revision 当作连续事件序号。重复命令、旧版本、事件丢失、乱序、重复、关闭和会话替换必须明确处理。
- 现有 v1 只对部分缺口/重连提供快照恢复；**在线最后一条事件丢失可能无法及时发现**。审计涉及内存故障注入，不等同于真实网络复现。快照只能恢复当前状态，不能保证补回缺失日志/动画；新序号、水位或恢复机制须端到端协议评审，不能擅自向严格 v1 投影加字段。
- 重连、同步失败或状态不可证明时禁用会影响权威的交互并展示原因；应避免无变化的同步清空玩家草稿。命令是否结算未知时不得重复结算，需按命令身份/权威快照协调。历史缺失必须标注，不能补造。
- 仅桌面用户主动发起或批准的机甲对局，可以向该场获授权设备传递 `RemoteArenaV1` 和必要比赛命令、快照、事件；Rust 可信边界做严格版本化白名单和逐请求/交付前权限检查。relay 仅允许短期房间授权、邀请、撤销和票据等元数据落盘，比赛正文只在内存转发。禁止外发完整 City、日志、提示词、分析、路径、原生标识、密钥和任意宿主数据；无通用 IPC/SQL/插件访问。TLS 不等于端到端加密。
- 上线前针对当前代码逐项核对投影、撤销与竞态，旧文档对投影覆盖范围的描述存在时间差，不能直接当作当前合规证明；真实 Tauri、两个不同好友设备与公网 relay 验收不可由 mock 代替。

## 9. 城市背景与性能

- 战斗时降低道路灯球、非战斗标签和无关装饰的存在感；强化棋盘边界、格面、格线和单位标记。可以试验棋盘外城市渐隐、雾化或降低对比度，但保留必要的地形、遮挡与城市身份。战斗退出、异常、切站点后恢复原场景和用户视角/设置，不销毁共享资源。
- 视觉雾化不必然减少 draw call、三角形、纹理驻留或内存；部分透明/雾效果可能反而增加开销。单独评估视锥剔除、区域隐藏、LOD、实例化、纹理/模型资源生命周期及合理释放；不要为了省资源隐藏规则相关对象或破坏拾取。
- 性能验收先记录同场景、同设备、分辨率、DPR、版本、采样方法及空闲/交互/演出数据，比较帧时间、GPU 时间/利用率（若可测）、draw call、三角形、内存；给出实测数值与差异。性能阈值待目标硬件及基线测量后约定，不预设雾化一定有效。

## 10. 分批实施及验收

批次优先级采用用户最新排序；远程安全/同步问题虽不抢占本地 UI 第一批，仍是**远程发布阻塞项**。

### 第一批 P0：看得清、认得出、分得清

| ID | 交付 | 可验证验收 |
| --- | --- | --- |
| P0-1 战场分层 | 可逆弱化非战斗城市装饰，增强棋盘边界/格面/格线 | 同 seed/视角前后截图，棋盘与单位为第一视觉焦点；检查高楼/坡地、10×10 全局和受 HUD 遮挡格的可操作路径，退出后场景恢复 |
| P0-2 单位识别 | 棋盘小血槽、侧栏短名/头像、左下大设定稿头像、选中轮廓/箭头，模型与卡片同步；禁用棋盘身份标签/引线 | 无须依赖 HP 或颜色，能区分三机与敌人；切换、移动草稿、演出和退出不留错位/旧标记 |
| P0-3 范围与图例 | 可达、当前敌意、草稿威胁、目标和可信推移分别表达，常驻短图例 | 同格重叠、多个敌人、失败/未知、目标确认取消时仍可区分；文字与棋盘基于同次有效试算，无法证明的不画成功效果 |

**门禁**：先验证坐标/拾取、预测真实与状态清理，再做视觉评审。纯截图好看不算 P0 通过；图形、图例和操作不应遮住必要控件。

### 第二批 P1：构图、操作及核对

| ID | 交付 | 可验证验收 |
| --- | --- | --- |
| P1-1 构图 | 默认视角、缩放与 HUD 安全区域调优 | 交战区居中，关键格/单位不被遮挡或可经地图聚焦访问；不以局部放大牺牲 10×10 全局和交互；高楼、旋转、缩放后坐标一致 |
| P1-2 动作卡 | 左下大设定稿头像 + 并排动作卡、技能可用状态与原因、下一步提示 | 不展开长说明即可理解待机/攻击为何可用或不可用；移动改变条件后状态更新；确认/取消可达 |
| P1-3 计划摘要与提交 | 三机移动 + 动作 + 目标、系统建议/主动/待机来源；关键风险与提交状态 | 用户能逐机核对完整计划；未规划不可误判为已提交的待机，非法或未知不显示安全；结束回合持续易找 |
| P1-4 渐进披露、回看及操作语义 | 重组窄窗侧栏与底栏；结果摘要/完整日志；明确顺序查看 | 中英文不截半行，查看顺序不偷换棋盘点击；跳过后可回看，键盘焦点和控件可达 |

### 第三批 P2：设计收敛

| ID | 交付 | 可验证验收 |
| --- | --- | --- |
| P2-1 信息精简 | 缩小目标卡、明确攻击预览、“详情/攻击顺序”等清晰文案 | 目标优先，主信息无需展开，次要信息不抢棋盘；风险未知仍可发现 |
| P2-2 视觉统一 | 方角双线、字体层级、适用时分段守护资源条、动作图标与颜色规范 | 对照两张 refined SVG 评审，风格一致且不冒充原作资源或改真实规则；不以装饰覆盖战术信息 |

### 独立工作流：共享架构、远程组局与上线

1. 先固定现有 PvE/PvP 行为测试，明确共用接口；再增量复用规划视图模型及 HUD，分别通过本地/远程回归。
2. 评审房间角色、席位、邀请、协议兼容和安全；实现房主参赛/仅观战两种配置、授权投影及状态恢复。该能力不默认随 UI P0 完成。
3. 处理远程尾部丢失、状态不同步及严格投影的发布门禁；进行真实设备、Tauri 与公网 relay 测试后才可宣布可用。与 UI 分批并行不代表可以绕过上线门禁。

## 11. 测试、截图与发布标准

### 11.1 功能与一致性

- 固定 seed 与局面覆盖完整规划、待机、系统建议、移动冲突、撤销/重置、非法目标、目标确认/取消、伤害、推挤、墙/建筑碰撞、先行行动造成落空、终局及上一回合回看。
- 对同 revision、同完整计划比较试算与权威事件及最终状态；测未规划待机假设、预测异常→恢复、过期响应、对局/草稿切换、退出和重开。PvE/PvP 用各自规则与适配器，不能互相冒充。
- 测当前宣告与草稿威胁不同/重叠、多敌同格、不可用无陈旧标记；旋转、坡地、不同 DPR 与视口下棋盘渲染/坐标/鼠标触屏拾取一致。
- 演出暂停/继续/跳过、连点提交、重复事件、对局终止、重连、观战越权及旧 revision 拒绝均有回归；完整远程故障注入和真实验收按专项文档执行。

### 11.2 视觉与可用性

- 每批产出来自**正在验收的 worktree/commit**的截图，注明数据来源（合成或真实）、seed、DPR、窗口尺寸、语言与运行环境；同局面对照两张 refined SVG，不把设计稿数字当真实数据。
- 至少中文及较长英文的 640×480、800×600、1100×700：规划、选目标、确认/取消、结束回合、展开详情/滚动、回看、预测失败与恢复，检查布局、可读性和真实点击。小屏可补地图聚焦截图；宽屏检查 HUD 安全区。
- 除自动几何断言，需人工检查边界可见性、城市灯光、实体辨识、叠层关系、文字截半及焦点。自动测试覆盖不到的屏幕阅读器、实体输入、真实 Tauri 逐项列为待验。
- 建议按 [用户研究方案](MECHA_BATTLE_UX_USER_STUDY.md) 邀请至少 5 名未参与设计的目标用户，无提示完成对应任务；以记录的分子/分母及正确答案判断，不把自动化或开发者体验冒充用户测试。

### 11.3 工程门禁

- 参考命令：`npm --prefix apps/agent-city/ui run typecheck`、`npm --prefix apps/agent-city/ui run verify:mecha`、`npm --prefix apps/agent-city/ui run build`，加相关目标测试、浏览器脚本及 `git diff --check`；远程相关改动再运行 `verify:mecha-remote`、协议/relay/网关测试。命令需在实际 worktree 执行，记录失败及未运行项。
- 真实桌面检查按仓库要求通过 Tauri `.app` bundle，不直接运行裸 menubar 二进制。部署、真实双端、性能与安全检查分别记录环境及结果。
- 编码在独立 worktree 进行，保留其他工作区未提交修改；集成前审查差异和测试，明确目标分支是否包含并行 WIP。用户确认后再合并，不因本文存在就宣称已合并或全部通过。

## 14. 方格查看与点击单位预告（2026-11-01 增补）

本节是对既有战斗 HUD 的扩展，不恢复棋盘头像标签，也不改变战斗规则。

- **点击格子**：右下查看实际地形、坐标、高度及占位。空地展示地面/水域/山地/道路；掩体、场景障碍、建筑、废墟各自区分，建筑读取对应共享 HP 池。点击空格同时排移动时，属性卡仍保留这次地形查看，不因机甲的草稿终点覆盖成单位卡；再次点击已绘制的机甲可查看其单位属性。
- **点击单位**：显示该规则实体的 HP/maxHP、基础攻击、防御、移动与冷却；已知头像复用既有设定稿裁图。未知身份/生命上限不以猜测补齐。左下大设定稿与动作区继续承担当前操作机甲的信息。
- **敌方预告**：红色方向箭头连接当前实体/大怪脚印中心与 `intent.projected` 的攻击落点。横扫是多落点的攻击集合，不能按数组顺序连成行走路线。`skip`、`void`、缺失宣告、死亡实体没有虚构路线。
- **时序与来源**：敌方移动在 `bossPrepare`/`planRaiders` 中完成后才宣告攻击，因此本 UI 不再推算“尚未宣告的敌方移动”。蓝色 P 格仍是整包草稿预测；`null` 是未知、`[]` 是成功预测无威胁。草稿预测敌人死亡不取消活体的查看选择，不隐藏当前宣告。
- **我方移动**：点击已有移动草稿的我方单位，绿色路线使用规则层 `movementPath`，而非穿越障碍的直线；标注尚未执行。
- **拾取**：格面与可见活体模型一并拾取，按射线距离选择前方命中；模型映射到实际显示单位的格子，避免点击抬高的机身落到后方空格。保留拖动阈值与触屏目标先预览、再确认的契约。
- **结果共存**：通常是独立右下属性卡；触屏目标试算时共用结果滚动区，属性摘要折叠详细规则，确保确认/取消按钮默认可见。属性卡展开/滚动沿用整行边界适配。
- **生命周期**：关闭查看、重新开局、回合切换/演出清理旧查看与路线；演出期间不新增棋盘属性选取。远程锁定时查看不会发出本地战斗指令。

实现位于独立 `codex/mecha-battle-clarity-p0` worktree。是否合并、native/远程上线及用户主工作区并行 WIP 仍须单独核验，不能从浏览器 UI 验收推导。
